## 명령과 요청 흐름

| CLI 명령 | 주요 경로 | service 모듈 |
| --- | --- | --- |
| `search locations` | v2/search → 지역·오피스텔·아파트 후보 | `region` (단지 후보는 `complex`) |
| `search listings room` | 지역/역 해석 → 유형별 핀 → items/list | `listing` |
| `search listings apt` | 동·구: 지역 목록 / 반경: nearby-danjis → item-catalogs | `apt` |
| `search listings store` | 상가 핀 → 요약 → 로컬 가격·업종 필터 | `store` |
| `search listings stay` | 지역 검색/지도 → by-ids → 정렬·할당량 | `stay` |
| `complex` | apt-/officetel- ID 분기 → 단지·건물 정보 | `complex` |
| `search listings --complex` | 아파트 catalog / 오피스텔 건물 핀·요약 | `complex` |
| `real-price` | 아파트 실거래 → 거래 유형 필터·페이지 조회 | `real_price` |
| `listing` | ID 접두사 분기 → 주거·상가·단기임대·제휴 상세 | `detail` (ID 분기) → `listing`·`store`·`stay` |

## 소스 고유 구현

### 인증·헤더

- `account.zigbang.com` 에서 익명 토큰을 받아야 한다. `ZigbangGuestAuth`(httpx `Auth`)가 첫 요청 때 토큰을 발급하고 401 이면 한 번 재발급한다 (2026-10-11 실측: 지금은 가짜 토큰·토큰 없이도 목록·요약·상세·단지·단기임대가 모두 정상 200 이라 토큰 오류가 빈 결과로 숨지 않는다). sync/async 클라이언트가 같은 `_auth` 인스턴스를 공유한다. `/v2/search` 는 토큰이 필요 없어 `auth=None` 으로 부른다.
- `x-zigbang-platform: www` 헤더가 없으면 일부 상세가 404 를 준다.

### 원룸·오피스텔·빌라 목록 (`room`)

- 목록은 geohash 타일로 핀(ID·좌표)을 받고 → 가까운 순으로 정렬하고 → 가까운 `--limit` 개만 `items/list` 로 15개씩 요약을 받는 3단계다. 요약에서 뺀 매물은 다시 채우지 않는다.
- 원룸은 방 하나짜리를 뜻해, 원룸 목록(`items/onerooms`)이 섞어 주는 오피스텔 중 투룸은 원룸형 `roomType` 만 요청해 막고 원룸형 오피스텔은 결과에 둔다 (직방 웹 원룸 화면도 방 구조를 고르지 않으면 같은 목록을 보여 준다). 원룸 목록 핀에는 건물 ID(`buildingId`)가 없어 (실측: 모두 null, 요약에도 없음), 오피스텔을 따로 조회하지 않은 검색에서 건물 ID 없는 오피스텔이 결과에 있으면 그 매물이 있던 지도 칸에서 같은 조건으로 오피스텔 목록을 한 번 더 받아 `complex_id` 를 채운다 (실패하면 `null`).
- 빌라 목록은 투룸 이상뿐이라 원룸형 구조만 주면 빌라는 요청하지 않는다.
- `search listings room` 에서 역 이름이 지하철역으로 풀리면 지도 칸 대신 `items/subways/{id}/<유형>` 을 유형별 1회 부르고 반경 밖은 버린다 (좌표 검색은 지도 칸 그대로).

### 지도 칸과 동 경계 (`room`·`store`)

- 지도 칸(`geohashes_covering`)은 칸 절반 이하 간격으로 샘플링해 원에 닿는 칸을 모두 받는다. 상가(정밀도 6)는 반경 5km 면 약 160칸이라 요청 제한 대기로 1분 가까이 걸린다.
- 동 경계 검색(`search listings room`·`store`)에서 검색어와 같은 이름의 동이 없고 `<검색어>N가` 후보만 있으면(성수동 → 성수동1가·2가) 같은 시·구의 그 동들 경계를 하나씩 받아(동마다 1회) 다각형을 합치고, 검색 중심을 합친 범위의 가운데로 옮긴다. 첫 후보만 찾으면 나머지가 조용히 빠졌다 (2026-10-10 실측: 성수동은 1가 상가 283건만, 2가 217건 누락).
- 동 경계 검색은 경계를 감싸는 원 대신 경계에 닿는 칸(`geohashes_touching`)만 받는다 (2026-10-10 실측: 역삼동 상가 28 → 14칸, 울릉읍 12,215 → 64칸, 역삼동·성수동 상가와 원룸 3개 동의 경계 안 핀 3,680개는 그대로). 그래도 반경 5km 원의 칸 수보다 많으면(홍천 내면 상가 851칸·원룸 41칸) 경계 대신 중심 반경으로 찾고 알린다(`wide_boundary_note`). 경계 API 는 geohash 칸 중심이 속한 동을 주어 정밀도 7 로 묻는데, 옆 동이 잡히면 8 로 한 번 더 묻는다 (실측: `○가` 동 64곳 중 6곳이 7 에서 옆 동, 8 에서 모두 맞음). 직방 지역 검색의 동 중심은 늘 그 동 경계 안이라 경계를 못 받는 동은 없었다 (2026-10-11 실측: 강변·해안·섬 읍·면·동 28곳). 그래서 경계를 못 받아 반경으로 찾게 된 경우의 안내는 두지 않는다. 반경으로 자르지 않아 반경 안 매물이 모자라면 반경 밖 매물도 이어 준다.
- 같은 이름의 동이 따로 있으면(당산동) 그 동만 찾고, 반경·아파트처럼 동을 합치지 않는 검색과 함께 `○가` 안내(`ga_dong_note`)를 붙인다.
- 같은 이름·같은 종류의 지역 결과(신사동 → 은평구·강남구, 중구)가 여러 곳이면 `region_notes` 가 `REGION_AMBIGUOUS` 로 멈춘다 (네이버와 같게, 2026-10-15). 역(양평역)은 첫 역으로 찾고 안내한다. 전체 주소('서울특별시 강남구 신사동')는 직방 지역 검색이 학교만 주므로 힌트는 '구 + 동'(`강남구 신사동`)으로 든다.

### 아파트 (`apt`)

- 아파트 동 검색도 `○가` 동마다 지역 목록(`locals/.../item-catalogs`)을 받아 합치는데(`extra_regions`), 한 동이 예산을 다 쓰지 않도록 남은 예산을 아직 끝나지 않은 동 수로 나눠 번갈아 받는다. 겹친 매물은 `seen` 으로 한 번만 낸다. 여러 동이면 `seen` 을 이어 받기 표에도 담아, `--next` 로 받은 다음 쪽에 앞 쪽 매물이 다시 나오지 않게 한다 (2026-10-23 실측: 담지 않으면 문래동 30건씩 세 쪽이 서로 9~11건 겹쳤다). `--limit` 이 동 수보다 작으면 뒤쪽 동은 부르지 않으므로, 결과의 동 이름·`local_code` 에는 부른 동만 넣고 빠진 동은 `notes` 로 알린다 (문래동 1가~6가 + `--limit 3` 은 1~3가만). 검색 중심은 첫 지역 결과인데, 그 이름이 검색어와 다르고 `<검색어>N가` 동이 있으면 첫 `○가` 동을 고른다(`best_region_item`). 직방은 '부민동' 을 [남부민동, 부민동1가, 2가, 3가] 순서로 줘서 첫 결과를 고르면 다른 동을 찾았다 (2026-10-10 실측). 검색어는 마지막 낱말(`_dong_name`)로 비교해, 다른 후보를 고르라는 안내대로 구 이름을 앞에 붙여도('성동구 성수동', '서구 부민동') 같은 `○가` 동을 합친다. 아파트는 법정동코드가 있는 지역만 보고, 검색 중심 동을 뺀 나머지 `○가` 동을 넘긴다.
- 아파트 지역 목록은 시·도 2자리 코드에 늘 0건이라(2026-10-11 실측: 11·41·26·36 모두 0건, 강남구 11680 은 1683건) `resolve_apt_region` 이 시·도를 `RegionNotFoundError` 로 넘겨 CLI 가 반경으로 찾는다.
- 구가 있는 시는 직방 지역 검색이 시 대신 그 구들을 주고 시 코드(성남시 41130)는 0건이라, 같은 시의 구를 모두 `extra_regions` 로 넘겨 합친다(`city_gu_items`, 결과 지역은 `merged_gu_region`). 첫 구만 찾으면 성남시는 분당구 255건만 나오고 수정구 558건·중원구 116건이 빠졌다. '시' 를 떼고 쓴 이름('성남')도 검색 중심이 '<이름>시 ○구' 면 같은 시로 본다 (2026-10-28 실측: 성남·안양·고양 모두 직방이 구들을 맨 앞에, 같은 이름의 동을 그 뒤에 준다. 전에는 '성남' 아파트가 분당구 283건만 찾고 다른 구 안내도 없었다 → 세 구 1058건, 단기임대 38 → 47건으로 '성남시' 와 같다). 검색 중심이 그 시의 구가 아니면(동 이름 등) 합치지 않는다.
- 리는 10자리 코드가 0건이라 읍·면 8자리로 찾고(양근리 → 양평읍 88건) `notes` 로 알린다.
- 아파트 반경 검색은 반경 안 아파트 매물을 한 번에 주는 공개 API 가 없어 `nearby-danjis` 로 단지를 받고 가까운 단지부터 `danjis/{id}/item-catalogs` 를 단지마다 부른다 (최대 30곳·2km, 면적 조건이 있으면 60곳, 요청당 50건, 받은 원본 개수로 `--limit` 예산을 세고 남은 예산은 다음 단지로). 단지 목록(`danjis`)은 50건씩, 동·구 지역 목록(`locals`)은 20건을 넘으면 400 이라 20건씩 받는다 (2026-10-10 실측: 단지 목록은 50건씩 받아도 순서·내용이 같다). 공급면적 조건이 있으면 단지마다 `limit=1` 로 평형 목록(`roomTypes`, 이름이 공급면적 ㎡)을 먼저 받아 맞는 평형만 `danjiRoomTypeIds` 로 요청한다. 이 1건은 예산에 넣지 않는다.

### 오피스텔 건물·주거 상세

- 오피스텔 건물 매물(`items/officetels/{buildingId}`)은 서버가 거래 유형으로 거른 거래 중 매물만 줘서 핀 수가 곧 조건에 맞는 수다.
- 오피스텔 건물 정보의 `elevator: false` 는 믿을 수 없어 `complex` 에서 `null` 로 낸다 (실측: false 30곳이 모두 매물 상세에서는 엘리베이터 있음).
- 주거 상세는 `items/{id}/detail` 이 기본이고, 입주일(`moveInAt`)이 null 이면 `/v3/items` 로 입주 문구·주차를 보완한다. 아파트는 입주일이 늘 null 이라 매번 보완 호출을 타고, 두 API 의 `status` 는 늘 같다(실측). 등록일·단기임대 여부는 상세에 없어 `items/list` 요약에서 받는다. 요약의 `status`(노출 여부)도 상세와 늘 같아 (2026-10-10 실측 180건: true ↔ open, false ↔ close·cancel, 요약 없음 ↔ 404) 상세에서는 다시 보지 않는다.

### 실거래 (`real-price`)

- 실거래 API 는 없는 단지에도 빈 성공을 줘서, 첫 쪽의 단지 평형 정보(`areaInfos`)가 비면 단지 정보(`danjis/{id}`)로 있는지 한 번 더 확인해 없으면 `NOT_FOUND` 로 낸다 (거래 없는 단지도 평형 정보는 와서 평소에는 요청이 늘지 않고, 평형이 아직 없는 새 단지는 정상 0건이 된다). 지정한 평형이 평형 정보에 없으면 `INVALID_ARGUMENT`.

### 단기임대 (`stay`)

- 단기임대(`stay-apis.zigbang.com`)는 지역 전체면 지역 검색(`guest/items/search`), 반경·동 경계면 지도(`guest/items/markers`)로 ID 를 모아 `guest/items/by-ids` 로 50건씩 요약을 받는다. `by-ids` 는 노출 중·검수 완료 매물만 돌려줘서(실측) 목록에서는 상태를 다시 보지 않는다. 예약 달력(`guest/items/{id}/calendar`)은 게스트 토큰으로 403 이다.
- 단기임대 날짜는 `checkOutDate` 까지 이용일로 센다 (11-02~11-08 = 7일). 검색(`guest/items/search`·`markers`)은 7~84일만 받아 `STAY_SEARCH_MIN_DAYS`·`STAY_SEARCH_MAX_DAYS` 로 요청 전에 막고, 서버의 `MIN/MAX_DURATION_VIOLATION` 도 입력 오류로 바꾼다(`_stay_search_call`). 요금 계산은 매물 계약 범위(최소 1~8주)를 서버가 판단해 7~84일 검사를 하지 않는다.
- 단기임대 지역 전체 검색은 경계 대신 `○가` 동마다 `guest/items/search` 를 불러 ID 를 합친다(`extra_regions`).
- 단기임대 지역 검색은 세종의 동을 local1·local2 를 어떻게 줘도 400 `REGION_NOT_FOUND` 로 거절한다 (2026-10-11 실측: 반곡동을 세종특별자치시·세종시 × 세종·없음 조합 모두 400, 세종특별자치시 전체·양평읍·역삼동은 200). `_stay_region_search` 가 이를 `RegionNotFoundError` 로 바꾸고, CLI 가 room·store 와 같은 `_scope`(동 경계, 넓으면 반경)로 지도 칸을 다시 찾는다.
- 단기임대 지역 전체 검색도 구가 있는 시는 구마다 검색 API 를 불러 합친다(`city_gu_regions`, 2026-10-11 실측: 성남시는 분당구 35건만 찾고 나머지 구가 빠졌다 → 세 구 43건). 리는 지역 결과의 local3 이 그 위 읍·면이라 읍·면 전체를 찾으므로(양근리 → 양평읍 창대리 매물) `boundary` 를 읍·면 이름으로 내고 `notes` 로 알린다 (`is_ri_code`).

### 지역 후보·주소

- `search locations` 는 `/v2/search` 를 오피스텔·아파트로 두 번 부른다 (지역·오피스텔 건물과 아파트 단지가 따로 나온다).
- 세종 주소는 소스마다 시를 한 번 더 넣는다 ('세종 반곡동'·'세종시 반곡동', 상가는 local1·local2 가 둘 다 '세종특별자치시'). `normalize_address` 가 세 경우 모두 뺀다.

## 원본 금액 단위

최종 출력 금액은 모두 만원이지만 직방 원본 응답의 단위는 action별로 다르다.

| 원본 응답 | 단위·처리 |
| --- | --- |
| 일반 주거 가격·상가 가격 | 대부분 만원. 해당 response 필드 설명을 확인한다 |
| 원룸·빌라 요약의 `manage_cost` | 원. `won_to_manwon`으로 환산한다 |
| 아파트 상세 관리비 | 원. `won_to_manwon`으로 환산한다 |
| 단기임대 응답 금액 | 원. 주당 임대료·관리비와 기간 비용 모두 해당 정규화 경로를 확인한다 |

새 필드를 추가할 때 소스 이름만으로 단위를 결정하지 않고 action의 client docstring·response 모델을 확인한다.

단기임대 서비스(`search listings stay`)는 요금이 주 단위라 출력에서도 `rent_manwon`·`manage_cost_manwon` 키를 빼고 `weekly_rent_manwon`·`weekly_manage_cost_manwon` 으로 준다 (공통 출력 계약의 예외).

## 페이지네이션과 조건 처리

유형마다 요청 경로와 필터 적용 위치가 다르다. 원룸·오피스텔의 서버 필터, 아파트 전용면적의 후처리, 상가 가격의 로컬 필터, 단기임대의 주 단위 비용을 하나의 흐름으로 합치지 않는다. 단지 ID의 `apt-`·`officetel-`, 상세 ID의 `store-`·`stay-`·`coalition-` 접두사를 보존한다.

`--limit` 예산은 확인한 원본 수로 세고, 받은 뒤 뺀 매물은 다시 채우지 않는다. 직방에서는 조회 방식마다 이렇게 적용한다.

| 조회 | 예산 | 이유 |
| --- | --- | --- |
| 아파트 (동·구·반경·단지) | 받은 원본 수. 제외한 만큼 채우지 않음 | 조건을 서버가 건다 |
| 원룸·오피스텔·빌라 | 가까운 핀 `limit` 개의 요약만 받음. 채우지 않음. 오피스텔 없이 원룸을 찾았는데 결과에 건물 ID 없는 오피스텔이 있으면 빠진 매물이 있던 지도 칸만(역 검색은 1회) 오피스텔 목록을 더 부른다 (2026-10-11 실측: 역삼동 원룸 1·3·5km 모두 1칸, 전에는 2·4·11칸) | 조건을 서버가 걸고, 원룸은 원룸형 `roomType` 만 요청해 섞여 오는 투룸 오피스텔을 막는다. 원룸 핀에는 건물 ID 가 없어 `complex_id` 를 오피스텔 핀에서 채운다 |
| 오피스텔 건물 | 건물 핀 앞 `limit` 개의 요약만 받음. 채우지 않음 | 서버가 거래 유형·가격을 건다 |
| **상가 (예외)** | 가까운 후보를 `max(limit × 5, 60)` 개까지 확인하며 결과를 채움 | 가격 조건을 서버가 받지 않아 요약을 받은 뒤 거른다. 채우지 않으면 가격 조건을 건 검색이 거의 비어 온다 (2026-10-10 역삼역 1km 임대 월세 300 이하: 75건 중 8건, 보증금 3천·월세 200 이하: 75건 중 4건). 요약은 50건씩이라 요청은 많아야 후보 수 ÷ 50 회다 (`--limit` 20 까지 2회, 60 이면 6회, 120 이면 12회. 2026-10-10 역삼역 실측과 같음) |
| **단기임대 가격순·최신순·지역 전체 (예외)** | 반경 안(지역 전체 거리순이면 지역 안) 후보 요약을 모두 받은 뒤 정렬하고 자름. 상한은 두지 않는다 (2026-10-11 실측: 서울시 전체 거리순 1,491건이 by-ids 30회·약 7초). 지역 전체 가격순·최신순만 검색 API 가 정렬한 순서로 동마다 앞 `limit` 개의 요약을 받고, `total` 은 검색 ID 수다 (서울시 가격순 by-ids 30회 → 1회) | 주당 임대료+관리비·등록 시각은 요약에만 있고, 지역 검색 ID 에는 위치가 없다. 지역 검색 API 의 `PRICE_ASC`·`NEWEST` 순서는 요약의 임대료+관리비·등록 시각 순서와 같다 (2026-10-11 실측: 강남구·마포구 343건, 날짜·방 수·가격 조건을 줘도 역전 0건, 결과 15건 같음). 반경 밖 지도 핀은 받아도 버려 요약을 받지 않는다. 반경 거리순은 가까운 핀 `limit` 개만 받는다 (2026-10-10 실측: 강남역 by-ids 3회 → 1회). 반경 검색은 지역 검색 API 를 부르지 않는다. 반경 안 매물은 지도 핀에 모두 있고 지역 검색 ID 는 구·동 전체라 반경 밖 요약만 늘린다 (2026-10-11 실측: 6곳에서 핀에 없는 검색 ID 는 모두 반경 밖, 강남구 1km 가격순 by-ids 4회 → 1회, 결과 같음) |

원룸·오피스텔·빌라 검색과 오피스텔 건물 매물, 상가 거래 유형(임대·매매)은 [공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)대로 서버가 건 유형·거래 유형·방 구조를 요약을 받은 뒤 다시 거르지 않는다 (2026-10-10 실측: 원룸·빌라·오피스텔 월세·전세·단기임대와 방 구조 조건 200건, 오피스텔 건물 3곳 34건, 상가 역삼역·성수동 임대·매매 662건 모두 조건 안). 원룸 목록에 섞여 오는 원룸형 오피스텔도 그대로 둔다. 받은 뒤 빼는 것은 거래 불가(`status`), 지원하지 않는 거래 종류, 반경·동 경계 밖뿐이다. 직방 매물은 거래 조건이 하나라 거래 조건 선택이 없다. 서버가 받지 않는 조건(아파트 전용면적, 반경 검색의 공급면적, 상가 가격)만 받은 뒤 거르고, 값이 없으면 통과시키지 않는다.

검색 조건 묶음([공통 규칙](../provider-conventions.md#검색-조건-묶음))은 유형마다 따로 있다: `ZigbangRoomConditions`
(원룸·빌라·오피스텔 검색과 오피스텔 건물 매물, `common`), `ZigbangAptConditions`(`apt`), `ZigbangStoreConditions`(`store`),
`ZigbangStayConditions`(`stay`). `--condition`(기타 조건)은 모델에서 `extra_conditions` 다 (`conditions` 는 묶음 이름이라).
매물 유형(`property_types`)은 단지 매물 목록에 없어 `search_listings` 인자로 따로 받고, 단기임대 정렬은 `StaySort` 로 받는다.

핀 집계·조회한 원본 수·가격 확인 후보 수·최종 반환 수를 구분한다. 가격·기간·관리비 없음 옵션의 충돌은 CLI에서 거절한다. 라벨 옵션(업종·방 구조·단기임대 방 종류·옵션·할인·층)은 CLI 의 `split_csv` 가 허용값으로 검증하고, service 는 검증된 라벨만 받는다. 라벨 → 서버 코드 사전(`*_BY_LABEL`) 조회의 KeyError 는 입력 오류가 아니라 내부 오류라 따로 잡지 않는다 (2026-10-10 실측: 잘못된 라벨 7종 모두 요청 전에 `INVALID_ARGUMENT`). 기간 비용의 요금 계산과 실제 예약 가능 여부 확인은 별도 요청이다. 실거래 전세·월세는 혼합 응답에서 필터하며, 쪽 수 상한 없이 넘기면 `--limit 1000` 에 요청이 62회까지 나가(2026-10-10 실측: 헬리오시티 전세) 당근처럼 24쪽(최근 1200건)에서 멈추고 `notes` 로 본 범위를 알린다. 매매는 받은 거래를 모두 써서 `--limit` 최대 1200 도 24쪽이면 된다. 갱신 여부는 알려지지 않았으면 `null`이다.

## API 변경 시 점검

익명 인증은 client의 `ZigbangGuestAuth`, 호스트·플랫폼 헤더·재시도는 client, 유형별 필터 직렬화는 request, catalog·핀·요약·상세는 response를 확인한다. service의 상세 보완 호출과 만료 판정, 제휴 매물의 누락값을 함께 확인한다. 토큰 발급 HTTP도 공통 요청 제한 훅을 유지한다.
