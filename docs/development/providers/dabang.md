## 소스 고유 구현

### 두 API 방식과 헤더

- 새 방식 `/api/v5/` 는 웹이 붙이는 헤더(`D-Api-Version: 5.0.0`, `D-App-Version: 1`, `D-Call-Type: web`, `V5_HEADERS`)를 붙이고, 응답 봉투 `{code, msg, result}` 의 `result` 를 쓴다. 키는 camelCase.
- 옛 방식 `/api/3/`(상세·매물번호)은 헤더 대신 쿼리에 `api_version=3.0.1&call_type=web&version=1` 을 붙이고(`DabangV3RequestParameterModel`) 봉투 없이 snake_case 로 온다.
- 모든 요청에 웹 axios 인스턴스(v5·v3 둘 다)가 붙이는 기본 헤더 `Accept: application/json, text/plain, */*`·`csrf: token`·`Cache-Control: no-cache`·`Pragma: no-cache`·`Expires: -1` 을 붙인다 (`base_header`, 2026-11-12 웹 화면 8개 요청 109건 실측과 번들. 요청마다 바뀌는 헤더는 없다). v5 인스턴스만 `V5_HEADERS` 를 더 붙인다. 토큰·쿠키는 없다.
- 없는 주소·경로 값은 404 대신 **403 빈 응답** 이다 (아무 경로나 넣어도 같다). 요청 제한과 섞지 않는다. ID 가 경로에 들어가는 요청(단지 상세·주변 시설·학교)만 `is_missing_id` 로 빈 403 을 `NOT_FOUND` 로 본다. ID 가 쿼리로 가는 요청(분양 상세·교통·단지 실거래·매물 실거래)은 없는 ID 에 400 이나 빈 결과를 줘서(2026-10-27 실측) 빈 403 이면 다방 주소가 바뀐 것으로 `UPSTREAM_ERROR` 다 (`in_path=False`).

### 브라우저 요청

(2026-11-09 실측) 공통 동작은 [브라우저 요청](../architecture.md#브라우저-요청). 다방만의 값:

- 첫 화면은 `https://www.dabangapp.com/`. 다방이 심는 쿠키는 분석·광고용(`_ga`·`wcs_bt`·`dable_uid` 등)뿐이고 API 는 쿠키 없이
  응답해 기다릴 쿠키가 없다 (`browser_ready_cookie = None`). 첫 화면이 다방 API 를 XHR 로 11번 부른다. JS 파일(`/_next/static`)도
  같은 호스트라 요청 제한에는 XHR·fetch 만 센다.
- 403 이 없는 주소라 `browser_discard_statuses` 를 비운다 (403 에 쿠키를 버리지 않는다). API 가 쿠키를 보지 않아 막힌 403
  이어도 쿠키를 버려서 풀릴 것이 없다. 다방이 방문자 쿠키(WAF 토큰 등)를 요구하기 시작하면 본문이 있는 403 만 버리게 바꾼다.
- 동 경계 CDN(`geojson_host`)은 `Access-Control-Allow-Origin: *` 라 다른 출처 fetch 가 되지만, `csrf` 헤더를 붙이면 브라우저의
  사전 확인(OPTIONS)이 403 이다. 웹도 이 파일은 axios 가 아니라 `fetch(url)` 로 받아 헤더를 하나도 붙이지 않으므로, 동 경계
  요청에서는 기본 헤더를 모두 뺀다 (`_geojson_request`, 2026-11-12 실측).

### 매물 목록 (`search listings`)

- 다방 목록은 유형(`one-two`·`house-villa`·`officetel`·`apt`)마다 따로이고 필터 항목도 다르다. **필터 항목이 하나라도 빠지면 400** 으로 빠진 항목을 한국어로 알려 준다. 그래서 유형마다 요청 모델(`DabangOneTwoFiltersModel` 등)을 두고 주지 않은 항목을 '전체' 값(`{min: 0, max: 999999}`, 모든 목록 값)으로 채운다. `zoom`·`useMap=naver` 도 필수다 (`ZOOM_BY_SEARCH_TYPE`: 동 14, 역·대학 15, 지도 16).
- 필터 범위 값은 하한·상한 모두 999999 까지만 받는다 (넘으면 400 '최대값은 999999 이하로 입력해주세요'). 큰 상한은 `range_of` 가 999999 로 줄이고 큰 하한은 CLI 가 막는다. 압구정·청담·한남동 아파트 매매도 98억까지라 999999 로 빠지는 매물은 보지 못했다.
- 한 쪽은 24건이고 `limit` 을 보내도 무시한다. 다만 다음 쪽이 있어도 더 적게 줄 때가 있다 (2026-11-13 웹 캡처: 아파트 강남역 1쪽·대치동 화면 2쪽 23건. 2026-11-14 실측: 아파트 강남역 반경 3km 6~8쪽 22·22·21건). `total`·`hasMore` 는 일반 목록 기준이라 정확하다. 그래서 이어 받기 위치를 받은 수로 셈하지 않는다. 이어 받기 표(`DabangListPosition`)에 다음에 물을 다방 쪽(`page`)·그 쪽에서 쓴 칸(`skip`)·받은 수(`received`, `[일부] N번째부터` 안내에만 쓴다)·아파트 동 사각형(`bbox`)을 담고, 다음 호출은 그 쪽의 남은 칸부터(다 썼으면 다음 쪽 처음부터) 받는다. 받은 수로 쪽을 셈하면(`수 // 24 + 1` 쪽의 `수 % 24` 번째) 23건짜리 쪽 뒤에 다음 쪽 첫 건을 다시 받아 같은 매물이 또 나온다 (`test_next_resumes_after_short_page_without_repeating_listings`). 단지 매물(`search listings --complex`)·단지 목록·분양 목록도 받은 수가 24건보다 적다고 끝내지 않고 `hasMore` 로만 다음 쪽을 본다. 네 목록(분양은 지역 목록·지도 목록 둘 다)과 동 안 학교·핫플레이스는 쪽 따라가기를 `fetch_pages`(`service/common/functions.py`) 하나로 해 이 규칙이 한 곳에 있다. 더 있는지(`has_more`)는 네 목록과 인기 매물·지역 순위·실거래가 모두 `more_after`(`service/common/functions.py`) 하나로 정한다: `--limit` 에 맞춰 잘라 낸 줄이 있으면 서버 `hasMore` 와 상관없이 더 있고, 아니면 `hasMore` 를 따르되 빈 쪽이면 `hasMore` 가 와도 더 묻지 않고 더 없다로 본다 (빈 쪽을 상한까지 묻고 '다방에 더 있음' 이라 잘못 알리지 않게, 2026-11-14 리뷰). 쪽 수도 `--limit` 을 24건으로 나눠 정하지 않고 `--limit` 이 찰 때까지 받는다 (목록마다 `fetch_pages` 가 `2 * ceil(max_limit / page_size)` 로 정한 상한: 24건 목록은 10쪽, 동네정보 30줄 목록은 8쪽). 상한까지 받고도 못 채웠는데 더 있으면 `fetch_stop_notes` 가 `[일부]` 로 알린다 (`limit_notes` 는 받은 수가 `--limit` 보다 적으면 다 받은 것으로 보고 안내하지 않는다). 쪽이 쪽 크기의 절반 아래(24건 목록은 평균 12건 아래)여야 닿는 상한이라 실측에서는 닿지 않았고, 상한을 낮춰 그 안내를 확인했다 (2026-11-14).
- 가격·층·면적·관리비는 숫자 없이 글자(`priceTitle` '1억2000/50', `roomDesc` '5층, 19.83m², 관리비 7만')로만 온다. `manwon_from_text`·`listing_prices`·`parse_room_desc` 가 읽고, 읽지 못한 매물은 빼고 `notes` 로 알린다 (`tests/test_dabang.py`). 단지 목록·요약은 억 뒤에 띄어쓰기·쉼표를 넣는다('31억 3,000'). 다방은 반지하를 '반지층' 으로 쓴다.
- 출력 날짜(`registered_date`·`approved_date`, 실거래·단지 최근 거래의 계약일)는 공용 `read_date` 로 읽는다. 계약일은 `'20' + 글자` 로 조립하므로 안내에 보일 원래 글자를 `raw` 로 넘기고, 다방이 값 없음으로 주는 `'-'`·빈 글자는 안내 없는 `null` 이다. `search listings --details` 는 상세에서 받은 사용승인일이 결과 `approved_date` 에 `null` 로 나갈 때만 못 읽은 날짜를 알린다 (목록이 이미 값을 줘 상세 값을 쓰지 않은 매물의 안내는 내지 않는다). 연월 칸(`price-trend` 의 `month`, 순위의 `price_month`·`prev_price_month`)은 `read_month`·`add_unread_date` 로 읽고 못 읽으면 `null` + `[참고]` 다.
- `roomDesc` 의 면적은 원룸·빌라·오피스텔이면 상세 전용면적(`room_size`)이지만 **아파트면 공급면적**(`provision_size`)이다. 아파트 목록·단지 매물·인기 매물과 원룸·투룸 목록에 섞인 아파트 모두 같고, 목록 칸에 전용면적은 없다. 그래서 아파트는 `area_m2` 를 `null` 로 두고 `supply_area_m2` 에 넣는다 (`room_item_to_listing`). 아파트 목록의 평 조건(`pyeongRange`)도 공급 평으로 걸린다 (34평 → 공급 112~113㎡).
- 다방 단지 목록(`complex-list`)은 쪽마다 순서가 흔들려 앞 쪽 끝 단지를 다음 쪽 첫머리에 다시 준다 (정렬 옵션 없음, 잠실동 3쪽 71줄 중 69곳). 단지 ID 로 한 번만 넣고 `[제외]` 로 알린다. 매물 목록도 쪽끼리 같은 매물을 겹쳐 준다 (2026-11-13: 아파트 강남역 1~5쪽 120줄 중 108곳만 서로 달랐고, `--next` 1·2차 사이에 3건이 겹쳤다). 한 호출 안에서는 매물 ID 로 한 번만 넣고 `[제외]` 로 알린다. 호출과 호출 사이(`--next`)의 겹침은 웹도 쪽을 넘기면 그대로 보여 주는 서버 동작이라 그대로 둔다.
- 원룸·투룸 목록은 매매를 받지 않는다 (매매만 보내면 무시하고 월세를 준다). 그래서 `room` 의 `--trade` 에서 매매를 뺐다.
- 단기임대는 별도 거래가 아니라 월세 매물의 표시(`roomTypeName` 의 ' • 단기', 상세 `short_lease_str`)다. `trade_type` 을 단기임대로 바꾸지 않고 `short_term` 로 알린다. 보증금 1000·월세 90 같은 보통 월세에도 붙어, 단기임대로 바꾸면 `--trade 월세` 검색에서 월세 대부분이 빠진다.
- 원룸·투룸 목록에 오피스텔·아파트가, 아파트 목록에 주상복합·도시형이 섞여 온다. [공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)대로 다시 거르지 않는다. 주택·빌라 목록은 매물을 방 개수(원룸·투룸)로 표시해 `property_type` 을 '빌라' 로 둔다.
- 광고(`premiumList`, 광고 중개사별 매물)는 일반 목록과 따로 오고 `total` 에 들지 않는다. 넣지 않고 뺀 수만 `notes` 로 알린다.
- 사용승인 조건(`useApprovalDateRange`, `--built-within`)은 날짜가 아니라 연도로 센다. 2026-10-31 실측: `{max: 2}` 에 2024-02-21 승인(신림동·화곡동 16건 중 가장 오래된 것), `{max: 10}` 에 2016-02-03 승인 건물이 들어오고 그 앞 해 승인은 없었다. 서버 필터라 다시 거르지 않고(목록에 사용승인일도 없다) `search_listings` 가 기준 날짜(`올해 - N` 년 1월 1일)를 `[참고]` 로 알린다. 날짜로 따지려면 `--details`(`attach_details`)가 앞 30건에 상세(`get_listing`, 1회씩)의 사용승인일·건물 용도를 붙인다. 상세에서 내려간 매물은 뺀다. 햇수가 넘은 매물을 짚는 `[참고]` 는 날짜로 읽은 사용승인일만 비교한다 (읽지 못한 승인일은 `read_date` 가 `null` 로 내므로 비교하지 않고 `사용승인일` `[참고]` 가 따로 알린다). 상세 요청이 그 밖의 이유(요청 제한·서버 오류·응답 형식)로 실패한 매물은 목록 값 그대로 두고 `[실패]` 로 알리며, 요청 제한이면 남은 상세는 요청하지 않는다 (예외 범위는 `service/common/functions.py` 의 `OPTIONAL_LOOKUP_ERRORS`. 단지 덤 조회와 같이 쓰려고 `complex` 에서 옮겼다. 2026-11-19 리뷰 전에는 한 건만 실패해도 받은 목록 전체가 에러로 끝났다).
- 오피스텔·아파트 필터의 `parkingNumRange` 는 단지 세대당 주차 대수다. 웹 주차 필터의 '세대당 1대 이상'·'2대 이상' 이 `{min: 1|2, max: 999999}` 로 간다 (parking 청크, 2026-11-13. 같은 날 실측: 아파트 강남역 113 → 1대 이상 79 → 2대 이상 19건, 오피스텔 126 → 6 → 0건). 원룸·빌라·오피스텔의 `canParking`(`--condition 주차`, 주차 가능 여부)과 다른 조건이라 옵션을 `--parking-min` 으로 따로 둔다 (`PARKING_NUM_RANGE_DESCRIPTION`).
- 아파트 필터의 `hasTakeTenant` 는 웹 아파트 '추가필터' 의 '세안고'(세입자가 있는 채로 파는 매매 매물)다 (아파트 강남역 113 → 7건, 모두 매매, 2026-11-13). 웹은 거래 유형에 매매가 있을 때만 이 필터를 보여 주고 매매를 빼면 끈다 (filter 청크). 그래서 CLI 는 검색할 거래 유형(`--trade`, 단기임대·가격 조건으로 좁힌 결과 포함)에 매매가 없으면 웹에 없는 조합이라 `INVALID_ARGUMENT` 로 막는다 (`_search`).
- 목록 좌표(`randomLocation`)는 다방이 몇 m 흔든 값이다. 거리(`distance_km`)와 반경 판정에만 쓰고 출력하지 않는다.

### 위치 해석 (`region`)

- `loc/search` 는 시·군·구를 주지 않는다 (`강남구` 를 찾으면 강남구의 동들). 구·시 이름은 `REGION_NOT_SUPPORTED` 로 막는다. 행정동은 결과가 없어 `legal_dong_hint` 를 붙인다.
- 고르는 순서는 이름이 똑같은 동 → 역('역' 으로 끝나면 역 먼저) → 대학 → `○동N가` 동이다. 같은 이름의 동이 여럿이면 `REGION_AMBIGUOUS`, '강남구 신사동' 처럼 앞 낱말이 있으면 동의 전체 이름에 그 낱말이 든 후보만 본다. 시·도 줄임말('서울 신사동')은 `SIDO_OFFICIAL_NAMES` 의 정식 이름으로도 맞춘다 (전체 이름은 '서울특별시 …'). 대학은 이름이 똑같은 곳을 먼저 보고, 없으면 앞부분이 맞는 곳을 본다. 앞부분이 맞는 곳이 둘 이상이면('연세대' 는 세 캠퍼스) 고르지 않고 `REGION_AMBIGUOUS` 로 대학 이름을 후보로 준다 (후보 이름을 그대로 주면 이름이 똑같은 대학으로 찾는다). 장소 검색은 괄호가 든 검색어에 0건이라 괄호를 띄어 보낸다. 이름이 똑같은 역이 여럿 와도 `REGION_AMBIGUOUS` 이고 후보 글에 노선을 붙인다. 다방은 같은 이름의 역을 '양평역'·'양평역(중앙선)' 처럼 이름으로 갈라 주어(2026-11-13 실측) 드물고, 이름으로는 다시 가를 수 없어 `hint` 가 `search locations` 의 좌표로 찾게 한다. 한 종류만 받는 명령은 `resolve_places(only=)` 로 그 종류를 알린다 (`neighborhood`·`hot-places`·`popular-listings`·`search schools` 는 `'dong'`, `station-prices` 는 `'station'`). 시·군·구 이름의 `REGION_NOT_SUPPORTED` `hint` 도 `only` 로 갈라 받는 이름만 권한다 (`'dong'` 은 그 안의 동 이름, `'station'` 은 역 이름, `None` 은 동·역·반경). 동을 받는 명령의 `resolve_dong(subject=, elsewhere=)` 는 `INVALID_ARGUMENT` 의 주어('동네정보는'·'인기 매물은'…)와 역 둘레를 볼 다른 명령을 명령마다 받고, 볼 명령이 없으면(`hot-places`·`search schools`, 학교·식당은 다른 명령이 주지 않는다) `elsewhere=None` 으로 '이 명령은 역·대학 둘레를 찾지 않습니다' 를 알린다. 받지 않는 종류의 후보가 여럿이면 고르라고 알리지 않고 첫 후보를 돌려줘, 부른 쪽이 '동 이름으로만 찾습니다'·'역 이름이 아닙니다'(`INVALID_ARGUMENT`)로 막는다. 이때 첫 후보의 이름은 사용자가 준 이름으로 바꿔, 에러 문구에 고르지도 않은 후보('성수동1가')가 아니라 준 이름('성수동')이 찍힌다. 후보를 골라 다시 줘도 그 명령이 받지 못하기 때문이다 (2026-11-13 리뷰: `neighborhood 연세대` 가 대학을 고르라고 한 뒤 다시 막았다). 좌표를 받지 않는 `station-prices` 는 이름이 똑같은 역을 가려 받지 못한다고 `hint` 로 알린다.
- 위치 찾기(`resolve_places`)는 위치 하나만 돌려주고 매물·단지·분양 검색, 동네정보, 핫플레이스, 인기 매물, 동 안 학교, 역 평균 매물가가 모두 이것을 쓴다. `○동N가` 로만 나뉜 동(성수동)은 `○가` 동이 둘 이상이면 합쳐 찾지 않고 `REGION_AMBIGUOUS` 로 전체 주소 후보를 모두 준다 (같은 동의 `○가` 는 몇 곳뿐이라 자르지 않는다). 다방 웹 검색창도 성수동1가·성수동2가를 따로 보여 주고 고른 동 하나의 목록만 연다 (2026-11-13 웹 대조). 시·도가 다른 `○가` 동이면 시·도를 후보로 준다. 이어 받기 표에는 첫 결과가 찾은 위치(동 코드·역 번호 포함)도 남겨 `--next` 때 장소 검색을 다시 묻지 않는다.
- 아파트 매물 목록·아파트 단지 목록은 동·대학 검색이 없다 (403). 오피스텔 단지 목록은 동(`region`)·대학(`univ`) 검색이 된다 (2026-10-26 실측: 역삼동 97곳, 홍익대학교). 동은 다방 지도 집계가 주는 동 경계 파일(`d2pi55cyzoqmrc.cloudfront.net/geojson/region/{8자리 코드}`)로 사각형을 만들어 `bbox` 로 받고, 목록의 동 번호(`gid`)가 그 동인 것만 남긴다. 대학은 1km 반경이다. 경계 파일도 같은 요청 제한 훅을 거친다. 아파트 매물 검색은 사각형을 이어 받기 표(`next`)에 남겨 `--next` 마다 경계를 다시 받지 않는다.
- 역은 다방이 정한 역 반경(강남역 750m, `loc/search` 의 `radius`)이고, `--radius` 를 주면 그 반경을 덮는 사각형으로 받아 반경 밖을 뺀다. 단지 목록은 반경을 덮는 사각형을 그대로 받고 반경 밖을 빼지 않는다 (CLI 도움말도 그렇게 적는다, `ComplexRadiusOption`).
- 목록 주소는 찾은 동(`gid`)의 매물만 시·구까지 붙인다. 목록 칸에는 동 이름만 있어 다른 동의 시·구는 모른다. 그래서 동 이름에 `--radius` 를 주면 두 꼴이 섞인다.
- 동 코드는 법정동코드 앞 8자리다. 출력은 뒤에 `00` 을 붙여 10자리로 맞춘다. 다방은 이미 '전남광주통합특별시'(시·도 코드 12)를 쓴다.

### 상세·단지·학교·실거래

- 상세 유형(`room_type_str`)은 목록과 달리 구조를 붙여 온다 ('오피스텔(분리형)'·'원룸(분리형,복층)'). 단지 ID·이름은 다방이 주면 유형과 상관없이 두고, 없을 때만 앞부분이 오피스텔·아파트인지로 해당 없음(키 삭제)과 모름(`null`)을 가른다 (`is_complex_type`).
- 상세 `price_info` 는 `[보증금 또는 매매가, 월세, 거래 유형 코드]` 숫자(만원)다 (0 월세, 1 전세, 2 매매). 화면처럼 `status` 0·3·4 는 비공개로 보고, `is_contract` 도 거래 불가로 본다. 없는 매물은 400 "존재하지 않는 매물입니다."(매물번호는 "존재하지 않는 방입니다.")다. 다른 소스 ID 를 넣어도 이 응답이라 사유를 `ListingUnavailableError` 에 넘기지 않는다 (넘기면 다른 소스 ID 힌트가 빠진다).
- 관리비 포함 항목(`_manage_cost`)은 웹 관리비 칸과 상세보기(safety-option-chunk `E`, room-chunk, 2026-11-13)를 따른다. 입력 방식(`maintenance_input_type`)이 `DETAIL` 이 아니면 웹처럼 포함 항목 글(`maintenance_items_str`)만 본다. `DETAIL` 이면 부과 방식(`maintenance_charge_type`: `FIXED_FEE_CHARGE` 정액관리비·`ETC_FEE_CHARGE` 기타부과·`UNABLE_CHECK` 확인불가)으로 가른다. 정액관리비이고 세부 종류(`maintenance_charge_detail_type`)가 없거나 `ABOVE_FIXED_FEE_THRESHOLD` 이면 `maintenance_fixed_fee_charge_detail_list` 에 항목(F01 공용·F11 전기·F12 수도·F13 가스·F14 난방·F15 인터넷·F16 TV·F99 기타)마다 `FIXED_FEE`·`ACTUAL_EXPENSE`(실비)로 온다. 공용(F01)은 실비로 와도 웹이 금액과 함께 보여 주고 합계에 넣어 포함 항목이고(`E` 의 `h`), 나머지는 `FIXED_FEE` 면 포함, `ACTUAL_EXPENSE` 면 `manage_cost_excludes` 다 (`FIXED_FEE_ITEM_LABELS`). 예: 6ae45e683b53321aea64a773 관리비 20만원은 공용이 실비로 와서 포함 항목이 `['공용 관리비']` 다 (웹 상세보기 '공용 200,000원 · 사용료 실비'). `BELOW_FIXED_FEE_THRESHOLD`·`ABOVE_FIXED_FEE_THRESHOLD_NO_DETAILS` 정액관리비와 기타부과는 `maintenance_etc_fee_charge_detail.detail_include_types` 코드를 웹의 표(`MANAGE_ITEM_LABELS`)로 바꾸고(`E` 의 `g`), 따로 내는 항목은 웹도 보여 주지 않아 `null` 이다. 확인불가는 웹도 항목을 보여 주지 않아 항목이 `null` 이다 (`E` 의 `_`). 부과 방식은 `manage_cost_charge_type` 으로 낸다 (`MANAGE_CHARGE_TYPE_LABELS`).
- 계약면적(`contract_size`)은 오피스텔만 값이 오고 다른 유형은 0 이라 (2026-11-13 실측: 상세 46건 중 오피스텔 5건만 값) 0 이면 키를 뺀다. 유형이 `오피스텔` 로 시작하는 매물은 0 이 와도 해당 없음이 아니라 모름이라 `null` 로 둔다 (2026-11-13 실측: 오피스텔 34건은 모두 값이 있어 0 인 매물은 아직 보지 못했다). 웹은 유형 코드가 오피스텔(`roomType === 3`)이고 상세 응답의 `complex.isUrbanOfficetel` 이 false 인 매물에 '전용/계약면적' 으로, 그 밖에는 '전용/공급면적' 으로 보여 준다 (room-chunk). jibsa 는 유형 글자(`room_type_str`)가 `오피스텔` 로 시작하는지로 가르는데, 유형 코드와 글자는 늘 같이 왔다 (2026-11-13 실측: 상세 29건, 3 은 `오피스텔`·`오피스텔(분리형)`, 4 는 `아파트`·`아파트(복층)`). 이름에 '(도시형)' 이 붙은 단지는 오피스텔이 아니라 아파트 유형으로 와서(다방 단지 검색 50곳 모두 아파트, 5곳 매물 17건 모두 `roomType` 4·계약면적 0·`isUrbanOfficetel` false) 키가 빠지고 웹도 공급면적을 보여 준다. 세입자 낀 매물(`is_take_tenant`)·LH 전세임대(`is_lh_lease`)·임차권 등기명령(`is_leasehold`)·미등기 건물(`is_new_construction`)은 `null` 이면 웹이 없는 것으로 본다 (safety-option-chunk 의 `?? false`). 위반건축물(`is_non_compliant_building`)만 `null` 이면 웹이 그 줄을 감춰 `null`(모름)로 둔다 (room-chunk, true·false 는 '해당'·'해당없음'). 기존 세입자 금액(`take_tenant_price_title`)은 '20억'·'1억/50' 같은 만원 글자라 `get_listing` 이 보증금·월세로 나누고, 읽지 못하면 둘 다 `null` 이다. 세입자 낀 매물은 매매, LH 전세임대는 매매가 아닌 거래에만 키를 두되 다방이 표시를 붙였으면 웹처럼 둔다 (`not_applicable_fields`).

'SALE' : 'LEASE'`, room 청크 `Rr`). `--trade` 를 주지 않으면 이 값을 쓴다. `--trade` 를 주면 `init` 을 받지 않는다. 거래 유형을 정할 일이 없고, 범위·동·건물 유형은 `house/history` 첫 쪽이 준다 (2026-11-14 실측: 매물 7곳 × 매매·전월세 모두 거래 0건인 기간에도 `dongName`·`historyBaseType`·`buildingViewType` 이 왔고 `init` 과 같았다). 출력은 같고 요청만 1회 줄어든다. 그래서 매일 감시는 `--trade 전월세`(요청 1회)와 `--trade` 없는 기본(요청 2회)을 함께 불러 `init` 도 본다. `historyBaseType` 이 `JIBUN` 이면 이 집(같은 지번) 거래, `DONG` 이면 같은 동의 같은 건물 유형 거래이고, 웹 제목도 '이 집의 ○○ 거래정보는?'·'{동} ○○ 거래정보는?' 이다 (room 청크 `ii`, 2026-11-13 웹 캡처: 망원동·역삼동 다세대 `JIBUN`, 망원동 단독 `DONG`). 범위는 거래 유형마다 다르다 (2026-11-13 실측: 역삼동 월세 다세대 매물 하나가 전월세는 `JIBUN` 2건, 매매는 `DONG` 585건). `init` 의 범위는 매물의 거래 유형 것이라, `--trade` 로 다른 유형을 받을 때도 맞도록 `basis` 와 안내의 범위·동은 받은 `house/history` 응답의 `historyBaseType`·`dongName` 으로 만든다. 건물 유형(`buildingViewType`)은 거래 줄의 면적 키(아래)와 `basis`·안내의 건물 이름·면적 기준이 같은 값을 쓴다 (목록 첫 쪽 값, 없으면 `init` 값). 그 응답이 범위를 주지 않으면 `init` 으로 매물이 있는지 확인하고, `init` 의 범위는 찾는 거래 유형이 매물의 유형과 같을 때만 쓴다 (아니면 범위를 모른다고 `[참고]`). `basis` 는 `JIBUN` 이면 `'이 집 (망원동 다세대·연립)'`, `DONG` 이면 `'역삼동 단독·다가구'` 이고, 모르는 값이면 짐작하지 않고 `null` 과 `[참고]` 업데이트 안내다. `buildingViewType` 이 `MULTIPLEX`(다세대·연립)면 웹 표가 전용면적·층수(`Kr`)라 `area_m2`·`floor`, 그 밖(`DETACHED` 단독·다가구)은 연면적·주택유형(매매만)이고 층 칸이 없어(`ei`) `total_floor_area_m2`·`house_type` 으로 낸다. 단독·다가구의 면적은 164~1,214㎡ 같은 건물 전체 값이라 매물 전용면적과 견주지 않게 알린다. 거래 줄의 `isRegistration`(등기)·`isNew`(새 거래) 표시는 `registered`·`newly_added` 로 내고, 단독·다가구 줄에는 `isRegistration` 이 없다 (2026-11-13 실측). 없는 매물·단지 매물에는 `init`·`house/history` 가 에러 대신 `searchType`·`dongName`·`historyBaseType` 이 모두 `null` 인 결과를 줘서 `NOT_FOUND` 로 바꾼다 (2026-11-13·11-14 실측. 거래가 0건인 매물도 동·범위는 온다). `init` 의 `compare`(시세 대비 값)는 다방이 표시를 꺼 두어 웹에 나오지 않아 모델에 두지 않는다 ([아직 가리지 못한 것](#아직-가리지-못한-것)).
- 단지 매물(`room-list/category/{apt·officetel}/complex`)의 `order` 는 웹 단지 매물 탭의 정렬 메뉴 값이다 (complex 청크 `xt`, 2026-11-13): 랭킹순 `RANKING`(웹 기본)·최신순 `LATEST`·높은가격순 `SELLING_HIGHEST`·낮은가격순 `SELLING_LOWEST`·면적넓은순 `ROOM_SIZE_LARGEST`·면적좁은순 `ROOM_SIZE_SMALLEST` (`COMPLEX_SORT_BY_LABEL`, `DabangComplexRoomOrder`). 없는 값은 400 이다. 은마 매매 5건이 `SELLING_LOWEST` 는 30억7000 → 34억, `SELLING_HIGHEST` 는 그 반대로 왔다 (같은 날 실측). 서버가 정렬한 순서를 다시 세우지 않고, 결과 `sort` 와 `[일부]` 안내 문구(`COMPLEX_SORT_BY_LABEL` 의 `text`)가 고른 정렬을 알린다. 동·역·대학 매물 목록은 웹에도 정렬이 없어 `--sort` 를 열지 않는다.
- 매물·단지 주소 `/room/{id}`·`/complex/{id}` 는 서버가 지도 화면으로 넘겨 준다 (302).

### 동네·주변 (`neighborhood`·`hot-places`·`popular-listings`·`nearby`·`station-prices`)

- 동네정보는 탭마다 주소가 둘이다: `summary`(항목 하나의 값과 전국·시도·구 순위, `summaryType` 하나씩)와 `count`(그 탭 항목별 수를 한 번에). 요청을 아끼려고 매물·거래·시세·인구는 `summary`, 학교·편의·교통·안전은 `count` 만 부르고, 이 네 주제의 `summary` 는 `--ranks` 일 때만 종류마다 부른다 (아래). 수와 순위는 글자('1,074개', '60위')로 와서 숫자로 바꾼다. 출처는 화면 문구대로 매물 수·선호도는 다방, 거래량·평균가는 국토교통부, 인구는 행정안전부다. 시세 탭의 순위(`rankingGroup`)는 웹 표시대로 '아파트/매매 기준' 이다 (오피스텔·전세 평균가는 순위에 들지 않는다).
- 인기 매물은 선호도(조회수·찜수·문의수 종합 점수) 순위다. 순위(`rank`)는 받은 수가 아니라 `(page - 1) × 쪽 크기 + 칸` 으로 센다. 다방이 한 쪽을 덜 채워도 다음 쪽은 그 자리부터라, 받은 수로 세면 그 뒤 순위가 앞으로 당겨진다. 매물 칸에 동 번호·좌표가 없어 주소는 찾은 동으로 채운다. 매물 유형은 주택/빌라·오피스텔·아파트뿐이다. 칸에 건물 유형도 없어 여러 유형을 섞어 받으면 '오피스텔'·'아파트' 표시는 그 이름으로, 방 개수 표시('원룸'·'투룸')는 빌라로 본다 (`POPULAR_KIND_BY_ROOM_TYPE`). 더 있다는 `[일부]` 안내는 동 하나의 순위라 좁힐 지역이 없어, 아직 고르지 않은 `-t`·`--trade` 만 권한다 (둘 다 하나씩 골랐으면 `limit_notes(narrow=None)` 이 `--limit` 만 알린다).
- `{target}/{id}/near` 의 시설 종류 `query` 는 카카오 장소 분류 코드(MT1·CS2·CE7·BK9·PM9·PO3·SW8)와 다방 코드(BS·POLICE·CCTV·NS·KS·ES·MS·HS)다. 대상마다 주는 종류가 다르다: 매물은 CS2·CE7·BK9·PO3, 단지는 MT1·CS2·BK9·PM9. 종류 이름은 웹 주변 지도의 이름표 그대로다 (`NEAR_LABELS`, distance-km-m 청크, 2026-11-13: BS 버스, SW8 지하철역, MT1 마트, CS2 편의점, CE7 카페, BK9 은행, PM9 약국, PO3 관공서, POLICE 치안, NS 어린이집, KS 유치원, ES 초등학교, MS 중학교, HS 고등학교). 편의 종류는 거리순 15곳까지 오고 어린이집·CCTV 는 순서가 섞여 와서(2026-11-13 실측: 역삼동 매물 어린이집 6곳), 종류마다 다방 거리 값으로 세워 가까운 순 3곳(`NEAR_PLACES_PER_TYPE`)을 낸다. 치안은 이름 대신 `gubun`('지구대'), CCTV 는 `usage`('생활방범')가 와서 치안은 `name` 이 `null` 이고 CCTV 는 쓰지 않는다. 시설 좌표·전화는 내보내지 않는다.
- 분양 주변(`nearby --sale`)은 웹 분양 상세의 주변 정보와 같은 두 주소에 대상만 `sale` 이다: `sale/{id}/near` 와 `transit/near/sale?saleId=` (2026-11-13 실측: 호반써밋 풍무Ⅱ 68f1ac43… 는 시설 종류가 단지와 같은 BS·SW8·MT1·CS2·BK9·PM9·POLICE·CCTV, 교통은 풍무역 476m). `transit` 은 `saleId` 만 받는다 (`id`·`saleInLotsId` 는 400). 분양 ID 와 단지 ID 가 둘 다 28자리라 길이로 가르지 못해 CLI 가 `--sale` 옵션으로 받는다 (`get_nearby(sale=True)`). 없는 분양 ID 는 매물·단지처럼 시설 요청(ID 가 경로에 든다)의 에러를 `is_missing_id` 로 보아 `NOT_FOUND` 다 (2026-11-13 실측: 없는 ID·단지 ID 모두 `NOT_FOUND`).
- 학교·편의·교통·안전 탭의 `summary`(`neighborhood --ranks`)는 탭마다 종류를 받는 칸 이름이 다르다: `schoolType`·`amenityType`·`mobilityType`·`lifeSafetyType` (매물·시세는 `summaryType`, 요청 모델 검사기가 탭마다 그 칸 하나만 받게 한다. 빠지면 400 '유형은 필수입니다'). 종류 값은 순위 항목 이름과 달라 `ELEMENTARY_SCHOOL`·`SAFETY_FACILITY` 처럼 쓴다 (`ELEMENTARY`·`SAFETY` 는 400, 2026-11-14 실측). 종류와 순서는 웹 요약 칸의 고르기 그대로다 (school·facility·traffic·life-safety 청크 tabList, 2026-11-13, `RANK_TYPES_BY_TOPIC`). 합계는 `formattedTotalCount` 글자, 구성은 `distributionList` 의 `count`(없으면 `formattedCount`)로 읽고, 순위(`rankingGroup`)는 다른 주제와 같은 꼴로 낸다 (2026-11-14 실측: 역삼동 교통시설 78 = 지하철 5·버스 73, 전국 747·서울 37·강남구 2위).
- 핫플레이스(`region-info/hot-places?regionGid=&type=&limit=30&page=`)는 웹 동네정보 '핫플레이스' 이고 미쉐린·블루리본 가이드에 오른 식당이다 (hot-place 청크, 2026-11-13). `type` 은 웹 고르기 값 `ALL`·`MICHELIN_GUIDE`·`BLUE_RIBBON` 이고 줄의 `type` 도 같은 값이라 '미쉐린'·'블루리본' 이름표로 바꾼다 (`HOT_PLACE_GUIDE_LABELS`). 한 쪽은 웹 값 30이고 31 이상은 400 이다 (2026-11-14 실측: 31·40). 동 안 학교 목록·동네정보 순위와 같은 한도라 `REGION_INFO_PAGE_LIMIT` 하나를 같이 쓴다. `updateDate` 를 기준 달(`base_month`)로 낸다. 사진(`thumbnail`)은 내지 않고, `cuisineType` 은 웹이 아이콘에만 써서 내지 않는다.
- 반려동물 장소(`pet-places?complexId=`, 웹 '펫세권' 2km)는 웹이 단지 화면에서만 부른다 (dong-info 청크, 2026-11-13). 매물·분양 ID(`roomId`·`saleId`)로는 빈 목록이라(2026-11-14 실측) 단지만 받고, 다른 대상은 빈 목록을 '없다' 로 잘못 읽지 않게 요청 전에 `INVALID_ARGUMENT` 로 막는다 (`EXTRA_TARGETS`). 종류(동물병원·미용실·카페·호텔)마다 가까운 순 10곳까지 오고, 전화(`phone`)도 오지만 모델에 두지 않는다.
- 카셰어링 존(`public-data/{room·complex}/car-share-zone`, 웹 'Car세권' 2km)은 쿼리 키가 대상에 따라 `roomId`·`complexId` 로 바뀐다 (dong-info 청크, 2026-11-13 캡처). 분양은 403 이라(2026-11-14 실측) 매물·단지만 받는다. 업체 `zoneType` 'SOCAR'·'GREENCAR' 는 웹 이름표 '쏘카존'·'그린존' 으로 바꾼다 (`CAR_SHARE_LABELS`). 20곳까지 와서 전체 수를 알 수 없어 수를 내지 않는다. 반려동물·카셰어링 모두 다방 거리 값으로 가까운 순 3곳(`NEAR_PLACES_PER_TYPE`)을 낸다.
- 역 둘레 평균 매물가는 원룸·투룸 지도 집계(`markers`)의 역 표시에만 붙는다 (빌라 집계는 원룸·투룸 평균만, 아파트 집계는 없음). 웹은 '평균 매물가' 라고 부르며 실거래가가 아니다. 역을 덮는 작은 지도 범위(±0.3km, 확대 16)로 부르고 역 번호가 같은 표시를 고른다.

### 분양·순위 (`search sales`·`sale`·`sale-schedule`·`trending-complexes`·`trade-rankings`·`region-ranking`)

- 분양 목록은 둘이다. 전국·시·도·시·군·구는 **지역 목록**(`3/sale-in-lots/list/search3`, 웹 '분양정보' 목록 `/sale-in-lots/list`)이다. 시·도 코드(`state_code`, 2자리)와 시·군·구 코드(`city_code`, 5자리)로 찾고 둘 다 없으면 전국이다 (2026-11-13 웹 캡처: 강남구 `state_code=11&city_code=11680`, 전국 `total` 1143). 두 코드는 범위를 찾은 `region/states`·`region/cities` 의 `code` 다 (`DabangScope.state_code`·`code`). 웹 지역 고르기도 같은 목록의 값을 보낸다. 쪽 크기는 웹 값 24(list 청크 `limit:24`)이고 `keyword=ALL` 이다. 필터는 이름이 아니라 번호 목록 JSON(`{"building_type":[],"state":[],"new_schedule_state":[],"supply_type":[]}`)이고 빈 목록이 전체다 (웹 초기값). 번호는 supply-type 청크의 `numValue` 다 (`SALE_BUILDING_TYPE_NUMBERS`·`SALE_STATE_NUMBERS`·`SALE_SUPPLY_TYPE_NUMBERS`, 2026-11-13). 일정 단계(`new_schedule_state`)는 고르지 않아 늘 빈 목록이다. 줄은 snake_case 이고 웹 표의 세대수 칸이 `lots_household_num`(분양 세대수, `presale_household_count`), 총세대수가 `total_household_num`(`household_count`), 가격 이름표가 `price_supply_type_str`('분양가'·'임대가'), 가격이 `price_str`(만원 글자), 일정 줄이 `title` 이다. `features` 는 분양 홈 위쪽의 추천 단지 칸(home 청크 `features`)과 같은 꼴이고 웹 지역 목록은 그리지 않아(list 청크는 `saleInLotses`·`total` 만 쓴다) 넣지 않고 `[제외]` 로 수만 알린다 (2026-11-13: 전국 1쪽 1곳, 김포시 0곳). 수만 세므로 응답 모델은 `features` 의 줄을 꼴 없는 dict 로 받고 칸을 검사하지 않는다. 쓰지 않는 칸이 `null` 로 와도 `PARSE_ERROR` 로 끝나지 않게 하려는 것이다. 좌표(`location`)·사진(`represent_image`)은 모델에 없다.
- 동·역·대학·좌표는 **지도 목록**(`sale-list/category/bbox`)이다. 지도 범위만 받고 칸에 좌표·동 번호가 없다. 동 이름은 동 경계를 덮는 사각형으로 받아 주소(`address`)가 그 동으로 시작하는 단지만 남긴다. `recommendList` 는 범위와 상관없는 추천 칸이라 넣지 않는다. 목록 칸의 `householdNumTitle`('87세대')은 총세대수가 아니라 분양 세대수(상세 `lots_household_num`)라 `presale_household_count` 로 낸다 (2026-11-13: 김포시 37곳 중 2곳에서 상세 총세대수와 달랐다). 총세대수는 오지 않아 `household_count` 가 `null` 이다.
- 분양 상세는 옛 방식(`/api/3/`)이고 `provider_name` 이 시공사, `constructor_name` 이 시행사다. 가격 이름표는 웹처럼 공급 유형 코드(`supply_type`)가 4·5(공공임대·민간임대)면 '임대가', 아니면 '분양가' 이고 (ic_24_download 청크 `x`, 2026-11-13. 민간임대 6acca80f… 화면 '임대가 4억7770') `price_kind` 로 알린다. 임대가는 임대 보증금이라 금액을 `price_manwon` 이 아니라 `deposit_manwon` 에 담는다 (군포대야미 A-1블록 6년 분양전환공공임대 55A 다방 임대가 8561 = 모집공고 임대보증금 85,614,000원, 월임대료는 다방이 주지 않는다, 2026-11-25). 지도 목록·지역 목록 모두 임대 공급의 이름표는 '임대가' 라(`'군포시 둔대동'`·`군포시`, 2026-11-25) 목록은 가격 이름표로, 상세는 공급 유형 번호(4·5)로 금액 칸을 고른다. 다방이 공급 유형을 잘못 매긴 단지(부산 'e편한세상 에코델타 센터포인트(19BL)' 는 공고문상 공공분양인데 다방은 '민간임대' 로 보여 준다)도 다방 표시를 따라 `deposit_manwon` 으로 낸다. 지역 평균 평당가(`price_info.region_average_pyeong_price`, 최근 6개월)는 만원 글자다. 청약 결과(`subscriptionResult`)는 바깥 키만 camelCase 이고 안쪽 키는 snake_case 이며(2026-11-13 실측), 청약 전이면 `null` 이다. 경쟁률('5.52:1')·당첨가점('43점')·분양/총세대('261/1071')는 글자라 앞 숫자를 읽는다. 상담 전화(`contact`)는 옮기지 않는다. 일정 날짜는 '26.09.07'(날)·'26.08월'(달) 꼴이라 `sale_date` 가 `YYYY-MM-DD`·`YYYY-MM` 으로 바꾼다. 청약 일정(`list/schedule`)은 7일을 넘기면 400 이라 요청 모델이 막는다. 일정 칸에는 글과 좌표뿐이다.
- 청약 일정 하루 상세(`3/sale-in-lots/list/schedule/search?from=`, `sale-schedule --details`·`--region`)는 웹 청약 일정에서 날짜를 누르면 부르는 표다. 날짜는 웹처럼 날만 0 을 채우지 않고 보낸다 (schedule 청크 `yyyy-MM-d`, '2026-11-5'). 줄은 지역 목록과 같은 공통 칸(부모 `DabangSaleInLotsRowModel`)에 그 날 일정의 종류 번호(`grouping`)가 붙고, 요약 묶음의 `type`(1 접수·4 발표·5 계약 등)과 같은 값이다. 지역 목록 줄(`DabangSaleInLotsItemModel`)은 결과로 나가는 줄이라 분양 ID·단지 이름이 꼭 있어야 하지만, 표 줄(`DabangSaleScheduleTableRowModel`)은 맞춰 보는 데만 써서 분양 ID·종류 번호가 `null` 이어도 받는다 (한 줄 때문에 표 전체가 `PARSE_ERROR` 로 끝나지 않게). 요약 줄은 분양 ID 와 종류 번호가 모두 같은 상세 줄과 맞춘다 (2026-11-13 캡처: 11-16 24건이 요약과 같은 순서로 둘 다 같았다). 같은 날 두 종류(접수·계약)인 단지가 있어 분양 ID 만으로 맞추지 않고, 종류 번호가 없는 줄은 맞추지 않는다. 맞춰 본 줄(분양 ID·종류가 둘 다 있는 줄)을 한 줄도 맞추지 못하면 다방이 두 목록의 꼴을 바꾼 것으로 보고 `[참고]` 에 업데이트 안내를 붙인다 (매일 감시가 이것으로 고장을 본다). 다방이 분양 ID·종류를 주지 않아 맞춰 보지 못한 줄은 이 셈에 넣지 않고 `[참고]` 로 따로 알리며 업데이트 안내를 붙이지 않는다. `--details` 는 내보낼 줄(`--limit`)이 든 날만 받는다. `--region` 은 일정이 있는 날마다 상세를 받아 주소의 시·도로 거르고, 상세에서 찾지 못한 줄만 글 앞의 시·도 줄임말('충북')을 정식 이름으로 바꿔 본다. 둘 다 없으면 지역을 모르는 것으로 두고 빼서 수를 알린다 (글이 '남춘천 센트레빌' 처럼 시·도 없이 시작해도 주소로 가린다). 남긴 줄이 `limit`+1 줄(더 있는지 알 만큼)을 채우면 일정이 있는 다음 날에서 멈추고 그 뒤 날은 받지 않는다. 뒷날 줄을 상세 없이 일정 글의 시·도만으로 거르면 앞날과 기준이 달라져(글에 시·도가 없는 일정이 빠진다) 아예 보지 않는다. 그래서 멈추면 `[참고]` 의 본 수, `[제외]` 의 지역 모름 수는 멈춘 날 전날까지 센 것이고 `[일부]` 의 전체 수는 '적어도' 로 알린다. 상세를 받은 줄(`fetched`)에서 짝을 못 찾으면 `sale` 이 `null`(모름), 상세를 받지 않은 줄은 `sale` 키를 뺀다 (`drop_unfetched_sale`).
- `search sales` 는 `find_scope`(`service/region/functions.py`)로 범위인지 먼저 본다. 이름 모양(전국·시·도·구·군·시로 끝남, `find_scope` 의 조건)이면 `resolve_scope` 로 범위를 찾고, 범위로 찾지 못하면 동·역으로 다시 찾는다. 이름 모양만으로는 시·군·구인지 알 수 없기 때문이다. 다만 마지막 낱말이 '입구' 로 끝나는 이름('홍대입구'·'을지로입구'·'서울대입구' 같은 역)은 '구' 로 끝나도 범위로 보지 않는다 (`is_district_word`). '입구' 로 끝나는 시·군·구는 없고, 범위로 보면 '서울 홍대입구' 가 시·도 목록·시·군·구 목록 요청 2회를 버린 뒤에야 장소 검색으로 넘어간다. `resolve_scope`·`resolve_places` 도 같은 함수로 시·군·구 모양을 봐서, `region-ranking '서울 홍대입구'` 는 목록 요청 없이 `REGION_NOT_FOUND`(동 단위)나 장소 검색 1회 뒤 동이 아니라는 `INVALID_ARGUMENT`(`--unit 단지`)로 끝난다. 전국·시·도와 시·도를 붙인 이름('서울 중구')은 장소 검색 없이 찾는다 (전국은 요청 없이, 시·도는 시·도 목록 1회). 시·도 없는 이름만 장소 검색을 받고, 다시 찾을 때는 그 결과를 넘겨(`searched`) 같은 요청을 두 번 보내지 않는다.
- 범위 이름은 `resolve_scope` 가 웹 랭킹·분양 지역 고르기처럼 시·도 목록(`region/states`)과 시·군·구 목록(`region/cities?stateCode=`)에서 이름으로 찾는다 (useSiGuDong 청크, 2026-11-13). 시·도는 시·도 목록 1회다. 시·도를 붙인 시·군·구('서울 중구', '경기 성남시 분당구')는 시·도 목록과 그 시·도의 시·군·구 목록으로 찾는다 (요청 2회). 장소 검색으로 먼저 찾지 않는 까닭은 장소 검색이 같은 이름의 동을 50곳까지만 줘 붙인 시·도가 빠질 수 있어서다 (2026-11-14 실측: '인천 중구' 장소 검색의 동 50곳 중 인천 중구는 0곳, 대전 중구 12곳). 시·도의 시·군·구 목록은 그 시·도를 모두 준다. 시·도 없는 이름('강남구')은 장소 검색이 주는 그 시·군·구의 동으로 시·도를 고르고(동 코드 앞 2자리), 그 시·도의 시·군·구 목록에서 이름을 맞춘다 (요청 2회). 시·군·구 목록은 시·도마다 따로이고 `stateCode` 가 꼭 있어야 해서(없으면 400) 목록만으로 찾으려면 시·도 17곳을 모두 받아야 한다. 장소 검색은 '중구' 에 서울·부산·대구·대전·울산 중구의 동을 섞어 주므로 시·군·구가 둘 이상이면 `REGION_AMBIGUOUS` 로 시·도를 붙이게 한다. 장소 검색이 동을 50곳까지만 줘 후보에 빠진 시·도가 있을 수 있는 한계는 시·도 없는 이름에만 남는다. 시·군·구 목록은 구가 있는 시를 구마다 '성남시 분당구' 로 두고 시 하나('성남시')는 두지 않아 (2026-11-13 캡처: 경기도 47곳) 시 이름이면 `REGION_NOT_SUPPORTED` 로 구 이름을 붙이게 한다. 웹 지역 고르기에도 시 전체가 없다. 공통 시·도 표(`SIDO_OFFICIAL_NAMES`)에 옛 광주광역시로 있는 '광주시' 는 다른 소스(당근 지역 이름·네이버 `regions`)처럼 경기도 광주시로 본다 (`state_name`, 범위·분양·청약 일정 지역). 동·범위 이름의 앞 낱말('광주시 송정동')도 경기도 광주시로 먼저 맞추고, 맞는 곳이 없을 때만(경기도 광주시에 없는 구를 붙인 '광주시 광산구') 시·도 표대로 넓힌다 (`_in_context`, 네이버 `regions` 와 같은 규칙). 늘 넓히면 '광주시 송정동' 이 경기도 광주시와 광산구 두 곳에 맞았고 (2026-10-28 실측), 넓히지 않으면 '광주시 광산구 송정동' 을 못 찾았다 (2026-10-30 실측). `search sales` 는 `--radius` 를 줘도 전국·시·도·시·군·구 이름인지 먼저 보고 그러면 `INVALID_ARGUMENT` 로 막는다 (`_scope_radius_error`). 전국·시·도 이름은 `is_national_or_state` 로 시·도 목록 요청 전에 막고, 시·군·구 모양 이름은 범위로 못 찾으면 동·역으로 다시 찾으므로 `find_scope` 로 범위를 찾은 뒤에 막는다.
- 순위 항목마다 받는 값과 값 글자 키가 다르다 (`MetricSpec`): 평균가·평당가·시세증감은 `priceType` 하나, 거래량·매물수는 `priceTypeList`, 전세가율·갭가격은 단지 순위에만 있고 유형만, 세대수·연식은 아무것도 받지 않는다. 단지 유형(`MetricSpec.types`)은 웹 랭킹 스토어를 따른다 (real-estate 청크 `E()`·`T()`·`b()`, 2026-11-13). 거래량·매물수·선호도·전세가율·갭가격('many')은 웹 기본 `buildingTypeList` 가 {OFFICETEL, APT} 이고 둘이면 `complexType` 을 빼고 보내 아파트·오피스텔 합산 순위를 받는다 (`size===2 ? null : 하나`. 강남구 동 거래량 1위가 합산 역삼동 298개, 아파트만 개포동 233개). 평균가·평당가·시세증감·최고가증감('one')은 하나만 고르고 기본 아파트, 세대수·연식('none')은 받지 않는다. 어느 유형의 순위인지 결과 `complex_type` 으로 알린다. 값은 '61.1억'·'27개'·'133.3%'·'44년 6개월'·'+0.8%' 글자라 항목에 맞는 숫자 필드로 바꾼다. 거래·매물이 없는 줄은 '-' 로 와서(세종 동 평균가 33곳 중 8곳) 그 결과의 다른 줄에 있는 칸을 `null` 로 둔다. 둘째 쪽부터는 50곳씩 받아 `--limit` 에 맞춰 자르므로 자른 줄이 있으면 서버 `hasMore` 와 상관없이 `has_more` 다 (`more_after`, [매물 목록](#매물-목록-search-listings)). 시세증감의 `formattedPrice` 는 현재가가 아니라 변화 금액이다 (대우로얄카운티II 19.6억 = 27.7억 → 47.3억, +70.8%).
- 거래증감·매물증감(`trade-volume-change`·`room-count-change`)은 웹 랭킹의 같은 이름 탭이다. 단지 유형·거래 유형의 꼴과 기본은 거래량과 같다 ('many', 웹 기본 아파트·오피스텔 합산·매매·전세·월세 모두, real-estate 청크 TradeVolumeChange·RoomCountChange 스토어, 2026-11-13). 줄의 값 키는 인구 증감과 다르다: `formattedCount` 가 부호 없는 변화 수, `formattedPrevCount`·`formattedCurrCount` 가 앞·지금 수, `formattedChangeRate` 가 변화율, `changeStatus` 가 늘었는지 줄었는지다 (2026-11-13 강남구 동 거래증감 1위 논현동: '73개' = 72개 → 145개, '+101.4%', `INCREASE`). 인구 증감처럼 앞·지금 수가 둘 다 오면 그 차로 내고, 하나라도 없을 때만 `changeStatus`·변화율 부호로 음수를 만든다 (`ValueKind` 'count-change'). 무엇과 견줬는지는 웹 설명 글 그대로 거래증감 '전월대비', 매물증감 '최근 30일 전 대비' 를 결과 `comparison` 으로 낸다 (`MetricSpec.comparison`). 앞 수가 0 이면 다방이 변화율을 '0%' 로 준다.
- 웹 단지 순위의 범위는 고른 동이 있으면 동 `gid`, 없으면 시·군·구, 시·도 순이다 (real-estate 청크 `dong.gid → city.gid → state.gid`, 2026-11-13). 동네정보·동 순위 청크는 `city.gid → state.gid` 만 써서 동 범위가 없다. 그래서 `resolve_scope(dong=True)` 는 단지 순위에서만 동 이름을 받고(`takes_dong_scope`, `_dong_scope` 가 위치 찾기 `resolve_places(only='dong')` 1회로 동 `gid`), 동 순위·동네정보 항목은 동을 찾지 않는다. 이때 동 모양 이름(`역삼동`·`봉담읍`·`종로1가`)은 `check_scope_name` 이 요청 없이 `INVALID_ARGUMENT`(`--unit 단지`·시·군·구 안내)로, 그 밖(역·오타)은 `resolve_scope` 가 요청 없이 `REGION_NOT_FOUND` 로 막는다. 역삼동(`gid` 10063) 단지 평균가 1위는 개나리푸르지오 39.5억, 2위 역삼자이 38.8억이었다 (같은 날 실측). 동 범위는 시·군·구처럼 더 좁힐 범위가 없어 `[일부]` 는 `--order` 를 권하고, 순위 줄의 `area` 가 시·도뿐이라는 `[참고]` 도 붙이지 않는다. `search sales` 는 `dong` 을 넘기지 않는다 (동은 지도 목록으로 찾는다).
- 거래 순위는 `limit` 을 작게(2) 보내면 500 을 준다. 웹처럼 50으로 받고 자른다. 조회 순위는 `limit` 과 상관없이 늘 50곳이고, `watchCount` 는 조회 횟수가 아니라 웹이 'N명' 으로 보여 주는 조회한 사람 수다. 둘 다 전국 단위다. 거래 순위는 막 시작한 기간(월요일 아침의 이번주)에 빈 목록이라, 비면 `PREVIOUS_TRADE_PERIOD` 의 지난 기간을 `[참고]` 로 권한다. 매일 감시는 이 때문에 `--period 지난주` 로 본다.
- 최고가증감은 시세증감처럼 `formattedPrice` 가 오른 금액이고, 앞 최고가는 `formattedPrevPrice` 가 아니라 `formattedMaxPrice`·`formattedMaxPriceDate` 로 온다 (강남구 단지 1위 아이파크삼성 15.2억 = 62.8억 × 24.2%). 단지 순위의 `formattedPriceDate` 는 새 최고가 달, 동 순위는 줄 대신 결과에 기준 달('26년 10월')이 와서 `base_month` 로 낸다.
- 동네정보 순위(`region-info/{주제}/ranking/{항목}`, `InfoMetricSpec`)는 동 단위만 있고 한 쪽이 **30곳까지** 다 (31 이면 400 '페이지 당 호출 가능한 최대 행수는 30를 초과할 수 없습니다'). 학원 순위는 `academyType` 이 없거나 'ALL' 이면 빈 목록이라 늘 보낸다 (기본 입시). 진학률은 `schoolType`(중학교 → 고교 유형, 고등학교 → 대학)과 `schoolAdvancementType` 을 늘 보낸다. 학교 수·시설 수의 종류(`schoolEstablishmentType`·`facilityType`)와 인구의 성별·연령은 주지 않으면 전체다. 인구 증감의 변화 수는 부호 없이('327명') 와서, 앞·지금 수가 둘 다 오면 그 차(`count - prev_count`)로 내고 하나라도 없을 때만 `changeStatus`·변화율 부호로 음수를 만든다 (`_fill_count_change`). 학원·진학률 순위는 `parentRegionName` 이 시·도('서울')뿐이라 범위가 시·군·구가 아니면 `[참고]` 로 알린다.
- 동네정보 '매물정보' 탭 순위(`region-info/room/ranking/{room-count·trade-volume·reaction-score}`, `-t 빌라`)는 부동산 순위(`real-estate/ranking`, 아파트·오피스텔 단지 기준)와 다른 화면이고, 주택/빌라를 고를 수 있는 순위는 이것뿐이다. 웹 room-info 청크 기본을 따른다 (2026-11-13): 매물 유형 `buildingCategoryList`(HOUSE_VILLA·OFFICETEL·APT, 여럿, 같은 키를 값마다 되풀이)·거래 유형 `priceTypeList` 기본 전체, `limit` 30, 범위 `scopeRegionGid` 는 고른 시·군·구 → 시·도 `gid`(없으면 전국)이고 동 순위만 있다. jibsa 는 `-t` 로 고른 유형만 보내고 결과 `property_type` 으로 알린다 (웹 기본은 셋 다라 `-t 빌라` 는 웹에서 주택/빌라만 고른 것과 같다). 거래량 값 글자는 `formattedVolume` 으로 온다. 웹 거래량 화면이 보내는 `baseMonth`(이번 달)는 부동산 순위처럼 보내지 않는다 (2026-11-14 실측: 강남구 빌라 거래량이 보낸 것과 같았다). 매물수·거래량·선호도는 '시세정보'·'매물정보' 두 탭에 있고 값이 달라 모든 순위 결과에 웹 탭 이름을 `tab` 으로 낸다 (`REAL_ESTATE_TAB`·`ROOM_TAB`·`TAB_BY_TOPIC`. 2026-11-14 실측: 강남구 매물수 1위가 '매물정보' 빌라는 역삼동 262개). 정렬 `sort` 는 웹 상세 화면의 높은순·낮은순 메뉴 값 `DESC`·`ASC` 다 (room-info 청크 `[{name:'높은순',value:'DESC'},{name:'낮은순',value:'ASC'}]`, 2026-11-14 번들). 서버가 `sort` 를 따른다 (같은 날 실측: 강남구 빌라 매물수 높은순 1위 역삼동 262, 낮은순 1위 세곡동 0). 그래서 `--order 낮은순` 은 웹에 있는 정렬이라 [웹과 다른 점](#웹과-다른-점)이 아니다 (2026-11-14 리뷰 오탐).

## 페이지네이션과 조건 처리

모든 매물 조건은 다방 서버가 건다 (서버 필터를 적용한 조회). 받은 뒤 빼는 것은 반경 밖(반경 검색), 다른 동(아파트·단지 동 검색), 가격을 읽지 못한 매물, 한 호출 안에서 다방 목록에 두 번 나온 매물·단지(다음 쪽에 다시 온 것)뿐이고, 뺀 만큼 다시 채우지 않는다. 다방 매물은 거래 조건이 하나라 거래 조건 선택이 없다.

검색 조건 묶음은 `DabangListingConditions`(`common`) 하나다. 유형마다 받는 조건이 달라 CLI 가 유형별 하위 명령에 그 유형의 옵션만 열고(`TRADE_TYPES_BY_KIND`·`ROOM_LABELS_BY_KIND`·`CONDITIONS_BY_KIND`), `filters_of` 가 그 유형 필터 모델로 바꾼다. 방 크기 필터(`pyeongRange`)는 평(정수)만 받아 ㎡ 옵션을 두지 않았다. 기준 면적은 웹 필터 이름표대로 원룸·투룸 '매물유형별 기준면적', 주택·빌라 전용, 오피스텔 계약, 아파트 공급이다 (room-size-type-chunk, 2026-11-13. 오피스텔 강남역 `--area-pyeong-min 17` 결과 23건이 모두 전용 17평 미만). 목록의 `area_m2` 는 전용이라 기준이 다른 유형은 도움말(`AREA_BASIS_BY_KIND`)에 적는다. 세대당 주차 대수(`parkingNumRange`)·세안고(`hasTakeTenant`)의 뜻은 [매물 목록](#매물-목록-search-listings)에 있다. 360° 사진(`hasPano`)만 사진 기능이라 늘 '전체' 로 보낸다.

다방이 목록 칸을 `null` 로 주어도 `PARSE_ERROR` 로 끝내지 않는다. 기본값이 `[]` 인 칸은 기반 응답 모델 `DabangBaseResponseModel` 이 `null` 을 키가 없는 것으로 지워 빈 목록으로 읽고 ([모듈 구성](../provider-conventions.md#모듈-구성)), 빈 목록과 뜻이 다른 칸은 `list | None` 으로 받아 아래처럼 뜻에 따라 읽는다. 쪽으로 받는 줄(동 안 학교 `list`, 핫플레이스 `list`, 분양 지역 목록 `saleInLotses`)은 빈 쪽으로 읽어 거기서 멈춘다. 쪽의 `result` 자체가 `null` 이면 `fetch_pages` 가 거기서 멈춘다: 처음 부른 첫 쪽이면 `total` 이 `null` 인 빈 목록이고 (다방은 정말 없는 목록을 `total` 0 으로 주어 `total` `null` 이 모름을 가른다. 매물·단지 목록과 같은 규약이다, 2026-11-15 리뷰 오탐), 앞 쪽이 `hasMore` 였거나 `--next` 로 이어 받은 첫 쪽이면(이어 받는 위치는 앞 결과가 `hasMore` 일 때만 생긴다) `cut_short` 로 `fetch_stop_notes` 의 `[일부]`(다방이 다음 쪽 결과를 주지 않아 멈췄다)를 낸다. 이어 받은 첫 쪽이면 같은 위치의 `next` 를 그대로 남겨 앞 결과의 안내와 맞춘다 (2026-11-14 리뷰). 받은 수가 `--limit` 보다 적으면 다 받은 것으로 보는 `limit_notes` 만으로는 이 경우를 알리지 못해서다 (매물·단지·단지 매물·분양 목록, 동 안 학교·핫플레이스). 쪽이 짧게 와도 따라가는 쪽 수의 상한은 `fetch_pages` 가 목록마다 `2 * ceil(max_limit / page_size)` 로 정한다: 그 목록의 최대 `--limit` 을 꽉 찬 쪽으로 채우는 쪽 수의 두 배다 (24건씩 120건은 10쪽, 동네정보 30줄 120곳은 8쪽). 호출부가 `fetch_pages` 에 그 목록의 `page_size`·`max_limit` 을 넘겨야 상한과 안내의 '{N}쪽까지' 가 맞는다 (기본은 24건·120건. 동 안 학교·핫플레이스는 `REGION_INFO_PAGE_LIMIT`·`REGION_INFO_MAX_LIMIT`, 지역 분양 목록은 `SALE_SEARCH_PAGE_SIZE`). 줄에 붙는 꼬리표·분류(핫플레이스 `labelList`, 반려동물 `categoryList`)는 `[]`, 분양 추천 칸(`features`)은 0곳으로 센다. 결과 하나를 이루는 목록(반려동물 `petPlaceList`, 카셰어링 `zoneList`, 평형대 비교 `nearComplexes.trade`·`lease`·`areaAveragePrice`, 단지 상세의 `spaces`·`areaAveragePrice`)은 모름(`null`)으로 둔다. 단지 상세는 `pyeongs`·`area_prices` 가 `null` 이 되고, 평형이 필요한 쪽(`_recent` 의 평형 맞추기, 단지 매물의 `--pyeong` 검사, 실거래 평형 이름)은 평형을 모르는 채로 가고 없는 평형이라고 단정하지 않는다. 반려동물 종류의 `placeList` 가 `null` 이면 찾지 못한 종류처럼 뺀다.

### 목록 안 빈 항목 (`null_items`)

- 다방이 객체 목록 안에 null 원소를 주면 기반 모델 `DabangBaseResponseModel` 이 빼고 칸마다 센다 (`result.null_items('list_')`). 봉투 없이 목록 하나가 루트로 오는 분양 일정 응답 둘(`DabangSaleInLotsListScheduleV3ResponseModel`·`DabangSaleInLotsListScheduleSearchV3ResponseModel`)은 core 가 닿지 않아 `DabangRootListModel`(`api/response/sale.py`, `RootModel[list[T]]`)이 같은 규칙으로 빼고 `null_items()` 로 센다. 공통 규칙(계산한 값은 null, 자리 세기는 뺀 수를 더함, `[제외]` 안내)은 [모듈 구성](../provider-conventions.md#모듈-구성)에 있고, 다방의 자리별 처리는 아래와 같다. 안내는 `null_items_note` 라 끝말이 `UPDATE_MAYBE_NEEDED` 다.
  - **쪽으로 받는 목록(`fetch_pages`)**: 호출부가 한 쪽의 뺀 수를 `DabangPage.dropped` 로 넘기면(`DabangPage(rows, total, has_more, result.null_items('list_'))` 꼴. 매물·단지 목록·단지 매물·학교·핫플레이스·분양 목록. 실거래는 같은 꼴의 `_Page`) `DabangPages.dropped`(안내용)와 `dropped_used`(다 쓴 쪽의 몫)로 모은다. 뺀 줄은 `--limit` 의 줄로 세지 않지만 서버의 칸이라, 빈 항목만 온 쪽은 빈 쪽으로 보지 않고 `has_more` 와 이어 받을 위치(`received`)는 뺀 칸을 더해 센다. 쪽 중간에서 멈춘 쪽의 몫은 이어 받을 때 같은 쪽을 다시 받아 그때 세므로 `dropped_used` 에서 뺀다. 안내는 `fetch_pages` 를 부른 명령이 붙인다 (매물 `search_listings`, 동네정보 `region_info_list_notes`, 분양 `_sale_list_notes`, 실거래·시세 흐름 매매 월별, 인기 매물).
  - **광고 묶음(`room_list_page`)**: 묶음 안의 빈 항목은 광고 자리로 센다. 묶음 자체가 null 로 빠진 몫은 안의 매물 수를 알 수 없어 세지 못하고, 광고 건수가 적게 나갈 수 있다 (자리별 안내는 없고 뺀 수는 공통 안내가 알린다).
  - **지역 랭킹(`get_region_ranking`)**: 둘째 쪽을 부르는 판정(`len(entries) + dropped < limit`)과 빈 쪽 판정에 뺀 칸을 더하고 안내한다.
  - **동네정보 유형별 합계(`_type_counts`)**: 유형 목록(`distribution_detail_list`·`distribution_list`)에서 뺐으면 받은 유형만 더한 적은 합계가 완전한 값처럼 나가지 않게 `count` 가 null 이다 (`neighborhood` 의 매물·거래).
  - **인기 매물 순위(`get_popular_listings`)**: 빈 항목을 뺀 쪽의 `rank` 만 null 이다. 순위는 쪽 번호로 `(page-1)*page_size+index+1` 을 세고 서버도 칸 단위로 같은 offset 을 주므로 뒤 쪽 순위는 맞아서, 모르는 쪽만 null 로 둔다.
  - **분양 일정(`get_sale_schedule`)**: 날 목록(루트)·종류 묶음·일정 어느 층에서든 뺐으면 `total`(`int | None`)이 null 이고 안내 문장의 건수는 '적어도' 로 쓴다. `--details` 로 받는 그 날의 분양 단지 표(`DabangSaleInLotsListScheduleSearchV3ResponseModel`)에서 뺀 수는 `[제외]` 로 알리기만 한다.
  - **매물 상세 관리비**: 정액관리비 항목 목록(`maintenance_fixed_fee_charge_detail_list`)에서 뺐으면 `manage_cost_includes`·`manage_cost_excludes` 가 null 이다 (`_manage_cost`).
  - **대표 평형(`first_space_notes`)**: 다방이 대표 평형을 주지 않아 평형 목록의 첫 평형으로 대신하는데(`primary_space_of`) 그 목록에서 뺐으면 뺀 항목이 웹의 첫 평형이었을 수 있어 안내만 한다. 단지 상세(`complex/functions.py`)와 실거래·시세 흐름의 평형 고르기(`primary_space`)가 부른다.
  - **실거래**: 거래 목록(`histories`)·시세 흐름 매매 월별(`statistics`)에서 뺐으면 안내만 한다.
- 손대지 않은 자리: `search locations` 의 후보 수 판정(`cli/dabang.py` 의 `counts`)은 서버 칸 수가 아니라 jibsa 가 `[:limit]` 로 자른 줄이 있는지 보는 것이라 뺀 뒤의 줄 수로 센다 (칸 수로 세면 빈 항목 하나 때문에 자르지도 않았는데 '11곳 중 10곳' `[일부]` 안내가 나간다).

## API 변경 시 점검

웹을 다시 배포하면 스크립트 이름이 바뀌고 주소·헤더가 바뀔 수 있다. 헤더·버전 쿼리는 client(`V5_HEADERS`)와 `DabangV3RequestParameterModel`, 유형별 필터 항목은 `request/common.py`, 목록 글자 꼴은 `service/common/functions.py` 의 해석기를 본다. 필터 항목이 늘면 400 본문의 `errorDetails` 가 빠진 항목을 알려 준다. 버전 값(v5 `D-Api-Version`·`D-App-Version`, v3 `api_version`·`version`)은 서버가 옛 값도 받으면 명령이 정상으로 돌아, 매주 월요일 API 감시가 첫 화면 스크립트(2026-11-13 `atoms-chunk`)의 값과 대조해 다르면 경고로 알린다 (`check_dabang_versions`, [매일 API 감시](../README.md#매일-api-감시)). 감시 내용의 웹 값으로 맞춘다.

## 웹과 다른 점

[웹 화면과의 대응](../provider-conventions.md#웹-화면과의-대응) 원칙 안에서 다방 웹과 다르게 한 곳을 모은다. 2026-11-13 에 다방 명령 전체를 다방 웹(번들 `web.DNlAthXv.js` 판)과 대조했고, 2026-11-14 에 웹에만 있던 조회(`search schools`·`nearby-complexes`·`hot-places` 등)를 더하며 그 화면도 대조했다. 자세한 근거는 각 절에 있고 여기서는 무엇이 다르고 왜 사실이 어긋나지 않는지만 적는다.

### 매물 찾기 (`search locations`·`search listings`·`listing`)

- **아파트 동 검색은 동 경계 사각형에서 그 동만.** 웹 아파트 목록은 bbox·역 검색만 있어 동을 고르면 동 목록 없이 줌 16 지도 화면의 bbox 목록을 보여 준다. jibsa 는 동 경계를 덮는 사각형으로 받아 그 동(`gid`) 매물만 서버 순서 그대로 남기고 뺀 수를 `notes` 로 알린다. 같은 bbox 목록의 부분집합이고 줌은 결과에 영향이 없으며(z16 = z12), `total` 은 사각형 안 수다 ([위치 해석](#위치-해석-region), 2026-11-13 web.js `en`).
- **반경으로 좁히기.** 아파트 대학(1km)·`--lat/--lng`(1km)·`--radius` 는 반경을 덮는 bbox(줌 16)로 받아 반경 밖을 뺀다. 웹은 지도 화면 bbox 를 그대로 보여 준다. 같은 bbox 목록의 부분집합이고 뺀 수를 알린다 (2026-11-13).
- **한 번에 최대 120건.** 웹은 24건씩 번호 쪽이다. 쪽이 24건보다 짧을 수 있어 `--limit` 이 찰 때까지 다음 쪽을 받는다 (상한 10쪽). 같은 쪽을 차례로 받은 것이라 매물·순서는 웹 쪽 넘김과 같다 ([매물 목록](#매물-목록-search-listings), 2026-11-13).
- **광고 칸 빼기.** 웹은 목록 위에 중개사별 `premiumList` 를 보여 준다. jibsa 는 넣지 않고 뺀 수만 `notes` 로 알린다. 광고는 일반 목록과 따로 오고 `total` 에 들지 않아 일반 목록의 매물·순서·수는 그대로다 (2026-11-13 onetwo·house·officetel·apt 청크).
- **한 호출 안의 겹친 매물은 한 번만.** 서버가 쪽끼리 같은 매물을 겹쳐 주고 웹은 그대로 보여 준다 (아파트 강남역 1~5쪽 120줄 중 108곳만 서로 달랐다). jibsa 는 한 호출 안에서 같은 ID 를 한 번만 넣고 `[제외]` 로 알린다. 남은 매물은 모두 웹 목록에 있는 것이고, 호출과 호출 사이(`--next`)의 겹침은 웹처럼 남긴다 ([매물 목록](#매물-목록-search-listings), 2026-11-13).
- **조건 값을 눈금 밖으로.** 웹 UI 는 눈금·선택지만 준다: 보증금·월세·매매가 슬라이더 눈금(slider-options-chunk), 방 크기 0~50평에서 50 은 무제한(room-size-for-api-chunk `[0,50]→{0,999999}`), 사용승인 5·10·15년 이내와 세대수 100 미만·100·500·1000 이상, 세대당 주차 1대·2대 이상(parking-chunk). jibsa 는 아무 정수나 보내고 서버가 받는다 (`--parking-min 3` 도 `{min: 3, max: 999999}` 로 간다). 웹의 방 크기 50 은 999999 로 바뀌지만 jibsa `--area-pyeong-max 50` 은 서버에서 그대로 50평 이하다 (대치동 화면 206 → 165건). 웹 UI 에 없지만 서버가 받는 값이라 서버가 거른 결과 그대로다 (2026-11-13).
- **`--condition 단기임대` 와 가격 조건의 거래 좁히기.** 단기임대를 주면 월세로 좁힌다. 웹은 월세+전세에 '단기월세만 보기' 를 켜면 전세가 섞여 오고, jibsa 결과는 웹에서 월세만 고르고 단기월세만 보기를 켠 것과 같다 (filter-chunk). 가격 조건만 줄 때 그 금액이 있는 거래로 좁히는 것도 웹에서 그 거래만 고른 것과 같다 (2026-11-13).
- **`search locations` 후보 수.** 종류마다 `--limit`(기본 10, 최대 50) 앞부분만 준다. 웹은 API 가 준 후보(종류마다 최대 50)를 모두 보여 준다. 순서는 같고, 자른 종류가 있으면 `[일부]` 로 몇 곳 중 몇 곳인지 알린다 (2026-11-13 web.js `In`).
- **검색어 괄호를 띄어 보내기.** 웹은 그대로 보내 '연세대학교(원주캠퍼스)' 가 0건이다. jibsa 는 '연세대학교 원주캠퍼스' 로 보내고, 이것은 웹 검색창에 그렇게 넣은 것과 같은 요청이다 ([위치 해석](#위치-해석-region), 2026-11-13 debounce-chunk `ae`).
- **표기 다듬기.** 빌라 `property_type` '빌라'(웹 카드는 '쓰리룸' 등), '오피스텔 • 단기' → 오피스텔 + `short_term`, 에어컨 옵션 이름에 '에어컨' 붙이기(listing-request 청크), 목록 주소에 시·구 채우기, `distance_km`, 단지 화면의 어린이집·유치원 설립 유형을 학군 화면 이름으로 맞추기(다방이 같은 시설을 단지 화면에서는 '국공립'·'공립', 학군 화면·상세에서는 '공공'·'국공립' 이라 부른다. `complex` 의 `nurseries`·`kindergartens` 를 `search schools`·`school` 과 같은 이름으로 낸다, 2026-11-14 실측). 매물·가격·순서·수를 바꾸지 않는 표기다 ([매물 목록](#매물-목록-search-listings)·[상세](#상세단지학교실거래), 2026-11-13).
- **관리비 포함 항목의 순서·이름 (바꾸지 않기로 함).** 기타부과 매물은 웹이 공용→전기→수도→인터넷→난방→가스→TV→기타 순으로 세우고 jibsa 는 응답 순서다. 이름도 웹 정액 표는 '공용'·'기타', jibsa 는 '공용 관리비'·'기타 관리비' 다. 항목 집합과 관리비 금액은 웹과 같아 사실이 어긋나지 않아, 대조에서 지적됐지만 이번에는 고치지 않았다 (2026-11-13 safety-option-chunk `E`).
- **이름 해석 요청.** 웹은 동을 고르면 `/api/v5/region/{gid}` 로 code 를 다시 받고 jibsa 는 `loc/search` 의 code 를 쓴다 (같은 값). 웹은 동·역·대학 목록에도 지도 bbox·zoom 을 붙이지만 결과에 영향이 없다 (대학 zoom 14 와 15 도 같다, 2026-11-13 web.js `en`).

### 단지·실거래·학교 (`search complexes`·`complex`·`search listings --complex`·`real-price`·`price-trend`·`nearby-complexes`·`school`·`search schools`)

- **`search complexes` 아파트 동 이름.** 웹 아파트 단지 목록은 bbox·역 검색만 쓰고, 동을 찾으면 지도를 그 동 중심(줌 14)으로 옮긴 화면 범위를 보여 준다 (대치동이면 잠실까지 849곳). jibsa 는 동 경계를 덮는 사각형으로 받고 `gid` 가 그 동인 단지만 남긴 뒤 `notes` 로 알린다. 같은 bbox 목록의 부분집합이다 ([위치 해석](#위치-해석-region), 2026-11-13).
- **`search complexes` 아파트 대학·좌표와 `--radius`.** 반경을 덮는 사각형을 그대로 bbox 로 보낸다 (반경 밖을 빼지 않는다). 웹에서 지도 범위를 그만큼 잡은 결과와 같다 (2026-11-13).
- **다음 쪽에 다시 나온 단지는 한 번만.** 다방 단지 목록은 쪽마다 순서가 흔들려 앞 쪽 끝 단지를 다음 쪽에 다시 준다. 한 호출 안에서 한 번만 넣고 알린다. 남은 단지는 모두 웹 목록에 있는 것이다 ([매물 목록](#매물-목록-search-listings), 2026-11-13).
- **단지 목록을 여러 쪽 한 번에.** 웹은 24곳씩, jibsa 는 최대 120곳이다. 같은 쪽을 차례로 받은 것이다 (2026-11-13).
- **`complex` 의 `area_prices` 는 웹의 '전체 평형 비교' 탭.** 웹 평당가 칸의 기본 탭은 'N평대 비교'(`real-price/complex/price-per-py`)이고 '전체 평형 비교' 탭이 `complex/{id}` 의 `areaAveragePrice` 다. `complex` 는 이 탭 값만 내고, 기본 탭은 `nearby-complexes` 가 낸다. 둘 다 웹 한 탭의 값 그대로다 (2026-11-13 complex-chunk, 2026-11-14).
- **`complex` 의 `overheated_district` 를 늘 낸다.** 웹은 이 값(`complex/{id}/loan-calc-condition` 의 `isOverheatedDistrict`)을 화면에 따로 보여 주지 않고, 대출 계산기에서 true 면 대출 가능액을 집값 절반으로 셈하다가 자본금이 모자랄 때만 '투기지역 (대출 비율 50% 제한)' 문구로 드러낸다. jibsa 는 같은 응답의 값을 늘 `overheated_district` 로 내고 뜻도 웹 계산기가 쓰는 대로('대출 비율을 50%로 묶는 지역인지') 적는다. 웹이 받아 계산에 쓰는 값을 더 보여 준 것이고 다른 해석(규제 지역 지정)을 붙이지 않아 사실이 어긋나지 않는다 ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-14 번들 대조: dong-info 청크, ic_24_cook_gray600 청크 `Ni`).
- **`complex` 의 학교·어린이집·유치원은 3곳씩.** 웹 '주변 보육/교육시설' 탭은 응답 순서(거리순)로 3곳씩 보여 주고 '더보기' 로 늘린다. jibsa 는 '더보기' 앞 화면처럼 중·고·어린이집·유치원을 3곳씩 낸다. `district`(`hakgudoName`)는 웹이 화면에 보여 주지 않는 같은 응답의 값이고, 초등학교를 "배정" 으로 부르는 것은 응답이 통학구역 학교를 주어서 붙인 jibsa 의 해석이다 (웹에 그 문구가 없다) ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-13 education 청크 `Y`·`X`·`Q`·`$`).
- **평형·관리비의 환산 값.** 웹 평은 `Math.floor(㎡/3.3058)` 정수(은마 '23평'), 관리비는 원 단위('237,845원')다. jibsa 는 `area_pyeong` 23.2 와 `manage_cost_manwon` 23.7845 (만원 규약, 원 단위까지). 평은 줄이고 금액은 줄이지 않는다. 같은 값의 단위 차이다 (2026-11-13 constants-chunk).
- **`--pyeong` 없을 때 대표 평형 0.** 웹은 `primarySpaceSeq ?? spaces[0].spaceSeq` 라 null 일 때만 첫 평형을 연다. jibsa 는 0 도 없음으로 보고 첫 평형으로 조회한다. 0 은 평형 번호가 될 수 없어 그대로 두면 `--pyeong` 없이 `INVALID_ARGUMENT` 로 끝나기 때문이고, 첫 평형은 웹이 대표 평형이 없을 때 여는 평형 그대로다. `[참고]` 가 대표 평형이 아니라 첫 평형으로 찾았다고 알린다 (2026-11-14 리뷰, complex-space-item 청크).
- **`complex` 의 최근 거래에 평형 번호·전용면적 덧붙임.** 웹 요약은 공급·계약㎡만 보여 준다. jibsa 는 그 면적을 그대로 내고, 면적이 같은 평형이 하나일 때만 `pyeong_id`·전용 `area_m2` 를 덧붙인다. 여럿이면 고르지 않고 `null` 과 후보 평형을 알린다 ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-13).
- **`search listings --complex`.** 가격 조건만 주면 그 금액이 있는 거래 유형으로 좁히고 알린다. 광고(`premiumList`)는 빼고 수만 알린다. 웹 `limit` 24 쪽 넘김을 최대 120건까지 한 번에 받는다. 위 매물 목록과 같은 성격이다 (2026-11-13).
- **`real-price` 의 쪽 크기·기간·거래 유형.** 쪽마다 50건씩 최대 200건 받는다 (웹은 5건씩 '더보기'). `--years 2` 는 웹에 없다 (웹은 1년·3년). `--listing` 의 `--years 1·2` 도 웹에 없다 (웹은 36달 고정). `--listing` 에 `--trade` 를 주어 매물과 다른 거래 유형(매매 매물의 전월세 등)을 보는 것도 웹에 없다 (웹은 탭 없이 매물의 거래 유형만 보여 준다). 모두 서버가 받는 같은 파라미터라 거래 한 건 한 건은 웹 자료 그대로다 (2026-11-13 room 청크 `Rr`).
- **`price-trend` 를 한 번에.** 웹이 토글로 나눠 보여 주는 1년·3년 최고·최저와 매매·전월세·갭 값을 한 번에 낸다. 평균 0 은 `null` 로 바꾼다. 같은 `charts` 응답의 값이다 ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-13).
- **`school` 의 진학 갈래.** 웹은 인원이 0 인 갈래(특성화고·취업자)를 숨기고 과학고·외국어고·예술체육고·자사고 비율은 그리지 않는다. jibsa 는 같은 응답에서 모두 낸다. 갈래 이름도 줄였다 (특수목적고→특목고, 자율형고→자율고, 국외진학→국외, 취업자→취업). 웹이 숨긴 값을 더 보여 준 것이라 값은 같다 (2026-11-13 school-chunk).
- **`school` 의 어린이집 `base_period`.** 어린이집 상세 화면은 공시 기준(`base_date`)을 그리지 않는다. jibsa 는 학교·유치원처럼 같은 응답의 값을 `base_period` 로 낸다. 웹이 받은 값을 더 보여 준 것이고 다른 칸은 화면과 같다 ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-14 school 청크).
- **`school` 의 유치원 교육비를 내지 않는다.** 웹 유치원 상세는 기본·방과후 교육비(`avgBaseCost`·`avgCareCost`)를 '지원금을 제외한 실제 학부모에게 고지하는 금액' 이라며 원 단위로 그린다 (0 이면 '-', school 청크 `Xe`). jibsa 는 이 두 값을 내지 않는다. 유치원알리미 공시와 견주면 사립 5곳은 공시 학부모 부담금이 있는데 다방이 0 을 주고, 0 이 아닌 1곳은 수업료를 뺀 교재비였다 (2026-11-14 대조: 유치원 8곳). 웹 설명대로 원비로 읽으면 사실과 어긋나서 원비는 결과 `disclosure_url`(유치원알리미)의 '비용·회계' 에서 보게 한다. 웹에 있는 값을 빼는 것이라 사실이 어긋나지 않는다.
- **`school` 의 유치원 통학 차량 0.** 웹 '통학버스' 칸은 차량 수가 '0' 이면 '-' 로 쓴다 (`Ue`). jibsa `school_bus_vehicles` 는 0 그대로 낸다. 유치원알리미 '통학차량 현황'의 운행 차량수와 같은 값이고 0 은 미운영이라 (2026-11-14 대조: 6곳) 같은 사실을 숫자로 보인 것이다.
- **`search schools` 를 여러 쪽 한 번에.** 웹 동네정보 '학군' 상세 목록은 30곳씩 쪽을 넘긴다. jibsa 는 `--limit` 까지(최대 120곳, 4쪽) 차례로 받는다. 같은 쪽을 차례로 받은 것이라 목록·순서·`total` 이 웹과 같다 (2026-11-14 school-regional 청크).
- **`nearby-complexes` 의 주변 단지 수와 거리.** 웹 'N평대 비교' 탭은 주변 단지를 3곳씩 '더보기' 로 늘리고 거리를 그리지 않는다. jibsa 는 응답의 10곳을 서버 순서 그대로 모두 내고, 같은 응답의 거리(`distance`)를 `distance_m` 으로 낸다. 단지·평당가·순서는 웹 탭과 같은 응답의 값이다 ([상세·단지·학교·실거래](#상세단지학교실거래), 2026-11-14 complex 청크 `nn`).

### 동네·주변·분양·순위

- **`popular-listings` 한 쪽 크기.** 웹은 `limit 30`·쪽 번호이고 순위 배지는 쪽마다 앞 3개에만 붙인다. jibsa 는 50건씩 받고 쪽·칸 위치로 이어지는 `rank` 를 붙인다. 역삼동 빌라 60건이 웹 30+30 과 집합이 같았다. 붙은 두세 쌍의 순서가 뒤바뀌는 것은 웹과 똑같은 요청을 두 번 보내도 생기는 서버 쪽 흔들림이다 ([동네·주변](#동네주변-neighborhoodhot-placespopular-listingsnearbystation-prices), 2026-11-13 hot-room-list-chunk).
- **`neighborhood` 는 탭 여덟 개를 한 번에, 네 주제의 순위는 `--ranks` 일 때만.** 웹은 학교·편의·교통·안전 탭마다 요약 칸(`regional/summary`, 고른 종류의 합계·구성·순위)과 `regional/count` 를 부른다. jibsa 는 기본으로 `count` 만 불러 이 네 주제에는 순위가 없고, `--ranks` 면 종류마다 `summary` 를 모두 받는다 (넷 다면 17회). 기본은 웹에 있는 값을 덜 낸 것이고, `--ranks` 는 웹 요약 칸에서 종류를 차례로 고른 값을 한 번에 낸 것이라 수와 순위는 같다 ([동네·주변](#동네주변-neighborhoodhot-placespopular-listingsnearbystation-prices), 2026-11-13 school·facility·traffic·life-safety 청크 tabList, 2026-11-14).
- **`nearby` 는 종류마다 가까운 3곳 (사용자 결정).** 웹은 `/{room|complex|sale}/{id}/near` 의 시설 전부(편의 종류는 15곳)를 지도에 찍는다. jibsa 는 종류마다 다방 거리 값으로 가까운 순 3곳만 낸다. 같은 서버 거리 값으로 가까운 곳만 고른 것이라 시설·거리는 웹 지도에 있는 그대로다. `distance_m` 은 웹 `d`(`e<1 ? parseFloat(e.toFixed(1)) : Math.round(e)`. 편의·치안 `p`·`h` 와 교육이 모두 같은 `d` 를 쓴다)와 같게 1m 미만은 소수 한 자리, 그 위는 .5 를 올려 정수로 낸다 (`_nearest`) ([동네·주변](#동네주변-neighborhoodhot-placespopular-listingsnearbystation-prices), 2026-11-13 distance-km-m 청크).
- **`nearby --with` 반려동물·카셰어링도 가까운 3곳.** 웹 '펫세권'·'Car세권' 은 3곳씩 보여 주고 '더보기' 로 늘린다 (응답은 반려동물 종류마다 10곳, 카셰어링 20곳까지). jibsa 는 위 `nearby` 와 같은 수로 다방 거리 값의 가까운 순 3곳만 내고 전체 수는 내지 않는다. 같은 응답의 장소·거리라 웹에 있는 그대로다 ([동네·주변](#동네주변-neighborhoodhot-placespopular-listingsnearbystation-prices), 2026-11-14 dong-info 청크).
- **`hot-places` 를 여러 쪽 한 번에.** 웹 '핫플레이스' 는 30곳씩 쪽을 넘긴다. jibsa 는 `--limit` 까지(최대 120곳, 4쪽) 차례로 받는다. 같은 쪽을 차례로 받은 것이라 목록·순서·`total` 이 웹과 같다 (2026-11-14 hot-place 청크).
- **`station-prices` 의 범위·확대.** jibsa 는 역을 덮는 ±0.3km·확대 16, 웹은 역을 검색한 화면 범위·확대 15 다. 역 번호가 같은 표시의 평균을 고르므로 강남역 다섯 칸의 값이 모두 같았다 (2026-11-13 map-chunk `markers/category`).
- **`search sales` 전국·시·도·시·군·구를 여러 쪽 한 번에.** 웹 분양 지역 목록과 같은 `3/sale-in-lots/list/search3`·필터로 받아 목록·순서·`total` 이 같다 (김포시 `total` 37). 웹은 24곳씩 쪽을 넘기고 jibsa 는 `--limit` 까지(최대 120곳) 차례로 받는다. 첫 쪽에 함께 오는 `features` 는 웹 지역 목록이 그리지 않는 추천 칸이라 빼고 수만 `[제외]` 로 알린다. 남은 단지는 웹 목록 그대로다 ([분양·순위](#분양순위-search-salessalesale-scheduletrending-complexestrade-rankingsregion-ranking), 2026-11-14 list 청크).
- **`search sales` 동 이름.** 웹 지역 목록이 보내는 범위는 `state_code`·`city_code` 뿐이라 동은 지도에서 본다. jibsa 는 동 경계를 덮는 사각형으로 지도 목록(`sale-list/category/bbox`)을 받고 주소가 그 동인 단지만 남긴 뒤 뺀 수를 알린다. 같은 bbox 목록의 부분집합이고 `total` 은 사각형 안 수다 (2026-11-13 list-chunk, 2026-11-14).
- **`search sales` 조건 조합.** 웹 지역 목록 UI 는 고른 건물 유형에 따라 일부 분양 상태·공급 유형을 끈다 (지식산업센터만 고르면 상태는 분양예정·접수중·입주예정, 공급은 민간분양·민간임대만 고를 수 있다). jibsa 는 고른 조건을 서버가 받는 그대로 보낸다. 웹 UI 에 없는 조합이어도 서버가 거른 결과 그대로라 분양 단지가 어긋나지 않는다 (2026-11-14 list 청크 `disabled`).
- **`search sales` 역·대학·좌표의 기본 범위 (사용자 결정).** jibsa 는 1km 반경을 덮는 사각형(2×2km)·확대 14, 웹은 역을 고른 화면 범위(1440×900 기준 약 3.6×2.9km, 확대 15)다. 강남역은 웹 3곳, jibsa 1곳이고 jibsa 결과는 웹에서 확대하면 보이는 부분집합이다 (확대 값은 결과에 영향이 없다). 웹 범위는 화면 크기에 따라 달라 기준으로 삼지 않았다 (2026-11-13 사용자 결정).
- **`sale-schedule` 기간과 `--details`·`--region`.** jibsa 기본은 오늘부터 7일, 웹은 그 날짜가 든 주(일~토)를 `list/schedule` 로 부른다. `--details` 의 표는 웹에서 날짜를 누르면 나오는 하루 표(`list/schedule/search`)와 같고, 웹은 하루씩 보지만 jibsa 는 내보낼 줄이 든 날을 한 번에 받는다. 하루 24건이 웹과 집합·순서 모두 같았다. `--region` 은 웹에 없는 조건으로 좁히기다. 하루 표의 주소(표에서 못 찾은 줄은 일정 글)의 시·도로 거르고 남긴 수와 지역을 몰라 뺀 수를 알린다. 남긴 일정이 `--limit` 을 넘으면(`limit + 1` 줄, 더 있는지 알려고) 일정이 있는 다음 날에서 멈추고 그 뒤 날은 받지 않으며, 뒷날을 보지 않았다는 것과 전체 수가 하한('적어도')이라는 것을 알린다. 남은 일정은 모두 웹 달력에 있는 것이다 ([분양·순위](#분양순위-search-salessalesale-scheduletrending-complexestrade-rankingsregion-ranking), 2026-11-13 schedule-chunk, 2026-11-14).
- **`region-ranking` 쪽 크기와 인구증감.** 부동산 순위는 jibsa 50곳씩, 웹 30곳씩이다 (동네정보 순위는 둘 다 30). `인구증감` 은 성별 없이 부른다. 웹에는 남성·여성 인구증감만 있고, 성별 없는 응답은 남+여 합계다 (역삼동 68,936 = 32,746 + 36,190). 서버가 받는 조합이다. 단지 유형의 기본은 웹과 같고(거래량·매물수·거래증감·매물증감·선호도·전세가율·갭가격은 합산), `-t` 로 하나만 고르는 것은 웹에서 한쪽을 끈 것과 같다. `-t 빌라` 는 '매물정보' 탭에서 고른 유형만 켠 것이다 (웹 기본은 주택/빌라·오피스텔·아파트 셋 다, 쪽 크기는 둘 다 30, 2026-11-14 room-info 청크) ([분양·순위](#분양순위-search-salessalesale-scheduletrending-complexestrade-rankingsregion-ranking), 2026-11-13 real-estate 청크).
- **`trending-complexes`·`trade-rankings` 기본 개수.** jibsa 기본 20곳은 웹이 받는 50곳 목록의 앞부분이다 (2026-11-13 complex-chunk·map-chunk).
- **`region-ranking`·`search sales` 의 시·군·구·동 찾기 경로.** 웹은 사람이 `region/states` → `region/cities?stateCode=` 에서 고르고, jibsa 도 같은 두 목록에서 이름으로 찾는다. 다만 시·도 없는 시·군·구 이름('강남구')은 시·도를 알아야 시·군·구 목록을 받을 수 있어 `loc/search` 가 주는 그 이름의 동으로 시·도를 먼저 고른다. 고른 시·군·구의 `gid`·`code` 는 웹 목록의 값 그대로라 같은 범위를 받는다 (강남구 gid 5547). 장소 검색이 동을 50곳까지만 줘 같은 이름이 여러 시·도에 있으면 `REGION_AMBIGUOUS` 후보에서 빠지는 시·도가 있을 수 있지만, 고른 범위가 틀리지는 않고 시·도를 붙이면 목록만으로 찾는다 ([분양·순위](#분양순위-search-salessalesale-scheduletrending-complexestrade-rankingsregion-ranking), 2026-11-13 useSiGuDong-chunk, 2026-11-14). 단지 순위의 동 범위도 웹은 지역 고르기의 동 `gid` 를, jibsa 는 `loc/search` 의 동 `gid` 를 쓴다. 역삼동은 둘 다 10063 이라 같은 순위를 받는다 (2026-11-13 real-estate 청크 `dong.gid`).

### 아직 가리지 못한 것

사례를 찾지 못해 웹과 같은지 가리지 못했다. 다음 대조 때 본다.

- `listing`: `is_contract` 가 true 인 매물 (jibsa 는 `LISTING_UNAVAILABLE`, 웹은 이 값을 화면에서 쓰지 않는다), 건물 전체 매물(`is_building_unit_all`)의 면적·층 표시 (웹은 연/대지면적·지상/지하층). `complex.isUrbanOfficetel` 이 true 인 오피스텔 매물 (웹은 계약면적 대신 공급면적을 보여 준다. jibsa 는 이 값을 보지 않아 계약면적이 오면 그대로 내고 0 이면 `null` 로 둔다. 2026-11-13 오피스텔 12건·도시형 단지 매물 17건은 모두 false 라 true 인 매물을 보지 못했다).
- `search listings`: 원룸·투룸 목록에 섞여 오는 오피스텔·아파트에 걸리는 방 크기 기준, 서버 순서가 시간이 지나며 바뀌는 주기.
- `complex`: `buildingApprovalTypeName` 이 '사용승인일' 이 아닌 단지의 `approved_date`, `complexType` 이 APT·OFFICETEL 밖인 단지의 유형 가르기.
- `search complexes`: 오피스텔 대학(`univ`) 목록은 번들만 대조했다.
- `real-price --listing`: `JIBUN` 이 다세대·연립에서만 나오는지. `real-price/house/init` 의 `compare`(시세 대비 오름·내림과 %)는 다방이 표시를 꺼 두어(`settings.isPriceCompareExpose: false`, 값도 null) 웹에 나오지 않아 넣지 않았다. 다방이 켜면 웹 '시세대비' 칸이 무엇과 견준 값인지 보고 넣는다.
- `region-ranking`: 달이 바뀐 직후 `baseMonth` 를 보내지 않아도 웹과 같은지 (부동산 순위와 `-t 빌라` 의 '매물정보' 탭 거래량 모두).
- `trade-rankings`: `sameAddressComplexCount` 가 1 보다 큰 단지 (웹은 '+N' 표시).
- `search sales`: 동 범위에 분양이 여러 곳일 때의 순서.
- 배달 구역(`delivery-zones`): 단지·매물·분양 다섯 곳 모두 빈 목록이라 무엇을 주는지 확인하지 못해 넣지 않았다 (2026-11-14).
