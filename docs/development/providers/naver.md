| `real-price` | 단지·평형별 실거래 페이지, `--period` 면 기간 목록 1회 (빌라는 페이지를 기간 시작일까지), `--group` 이면 평형 묶음 1회 → 묶음 실거래 페이지. 빌라 단지면 평당 실거래가 1회(매매·전세만)·단지 좌표 1회·주변 실거래 1회를 더 부른다 | `real_price.real_price` |

| `search redevelopment` | 지역 해석(시 이름이면 구가 있는지, 시·도 이름이면 시·군·구가 하나뿐인지(세종) 확인 1회) → 동·시·군·구 경계 또는 반경 재개발 구역 목록·마커 | `redevelopment.search` |
| `search listings --redevelopment` | 구역 번호(이름이면 재개발 구역 자동완성 1회로 해석) → 재개발 매물 페이지 | `redevelopment.listings` |
| `trend` | 법정동 코드 해석(`전국` 은 해석 없이 전국 코드, 시 이름이면 구가 있는지 확인 1회) → 매물 수·평당 호가·거래 건수 3종 조회 | `trend.trend` |

## 소스 고유 구현

모든 응답이 `{isSuccess, detailCode, message, result}` 봉투다
 (`NaverResponseModel[T]`). service 는 `unwrap()` 으로 `result` 를 꺼내고, 실패면 `JibsaError`
 (`NOT_FOUND` / `UPSTREAM_ERROR`)를 던진다. 실패 봉투는 HTTP 상태와 별도로 검사한다. 금액은 원 단위라
 `won_to_manwon`로 원 단위까지 만원으로 바꾸고, 글자로 쓸 때는 `format_manwon` 을 쓴다 ([금액·단위](../output-contract.md#금액단위)). 가장 차단이 잦은 소스라 요청 수를 늘리는 변경(매물마다 추가 조회 등)은 피한다. 늘리려면 사용자와 정한다 (예: `listing` 의 개발 예정은 웹이 모든 매물 상세에 그려 1회 늘리기로 했다, `complex` 의 평형 묶음은 `--pyeong` 과 상관없이 1회 늘리되 빌라 단지는 묻지 않기로 했고, `--pyeong` 하나일 때 평당가는 매매·전세 2회 늘리기로 했다. 모두 2026-11-18. `real-price` 의 빌라 단지는 평당 실거래가·단지 좌표·주변 실거래를 1회씩, 월세는 평당 실거래가 없이 2회 늘리기로 했다, 2026-11-19).
 429 는 봇 차단이라 일반 재시도 대상이 아니다. `should_retry_naver`는 5xx 와 `RETRYABLE_TRANSPORT_ERRORS`(timeout·연결 실패 등)만 재시도한다.

덤 조회(본 조회에 덧붙여 받는 값. 실패해도 그 칸만 모름이다)는 `result_or_none`·`result_or_empty`(`service/common/response.py`)로 부르고, `notes`·`what`(조회 이름)·`unknown`(모름이 된 칸)을 꼭 키워드로 넘긴다. 실패하면 `add_failure_note` 가 `core/notes.py` 의 `lookup_failure_note` 로 `[실패]` 안내를 만들어 `notes` 에 더한다 (같은 안내는 한 번만. 안내는 무슨 일 → 할 일 → `unknown` 순서다). 네이버가 거절(4xx, `result_or_empty` 는 `isSuccess` false 도)했거나 응답 형식이 바뀐 것(`ValueError`)이면 `UPDATE_MAYBE_NEEDED` 를 붙여 매일 API 감시가 고장으로 보고, 서버 오류(5xx)·연결 실패·시간 초과는 '잠시 뒤 다시 시도하세요' 만 붙여 감시가 확인 못 함으로 둔다 (다방 `complex` 의 덤 조회도 같은 `lookup_failure_note` 를 쓴다. 매물 상세 안내는 같은 판정을 쓰는 `lookup_failure_reason`). `unknown` 은 영어 필드 이름 뒤에 조사가 붙지 않게 `'머리말: a, b'` 꼴로 쓴다. 그 실패로 실제 출력에서 `null` 이 되는 칸은 `모름(null)으로 낸 칸:` 꼴로 적고 (매물 유형에 따라 키가 없는 칸은 적지 않는다), 실패해도 매물 값으로 물러서 `null` 이 아닐 수 있는 칸은 `단지 값 없이 낸 칸:`(`listing` 의 단지 정보 조회: 단지 유형의 난방·난방 연료는 매물 값으로, 단지형 빌라의 주차는 매물 값으로 물러선다. 그래서 한 안내에 `모름(null)으로 낸 칸:`(단지 유형의 `approved_date`·`parking`, 단지형 빌라의 난방·난방 연료)과 함께 온다)·`주차 대수 없이 낸 칸:`(건축물대장 주차 대수 조회: `parking` 은 매물의 주차 가능 여부로 물러선다) 꼴로 적는다. `result_or_none` 은 `isSuccess` false 도 안내 없이 None 이다 (네이버는 고장이 아닌 응답에도 false 를 준다: 상가·토지의 `article/maintenanceFee`, 2026-11-24 실측. 진짜 거절과 가릴 수 없다). `result_or_empty` 는 false 를 실패로 보고 `[실패]` 를 붙인다. 성공했는데 `result` 가 null 이면 `result_or_none` 은 None, `result_or_empty` 는 빈 값이다. `notes=None` 은 호출부가 실패를 따로 알릴 때만 쓴다 (지역 해석: 구가 있는 시인지·시·도 아래 시·군·구가 하나뿐인지 확인은 실패해도 CLI 가 반경으로 찾았다는 `[실패]` 안내를 이미 낸다). 요청 제한(`RateLimitedError`)은 잡지 않아 덤 조회도 에러로 끝난다. 이 안내를 담는 결과 모델(`NaverListingDetail`·`NaverDistrictTrend`·`NaverSchoolDetail`·`NaverComplexSummary`)은 `core.listing.Result` 를 물려받아 `emit` 이 그 `notes` 를 스스로 붙인다 ([공통 규칙](../provider-conventions.md#service-함수)).

빌라 단지(A05·A06·A07)인지는 명령 맨 앞에서 한 번에 정하지 않고, 아파트 쪽 응답이 비었을 때 그 자리에서 정한다 (`service/common/response.py` 의 `villa_by_complex_response` docstring). 맨 앞에서 정하면 단지 종류를 모를 때마다(대부분 아파트) 요청이 1회 늘기 때문이다. 판별이 여러 곳에 흩어진 것은 이 때문이며, 한 번 빌라로 정해지면 빌라 엔드포인트의 실패 응답은 0건이 아니라 에러로 낸다. 단지 매물 목록은 아파트·빌라 모두 없는 단지 번호에도 빈 성공 응답을 줘서(2026-10-23 실측: 99999999 와 헬리오시티 111515 의 빌라 목록이 같은 `totalCount: 0`), 단지 번호만 받아 종류를 모른 채 0건이면 단지 정보(아파트 → 빌라)로 단지가 있는지 확인한다 (`list_complex_articles`). 빌라 단지에 거래·동이 없을 때 빌라 엔드포인트는 실패가 아니라 빈 목록을 주고(서진빌라 724112 월세 실거래 0건), 아파트 동 목록(`complex/buildingList`)도 빌라 단지에 `result=null` 이 아니라 빈 목록을 준다 (2026-10-10 실측).

응답 값을 요청 모델(Literal·pattern)에 다시 넣을 때는 먼저 아는 값인지 확인한다. 요청 모델 검증 실패는 `handle_errors` 가 사용자 입력 오류(`INVALID_ARGUMENT`)로 내기 때문이다. 매물 상세는 모르는 매물 유형을 `KNOWN_REAL_ESTATE_TYPES` 로 걸러 볼 수 없는 매물로 낸다.

service 가 부르지 않는 엔드포인트(`article/agent`, `complex/holdingTax`, `complex/declaredValue/pyeongType`, 지도 칸 `article/map/articleClusters`·`article/clusteredArticles`)는 라이브러리용으로 client 메서드만 있다 (`article/agent` 는 중개사 정보라 출력하지 않는다는 원칙에 따라 쓰지 않는다. 지도 칸 둘은 네이버 웹 지도도 부르지만 jibsa 매물 검색은 지도 범위·동 목록만 쓴다, [페이지네이션과 조건 처리](#페이지네이션과-조건-처리)). 모델은 [기준 7](../provider-conventions.md#service-모듈을-나누는-기준)대로 경로가 같은 기능 모듈에 둔다 (`article/agent` → `listing`, 지도 칸 둘 → `search`, 나머지 둘 → `complex`). 다만 공용 코드가 타입으로 쓰는 모델은 옮기지 않고 `response/common.py` 에 둔다 (`NaverComplexList*`·`NaverRedevelopmentArea*` 는 `service/common/paging.py` 의 쪽 넘김 타입과 `service/common/price.py` 의 `trade_article_counts` 가 쓴다).

### 브라우저 요청

(2026-11-09 실측) 공통 동작은 [브라우저 요청](../architecture.md#브라우저-요청). 네이버만의 값:

- 첫 화면은 `https://fin.land.naver.com/` (지도 `/map?...` 으로 넘어간다). load 시점 쿠키는 0~6개였다가 2초 안에 8개가 다 생겨
  `NNB`(400일)를 기다린다. 그 밖에 `NAC`·`BUC`(400일), `NACT`(24시간), `SRT30`(30분), `SRT5`(5분). `BUC` 는 front-api 응답마다
  서버가 새 값으로 바꿔, 명령이 끝날 때 남기는 쿠키에 따라 들어간다. 쿠키는 몇백 ms 에 걸쳐 나눠 생겨, `NNB` 가 생긴 뒤에도
  쿠키가 0.5초 동안 더 바뀌지 않을 때까지 기다린다 (`READY_COOKIE_SETTLE_SECONDS`). `NNB` 만 보고 멈추면 같은 순간에 생기는
  `NAC`·`NACT` 를 놓쳐 6개만 남았다. 30분 뒤 다시 열 때는 남긴 `NNB` 등 영구 쿠키를 넣고 열어 `NNB` 가 그대로다. `NNB` 가
  처음부터 있어 `NNB` 로는 첫 화면이 돌았는지 알 수 없으니, 이번 방문에서 사이트가 쿠키를 심거나 바꾼 것도 본다
  (2026-11-10 실측: 처음 열면 load 뒤 1.4초에 8개가 한 번에, 다시 열면 load 뒤 0.2초에 `BUC`·`SRT5`, 0.4초에 `NAC`·`NACT`).
- 첫 화면이 front-api 를 18~22번 부른다. 그래서 분당 상한을 예전 우리 요청 몫 30 에 그만큼 더한 60 으로 둔다. 상한은 첫
  화면 요청과 우리 요청을 합친 수에 걸려, 남긴 쿠키로만 보내는 명령(30분 중 대부분)은 우리 요청만 분당 60건(1초 간격의 최대)까지
  나간다. 아래 실측이 그 속도라 일부러 둔 값이다. 429 에 `Retry-After` 가 없어 차단이 얼마나 가는지 몰라, 쿨다운은 5분이고
  쿨다운 뒤 첫 명령은 첫 화면을 연 지 30분 안이면 남긴 쿠키로 요청 1건만 보내 풀렸는지 본다. 30분이 지났으면 첫 화면부터 다시
  연다 (아직 막혀 문서가 429 면 그 1건, API 만 막혀 있으면 첫 화면 요청 18~22건). 예전 쿨다운 15분은 첫 코드의 초깃값이고
  차단 길이를 잰 값이 아니다.
  2026-11-09 실측: 첫 화면을 새로 연 뒤 `search listings`·`listing` 을 쉬지 않고 10분 이어 불러(명령 102개, 요청 596건,
  1분 창 최대 60건) 429 가 한 번도 없었다. 첫 화면을 다시 여는 30분 주기와 차단 길이는 재지 못했다.
- 헤더 (2026-11-12 웹 화면 8개 요청 324건 실측과 번들): 웹은 front-api 를 모두 axios 인스턴스 하나로 불러 경로와 상관없이 같은
  헤더를 붙인다. 고정값은 axios 기본 `Accept: application/json, text/plain, */*` 와 본문이 있을 때의 `content-type` 뿐이고 jibsa
  와 같다 (`base_header`). 나머지 넷은 요청·페이지마다 바뀌어 넣지 않는다:
  - `x-page-url`: 보낸 순간의 주소창 주소 (`window.location.href`, 지도 상태가 다 들어 있다). 요청 인터셉터가 붙인다.
  - `x-attest`: 요청마다 다른 136자 서명 (11-09 에는 118자). 서버가 렌더링해 페이지에 넣은 토큰(페이지 로드마다 다름)을 시각·난수와
    함께 가려 만든다. 요청 인터셉터가 붙인다. 서버에는 헤더가 없을 때(`ABSENT`)를 포함한 상태값이 있고 지금은 없어도 200 이다.
    네이버가 진짜 웹에서 보낸 요청인지 보려는 값이라, 이 헤더를 요구하기 시작하면 네이버 명령이 모두 막힐 수 있다.
  - `sentry-trace`·`baggage`: Sentry 가 같은 출처 XHR 에 붙이는 추적 ID. 페이지 로드나 라우터 이동마다 새 값이다.
  사이트가 `window.fetch` 가 아니라 자기 API 클라이언트에서 `x-page-url`·`x-attest` 를 붙여 main world fetch 에도 붙지 않는다.
- 첫 화면의 front-api 요청을 막으면 쿠키가 `map_snb_collapsed` 하나만 생긴다. 이미지·지도 타일(`map.pstatic.net`)만 막는다.
- GitHub 러너 IP 는 브라우저로도 응답을 받지 못한다 ([매일 API 감시](../README.md#매일-api-감시)).

## 페이지네이션과 조건 처리

경계 검색·반경 검색·단지 검색·재개발 검색의 페이지 예산과 집계 범위는 서로 다르므로 해당 service 상수와 `PageScan`/`scan_pages`를 읽는다. 반환 개수와 서버 집계를 같은 값으로 취급하지 않는다. `--limit` 은 요청한 크기가 아니라 받은 개수로 센다. 네이버가 다음 쪽이 있다면서 새 항목을 주지 않는 쪽(같은 쪽을 되풀이하거나 빈 쪽)은 `scan_pages` 가 세지 않고 멈추며 `PageScan.stalled` 를 켠다. 멈춤은 준 항목이 모두 이미 받은 번호이거나 쪽이 비었을 때만이다. 번호를 모르는 항목(정보 없는 단지)·빈 항목(null)뿐인 쪽은 세고 넘어간다. 안내와 `has_more` 는 `PageScan.stopped_short(resumed=…)`(= `stalled and (resumed or total > received)`) 하나를 같이 쓴다. 이어 받기가 아니면 받은 수가 서버가 센 수에 닿았을 때 다 받은 것이고, 이어 받은 결과의 `total` 은 앞 결과까지 센 수라 견주지 않는다. `pagination_notes(stalled=scan.stopped_short(resumed=…), exhausted=scan.exhausted)` 가 '전부입니다' 대신 `[일부]` 로 알린다 (두 인자는 기본값이 없다. 새 호출부가 빠뜨리면 조용히 `[일부]`·`--limit` 을 늘리라는 안내로 돌았다. `exhausted` 는 `cursor is None and not stalled`). 지역 매물 검색의 `has_more` 는 `next_position is not None or scan.stopped_short(resumed=start is not None)` 이고 멈추면 `cursor` 가 None 이라 `next` 는 없다. 이어 받기가 없는 단지·재개발 구역 매물은 `scan.cursor is not None or scan.stopped_short(resumed=False)` 다. 이어 받기가 아니면 전체 수를 함께, 이어 받기면 '이번에는 N건까지만' 으로 알리고 `--limit` 을 늘리라고 하지 않는다. 같은 자리에서 다시 멈춘다). 검색 모드의 최대값은 `MAX_LIST_LIMIT`(120) 하나를 CLI 옵션과 상한 안내가 함께 쓴다.

매물 목록 항목은 대표 매물(`representativeArticleInfo`)과 중복 묶음(`duplicatedArticleInfo`: 같은 집을 올린 중개사 수, 거래별 호가 범위 `representativePriceInfo`, 묶인 매물 전부)이다. 묶인 매물 목록은 매우 커서 받지 않고 수와 범위만 `NaverListing` 의 `realtor_count`·`asking_range` 로 낸다. 서버 가격순은 이 범위로 정렬한다 (2026-10-31 실측: 헬리오시티 84㎡ 매매 가격높은순 첫 매물이 대표 30억, 범위 30억~33억, 다음이 32억들. 가격낮은순은 범위 최저 순). 대표 가격만 내던 때는 33억 호가가 보이지 않았다. 범위로 다시 정렬하지 않는다 (서버 정렬 그대로). 가격 조건도 대표 호가로만 걸린다 (같은 날 실측: 가격 30억~30억에는 그 묶음이 나오고 33억~33억은 0건). 범위 필드만 두자 에이전트가 가격 조건 0건을 믿어, `group_sort_notes` 가 끝 호가 값과 이 동작을 함께 알린다. 호가 범위는 중개사마다 같으면 키를 지우고(해당 없음), 네이버가 범위를 주지 않았거나 두 끝이 모두 `null` 이거나 한 끝은 0 이고 다른 끝은 `null` 이면 `null` 로 낸다 (`unknown_group_fields` 가 `not_applicable_fields` 에서 뺀다). 한 끝만 `null` 이면 아는 끝의 금액을 남기고 다른 끝만 `null` 로 낸다 (재개발 호가 범위 `asking_ranges` 와 같다). 보증금·매매가의 0 은 받은 그대로 내고(보증금 0원 매물이 있다), 월세의 0 은 월세 0원 매물이 없어 네이버가 비운 값이라 그 끝의 `rent_manwon` 을 `null` 로 읽는다 (`_rent_amount` 와 같은 규칙). 호가가 같다는 뜻과 모른다는 뜻을 섞지 않는다. 매매가·보증금 범위의 두 끝은 묶인 매물(`articleInfoList`)의 최저·최고다. 월세 범위(`rentPrice`)의 두 끝은 월세 최저·최고가 아니라 (보증금, 월세) 순으로 첫 매물과 끝 매물의 월세이고 `asking_range` 는 이 월세를 보증금과 짝지어 낸다 (2026-11-25 잠실동·역삼동·신림동 묶음 177개 실측: 매매 46·보증금 131 모두 최저·최고, 월세·단기임대 124 모두 이 짝이고 그중 37 은 월세 최저·최고와 달랐다. 2658449927 은 500/58·1000/55·1000/55 라 `asking_range` 의 월세가 `lowest` 58·`highest` 55). 그래서 월세 두 끝이 같아 키를 지워도 가운데 매물의 월세는 다를 수 있다 (4개).

사각형 목록(`boundedArticles`·`boundedComplexes`)은 지도 줌(`precision`)이 높을수록 사각형을 다 주지 않고 중심 근처만 준다. 그래서 매물 반경 검색과 `search complexes` 반경 검색은 반경에 맞춘 줌(`bounded_precision`: 1.5km 까지 16, 2km 까지 15, 3km 까지 14)을 보낸다. 모델 기본값 16 만 보내던 때는 반경 2km 부터 가장자리 매물이 빠져, 빠진 매물만 조건에 맞으면 '0건이 전부' 라고 냈다 (2026-10-31 강남역 2km 아파트 전세 5억 이하 + 500세대 이상: 가격낮은순 0건, 지도 칸 매물(`clusteredArticles`) 6건). 세대수 조건 탓으로 보였지만 세대수만 걸면 줌 16 에서도 1,129건 중 673건으로 줄어 서버가 받는다. 줌별 실측 수는 `bounded_precision` 주석에 있다.

매물 정렬은 네이버 웹 정렬 여섯 가지(`SORT_TYPE_BY_NAME`, 웹 `ARTICLE_SORT_TYPE`)뿐이고 기본은 랭킹순이다. 웹 지도 목록은 지도 범위(`boundedArticles`)나 지도 칸 하나(`clusteredArticles`)를 이 정렬로 보여 줄 뿐, 여러 칸의 매물을 모아 거리로 다시 세운 목록은 없어 거리순은 두지 않는다 (2026-11-16 번들 대조). `--sort 가까운순` 은 `NEAREST_SORT_HINT` 를 붙인 입력 오류다.

단지 매물(`complex/article/list`)의 `lastInfo` 는 다음 쪽이 있는 동안 리스트로 온다 (`[1, 점수, 매물 번호]`, 가격순·최신순은 가격·날짜가 하나 더. 헬리오시티 1,774건 랭킹·가격낮은·최신순 각 3쪽, 2026-10-10). 정수 커서를 막는 검사는 응답 형식이 바뀌었을 때를 위한 것이다. 마지막 쪽과 재개발 구역 매물(`redevelopmentArea/articleList`)도 리스트로만 온다 (개포자이 6쪽, 봉천4-1-3·봉천14구역 3개 정렬 12쪽, 2026-10-11). 그래서 재개발 매물에는 정수 커서 검사를 두지 않고, 단지 매물의 검사가 멈출 때 따로 안내하지 않는다 (실제로 오지 않는 경우라 코드를 늘리지 않음). 이 검사를 `scan_pages` 로 옮겨 모든 목록에 걸지 않는다: 지도 범위 매물(`boundedArticles`)과 동 전체 매물(`legalDivisionArticleList`)이 쓰는 `NaverArticlePagingRequestModel` 은 커서가 리스트 또는 정수다.

필터는 request 모델의 서버 코드로 변환한다. 거래 유형·가격 조건 `NaverTradeConditions`(`common`, 단지·재개발 매물)를 지도 검색 조건
`NaverListingConditions`(`search`)가 이어받는다 ([공통 규칙](../provider-conventions.md#검색-조건-묶음)). 단지·재개발 목록은
`price_filter_of`, 지도 검색은 `search_area` 가 원 단위 필터를 만든다. 시설·주차의 AND와 나머지 다중 조건의 OR, 가격별 거래 유형 추론을 유지한다. 반경·동 전체·단지·재개발 매물은 모두 서버 필터 응답이라 [공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)대로 가격·유형을 다시 거르지 않는다 (`listing_keeper`. 2026-10-10 실측: 가격 조건 4종 지역 검색 118건, 단지 매물 38건 모두 조건 안). 받은 뒤 빼는 것은 중복·모르는 거래 유형 코드와, 사각형으로 받은 반경 검색의 반경 밖·좌표 모름뿐이다. 목록 응답에는 매물 상태·노출 여부 필드가 없어 거래 불가로 뺄 매물이 없다 (`EXCLUDED_REASON`. 2026-10-14 실측: 역삼동 동 전체 목록 20건). 네이버 매물은 거래 조건이 하나라 거래 조건 선택이 없다. 서버는 틀린 필터 키를 조용히 무시하므로 필터 키를 바꾸면 원본 응답이 조건 안인지 live로 확인한다. 단지·재개발 모드는 지역 검색의 모든 옵션을 지원하지 않으므로 CLI 분기의 검증을 먼저 확인한다. 부가 조회 실패로 정보가 `null`인 경우와 거래 불가를 구분한다.

세대수(`householdNumber`)·단지 주차(`parkingTypes`)는 단지 매물만 남기고, 현관 구조(`entranceTypes`)는 단지 여부와 상관없이 현관 구조가 등록된 매물을 남긴다. 그래서 안내도 `COMPLEX_FILTER_NOTE`·`ENTRANCE_FILTER_NOTE` 로 나눈다. 둘을 함께 주면 세대수·주차 조건이 단지 아닌 매물을 이미 빼므로 현관 안내는 '단지가 아닌 빌라도 나온다' 는 괄호 말을 뺀 `ENTRANCE_WITH_COMPLEX_FILTER_NOTE` 다 (2026-11-17 연남동 빌라 297건: `--entrance 계단식` 102건에 단지가 아닌 빌라 2661884425·2661802815·2661884583 이 남고, `--household-min 1` 78건·`--parking 세대당1대` 14건에는 셋 다 빠졌으며 표본 3건은 모두 단지 매물).

### 목록 안 빈 항목 (`null_items`)

- 네이버가 객체 목록 안에 null 원소를 주면 기반 모델 `NaverBaseResponseModel` 이 빼고 칸마다 센다 (`page.null_items('items')`). 공통 규칙(계산한 값은 null, 자리 세기는 뺀 수를 더함, `[제외]` 안내)은 [모듈 구성](../provider-conventions.md#모듈-구성)에 있고, 네이버의 자리별 처리는 아래와 같다. 안내는 `null_items_note` 라 끝말이 `UPDATE_MAYBE_NEEDED` 다.
  - **봉투 `result` 목록**: `result_with_null_items`(`service/common/response.py`)가 `result` 와 뺀 수를 함께 돌려준다. `result_or_none` 은 이것에 위임하고 뺀 수는 쓰지 않아, `result` 가 목록이고 그 목록으로 계산하거나 자리를 세는 호출부(동향의 평당가 주간 목록, 시·군·구 목록)만 `result_with_null_items` 를 부른다.
  - **매물·단지·구역 목록 쪽 넘김(`scan_pages`)**: `PageScan.null_items` 에 뺀 수를 모으고 `received` 는 뺀 자리를 더해 센다 (네이버 서버는 빈 항목도 한 자리로 센다). 쪽 넘김·남은 매물 판정이 같은 자리를 다시 받거나 일찍 멈추지 않는다. 안내는 `scan_null_items_notes`(지역 단지·매물·재개발 구역·구역 매물은 `search/complexes.py`·`search/listings.py`·`redevelopment/search.py`·`redevelopment/listings.py`, 단지 매물은 `listing/complex.py` 의 `list_complex_articles`)이고, `pagination_notes(null_items=scan.null_items)` 가 뺀 자리를 '중복·거래 유형으로 뺀 수' 에서 빼 빈 항목을 그 사유로 안내하지 않는다. 첫 쪽이 빈 항목만 와도 빈 쪽으로 보지 않아 빌라 목록을 다시 묻지 않는다.
  - **관리비(`listing`)**: 항목별형 `fixDetailList` 에서 뺐으면 합계 `manage_cost_manwon` 과 `manage_cost_includes` 가 둘 다 null 이다 (`service/listing/cost.py` 의 `manage_cost`).
  - **동향(`trend`)**: 평당가 주간 목록에서 뺐으면 `asking_price_per_pyeong.latest_manwon` 이 null 이고 `weeks` 는 받은 대로 둔다 (`get_district_trend`).
  - **실거래(`real-price`)**: 아파트 쪽·빌라 쪽·기간 조회에서 빈 항목만 온 쪽을 빈 쪽으로 보지 않아 멈추지 않고(빌라 판정·`break` 조건), 주변 실거래는 상한(`AROUND_TRADES_LIMIT`) 판정에 뺀 수를 더한다 (`get_real_prices`).
  - **학교 배정 단지(`school`)**: `total`·받은 수·상한·쪽이 비었는지·안내 숫자를 뺀 수를 더해 센다 (`list_school_complexes`).
  - **이름 해석(`service/region/common.py`·`search.py`)**: 단지·구역·법정동·역 자동완성의 `has_more` 를 `len(items)` 에 뺀 수를 더해 부른다 (`collect_matching` 은 뺀 수를 함께 돌려주고 `search_complexes` 는 네 번째 값으로 돌려준다). 시·군·구 목록에서 뺐으면 빠진 곳이 구일 수 있어 `city_district_names` 는 None, `only_district_of_province` 는 `'unknown'` 이고 `list_regions` 는 '하나뿐' 이라고 단정하지 않는다. `cli/naver.py` 의 시 구 확인·시·도 하나뿐 확인은 빈 항목이라서 모르는 경우에도 조회가 실패했을 때와 같은 기존 '확인하지 못해 반경으로 찾았다' 안내를 낸다. 자리별 빈 항목 안내는 없지만(붙이려면 service 반환형을 늘려야 한다) 뺀 수는 명령 전체 집계에 들어 공통 안내(`null_items_total_note`)가 붙는다.
- 손대지 않은 자리: 평형 목록으로 빌라·없는 평형을 판정하는 곳(`pyeong_list`·`check_pyeong_numbers`·`resolve_dong_numbers`)과 그 `NOT_FOUND` 는 에러 경로·흐름 판단이라 빈 목록 그대로 둔다. 보여 주기만 하는 목록(주변 개발 `rail`·`area`, 교통·학교, `weeks` 목록, 평당가 `rows`)과 `_subway_label` 의 `min(minutes)` 도 값이 틀리지 않아 그대로다 (뺐으면 공통 안내가 알린다). `scan_pages` 의 '처음 보는 항목이 없으면 멈춤' 판정과 이름 해석의 후보 수(`len(same)`)는 서버 자리 세기가 아니라 읽은 항목 기준이고, 빈 항목만 온 쪽에서만 달라지는 극단이라 그대로 둔다.

- `development/article`(`articleNumber`)은 `result.railList[]`(역·노선 이름·개통 예정 연도 `openDate`·거리 m·도보 분)와 `jiguList[]`(이름·유형·단계·기간 `period`, 기간은 없을 수 있다)를 준다. 좌표도 오지만 읽지 않는다. 원룸은 `{"railList": [], "jiguList": []}` 로 온다. `stationId`·`railId`·지구의 `id`·`step` 의 자료형은 실측으로 가리지 못해 `int | str | None` 으로 받는다. 웹 `ArticleMain`(청크 c29992b834_0l4pkwg0qhg2t)은 매물 유형 조건 없이 부르고 두 목록이 비면 칸을 그리지 않는다.
- `education/complex/pages`(`schoolCode`·`size`·`page`·`sortType`)는 학교에 배정되는 단지를 준다. `sortType` 은 `DISTANCE`·`HOUSEHOLD_COUNT` 만 받고 그 밖은 400 이다 (웹 enum `ELEMENTARY_SCHOOL_SORT_TYPE`). 항목은 단지 정보·매물 수·호가 범위(원, 매물이 없으면 `{}`)와 배정 동(`isAllBuildingAssigned`·`convertedBuildingNameGroups`)이다. 끝 쪽을 넘긴 쪽(page=9)은 `list: []`·`hasNextPage: false`·`totalCount: 0` 이라 총수는 첫 쪽에서만 믿는다. `hasNextPage` 가 null 이면 첫 쪽 `totalCount` 가 받은 수보다 클 때 더 있는 것으로 보고 이어 받으며(쪽 요청 상한 5회 안), 상한에 걸려 `--limit` 에 못 미치면 `--limit` 을 권하지 않는 안내를 따로 낸다. 빌라가 `villaInfo` 로 올 경우에 대비해 그 칸도 받는다 (오는지는 확인하지 못했다: 2026-11-18 인천일신초 E100000875 에 배정되는 빌라 가람아트빌 673573 이 목록에 없었다).
- `search/autocomplete/redevelopmentAreas`(`keyword`·`page`·`size`)는 `{hasNextPage, totalCount, list[]}` 를 주고 항목은 구역 번호(`redevelopmentAreaNumber`)·이름·법정동 이름·코드다 (좌표도 오지만 읽지 않는다). `size` 를 빼면 서버 기본 5건이 오고, 없는 이름은 `totalCount: 0`·`list: []` 다. 한남제3재정비촉진구역은 한남동 10017678·보광동 1000208 로 법정동마다 따로 와서 이름이 정확히 같은 후보가 둘이다 (`resolve_redevelopment_number`).
- `complex/villa/realPricePyeongPrice`(`complexNumber`·`tradeType`·`startDate`[·`pyeongTypeNumber`])는 빌라 단지의 평당 실거래가를 준다. 웹 빌라 단지 실거래 탭(`ComplexVillaTransactionTab`, 청크 b042d8aace_1okty1145x932)이 `useComplexVillaRealPricePerPyeongQuery`(청크 26e0315e74_3kmdmwb6eaqal)로 부르고 `startDate` 는 오늘의 5년 전(`VILLA_TRANSACTION_PER_PYEONG_YEAR_RANGE` 5, `yyyy-MM-dd`)이다. `result` 는 `[{tradeDate: '2026-10-31', pyeongPrice: 21890000}, …]`(원/평, 지금까지 본 값은 만원 자리로 떨어졌다. 나눗셈 값이라 응답 모델은 소수로 와도 받게 `float` 다. 평균 필드도 같아 관리비·시세 평균·`avgPrice`·`averagePyeongPrice` 는 `float`, `averageCount` 계열은 `int | float` 로 받는다)이고 거래가 없으면 `[]` 다 (2026-11-18·19 실측, 로그인 없이 200). 572549 전세 평형 4 는 5건이고 `real-price 572549 --pyeong 4 --trade 전세 --period 5년` 의 5건과 날짜·금액이 같으며 매매는 0건이었다. 웹(`ComplexVillaTransactionPricePerPyeong`)은 거래 유형이 매매·전세일 때만 이 칸을 그리고 월세면 칸이 없어 jibsa 도 월세는 묻지 않고 키를 두지 않는다 (`SALE_JEONSE_CODE_BY_NAME`, `service/common/constants.py`: 매매 A1·전세 B1). 조회가 실패하면 `price_per_pyeong_trades` 는 `null`(모름), 성공인데 `result` 가 null 이거나 빈 목록이면 `[]`(없음)이다.
- `complex/villa/realPriceAround`(`complexNumber`·`tradeType`[·`pyeongTypeNumber`]·`top`·`bottom`·`left`·`right`·`zoom`)는 지도 범위 안 빌라 실거래를 준다 (웹 `ComplexVillaTransactionPriceForAround`, 훅 `useComplexVillaRealPricePyeongAround`, 같은 청크). 범위 네 값과 `zoom` 이 모두 필요하다: **zoom 16 이면 결과가 오고 14 면 0건이며 빼면 400**(`FST_ERR_VALIDATION`) 이다 (2026-11-19 실측). 웹은 단지 좌표(`GET complex/villa` 응답 `result.coordinates` 의 `xCoordinate`(경도)·`yCoordinate`(위도))를 가운데로 작은 지도(388×200px, zoom 16) 범위를 한 번 잡는다: 572549(위도 37.47)에서 위도 폭 0.001703°, 경도 폭 0.0041628° 였다. 이 두 값은 축척 `360 / (256 * 2**17)` 도/px 의 메르카토르 지도와 소수 일곱째 자리까지 같아, jibsa 는 도 값을 고정하지 않고 픽셀 크기와 이 축척으로 단지 위도에서 범위를 계산한다 (`get_real_prices`). 경도 폭은 위도와 상관없이 같고 위도 폭은 위도마다 달라, 제주(33.5°)는 0.0017893° 로 서울보다 5% 넓다. 범위를 넓혀도 zoom 16 으로 되고(0.5km·1km 사각형 모두 10건) `--around-km` 은 `box_around` 사각형(한 변이 반경의 두 배)을 같은 zoom 16 으로 보낸다. 응답 `result.aroundRealPriceList[]` 는 건물마다 `{complexInfo: {realEstateType: 'A06', coordinatesDto: {xCoordinate, yCoordinate}}, realPriceList: [{contractDate, exclusiveArea, completionYearMonth: '20100628', floor: '5'(글자), isRenewRequestRight, price: {dealPrice, deposit, monthlyRent}}]}` 이고 금액은 원이다 (월세 행 예 `{dealPrice: 0, deposit: 160000000, monthlyRent: 400000}`). 단지 번호·이름은 오지 않는다. 서버는 범위 안 거래를 **10건까지만** 준다 (고르는 기준은 확실하지 않다: 0.5km 의 가장 오래된 계약 2025-09-02, 1km 는 2024-07-31). 웹 범위에서 온 묶음은 그 단지 자신이다 (좌표가 가운데와 같다). `pyeongTypeNumber` 를 주면 서버가 비슷한 면적까지 함께 준다. 웹 표는 계약일 내림차순 → 준공연도 내림차순 → 전용면적 내림차순으로 정렬해 처음 5건 + 더보기이고(웹 비교식, 청크 1okty1145x932 의 정렬 함수도 `completionYearMonth` 의 앞 네 자리(연도)만 비교하고 연도가 같으면 전용면적 내림차순이라 jibsa 가 `completed_year` 로 가르는 것과 같다. 리뷰 오탐 (2026-11-19): 준공 월·일까지 비교하지 않는다), 층은 '-'(넘기지 않는다)·갱신 배지는 없으며 응답이 비거나 단지 좌표가 없으면 칸을 그리지 않는다. jibsa 는 `nearby_trades` 로 낸다. 서버가 `[]` 를 주거나 성공인데 `result`·`aroundRealPriceList` 가 null 이면 `trades: []`, 조회 실패나 단지 좌표를 모르면 `null` 이다. 건물 좌표(`coordinatesDto`)는 `distance_m`·`same_complex` 를 구하는 데만 쓰고 출력하지 않는다 (같은 점인지는 반올림한 거리 0 으로 가린다, 소수 자릿수가 6~7자리로 달라도 같게 보려는 것이다).

## API 변경 시 점검

client의 action별 endpoint/docstring → request 별칭·필터 → response 봉투와 중첩 모델 → service unwrap·만원 변환 → CLI 모드별 검증 순으로 확인한다. 학교·교통·세금·선택 평형 시세는 부가 요청 경로도 따로 확인한다. 재개발은 구역 목록과 매물 목록, trend는 호가와 실거래 건수를 구분한다.

## 웹과 다른 점

[웹 화면과의 대응](../provider-conventions.md#웹-화면과의-대응) 원칙 안에서 네이버 웹(`fin.land.naver.com`)과 다르게 한 곳을 모은다. 2026-11-16 에 네이버 명령 전체를 네이버 웹(요청 캡처와 웹 번들)과 대조했다. 자세한 근거는 각 절에 있고 여기서는 무엇이 다르고 왜 사실이 어긋나지 않는지만 적는다. "그대로 두기로 함" 은 대조에서 지적됐지만 웹에서 고를 수 있는 값이거나 사용자가 그대로 두기로 정한 것이다.

### 위치·단지 이름 해석

- **검색어 종류 우선순위 (그대로 두기로 함).** 웹 검색창은 지역·지하철·재개발·분양·단지·초등학교 자동완성과 주소 검색을 한꺼번에 불러 종류별로 보여 주고 사람이 고른다. jibsa 는 주소 → 동 → 역 → 단지 순으로 처음 찾은 종류를 쓴다 ('역' 으로 끝나면 역 먼저, `resolve_search_region`). 검색어는 웹 검색창처럼 앞뒤 공백을 떼고 쓴다 (번들 검색창 `e.trim()`, 2026-11-17 리뷰: '파크리오 ' 가 이름이 정확히 같은 단지를 못 맞춰 후보 3곳으로 멈췄다). 쓰는 종류는 웹 검색창이 같은 검색어에 보여 주는 종류 하나이고, 종류가 겹칠 때마다 물으면 쓰기 불편해 그대로 둔다. 같은 종류 안에서 후보가 여럿이면 `REGION_AMBIGUOUS` 로 묻는다 (2026-11-16 사용자 결정). 같은 이름이 여러 곳일 때와, 역·동 자동완성에 이름이 맞는 곳이 없고 후보가 둘 이상일 때다 ('서울대' → 서울대입구역·서울대벤처타운역, '인천공항' → 인천공항1터미널역·2터미널역, 2026-11-16 실측). 후보가 하나뿐이면 그곳으로 찾고 `[참고]` 로 알리니 웹 검색창이 보여 줄 후보 하나 그대로다. 좌표 없는 후보도 후보로 세고 정한 동·역에 좌표가 없으면 웹이 보여 줄 다른 후보로 바꾸지 않고 `REGION_NOT_FOUND` 다. 동 경계 검색은 좌표가 필요 없지만, 경계·반경은 지역을 찾은 뒤 cli(`_area_location`)가 정하고 지역 해석의 `radius_km` 는 `--radius` 가 없어도 기본값이 들어가 지역 해석에서는 가릴 수 없다. 허용하려면 사용자가 `--radius` 를 줬는지를 지역 해석까지 넘기고, 동 후보만 통과시키고(구 있는 시는 반경으로 떨어진다), 이어 받기(`--next`)가 되살리는 지역 좌표도 비게 해야 한다. 사용자 결정 (2026-11-24): 고치려면 위 세 곳을 함께 바꿔야 해 지금은 막아 둔다. 좌표 없는 동 후보는 아직 실측에서 본 적이 없다. 이름이 맞는 동도 다음 쪽이 남았는데 하나뿐인지 확인할 수 없으면 고르지 않고 `REGION_AMBIGUOUS` 다 (뒤쪽에 같은 이름 동이 더 있을 수 있어, 2026-11-16 사용자 결정. 번들 `getAutoCompleteInfiniteQueryOptions` 의 hasNextPage). 이름 전체 주소 검색이 한 곳만 줘도 그 `bcode` 가 찾은 동의 법정동 코드와 같을 때만 하나뿐으로 본다 (주소 검색은 자동완성에 없는 곳도 `bcode` 를 비워 섞어 준다: '신흥동' 14곳 중 부천 오정구·인천 제물포구 등 4곳, 2026-11-16 실측). 이름이 맞는 곳은 끝말과 상관없이 센다 ('신평' → 신평동·신평면이면 둘 다 후보, 주소 검색 없이 멈춘다. 2026-11-16 리뷰). 다음 쪽이 남았는데 `totalCount` 가 비어 오면 `candidate_count` 는 모름(`null`)이다. 이름이 같은 역이 여러 곳이어도 고르지 않고 후보를 좌표와 함께 알린다 ('시청역' → 서울·대전·부산 시청역이 따로 온다. 역 이름·노선이 같은 역이 있어 이름으로는 못 고르니 후보의 `--lat/--lng` 로 다시 찾게 한다, 2026-11-17 실측·사용자 결정).
- **`○가` 동 후보를 자동완성과 하위 지역 목록으로 모으기.** 웹 검색창은 '성수동' 에 법정동 자동완성으로 성수동1가·성수동2가를 따로 보여 주고 사람이 하나를 고른다. jibsa 는 주소 검색이 1가 한 곳만 줘서, 웹 검색창이 쓰는 같은 법정동 자동완성을 앞 이름으로 1회 불러 다른 시·구의 `○가` 동까지 모으고 (충정로 → 중구 충정로1가·서대문구 충정로2가·3가), 자동완성에 다음 쪽이 있을 때만 찾은 동의 시·구 하위 지역 목록(`legalDivision/subInfoList`)을 1회 더 불러 합친다 (`_check_ga_dongs`). 시·구를 붙인 검색어('서대문구 충정로')는 그 시·구의 동만 센다. 하위 지역 목록은 찾은 동의 시·구만 덮으므로 다음 쪽이 남았는데 `○가` 동이 한 곳만 모이면 다른 시·구의 것이 뒤쪽에 있을 수 있어 고르지 않고 `REGION_AMBIGUOUS`(`candidate_count` `null`)다 (2026-11-17 리뷰, 그런 앞 이름은 아직 찾지 못했다). 모은 동은 `REGION_AMBIGUOUS` 후보를 알리는 데만 쓰고 결과는 웹처럼 사람이 고른 동 하나로 내 사실이 어긋나지 않는다 ([기간 조회·지역 목록·학교 엔드포인트 메모](#기간-조회지역-목록학교-엔드포인트-메모), 2026-11-16 웹 캡처 `search/autocomplete/legalDivisions`, 실측: 성수동·충정로·부민동은 다음 쪽 없음, 을지로 7곳·종로 90곳은 다음 쪽 있음).
- **단지 이름이 하나로 정해지면 묻지 않기.** 웹 검색창은 단지 자동완성 후보를 10건씩 보여 주고 '더보기' 로 다음 쪽을 보며 사람이 고른다. jibsa 는 첫 쪽(`size=10&page=0`)만 받고 다음 쪽은 부르지 않는다. 그래서 후보 전체가 첫 쪽에 다 들어와 다음 쪽이 없을 때(`hasNextPage` 가 true 가 아니고 `totalCount` 가 받은 수보다 크지 않을 때)만, 그 후보 안에서 이름이 정확히 같은 단지가 하나이거나 후보가 하나뿐이면 그 단지로 정하고(이름이 다르면 `[참고]`), 그 밖에는 고르지 않고 `REGION_AMBIGUOUS` 다 (`pick_complex`). 정한 단지는 웹 검색창이 보여 줄 수 있는 후보 전부 안에서 같은 이름이 하나뿐인 것이라 웹에서 고를 수 있는 단지이고, 다음 쪽에 같은 이름이 더 있을 수 있으면 고르지 않아 사실이 어긋나지 않는다 ([기간 조회·지역 목록·학교 엔드포인트 메모](#기간-조회지역-목록학교-엔드포인트-메모), 2026-11-16 번들 `getAutoCompleteInfiniteQueryOptions`). 위치로 쓸 단지가 좌표 없는 단지로 정해지면 좌표 있는 다른 후보로 바꾸지 않고 `REGION_NOT_FOUND` 로 멈춘다 (바꾸면 사람이 고르지 않은 단지가 된다).

### 매물 (`search listings`·`listing`)

- **기본 매물 유형·거래 유형.** `-t`·`--trade` 를 주지 않으면 아파트·오피스텔·빌라·원룸·단독·다가구·전원주택·상가주택(`DEFAULT_SEARCH_PROPERTY_TYPES`)과 거래 네 가지(매매·전세·월세·단기임대)를 보낸다. 웹 지도 기본은 아파트·재건축·아파트분양권과 매매·전세다. 웹 필터에서 같은 유형·거래를 고르면 같은 목록이라 웹에서 고를 수 있는 기본값이다 (2026-11-16 번들 `DEFAULT_MAP_FILTER`).
- **웹 UI 에 없는 유형 고르기.** `-t 한옥`(C06)·`-t 고시원`(G01)은 웹 유형 목록에 없고, 웹 '건물' 은 건물·상가건물·숙박·기타(D03·D04·E01·Z00)를 한 번에 보내는데 jibsa 는 하나씩 고른다 (`SEARCH_CODES_BY_PROPERTY`). 서버가 받는 유형 조합이라 서버가 그 유형으로 거른 결과 그대로다 (2026-11-16 번들 `SUPPORTED_MAP_REAL_ESTATE_TYPES`).
- **확인일은 날짜로, 배지 글자는 방식·HUG 만.** 웹은 방식 배지(집주인·소유자·현장)와 'HUG 안심임대인' 배지 옆에 날짜 배지를 그린다. 목록은 `isAssociationArticle` 로 협회 매물이면 '등록'(노출 시작일 `exposureStartDate`), 아니면 '확인매물'(`articleConfirmDate`) 글자이고 상세는 다른 규칙이다. jibsa `badges` 는 방식 배지와 'HUG 안심임대인' 만 담고 날짜 글자 배지는 만들지 않는다. 확인일은 `confirmed_date`(`articleConfirmDate`, 목록·상세 모두 `YYYY-MM-DD`)로, 노출 시작일은 `registered_date` 으로 따로 낸다. 웹이 규칙을 나눠 그리는 같은 두 날짜를 글자 대신 날짜 필드로 둘 다 낸 것이라 사실이 어긋나지 않는다 (2026-11-17 번들 `PropertyBadgeList.tsx` 청크 1d-izunecww47, 상세 헤더 청크 0l4pkwg0qhg2t·`ArticleMain` 청크 c29992b834).
- **고시원 확인 배지.** 비주거 열 개 유형(D01·D02·E04·D03·D04·E01·E02·Z00·E03·F01)에 없는 유형(고시원 G01)의 집주인 배지는 웹 목록이 '집주인', 웹 상세는 글자 없는 배지다. jibsa 는 목록·상세 모두 '집주인' 이다. 같은 확인 방식 코드를 같은 이름표로 옮긴 것이다 (2026-11-17 `getOwnerLabel` 청크 0n-xsnd22pdxz).
- **난방을 둘로 나눠 내기.** 웹은 난방을 '개별난방 / 도시가스' 한 칸으로 보여 주고 jibsa 는 `heating`·`heating_fuel` 둘로 나눠 낸다. 같은 두 값이다. `HT000`·`HF000`(미노출)은 웹 코드상 '미노출' 글자가 그대로 나오는 식이지만 jibsa 는 값을 받지 못한 것으로 보고 `null` 이다 (2026-11-17 `getHeatingAndCoolingContents`).
- **단지형 빌라 주차는 두 칸을 한 글자로.** 웹은 단지형 빌라 주차를 '주차 8대 (세대당 0.5대)'(단지 대수)와 '주차가능여부 가능'(매물 값) 두 칸으로 보여 주고 jibsa `parking` 은 `가능 (단지 전체 8대, 세대당 0.5대)` 한 글자로 합쳐 낸다 (가능 여부를 모르면 `단지 전체 8대 (세대당 0.5대)`, 단지 정보를 받지 못했고 매물 대수가 0 이면 가능 여부만). 같은 두 값을 한 글자로 합친 것이다 (2026-11-17 청크 0l4pkwg0qhg2t `ArticleVillaBuildingInfo`, 매물 2661158391). 아파트·오피스텔 등 단지 유형은 웹처럼 단지 대수만 내고 가능 여부를 붙이지 않는다 (2026-11-17 사용자 결정).
- **`building_type` 은 건물 이름이 있어도 낸다.** 웹은 이 이름을 건물 이름이 없는 매물의 제목에만 쓰고 건물 이름이 있으면 보여 주지 않는다. jibsa 는 건물 이름이 있는 매물에도 낸다. 네이버가 준 코드를 네이버 이름표(상수 `ARTICLE_BUILDING_TYPE_MAP`)로 옮긴 값이라 사실이 어긋나지 않는다 (2026-11-17 `getArticleNameParts`).
- **표에 없는 코드.** 웹은 시설 이름 표에 없는 코드를 그리지 않고 (switch 의 default 가 null), 현관 구조도 이름표(`ARTICLE_ENTRANCE_TYPE`)에 없는 코드면 칸을 넣지 않는다 (`ArticleBuildingInfo`·`ArticleComplexInfo` 의 `ARTICLE_ENTRANCE_TYPE[코드]&&push(...)`). 난방은 이름표를 글자 틀에 바로 넣어 모르는 코드면 `undefined` 가 그려질 수 있다 (`getHeatingAndCoolingContents`). 방향·건물 세부 유형·관리비 포함 항목은 웹이 모르는 코드를 어떻게 그리는지 번들에서 확인하지 못했다. jibsa 는 시설은 `알 수 없는 시설 (코드)`, 방향·난방·난방 연료·현관 구조·건물 세부 유형은 `알 수 없는 값 (코드)`(방향 기준이 있으면 `알 수 없는 값 (코드, 거실 기준)`), 관리비 포함 항목은 `알 수 없는 항목 (코드)` 로 알린다. 응답에 있는 값을 말없이 빼거나 코드·`undefined` 로 내지 않고 못 읽었다고 밝히는 것이라 웹에 없는 결과를 만들지 않는다 (2026-11-17 시설 이름 switch 청크 2acxv7b6he8q3, 현관 구조 청크 0l4pkwg0qhg2t, 난방 청크 0n-xsnd22pdxz).
- **단지 세대당 주차 대수를 모르면 빼기.** 웹 `ComplexParkingInfo` 는 `parkingCountPerHousehold` 가 null 이어도 `?? 0` 으로 `(세대당 0대)` 를 그리고, 총 대수가 null 이면 숫자 없이 '대 (세대당 0대)' 를 그린다 (2026-11-25 청크 `00-c-lsvp5jax.js`, 코드로 읽음, 그런 매물을 화면에서 보지는 못함). jibsa 는 모름을 0 으로 쓰지 않아 세대당이 null 이면 세대당 부분을 빼고(`단지 전체 N대`), 총 대수를 모르면 단지 주차 값을 내지 않는다. 웹이 보여 주는 것을 덜 내는 것이라 사실이 어긋나지 않는다.
- **건축물대장 유형의 주차는 두 칸을 한 글자로.** 웹은 건축물대장 유형(원룸·빌라 등 15개)의 주차를 '주차가능여부'(매물 값)와 '주차 N대'(매물 대수, 0·없음이면 건축물대장 대수) 두 칸으로 보여 주고(대수 칸에는 `(세대당 N대)` 가 붙는다) jibsa `parking` 은 `가능 (총 8대, 세대당 0.5대)` 한 글자로 합쳐 낸다 (가능 여부를 모르면 `총 8대 (세대당 0.5대)`). 같은 값들을 한 글자로 합친 것이라 사실이 어긋나지 않는다 (2026-11-18 청크 0l4pkwg0qhg2t `ArticleBuildingInfo`, 매물 2661724695·2661862868). 단지형 빌라의 같은 처리는 위 항목을 본다.
- **단지형 빌라의 현관 구조.** 웹 상세는 유형마다 다른 칸 묶음을 그린다. 건축물대장 유형(빌라·원룸 등, 단지 여부와 상관없이)은 `ArticleBuildingInfo`, 단지 유형(아파트·오피스텔 등)은 `ArticleComplexInfo` 가 그린다. 건축물대장 유형은 `facilityInfo.entranceType` 이 있을 때만 '현관구조' 칸을 넣고, 단지 유형은 `facilityInfo.entranceType || complexPyeong.entranceType`(번들 `j=I?.entranceType||S`, S 는 `/complex/pyeong` 값)로 칸을 넣는다. 단지형 빌라(A05·A06·A07)는 `ArticleVillaBuildingInfo` 가 그리는데 여기에는 현관구조 칸이 없어, 응답에 `entranceType` 이 와도 화면에 보이지 않는다. jibsa 는 단지형 빌라에도 `entrance` 를 낸다. 웹이 받는 같은 상세 응답에 네이버가 준 값을 같은 이름표로 옮긴 것이라 사실이 어긋나지 않는다 (2026-11-17 청크 0l4pkwg0qhg2t, 화면은 매물 2662400565 A06 `'10'` → jibsa `계단식`, 웹은 칸 없음). 단지가 아닌 매물에도 `entranceType` 이 오므로(빌라 2661884425) 값이 없으면 해당 없음이 아니라 모름(`null`)이다.
- **단지 번호가 없는 단지 유형.** 네이버 웹은 `ArticleComplexInfo` 를 `isValidComplexNumberSchema(단지 번호) && isComplexType` 일 때만 붙이고 '주차가능여부'·'총주차대수' 칸은 상가·사무실·빌라·원룸 등 다른 유형 칸 목록에만 있어, 단지 번호가 없는 아파트·오피스텔 매물에는 난방·현관·주차 칸이 없다 (2026-11-18 번들 청크 0l4pkwg0qhg2t). jibsa 는 이런 매물에 같은 상세 응답의 `facilityInfo` 값을 같은 이름표로 낸다 (`heating`·`heating_fuel`·`entrance`, `parking` 은 `가능 (총 N대)` 꼴, `approved_date` 은 매물 날짜). 웹이 받는 같은 응답에 네이버가 준 값을 옮긴 것이라 사실이 어긋나지 않는다 (단지형 빌라의 현관 구조와 같다). 실례 매물은 찾지 않았고 코드로 확인했다.
- **면적 조건은 전용 기준.** `--area-basis` 기본이 전용이라 면적 조건을 주면 `filtersExclusiveSpace=true` 를 보낸다. 웹 기본은 '전용면적만 보기' 꺼짐(공급, 오피스텔은 계약 면적)이다. 결과의 `area_m2` 가 전용이라 맞췄고, 웹에서 '전용면적만 보기' 를 켜면 같은 결과다 (2026-11-16 번들 `DEFAULT_MAP_FILTER`·`convertMapFilterToParams`).
- **반경 검색.** 웹 지도 목록은 화면 사각형과 그때 줌을 `boundedArticles` 에 보낸다. jibsa 는 반경을 감싼 정사각형(`bounding_box`)과 반경에 맞춘 줌 14~16(`bounded_precision`)으로 같은 `boundedArticles` 를 받아, 응답 좌표로 반경 밖·좌표 모름 매물만 빼고 `[제외]` 로 알린다. 서버가 받는 사각형·줌 조합의 목록에서 반경 안만 남긴 부분집합이고 순서는 서버 순서 그대로다. 동 이름에 `--radius` 를 주면 동 경계 대신 동 중심 반경이다 ([페이지네이션과 조건 처리](#페이지네이션과-조건-처리), 2026-11-16 번들 대조).
- **구·군·구 없는 시 이름은 경계 전체, 구 있는 시 이름은 반경.** `search listings`·`search complexes`·`search redevelopment` 에 구·군·구 없는 시 이름을 주고 `--radius` 가 없으면 그 경계 안 전체(`boundary`)를 시·군·구 단위(`legalDivisionType` GUN)로 받아 서버가 준 순서 그대로 낸다. 같은 경계 목록 API 를 동 대신 서버가 받는 시·군·구 단위로 부른 것이고 거른 결과를 다시 거르거나 합치지 않아 웹에 없는 결과를 만들지 않는다 (2026-11-18 성동구 실측, [시·군·구 경계 검색 메모](#시군구-경계-검색-메모). 웹이 구 단위 경계 목록을 쓰는지는 [아직 가리지 못한 것](#아직-가리지-못한-것)). 구 없는 시(구리시)도 같다 (시 코드 + GUN 이 200, 구리시 매물 180건, 2026-11-18 실측). 구 있는 시(성남시)는 시 코드 + GUN 이 오류 없이 0건이라 경계로 찾을 수 없어 중심 반경으로 찾는다 (위 반경 검색 항목과 같은 방식이라 사실이 어긋나지 않는다). 구가 있는지는 시·도 아래 시·군·구 목록을 1회 더 받아 가린다 (시 이름일 때만, 웹에 없는 판단이지만 결과를 거르지 않고 경계를 고르는 데만 쓴다). 구가 있는 시는 `[범위]` 안내가 구 이름(`성남시 분당구`, 웹 경기도 목록의 이름과 같은 꼴)으로 찾으라고 알린다. 구 확인 조회가 실패하면 시 전체로 찾지 않고 중심 반경으로 찾으며 `[실패]` 로 알린다 (같은 반경 검색이다). 시·군·구가 하나뿐인 시·도(세종) 이름도 `--radius` 가 없으면 그 시·군·구 경계로 찾는다 (시·도 이름일 때만 시·도 아래 시·군·구 목록 1회, 2026-11-19 실측, [시·군·구 경계 검색 메모](#시군구-경계-검색-메모)).
- **재개발(F01) 전월세의 취득세 (넣지 않음).** 웹은 재개발 매물이면 전세·월세에도 취득세 칸을 그린다 (`getArticleTaxExposeInfo`). jibsa `listing` 은 세금을 매매에만 붙인다. 2026-11-18 한남·노량진·성수·장위·성동구에 F01 전월세 매물이 하나도 없어 `article/tax` 가 전월세에 값을 주는지 확인할 수 없었고, 웹에 있는 값을 덜 내는 것이라 사실이 어긋나지 않는다. 매물이 나오면 실측해 넣을지 정한다.
- **한 번에 최대 120건과 `--next`.** 웹은 30건씩(`ARTICLE_PAGINATION_SIZE`) 무한 스크롤하며 seed·lastInfo 를 다음 쪽에 넘긴다. jibsa 는 같은 커서로 `--limit`(최대 `MAX_LIST_LIMIT` 120)까지 차례로 받고, 지역 검색은 그 커서를 `--next` 에 담는다. 같은 쪽을 차례로 받은 것이라 매물·순서는 웹 스크롤과 같다 (`search listings --complex`·`--redevelopment` 도 같다, 2026-11-16 번들 `ARTICLE_PAGINATION_SIZE`·`withSeed`).
- **가격 조건만 주면 거래 유형 좁히기.** `--trade` 없이 월세 조건만 주면 월세·단기임대, 매매가만 주면 매매, 보증금만 주면 전세·월세·단기임대로 좁히고 `[거래]` 로 알린다 (`infer_trade_types`). 웹은 고른 거래 유형에 맞는 가격 필터만 보여 주고 보낸다. 좁힌 거래 유형과 가격 조건은 웹에서도 고를 수 있는 조합이다 (2026-11-16 번들 `getPriceFilterVisibility`).
- **`area_pyeong` 자릿수.** 웹은 평을 소수 둘째 자리(`sizeToPyeong(size, 2)`, 23.23㎡ → 7.03평)로, jibsa 는 `m2_to_pyeong` 으로 소수 첫째 자리(7.0)로 낸다. `area_m2` 를 그대로 주고 덧붙인 환산이고, 평·면적·거리는 줄여 내도 된다고 정했다 (#259) (2026-11-16 번들 `Ee`).
- **입주 시기 표기.** 웹은 '2026년 12월 01일 이내입주'·'… 이후입주' 로, jibsa `move_in` 은 `2026-12-01 이내`·`2026-12-01 이후` 로 낸다 (`MOVING_IN_BOUND_LABELS`). 같은 코드(MV002·MV003)와 날짜를 날짜 꼴만 바꿔 쓴 것이라 뜻이 같다 (2026-11-16 번들 `getMovingInDateLabel`·`ARTICLE_MOVING_IN_TYPE`).
- **옛 형식 관리비는 필요할 때만 묻기.** 웹 매물 상세는 `article/maintenanceFee` 와 `article/oldMaintenanceFee` 를 늘 함께 부르고, jibsa 는 앞의 것으로 관리비 칸을 못 만들 때만 뒤의 것을 부른다 (`get_listing`, 요청을 아낀다). 웹도 그때만 뒤의 값을 그려, 같은 매물에 웹이 보여 주는 관리비와 같다 (2026-11-24 번들 `ArticlePriceInfo`·상가 2662726134 실측).
- **주변 개발 예정을 늘 붙이고 빈 칸은 `[]`.** 웹 상세 `ArticleMain`(청크 c29992b834_0l4pkwg0qhg2t)은 매물 유형 조건 없이 `development/article` 을 부르고 예정 역·개발 지구 두 목록이 모두 비면 칸을 그리지 않는다. jibsa `nearby_development` 는 같은 요청 값을 유형과 상관없이 모든 상세에 붙이고, 빈 목록은 칸을 그리지 않는 대신 `rail`·`area` 의 `[]` 로 낸다 (키를 지우면 '근처에 없음' 과 '조회 실패(`null`)' 를 가를 수 없다). 역·노선·사업 종류는 서버 글자를 가공하지 않고(역 이름에 `(2027년예정)` 이 붙어 온다), `step` 은 웹이 '사업 단계 {step}' 으로 값을 그대로 그려 가공하지 않는다. 사업 기간이 없는 지구는 웹이 그 줄을 그리지 않아 `project_period` 키를 뺀다 (2026-11-18 실측·번들 대조).
- **묶음 호가 범위를 칸별로 갈라 내기.** 웹 목록 카드(`ArticleCard`, 청크 `1365p71-zqkv3`)는 묶음 매물이면 대표 매물 가격 대신 `getPriceRangeLabel`(청크 `0000j9vpg5ad7`)로 `representativePriceInfo` 의 두 끝을 그린다. 매매·전세는 '24억 ~ 35억'(두 끝이 같으면 하나), 월세·단기임대는 보증금과 월세를 짝으로 '8억/220 ~ 9억/180' 이다 (2026-11-25 헬리오시티 단지 목록 화면 30개, 2663960110). jibsa 는 대표 매물 가격을 그대로 내고 범위를 `asking_range`(`{lowest, highest}`, 두 끝은 그 매물의 금액 칸)로 낸다. 월세·단기임대는 보증금·월세를 한 짝으로 담는다. 같은 응답의 두 끝을 그대로 옮긴 것이라 사실은 어긋나지 않고, 월세 두 끝이 보증금 끝 매물의 짝이라는 것은 `asking_range` 설명에 적었다 (범위 객체의 모양은 [칸 이름 규칙](../output-contract.md#칸-이름-규칙), 2026-11-25 사용자 결정).

### 단지 (`search complexes`·`complex`·`real-price`·`market-price`·`school`)

- **`search complexes` 기본 조건.** jibsa 는 아파트(A01)만, 거래 네 가지, 매물 있는 단지만 보낸다. 웹 기본은 아파트·재건축·아파트분양권, 매매·전세, '매물 있는 단지만 보기' 꺼짐이다. 웹 필터로 같은 조건을 만들 수 있다. 기본 `-t 아파트` 에는 재건축(A04) 단지(대치동 은마 등)가 들지 않는다 (2026-11-16). `-t 재건축`(A04)·`-t 분양권`(B01)·`-t 오피스텔분양권`(B02)으로 웹 기본 유형과 같은 단지를 고를 수 있다 (2026-11-18 실측: 재건축 대치동 5곳, 분양권 둔촌동 1곳, 오피스텔분양권은 넷 지역 모두 0곳이고 서버 답 그대로 낸다).
- **`search complexes` 반경.** 반경을 감싼 사각형과 반경에 맞춘 줌으로 `boundedComplexes` 를 부르고 응답 좌표로 반경 밖을 뺀다. `total` 은 사각형 기준이고 `notes` 로 알린다. 순서는 서버 그대로라 위 매물 반경 검색과 같은 부분집합이다 (2026-11-16).
- **세대수·연식 조건.** 웹 입력 상한은 세대수 4000·사용승인 25년(`MAP_FILTER_INPUT_MAX`)이고 늘 `{min: 0, max}` 로 보낸다. jibsa 는 상한 밖 값도 받고 준 쪽만 보낸다. 서버가 받는 조합이라 서버가 거른 결과 그대로다 (2026-11-16).
- **출력 보강.** `distance_km` 와 주소 정규화('서울시' → '서울특별시'). 단지·순서·수를 바꾸지 않는 덧붙임이다 (2026-11-16).
- **`real-price` 한 쪽 10건.** 웹은 최근 3건·요약 5건·전체 목록 100건(`TRANSACTION_PRICE_PAGE_PAGINATION_SIZE`)씩 보여 준다. jibsa 는 쪽마다 10건(`--pages` 최대 10)이다. 순서가 같아 앞쪽 N건이 웹과 같다 (2026-11-16).
- **빌라 단지 `real-price --period`.** 웹 빌라 실거래 목록에는 기간 조건이 없다. jibsa 는 최근 순 페이지를 받아 시작일 전 거래를 뺀다. 계약일을 모르는(`trade_date` 가 `null`) 거래는 기간 안인지 알 수 없어 빼지 않고 남기며, 쪽 넘김을 멈추는 판정(시작일 전 거래가 나왔는가)에는 세지 않아 모르는 날짜 하나 때문에 다음 쪽의 기간 안 거래를 놓치지 않는다. 한 쪽이 모두 계약일을 모르면 멈추지 않고 쪽 수 상한(`MAX_VILLA_PERIOD_PAGES`)까지 받아 `[일부]` 로 알린다. 받은 목록의 부분집합이라 웹에 없는 조건으로 좁히기다 ([기간 조회·지역 목록·학교 엔드포인트 메모](#기간-조회지역-목록학교-엔드포인트-메모), 2026-11-16).
- **탭을 한 번에.** `complex --pyeong` 은 실거래 요약을 매매·전세 둘 다(웹은 거래 탭 하나씩), 기관 시세 세 곳을 모두(웹은 기관 하나씩) 준다. 웹이 탭마다 보여 주는 값을 함께 낸 것이다 (2026-11-16).
- **평당가를 매매·전세 한 번에.** `complex --pyeong` 은 `asking_price_per_pyeong` 에 매매·전세 평당 호가와 동·구·시 평균을 둘 다 준다 (웹 `ComplexAreaPrice` 는 거래 탭마다 하나씩). 웹이 탭마다 같은 요청(`complex/pyeongPrice/pyeongType`)으로 받는 값을 함께 낸 것이다 (2026-11-18, 청크 b042d8aace_1okty1145x932).
- **평당가를 단지 유형 5종만 묻기.** 단지형 빌라(A05~A07) 등 5종(A01·A02·A04·B01·B02) 밖의 단지에는 평당가를 묻지 않아 키가 없다. 웹이 빌라에서 평당가 박스를 그리는지 확인하지 못해 묻지 않는 것이고, 웹에 있는데 jibsa 에 없는 쪽이라 사실이 어긋나지 않는다 (2026-11-18, 같은 청크).
- **평형 묶음을 `--pyeong` 과 상관없이 늘 붙이기.** `complex` 는 `--pyeong` 을 주든 말든 `pyeong_groups` 를 준다 (웹은 단지형 빌라가 아닐 때만 `complex/pyeongGroups` 를 부른다). 웹이 단지형 빌라가 아닐 때 부르는 같은 요청의 값 그대로이고 빌라 단지는 묻지 않아 웹에 없는 값을 만들지 않는다 (2026-11-18 실측).
- **`real-price --group` 은 웹 '유사면적 묶기' 와 같은 요청.** 웹은 이 묶기가 기본으로 꺼져 있고 jibsa 는 `--group` 을 줄 때만 쓴다. 같은 `complex/pyeong/realPrice/group` 을 웹과 같게 `[대표 번호, …나머지 번호순]` 으로 불러 서버가 준 묶음 거래 그대로 내고, 거래마다 평형을 알 수 없다는 안내(`[참고]`)를 붙인다. 쪽 크기는 위 '`real-price` 한 쪽 10건' 항목과 같다 (2026-11-18 실측).
- **학교 배정 단지 쪽 크기 20.** 웹 학교 상세는 배정 단지를 처음 3곳 보여 주고 '더보기' 로 전체 목록(쪽 크기 20)을 본다. `school --complexes` 는 같은 `education/complex/pages` 를 쪽 크기 20 으로 `--limit`(기본 20, 최대 100) 곳까지 이어 받는다. 웹 전체 목록과 같은 쪽을 차례로 받은 것이고 총수는 첫 쪽의 `totalCount` 만 믿는다 (끝 쪽 이후는 0). 정렬은 웹 enum 두 값(`DISTANCE`·`HOUSEHOLD_COUNT`)뿐이고, 단지 좌표·주소·사진은 내지 않으며, 단지마다의 배정 동 판정은 `school --complex` 와 같다 (위 `school` 배정 동 표기 항목) (2026-11-18 실측).
- **빌라 단지 `real-price` 의 두 칸 (평당 실거래가·주변 실거래).** 웹 빌라 단지 실거래 탭(`ComplexVillaTransactionTab`)이 같은 두 요청(`complex/villa/realPricePyeongPrice`·`complex/villa/realPriceAround`)으로 받는 값을 `price_per_pyeong_trades`·`nearby_trades` 로 낸다 (2026-11-19, 청크 b042d8aace_1okty1145x932·26e0315e74_3kmdmwb6eaqal). 평당 실거래가는 웹처럼 시작일을 오늘의 5년 전으로 고정하고 매매·전세만 낸다 (월세는 키 없음). 아래가 웹과 다르다:
  - `--around-km`(0.1~1.0)은 웹에 없는 옵션이다. 웹은 작은 지도 크기 범위만 보내지만 서버는 지도 범위 네 값을 받아, 같은 요청에 범위만 넓힌 것이다 (`box_around` 사각형, 줌은 웹과 같은 16). 서버가 거른 거래를 jibsa 가 다시 거르지 않는다. 기본 범위는 웹 작은 지도(388×200px)를 2026-11-19 에 잰 축척으로 단지 위도에서 계산해 웹과 같은 크기다 (서울 37.47° 남북 188m·동서 365m, 부산 35.1° 194m·377m, 제주 33.5° 198m·384m). 웹이 지도 크기를 바꾸면 기본값이 달라질 수 있다 (`AROUND_WEB_MAP_WIDTH_PX`·`AROUND_WEB_MAP_HEIGHT_PX`·`AROUND_WEB_DEGREES_PER_PX`, `get_real_prices`).
  - 웹 표는 처음 5건만 보이고 '더보기' 로 나머지를 연다. jibsa 는 서버가 준 10건을 한 번에 낸다. 정렬(계약일 → 준공연도 → 전용면적 내림차순)이 웹과 같아 앞 5건이 웹 표와 같다. 10건에 닿으면 `[일부]` 로 알린다 (고르는 기준은 확인하지 못했다).
  - 웹이 보여 주지 않는 층(웹 표는 '-')과 갱신 여부(`renewal_right`, 계약갱신요구권을 쓴 거래만)를 더 낸다. 같은 응답의 값을 옮긴 것이다. 건물 좌표로 `distance_m`·`same_complex` 도 덧붙이는데 서버가 준 거래의 순서·수를 바꾸지 않는 덧붙임이다. `height_km`·`width_km` 는 보낸 범위의 길이다.
  - jibsa 는 평균·합계를 내지 않는다. 서버가 준 거래를 더하거나 다시 세우는 계산은 웹에 없는 결과를 만들기 때문이다.
- **`complex --pyeong` 의 3년 평균 실거래가 (그대로 두기로 함).** `trade_summary.*.average_manwon` 은 웹도 같은 요청(`complex/pyeong/realPrice/summary`, 시작일 3년 전)으로 받지만, 웹 화면(`ComplexTransactionPriceSummary`)은 3년 최고·최저만 그리고 평균은 '3개월 평균 실거래' 에만 쓴다 (받은 번들 386개 중 평균값을 쓰는 곳은 그 화면과 로그인이 필요한 우리집 시세 둘뿐). 같은 응답에 서버가 준 값이라 그대로 낸다 (2026-11-16 번들 chunk `1un70f33iojlw`).
- **`complex --pyeong` 의 3개월 평균 실거래.** 웹은 3개월 평균을 매물 상세(`RecentTransaction`)에만 보여 주는데 jibsa 는 `trade_summary` 의 `recent_3m_average_manwon` 으로 낸다. 같은 요약 요청(`complex/pyeong/realPrice/summary`)을 3개월 전 시작일로 부른 서버 값 그대로라 웹에 없는 결과를 만들지 않는다 ([기간 조회·지역 목록·학교 엔드포인트 메모](#기간-조회지역-목록학교-엔드포인트-메모), 2026-11-18).
- **실거래 요약의 5년 대체를 `start_date` 로 밝히기.** 웹 단지 화면(`ComplexTransactionPriceSummary`)은 거래 유형마다 3년 요약이 비면 5년으로 다시 받아 그리고 5년을 썼다는 말은 따로 하지 않는다. jibsa 도 같은 순서로 받고 5년을 쓴 유형에만 `start_date` 를 붙인다. 같은 요청의 같은 값에 기간 정보를 더한 것이다. 3년 요약 조회가 실패한 유형은 5년으로 바꾸지 않고 `null`(모름)로 둔다 (실패는 거래 없음이 아니라 모르는 값이라 다른 기간의 값을 대신 내지 않는다) (2026-11-18, 청크 1un70f33iojlw).
- **월세·단기임대 호가를 짝 두 개로.** 웹 단지 호가 범위는 '보증금/월세 ~ 보증금/월세' 글자 하나로 보여 주고 jibsa `asking_ranges` 의 `wolse`·`short_term` 은 `{lowest, highest}` 각 `{deposit_manwon, rent_manwon}` 짝 두 개로 낸다. 같은 단지 가격 응답(`rentMonthly*`·`rentShort*`)의 네 값을 글자 대신 필드로 옮긴 것이다. 두 끝은 월세 최저·최고가 아니라 가격 낮은 순 첫 매물과 높은 순 첫 매물의 짝이라 월세가 거꾸로일 수 있다 (헬리오시티 111515 5000/420 ~ 700000/240, 2026-11-18). 네 값이 모두 0 이면 `null` 이다. 월세 0원 매물은 없어 서버가 0 으로 비운 것으로 본다. 그래서 한 짝의 월세만 0 이면 그 월세만 `null`, 보증금·월세가 모두 0 이면 그 짝은 두 값 모두 `null` 이고, 월세가 있는 짝의 보증금 0 은 그대로 낸다.
- **`--period` 선택지 3개월·1년·3년·5년.** 웹은 3개월·3년·5년이고 jibsa 가 1년을 더했다. 같은 기간 조회에 시작일만 다른 값을 보낸 것이라 서버가 거른 결과 그대로다. 7년은 서버가 받지만 웹 선택지에 없어 넣지 않았다 (2026-11-18 사용자 결정).
- **`area_pyeong` 자릿수.** 웹은 전용면적을 3.3058 로 나눠 정수(84.99㎡ → 26평), jibsa 는 `m2_to_pyeong` 으로 소수 첫째 자리(25.7)다. 같은 전용면적의 덧붙인 환산이다 (#259, 2026-11-16).
- **`school` 배정 동 표기.** jibsa 는 '202동~206동'·'전체 동', 웹은 '202~206동'·'전체동' 이다. 동 묶음은 같다 (2026-11-16).
- **재건축 단계.** 웹은 현재 단계와 상세 모달을 보여 주고, jibsa `reconstruction.steps` 는 날짜가 있는 단계만 낸다. 단계 이름·날짜는 같은 응답 그대로고 읽지 못한 날짜는 `null` 이고 `[참고]` 로 알린다 ([재개발·추이 엔드포인트 메모](#재개발추이-엔드포인트-메모), 2026-11-16).
- **`real-price --period` 의 단지 유형 값.** 웹은 단지 유형을 보내고 jibsa 는 늘 A01 을 보낸다. 오피스텔 105544 월세 5년을 A01·A02 로 각각 물어 둘 다 76건·같은 순서였다 (2026-11-16).
- **`market-price` 의 단지 유형 값.** 웹 시세 차트는 단지 유형을 보내고 매매/전세 흐름 차트는 보내지 않는다. jibsa 는 보내지 않는다. 값은 같다 (1년 51·51·52개 점 모두 일치, 2026-11-16).
- **`complex --pyeong` 여러 개·`--dong` 집계.** `article/stats` 에 `pyeongTypes[]`·`dongNumbers[]` 를 함께 보낸다. 웹 관심단지 필터가 같은 조합으로 부르는, 서버가 받는 조합이다 (2026-11-16).

### 지역·재개발·동향 (`regions`·`search redevelopment`·`redevelopment`·`trend`)

- **재개발 구역 이름을 하나로 정해지면 묻지 않기.** 웹 검색창은 재개발 구역 자동완성을 `size` 없이(서버 기본 5건) 보여 주고 '더보기' 로 다음 쪽을 보며 사람이 고른다. `redevelopment`·`search listings --redevelopment` 는 구역 이름을 받아 `size=10&page=0` 한 쪽만 받고 다음 쪽은 부르지 않는다 (단지 이름과 같다). 후보 전체가 첫 쪽에 다 들어와 다음 쪽이 없을 때(`hasNextPage` 가 true 가 아니고 `totalCount` 가 받은 수보다 크지 않을 때)만 이름이 정확히 같은 구역이 하나이거나 후보가 하나뿐일 때 그 구역으로 정하고(이름이 다르면 `[참고]`), 그 밖에는 고르지 않고 `REGION_AMBIGUOUS` 로 후보와 구역 번호를 알린다. 네이버는 한 사업 구역을 법정동마다 따로 등록해 같은 이름이 번호를 달리해 여럿 온다 (한남제3재정비촉진구역: 한남동 10017678·보광동 1000208, 2026-11-18 실측). 사람이 고르는 웹처럼 하나를 임의로 고르지 않고 번호로 다시 부르게 하므로 웹에서 고를 수 있는 구역만 쓰고 사실이 어긋나지 않는다 (`resolve_redevelopment_number`).
- **`search redevelopment` 기본 정렬 매물수순 (그대로 두기로 함).** 웹 기본은 세대수순(`DEFAULT_REDEVELOPMENT_LIST_SORT_TYPE`)이다. 웹에서 정렬을 매물수순으로 바꾸면 같은 목록이라 웹에서 고를 수 있는 기본값이다 (2026-11-16 번들 chunk `2yfs4ldfbaxvg`).
- **`search redevelopment` 기본 거래 유형 (그대로 두기로 함).** `--trade` 를 주지 않으면 매매·전세·월세(A1·B1·B2, `NaverArticleFilterModel` 기본값)를 보낸다. 웹 기본은 매매·전세(A1·B1)다. 거래 유형은 구역을 거르지 않고 매물수순 순서에만 영향을 주며, 웹 지도 필터에서 월세를 더 고르면 같은 요청이다. 순서가 갈리는 사례는 재현하지 못했다 (본 구역 14곳에 월세 매물이 없었다, 2026-11-16).
- **`search redevelopment --trade`.** 서버는 거래 유형으로 구역을 거르지 않는다 (매매·전세로 불러도 그 거래 0건 구역이 온다). jibsa 는 `listing_counts` 로 그 구역을 빼고 `notes` 로 알린다. 받은 구역의 부분집합이라 웹에 없는 조건으로 좁히기다 ([재개발·추이 엔드포인트 메모](#재개발추이-엔드포인트-메모), 2026-11-16).
- **`search redevelopment` 반경.** 웹은 지도 화면 범위와 지도 줌을 보내고 목록은 줌 13 이상에서만 보인다. jibsa 는 반경을 감싼 사각형에 줌 14(`REDEVELOPMENT_PRECISION`)를 고정해 보내고 마커 좌표로 반경 밖·좌표 없는 구역을 빼 `notes` 로 알린다. 서버가 받는 범위·줌의 목록에서 반경 안만 남긴 것이다 (2026-11-16).
- **`search redevelopment --limit` 최대 120.** 웹은 30곳씩 무한 스크롤이다. 같은 목록을 차례로 받는다 (2026-11-16).
- **`trend --period` 기본 1년 (그대로 두기로 함).** 웹 홈 동향 위젯 기본은 5년(`HOME_APARTMENT_ARTICLE_TREND_SELECTED_PERIOD`)이다. 웹에서 1년을 고르면 같은 값이라 웹에서 고를 수 있는 기본값이다 (1년 53주 × 3종 값이 웹 5년 응답의 같은 주와 모두 일치, 2026-11-16 번들 chunk `2rlr6s-93gudx`).
- **`trend` 동·읍·면 단위.** 웹 동향 위젯은 시·도 → 시·군·구 두 단계뿐이다. jibsa 는 동 코드, 역·주소·단지·좌표 자리의 법정동, 리가 속한 읍·면 추이도 준다. 서버가 받는 조합이고 값은 서버 그대로다 (2026-11-16). 웹 홈 위젯의 시·도 '전체'(`ALL_LEGAL_DIVISION_CODE` 0000000000, 청크 2d10adcfe2_2rlr6s-93gudx)는 `trend 전국` 으로 같은 요청을 한다 (2026-11-18).
- **`trend` 구 있는 시 이름은 막는다.** 웹 동향 위젯의 시·군·구 목록에는 '성남시' 가 없고 '성남시 분당구' 처럼 구가 펼쳐 나온다 (`regions 성남시` 항목). `trend 성남시` 는 서버가 받지만 모든 값이 0 이라(2026-11-18 실측, [시·군·구 경계 검색 메모](#시군구-경계-검색-메모)) jibsa 는 0 을 내지 않고 `REGION_AMBIGUOUS` 로 구 이름을 알린다. 웹에서 고를 수 있는 구 단위 추이만 내므로 웹에 없는 결과를 만들지 않는다.
- **`regions 세종`.** 웹은 세종시 → 시·군·구 '세종시' 하나 → 읍·면·동 순서다. jibsa 는 읍·면·동을 바로 주고 `notes` 로 알린다. 한 단계를 건너뛴 같은 목록이다 ([기간 조회·지역 목록·학교 엔드포인트 메모](#기간-조회지역-목록학교-엔드포인트-메모), 2026-11-16).
- **`regions 성남시`(구가 있는 시).** 웹 시·도 선택에는 '성남시' 단계가 없고 경기도 목록에 '성남시 분당구' 처럼 펼쳐 나온다. jibsa 는 웹이 경기도를 고를 때와 같은 요청(시·도 코드 + GUN)으로 받은 시·도 목록에서 '성남시 ' 로 시작하는 이름만 남긴다. 코드·이름·좌표는 웹 경기도 목록과 같다 (2026-11-16).
- **`regions` 시·도 이름.** 웹은 줄임 이름(서울시), jibsa 는 정식 이름(서울특별시)이다. 같은 응답이라 코드·순서는 같다 (2026-11-16).
- **`redevelopment` 용적률·건폐율.** 웹은 `Math.floor` 로 정수만, jibsa 는 응답 원값이다. 같은 값을 자르지 않고 낸 것이다 (2026-11-16).

사례를 찾지 못해 웹과 같은지 가리지 못했다 (2026-11-16 대조). 다음 대조 때 실제 응답으로 본다.
