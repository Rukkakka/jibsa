# 직방 개발 가이드

[CLI 사용법](../../zigbang.md) · [개발 환경·검증](../README.md) · [공통 아키텍처](../architecture.md) · [provider 작성 규약](../provider-conventions.md) · [출력 계약](../output-contract.md) · [코드 형식](../code-style.md)

공통 규약에 없는, 직방에만 있는 구현과 예외를 적는다.

## 명령과 요청 흐름

| CLI 명령 | 주요 경로 | service 모듈 |
| --- | --- | --- |
| `search locations` | v2/search → 지역·오피스텔·아파트 후보 | `region` (단지 후보는 `complex.detail`) |
| `search complexes` | 지역 검색(역·학교·동·구) → apt/danjis/ids → apt/subways/{id}·apt/schools/{학교코드}(덤, 역·학교) → apt/danjis/details(덤, 15곳씩) | `complex.search`(장소 해석은 `region`) |
| `search listings room` | 지역/역 해석 → 유형별 핀·섹션(지도 칸 또는 역 목록) → 섹션 순서로 잇기 → items/list | `room.search` |
| `search listings apt` | 동·구: 지역 목록 / 역·학교·좌표: locals/polygon(정밀도 10) → 그 동 지역 목록 | `apt` (지역 해석 `resolve_apt_region`·`local_code_of` 는 `region`) |
| `search listings store` | 상권(원) 또는 지역(법정동 코드) 위치 목록 → 요약 → 로컬 가격 필터 | `store` |
| `search listings stay` | 이름: 검색 API(서버 정렬) / 좌표·반경·동 경계: 지도 핀 → 웹 지도 정렬 → by-ids | `stay.search` |
| `complex` | apt-/officetel- ID 분기 → 단지·건물 정보 | `complex.detail` |
| `search listings --complex` | 아파트 catalog / 오피스텔 건물 핀·요약 | `complex.detail` |
| `real-price` | 아파트 실거래 → 거래 유형 필터·페이지 조회 | `real_price` |
| `listing` | ID 접두사 분기 → 주거·상가·단기임대·제휴 상세 (주거는 건물 학군·v2/bls/{pnu}/rts 덤을 더한다) | `listing` (입구 모듈, ID 분기. 주거 상세가 아파트 매물이라고 알리면 `apt` 로 넘긴다) → `room.detail`(주거)·`apt`(아파트·제휴)·`store`·`stay.detail`(단기임대) |
| `catalog` | 묶음 ID → item-catalogs/{areaHoId} 20건씩 → 아파트 상세 변환 | `apt` |

공용 심볼은 `service/common/` 패키지에 있다. `common.base`(지역·URL·ID·안내·상세 결과 모델·단지 조회), `common.room`(원룸·빌라·오피스텔 목록 공용), `common.apt`(아파트 목록·묶음 공용)으로 나뉘고 `__init__.py` 는 안내만 둔다. 기능 폴더(`room/`·`stay/`·`complex/`) 안은 `search`·`detail` 로 나뉘고, 둘이 같이 쓰는 것은 그 폴더의 `base` 에 둔다 (단기임대 목록 줄이 `stay.base`). 나눈 기준과 import 방향은 [service 모듈을 나누는 기준](../provider-conventions.md#service-모듈을-나누는-기준)이다.

## 소스 고유 구현

### 인증·헤더

- 토큰 없이 부른다. 로그인하지 않은 웹은 목록·상세 API 에 `Authorization` 을 붙이지 않고 손님 토큰(`account.zigbang.com/v2/unauth/token`)도 받지 않는다 (2026-11-12 웹 화면 8개 요청 137건 실측. 손님 토큰은 휴대폰 인증에서만 쓴다). 예전에는 첫 요청 때 손님 토큰을 받아 모든 요청에 붙였는데(`ZigbangGuestAuth`), 2026-10-11 에도 토큰 없이 모두 200 이었고 같은 날 토큰 없이 매일 API 감시 22개 명령이 모두 정상이라 뺐다.
- 헤더는 웹 axios 인스턴스가 API 묶음마다 붙이는 것과 같다 (2026-11-12 실측·번들). 모든 요청에 `Accept: application/json, text/plain, */*`(`base_header`)를 붙이고, 묶음마다 더 붙인다:
  - 옛 API(`/v2/search`·`/v2/local/polygon`·`/v2/bls/{pnu}/rts`): 더 붙이지 않는다 (웹의 옛 `APIS` 클래스. 건물 실거래 `/v2/bls/{pnu}/rts` 는 2026-11-19 웹 캡처에서 `Accept` 하나만 붙었다).
  - 주거·상가(`/house/property`·`/v3/items`·`/v2/store`): `x-zigbang-platform: www` (`PLATFORM_HEADERS`). 없으면 일부 상세가 404 를 준다.
  - 아파트(`/apt`): 위에 `sdk-version: 0.128.0` (`APT_HEADERS`). 단기임대(`stay-apis`): 위에 `sdk-version: zigbang-stay-sdk:0.12.0` (`STAY_HEADERS`, 2026-11-18 에 0.11.0 에서 올랐다). SDK 버전이라 직방 웹이 새로 배포되면 바뀐다. 서버는 이 값을 보지 않아(2026-11-12 실측: 지금 값·옛 값·헤더 없음이 같은 결과) 명령 감시로는 알 수 없어, 매주 월요일 API 감시가 첫 화면이 불러오는 `_app` 번들의 SDK 설정(`requestHeaders`)과 대조해 다르면 고장으로 알린다 (`check_zigbang_sdk_versions`). 첫 화면 HTML 은 브라우저가 아닌 요청을 403 으로 막아 jibsa 브라우저로 받는다.
  - 웹 SDK 는 Sentry trace ID 로 만든 `x-transaction-id` 를 일부 호출에 붙이지만 (번들, 실측 137건에는 없었다) 요청마다 바뀌는 값이라 넣지 않는다.

### 브라우저 요청

(2026-11-09 실측) 공통 동작은 [브라우저 요청](../architecture.md#브라우저-요청). 직방만의 값:

- 첫 화면은 `https://www.zigbang.com/`. 첫 화면이 `apis.zigbang.com` 을 4번 부른다. API 는 모두 다른 출처라 원래 쿠키 없이 응답해
  기다릴 쿠키가 없다.
- `apis`·`stay-apis` 모두 `www.zigbang.com` 출처를 CORS 로 허용한다(`*`). `x-zigbang-platform`·`sdk-version`·`content-type`
  헤더도 허용한다.
- 사전 요청 결과를 기억하라는 헤더(`Access-Control-Max-Age`)가 없어 주소가 다른 요청마다 CORS 사전 요청(OPTIONS)이 따라간다.
  세지 않으면 서버로 가는 요청이 정책의 2배까지 됐다 (2026-11-10 실측: 검색 2건에 서버 4건, 기록 2건). 사전 요청도 요청 제한에
  센다 (`count_preflight`).
- `Access-Control-Expose-Headers` 가 없어 다른 출처 응답의 `Retry-After` 등이 페이지 JS 에 보이지 않는다. 브라우저 `response`
  이벤트가 받은 전체 헤더로 채운다 (`_to_response`).

### 원룸·오피스텔·빌라 목록 (`room`)

- 목록은 종류마다 geohash 지도 칸으로 핀(ID·좌표)과 섹션(`sections`)을 받고 → 응답의 섹션 순서(VIP → 안심추천 → 안심일반 → 추천 → 일반, 원룸 목록의 추천은 '이 지역 오피스텔')대로 ID 를 잇고 → 앞 `--limit` 개만 `items/list` 로 15개씩 요약을 받아 고른 순서대로 낸다 (2026-11-15 번들 `_app` 의 `loadSectionsWithItemIdsByGeoHash`·`createSectionsToUpdate`). 섹션 안은 서버 순서 그대로이고 거리로 다시 세우지 않는다 (`distance_km` 는 덧붙이기만). 섹션 종류의 순서는 순서표(`SECTION_ORDER`)로 정하고, 지도 칸이 여럿이면 섹션 종류마다 칸 순서(`scope_geohashes`)로 잇고, 어느 섹션에도 없는 핀은 잃지 않게 맨 뒤에 핀 순서로 붙인다 (`section_ordered_ids`, 오피스텔 건물 매물과 같은 함수). 칸마다의 섹션 순서를 합치던 방식은 빈 섹션을 뺀 칸이 있으면 앞뒤가 뒤집혔다 (2026-11-16 리뷰. 실측으로는 강남역 3km 18칸 모두 다섯 섹션을 같은 순서로 주고 빈 섹션도 `ids: []` 로 둔다). 요약에서 뺀 매물은 다시 채우지 않는다.
- 범위는 핀 좌표로 좁힌다. 반경은 반올림 없는 거리(`distance <= radius_km`)로 자르고, 동 경계는 경계 안 핀만 남긴다. 반경·경계 안이 모자라도 밖의 핀으로 채우지 않는다. `total` 은 범위 안 서로 다른 ID 수다.
- 종류가 여럿이면(기본 세 종류) `limit` 을 조회할 종류 수로 고르게 나눈다 (`_split_limit`: 20 → 7·7·6, 앞 종류부터 한 건씩 더, 남은 매물이 제 몫보다 적은 종류의 남는 몫은 다른 종류로). 종류별 묶음을 요청한 종류 순서로 잇는다. 원룸 목록의 '이 지역 오피스텔' 섹션처럼 앞 종류 목록에 있는 ID 는 핀을 받은 뒤 뒤 종류 목록에서 빼(`_collect_pins`) 종류별 목록이 서로 겹치지 않게 하고, 뺀 수를 `[참고]` 에 알린다. 한 호출 안에서만 빼던 때는 강남역 `--limit 120` 이어 받기에서 앞 쪽 매물이 쪽마다 16~59건씩 다시 나왔고, 자리를 종류별로 더한 수가 `total` 을 넘어 4쪽부터 더 있는데도 `[일부]` 가 사라졌다 (2026-11-16 리뷰·실측). 종류마다 범위 안 몇 건 중 몇 번째를 받았는지 `[참고]` 한 줄로 알린다 (`_type_share_note`).
- 이어 받기 표는 `{'offsets': {종류: 그 종류 목록에서 다음에 받을 자리}}` 다 (`start`). 자리는 겹친 ID 를 뺀 종류별 목록의 자리라, 자리를 더한 수가 곧 앞서 받은 서로 다른 매물 수다. 표의 종류가 이번 검색과 다르거나 모양이 틀리면(예전 `{'offset': n}` 표 포함) `INVALID_ARGUMENT` 다.
- 섹션 안 서버 순서: 원룸·빌라는 매물 ID 오름차순이고 1시간 반 뒤에도 같았다. 오피스텔은 서버가 기본으로 섹션 안을 무작위로 섞어 주는데, 연달아 부르면 같지만 1시간 반 뒤에는 순서가 달라 그대로 받으면 `--next` 의 자리가 흔들린다. 그래서 오피스텔 요청(지도 칸·역 반경·건물)에는 늘 `withoutRandom` 을 보내 섞지 않은 순서를 받는다. 이 순서는 원룸·빌라처럼 매물 ID 오름차순이고 하루 뒤에도 남은 매물의 순서가 같았다 (2026-11-15~16 실측: wydm6 안심추천 168건·안심일반 363건이 섞는 요청과 같은 매물). VIP 섹션은 다른 섹션 매물 가운데 32건을 광고로 올린 것이고 요청마다·시간마다 달라져, 한참 뒤 `--next` 는 그 매물 몇 건이 겹치거나 빠질 수 있다 (같은 매물이 두 섹션에 오면 앞의 것만 둔다). 실측: 강남역 `-t 원룸 --limit 15` 15건이 역 목록 섹션 순서(안심추천 89 → 안심일반 47 → 이 지역 오피스텔 251)의 앞 15자리와 같고, 종류 없이 `--limit 20` 은 원룸 7·오피스텔 7·빌라 6 이다.
- 원룸은 방 하나짜리를 뜻해, 원룸 목록(`items/onerooms`)이 섞어 주는 오피스텔 중 투룸은 원룸형 `roomType` 만 요청해 막고 원룸형 오피스텔은 결과에 둔다 (직방 웹 원룸 화면도 방 구조를 고르지 않으면 같은 목록을 보여 준다). 원룸 목록 핀에는 건물 ID(`buildingId`)가 없어 (실측: 모두 null, 요약에도 없음), 오피스텔을 따로 조회하지 않은 검색에서 건물 ID 없는 오피스텔이 결과에 있으면 그 매물이 있던 지도 칸에서 같은 조건으로 오피스텔 목록을 한 번 더 받아 `complex_id` 를 채운다 (실패하면 `null`).
- 빌라 목록은 투룸 이상뿐이라 원룸형 구조만 주면 빌라는 요청하지 않는다.
- 목록 관리비는 웹 목록 카드처럼 `items/list` 응답의 `itemSummaries[].fee` 를 쓴다. 같은 응답의 `items[].manage_cost` 는 관리비 0원 매물도 null 이라 (2026-11-15 실측) 그 매물이 `itemSummaries` 에 없을 때만 쓴다. 응답 모델이 같은 ID 의 `items` 요약에 웹 카드의 `fee` 와 목록인 `badges` 를 실어 준다 (`attach_web_card`, 꼬리표는 [오피스텔 건물·주거 상세](#오피스텔-건물주거-상세)). `itemSummaries` 중 모델이 읽지 못하는 항목(ID 가 정수가 아니거나 `fee` 가 숫자·숫자 글자·null 이 아님)만 빼고, 그 매물은 `items[].manage_cost` 로 돌아간다 (`readable_summaries`). 금액은 원 단위까지 낸다 (`won_to_manwon`, [웹과 다른 점](#웹과-다른-점)).
- `search listings room` 에서 역 이름이 지하철역으로 풀리면 지도 칸 대신 `items/subways/{id}/<유형>` 을 유형별 1회 부르고 (반경은 서버가 받는다), 서버가 준 결과를 다시 자르지 않는다 (좌표 검색은 지도 칸 그대로).

### 지도 칸과 동 경계 (`room`, `stay` 대체 경로)

- 지도 칸(`geohashes_covering`)은 칸 절반 이하 간격으로 샘플링해 원에 닿는 칸을 모두 받는다. 상가는 지도 칸을 쓰지 않는다 ([상가](#상가-store)).
- 동 경계 검색(`search listings room`)에서 검색어와 같은 이름의 동이 없고 `<검색어>N가` 후보만 있으면(성수동 → 성수동1가·2가) 같은 시·구의 그 동들 경계를 하나씩 받아(동마다 1회) 다각형을 합치고, 검색 중심을 합친 범위의 가운데로 옮긴다 (`merge_dong_boundaries`·`merged_dong_region`). 첫 후보만 찾으면 나머지가 조용히 빠졌다 (2026-10-10 실측: 성수동 상가는 1가 283건만, 2가 217건 누락). 지도 칸의 핀을 경계로 좁히는 부분집합이라 합쳐도 웹에 없는 매물이 생기지 않는다. 지역 하나의 목록만 있는 아파트·단기임대 검색은 합치지 않고 묻는다 (`divided_region_error`).
- 동 경계 검색은 경계를 감싸는 원 대신 경계에 닿는 칸(`geohashes_touching`)만 받는다 (2026-10-10 실측: 경계 안 핀은 그대로). 그래도 반경 5km 원의 칸 수보다 많으면(홍천 내면 원룸 41칸) 경계 대신 중심 반경으로 찾고 알린다(`wide_boundary_note`). 경계 API 는 geohash 칸 중심이 속한 동을 주어 정밀도 7 로 묻는데, 옆 동이 잡히면 8 로 한 번 더 묻는다 (실측: `○가` 동 64곳 중 6곳이 7 에서 옆 동, 8 에서 모두 맞음). 직방 지역 검색의 동 중심은 늘 그 동 경계 안이라 경계를 못 받는 동은 없었다 (2026-10-11 실측: 강변·해안·섬 읍·면·동 28곳). 그래서 경계를 못 받아 반경으로 찾게 된 경우의 안내는 두지 않는다.
- 같은 이름의 동이 따로 있으면(당산동) 그 동만 찾고, 반경·아파트처럼 동을 합치지 않는 검색과 함께 `○가` 안내(`ga_dong_note`)를 붙인다. 아파트·`search complexes` 에는 `--radius` 옵션이 없어 그 둘은 `--radius` 를 권하지 않는 문구(`radius_hint=False`)로 부른다.
- 같은 이름·같은 종류의 결과(신사동 → 은평구·강남구, 양평역 → 영등포구·양평군, 중구)가 여러 곳이면 지역·역·학교 모두 `settled_item` 이 `REGION_AMBIGUOUS` 로 멈춘다 (지역은 2026-10-15, 역·학교는 2026-11-15). 첫 곳으로 찾으면 엉뚱한 곳의 결과가 조용히 나왔다 (양평역은 첫 곳이 서울 영등포구). 힌트는 후보 하나로 가려지는 검색어만 예로 든다 (`_retry_hint`): 후보 주소의 시·군·구(`영등포구 양평역`) → 동(신촌역: 서대문구 창천동·신촌동이라 `창천동 신촌역`) → 시·도(같은 이름 구: `서울특별시 중구`) 순으로 붙여 보고 `_qualified_item` 이 후보 하나를 고르는 첫 검색어다. 구 이름이 곧 검색어인 중구에 '구 이름을 앞에 붙이라' 고 하거나, `search complexes` 처럼 좌표를 받지 않는 명령에 `--lat/--lng` 를 권했다 (2026-11-16 리뷰. 실측: 직방은 '서울특별시 중구'·'서울 중구' 에 서울 중구 하나만 준다). 직방은 '신촌동 신촌역' 에도 두 역을 다 주어, 검색어 앞 낱말이 주소에 모두 든 후보가 하나뿐이면 그 후보로 찾는다 (`_qualified_item`. room·store·stay·apt·`search complexes` 모두 `settled_item` 하나로 정한다, 2026-11-15 실측: '신촌동 신촌역' → 신촌동, '창천동 신촌역' → 창천동, '영등포구 양평역' → 영등포구). 전체 주소('서울특별시 강남구 신사동')는 직방 지역 검색이 학교만 주므로 힌트는 '구 + 동'(`강남구 신사동`)으로 든다.
- 같은 이름 후보는 좌표 없는 결과까지 센다. `search_regions` 는 기본으로 좌표(lat·lng)가 없는 결과를 거르지 않는다: 먼저 버리면 같은 이름 후보가 둘인데 `settled_item` 이 남은 하나를 묻지 않고 고른다 (2026-11-20 리뷰). 고른 곳의 좌표를 검색 중심으로 쓰는 경로(room·store·stay, 아파트의 역·학교 이름 → 위치가 속한 동 찾기)는 좌표가 없으면 다른 후보로 넘어가지 않고 `region_from_search_item` 이 `UPSTREAM_ERROR` 로 알린다 (지역·역·`○가` 동·구가 있는 시 해석 모두). 좌표를 쓰지 않는 경로는 막히지 않는다: 아파트 동·구(`resolve_apt_region` 이 `apt_region_from_search_item` 으로 `common/base.py` 의 `ZigbangAptRegion` 을 만든다. `lat`·`lng` 가 `| None` 이라 좌표 없는 후보는 출력의 좌표만 null)와 `search complexes` 의 역(`resolve_station`)·학교·동·구(법정동 코드·ID·이름·주소만 쓴다). 어느 동·구인지 묻는 에러(`divided_region_error`)는 이름·주소만 써서 좌표 없는 후보가 섞여도 `REGION_AMBIGUOUS` 다. 단기임대의 `○가` 동·구가 있는 시 묻기도 지역으로 바꾸기 전의 검색 결과(`region_scope_items`·`city_gu_search_items`)로 판단해 좌표 없는 동이 섞여도 `REGION_AMBIGUOUS` 다. `resolve_region_scope` 는 `○가` 동을 검색 결과 그대로 주고, 그 좌표를 실제로 쓰는 room·store 의 동 안 찾기(반경 없음)만 지역으로 바꿔 좌표 없는 동이 섞이면 `UPSTREAM_ERROR` 다. `--radius` 로 찾을 때는 그 동들을 쓰지 않아 좌표가 없어도 막히지 않는다. 직방이 이름·종류·주소가 같은 결과를 중복으로 주면 같은 곳으로 보고 좌표 있는 쪽을 고르고(`_located_first`: `settled_item`·`_qualified_item`), `○가` 동 후보(`ga_dong_siblings`)도 이름·주소가 같은 중복은 하나로 줄여 좌표 있는 쪽을 남긴다. `search locations`(`search_regions_and_complexes`)는 후보를 고르지 않고 좌표를 함께 내는 목록이라 좌표 있는 결과만 낸다 (`require_coordinates=True`). 2026-11-20 실측(지역 검색 24회, 같은 이름 역·동·학교 결과 523건)에서 좌표 없는 결과는 0건이었다.

### 아파트 (`apt`)

- 아파트는 동·구 하나의 지역 목록(`locals/{코드}/item-catalogs`, 웹 지역 매물 화면 `/home/apt/items/{지역 코드}`)만 본다 (2026-11-15 캡처: 웹은 지역 코드 하나의 목록만 보여 준다). 같은 이름의 동 없이 `○가` 로만 나뉜 동(성수동 → 성수동1가·2가)은 목록 여럿을 합친 순서·수가 웹에 없어 합치지 않고 `divided_region_error` 로 `REGION_AMBIGUOUS`(후보 주소, 힌트 '성수동1가' 처럼 동 이름을 정확히)를 낸다. 검색 중심은 첫 지역 결과인데, 그 이름이 검색어와 다르고 `<검색어>N가` 동이 있으면 첫 `○가` 동을 고른다(`best_region_item`). 직방은 '부민동' 을 [남부민동, 부민동1가, 2가, 3가] 순서로 줘서 첫 결과를 고르면 다른 동을 찾았다 (2026-10-10 실측). 검색어는 마지막 낱말(`_dong_name`)로 비교해, 구 이름을 앞에 붙여도('성동구 성수동') 같은 `○가` 동을 알아본다. 이어 받기 표는 `{'code': 지역 코드, 'offset': 앞서 받은 수}` 이고, 다시 찾은 지역 코드가 다르면(예전 `codes` 표 포함) `INVALID_ARGUMENT`(`apt_resume_changed_error`)다. 동 하나는 offset 으로 이어 받아 겹치지 않아 `seen` 을 두지 않는다.
- 아파트 지역 목록은 시·도 2자리 코드에 늘 0건이라(2026-10-11 실측: 11·41·26·36 모두 0건, 강남구 11680 은 1683건) `resolve_apt_region` 이 시·도를 `RegionNotFoundError` 로 넘긴다. CLI 는 이 에러를 잡아 역·학교처럼 주소가 아닌 결과면 그 위치가 속한 동으로 찾고, 주소(시·도·행정동 등)면 에러를 그대로 낸다.
- 구가 있는 시는 직방 지역 검색이 시 대신 그 구들을 주고 시 코드(성남시 41130)는 0건이라 (2026-11-15 실측), 어느 구인지 묻는다 (`city_gu_items` → `divided_region_error`, 힌트 '성남시 분당구' 처럼 구 이름까지). 첫 구만 찾으면 성남시는 분당구만 나오고 다른 구가 조용히 빠졌다. '시' 를 떼고 쓴 이름('성남')도 검색 중심이 '<이름>시 ○구' 면 같은 시로 본다 (2026-10-28 실측: 성남·안양·고양 모두 직방이 구들을 맨 앞에, 같은 이름의 동을 그 뒤에 준다). 검색 중심이 그 시의 구가 아니면(동 이름 등) 묻지 않는다.
- 리는 10자리 코드가 0건이라 읍·면 8자리로 찾고(양근리 → 양평읍 88건) '직방이 리로는 찾지 않아 상위 읍·면 전체에서 찾았습니다' 라고 `notes` 로 알린다.
- 역·학교 이름과 좌표는 웹 아파트 지도의 '○○동 주변 매물보기' 처럼 그 위치가 속한 동을 `GET /apt/locals/polygon`(geohash 정밀도 10, `level=local3`, `polygon=false`)으로 찾아 그 동의 지역 목록을 준다 (`apt_dong_at`, 요청 1회). 칸이 크면 옆 동이 잡혀 정밀도 10 으로 묻는다 (2026-11-15 실측: 강남역은 정밀도 5 에 논현동, 6 에 역삼동, 7·8 에 서초동, 9·10·12 에 역 주소와 같은 역삼동). 응답에서 확인된 필드는 `code`(8자리)·`name` 뿐이라 결과 지역의 주소·local1~3 은 비어 있다. 웹은 geohash 를 암호화해 보내지만 평문도 받는다. `[범위]` 안내 끝에는 찾은 장소 이름으로 역이면 '역 주변 단지는 `search complexes <역 이름>`', 학교면 '학교 배정단지는 `search complexes <학교 이름>`' 을 알린다 (그 밖은 붙이지 않는다. 학교는 `school_has_assigned_complexes` 가 참일 때만 권한다: 그 명령이 찾는 학교만이다). 실측: 강남역 3건 + `--next` 3건이 역삼동 목록 6건과 같다 (2026-11-15~16).
- 카탈로그 한 건은 같은 호·거래 유형을 올린 매물 묶음이다 (`itemIdList`). 상세를 볼 수 있는 ID 전부를 응답 순서 그대로 `listing_ids` 에 담고 `id` 는 그 맨 앞이다 (`apt_listing_id`). 묶음의 `itemType`·`itemTitle`·`floor` 는 `itemIdList` 맨 앞 매물의 값이고 직방은 섞인 묶음에서 제휴 매물을 앞에 두기도 해서, 순서를 지켜야 `id` 와 줄의 종류·제목·층이 같은 매물을 가리킨다 (2026-11-17 실측: 서패동 41480119 묶음 `[coalition 254486, zigbang 50026248]` 이 `itemType: partner`·`floor: '11'`(제휴 매물의 숫자 층). 예전에는 직방 매물을 먼저 골라 `id` 만 중개사 매물이었다). 맨 앞이 상세를 볼 수 없는 출처면 묶음 `itemType` 이 `id` 매물의 종류가 아니라 `listing_kind` 는 null 이다. `isPriceRange` 가 true 면 웹 카드는 최저가를 보여 준다. 웹 카드는 가격 범위와 상관없이 누르면 그 호의 묶음 화면(`/home/apt/item-catalog?areaHoId=…&tranType=…`)으로 가서 (2026-11-15 번들 `ItemCard_AptItemCatalogCard` 의 `onPress`), `url` 도 호 ID 가 있으면 늘 그 화면이다 (`apt_catalog_url`). 신규분양 카드는 웹이 그 매물의 상세 화면으로 보내지만(`onPressOfferItem` → `HomeAptItemDetail`) 묶음 화면도 같은 매물 1건과 '일반 매매가 아닌 신규분양 매물입니다' 를 보여 준다 ([웹과 다른 점](#웹과-다른-점)). `areaHoId` 가 없으면 묶음 화면을 만들 수 없어 `url` 은 `id` 매물 페이지이고 `catalog_id` 는 null 이다. 묶음 화면이 받는 호 ID·거래 유형은 `catalog_id`(`<areaHoId>-<tranType>`, `apt_catalog_id`·`parse_catalog_id`)로 낸다. 묶음 ID·매물 ID 의 형식 검사는 서비스(`parse_catalog_id`·`get_any_listing`)가 요청 전에 하고, CLI 는 따로 검사하지 않아 `INVALID_ARGUMENT` 의 `hint` 가 전용 안내(`CATALOG_ID_HINT`, 매물 ID 접두어)다.
- 지역 목록에는 신규분양 카드가 일반 매물과 같은 목록에 섞여 온다. 웹 지역 매물 화면(`/home/apt/items/{지역 코드}`)은 '신규 분양 포함' 이 켜진 채 열려 첫 쪽에만 `includeOfferItem=true` 를 붙이고 스크롤해 받는 다음 쪽(`offset=10·20·…`)에는 붙이지 않는다 (2026-11-17 번들 `HomeAptItemsListScreen` 의 `onEndReached`). 서버는 `includeOfferItem` 이 없으면 `true` 와 똑같이 응답하므로 jibsa 는 기본으로 이 값을 보내지 않는다 (`--no-new-sale` 일 때만 보내는 것은 다음 항목이다. 2026-11-17 실측: 파주시 41480 은 값 없음·`true` 가 `count` 608 에 0~7번이 분양 카드 8장이고 `false` 는 600 에 분양 카드가 없다. 일반 매물의 순서는 같고 분양 카드도 `count`·`offset` 에 든다. 동 단위도 같다: 서패동 41480119 는 99 / 91). 분양 카드는 `itemType: offer`, `offerItem`, `itemIdList` 의 출처 `coalition` 이고 `dong`·`floor` 가 없어, `coalition-<id>` 줄이 되고 `floor` 는 null 이다. 일반 카드의 `itemType` 은 `self_ad`(중개사무소가 등록)나 `partner`(집주인이 내놓음)다. 이 `itemType` 을 `listing_kind`(신규분양·집주인·중개사, 처음 보는 코드는 그대로, 없으면 null, `apt_listing_kind`)로 옮겨 아파트 목록·`catalog`·상세에 내고, 분양가를 일반 호가로 읽지 않게 `--fields` 로 골라도 늘 낸다 (`ALWAYS_FIELD_GROUPS`). 서버는 거래 유형·가격 조건을 분양 카드에도 건다 (2026-11-17 실측: 파주시 `--trade 전세`·`--price-max 30000` 에서 분양 카드 0장, `--price-max 60000` 에서 분양 8장 중 58870 하나만. 공급면적 조건은 확인하지 않았다). `offerItemCount` 는 단지 요약(`/apt/danjis/{id}/item-catalogs/summary`)의 파라미터라 이 목록과 상관없다.
- `--no-new-sale` 은 웹의 '신규 분양 포함' 을 끈 지역 목록이다 (`ZigbangAptConditions.exclude_new_sale`). 켜면 이어 받는 쪽까지 모든 지역 목록 요청에 `includeOfferItem=false` 를 보낸다 (`search_apt_listings`, 끄면 값을 보내지 않아 `None`). 서버는 `false` 면 분양 카드를 빼고 `count` 도 줄이며(2026-11-17 실측: 파주시 41480 608 → 600, 동 단위 서패동 41480119 99 → 91), `false` 끼리는 `offset` 으로 이어져 겹치지 않는다. 첫 쪽만 `false` 로 보내고 다음 쪽을 값 없이 받으면 값 없는 목록의 `offset` 이 분양 카드까지 센 자리라 일반 매물이 분양 카드 수만큼 두 쪽에 겹친다 (2026-11-17 실측: 파주시 41480 `limit` 10 에서 값 없음 offset=0 은 분양 카드 8장 + 일반 매물 2건, `false` offset=0 은 일반 매물 1~10번째, 값 없음 offset=10 은 일반 매물 3~12번째라 일반 매물 3~10번째 8건이 두 쪽에 있다. [웹과 다른 점](#웹과-다른-점)). 거래 유형·가격 조건은 분양 카드에도 걸려 같이 쓸 수 있다. 단지 목록(`/apt/danjis/{id}/item-catalogs`)은 이 값을 조용히 무시해 (2026-11-17 실측: 분양 2건을 그대로 줌) 단지 매물 조회에는 옵션도 요청도 넣지 않는다.
- 아파트 상세·묶음 매물·목록 줄의 평형·확인일 같은 값은 응답에서 그대로 옮긴다 (2026-11-17 실측: 직방 매물 22건·제휴 매물 4건). 평형은 상세·묶음의 `roomTypeInfo.danjiRoomTypeId`·`roomTypeTitle.p` 와 목록 줄의 `danjiRoomTypeId`·`roomTypeTitle.p` 가 `pyeong_id`·`pyeong_name` 이 된다 (`ZigbangAptRoomTypeInfoModel`, `catalog_to_listing`·`apt_item_to_listing`). 단지 매물 목록(`--complex`, `/apt/danjis/{id}/item-catalogs`) 줄에도 같은 키가 온다 (2026-11-17 실측: apt-38487 세 줄 모두). 평 이름이 빈 글자면 `pyeong_name` 은 null 이다 (`text_or_none`, 실거래와 같다). `pyeong_id` 는 `complex` 의 `pyeongs[].id`·`--pyeong` 값과 같은 번호임을 실제로 넣어 확인했고, `pyeong_name` 은 `complex`·`real-price` 처럼 평 기준(`p`)이다. 확인일 `effectivenessUpdatedAt`(ISO 8601 초 단위 `+09:00`)은 `iso_date` 로 한국 날짜 `confirmed_at` 이 되고(날짜로 못 읽으면 null), 목록 줄에는 이 키가 없어 상세·묶음에만 낸다. `isActualItemChecked`·`hasViolations`·`realType` 은 `actual_listing_checked`·`non_compliant_building`·`residence_type`(중개대상물 종류) 이 된다. 목록 줄에도 `isActualItemChecked` 가 있지만 묶음 단위 값이고 분양 줄은 상세와 값이 달라 목록에는 내지 않는다. 제휴 매물(`coalition-…`)은 `hasViolations`·`realType` 키가 없고 웹도 그 줄을 숨겨 둘 다 null 이다. 직방 매물 22건은 모두 `hasViolations` false·`realType` '아파트' 였다. 확인일·실매물 확인·위반 건축물 여부는 원룸·빌라·오피스텔 상세에도 있어(아래 '오피스텔 건물·주거 상세') 아파트 전용이 아니다. 평형·공급면적·`listing_kind` 와 찜 수(`zzim_count`)는 아파트 상세에만 있어 `APT_ONLY_DETAIL_FIELDS` 가 다른 유형 상세에서 키를 뺀다. 아파트 상세의 `isHugLessor`(HUG 안심임대인)·`zzimCount`(찜 수)는 `hug_lessor`·`zzim_count` 로 그대로 옮기고, 찜 수 0 도 낸다 ([웹과 다른 점](#웹과-다른-점)).
- 묶음 화면은 `GET /apt/item-catalogs/{areaHoId}?tranType=…&limit=20&offset=…&firstItemSource=coalition` 을 `itemCount` 까지 20건씩 부른다 (번들 `getItemCatalog`·`useItemCatalogDetail`, 첫 쪽은 서버가 그려 넣는다. 2026-11-15). 매물마다 아파트 상세(`/apt/item-catalogs/items`)와 같은 꼴이라 `catalog` 는 `apt_item_to_listing` 으로 바꾼다 (실측: 은마 묶음 4건이 `listing` 상세와 필드까지 같다). 웹은 거르거나 다시 세우지 않고 서버 순서 그대로 보여 준다. `firstItemSource=coalition` 은 웹이 매물 ID(`firstItemId`) 없이도 늘 보내는 기본값이고 순서를 바꾸지 않는다 (2026-11-15 실측). 매물이 없거나 그 호에 그 거래 유형 매물이 없으면 404 (`not found item in catalog`)라 `LISTING_UNAVAILABLE`(reason `EMPTY_CATALOG`)이다. 첫 쪽이 200 빈 목록이어도 같은 에러다 (`_empty_catalog_error`). 묶음 ID 는 `listing` 에 넘길 수 없어 `listing_id` 대신 `catalog_id` 에 싣는다. 둘째 쪽부터의 404·빈 쪽은 받는 사이 묶음이 줄어든 것이라 받은 데까지 내고, 상한(120건)과 다른 `[일부]` 안내를 붙인다. `itemCount` 가 null 이면(실측에서는 늘 정수) `total` 도 null 이고, 쪽이 가득(20건) 찬 동안 상한까지 받아 덜 찬 쪽이나 404 를 끝으로 본다. 이때 `has_more` 는 상한에 닿았는데 마지막 쪽이 가득 찼을 때만 참이다. 응답 모델은 `items` 의 null 도 빈 목록으로 받는다 (`null_items_as_empty`). 묶음 매물의 거래 유형은 요청한 `tranType`(묶음 ID)으로 정한다 (웹도 매물의 `tranType` 으로 거르지 않는다). 응답의 근처 중개사무소(`acceptedLocalAgents`)·매물마다의 중개사·사진·설명은 내지 않는다.
- 단지 목록(`danjis`)은 50건씩, 동·구 지역 목록(`locals`)은 20건을 넘으면 400 이라 20건씩 받는다 (2026-10-10 실측: 단지 목록은 50건씩 받아도 순서·내용이 같다).

### 역·학교·동·구 주변 단지 (`search complexes`)

- 웹 아파트 지도에서 역·학교를 고르거나 지역 화면을 열면 나오는 단지 목록('<역> 주변단지'·'<학교> 배정단지'·동 화면의 최근입주 패널)과 같다. 순서와 수는 `GET /apt/danjis/ids?type=<subway|school|local>&id=<ID>&order=<viewCount|newest|priceChange|areaPrice>&limit=…&serviceType[0..2]=apt,offer,preOffer` 그대로다 (2026-11-15 캡처·번들 `getAPTTypedListIds`: 패널은 `limit=5`, 더보기 화면은 `limit` 없이 모든 ID 를 받아 15곳씩 카드를 받는다. 2026-11-19 캡처: 학교 화면 `/home/apt/schools/{학교코드}` 는 `type=school`, 동 화면 `/home/apt/locals/{법정동코드}` 의 최근입주 패널은 `type=local&order=newest`). 쪽 넘김(offset)이 없어 이어 받기는 없다. 서버 사실(강남역 ID 31, 인기): `limit` 5 → 5곳, 120·500·없음 → 112곳, `count` 는 늘 112. 최근입주(`newest`)·시세급변동(`priceChange`)은 순서만 다른 같은 목록이 아니라 그 조건에 든 단지만 담는다 (2026-11-20 실측: 강남역 인기 112곳·최근입주 2곳·시세급변동 55곳, 가락동 최근입주 1곳). 그래서 `count`·`total` 은 고른 목록의 단지 수이고(`SUBSET_ORDERS`) 그 곳의 전체 단지 수가 아니다. `notes` 가 이를 알리고 역·학교는 `--order` 를 빼고(인기) `--limit` 을 늘려 받아 `distance_m` 으로 가까운 곳을 고르라고 한다. 직방이 `count` 만 주고 `ids` 를 주지 않으면 '앞 0곳입니다' 같은 소용없는 안내가 나가므로 결과를 만들지 않고 `UPSTREAM_ERROR` 로 멈춘다.
- `--order` 의 탭 이름은 웹 탭 순서다: 인기 `viewCount`·최근입주 `newest`·시세급변동 `priceChange`·평당가 `areaPrice` (`DANJI_ORDER_BY_LABEL`). 웹 지역 화면(동·구)에는 최근입주 목록뿐이고 인기 순서는 화면 버튼으로 가는 길이 없어 (2026-11-19 웹 조사), 동·구는 웹에 없는 목록을 만들지 않으려고 최근입주 말고는 요청 전에 `INVALID_ARGUMENT` 로 막는다 (`complex_order_of`).
- 검색어 끝 글자로 역('…역')·학교('…학교')·그 밖(동·구)을 가르고(`query_place_kind`) 지역 검색은 한 번만 부른다. 이름을 찾아보기 전에 가르면 동·구에 받지 않는 `--order` 를 요청 전에 막을 수 있다. 동 이름은 동·구 경로라 같은 이름 동이 여럿이면 `REGION_AMBIGUOUS` 다 (2026-11-20 리뷰 재현: `search complexes 신사동`).
- 역 해석(`resolve_station`)은 지역 검색에서 역 결과만 본다 (검색어 마지막 낱말과 이름이 같은 역). '역' 으로 끝나는 검색어인데 지역 검색 결과가 하나도 없으면 `RegionNotFoundError`(hint `STATION_QUERY_HINT`, 이 명령에는 좌표 옵션이 없다), 결과는 있는데 그런 역이 없으면 `INVALID_ARGUMENT` 다 (`_station_place`, 같은 hint). 반환은 역 검색 결과(`ZigbangSearchItemModel`)이고 ID·이름·주소만 써 지역(`ZigbangRegion`)으로 바꾸지 않아 좌표 없는 역도 찾는다. 지역 결과를 먼저 고르면 같은 이름 후보 때문에 `REGION_AMBIGUOUS` 가 나고 그 힌트를 따라도 '역이 아닙니다' 가 되어, 역 결과만 본다 (2026-11-16 리뷰). 실측: 강남역 `--limit 4` → apt-13774·apt-51185·apt-51432·apt-559 로 2026-11-15 웹 캡처의 패널 순서와 같다.
- 학교 해석(`resolve_school`)은 학교 화면 코드(`source.school_code`)가 '아파트' 서비스 검색 결과에 있어(2026-11-19 실측: 해누리중학교) 그 서비스 검색에서 `type` 이 school 이고 이름이 같은 항목을 찾는다. 같은 이름 학교가 여럿이면 다른 검색처럼 `settled_item` 으로 `REGION_AMBIGUOUS` 이고 없으면 `RegionNotFoundError` 다. 아파트 서비스 검색에는 대학교가 나오지 않아 대학교는 찾지 못한다. **학교 ID 와 학교 코드는 다른 값이다**: 결과의 `id`(`detail.id`)는 단지 ID 목록(`danjis/ids?type=school&id=`)에 넘기는 학교 ID 이고, `_source.school_code` 는 학교 정보(`GET /apt/schools/{학교코드}?genderNullable=true`, 웹은 늘 true)를 부르는 코드다 (코드를 `id` 에 넣으면 500). 학교 코드가 'NL_' 로 시작하면 웹은 배정단지 목록을 그리지 않고(2026-11-19 번들 `isAptListRender`), 코드가 없으면 웹이 학교 화면 주소를 만들 수 없고 학교 ID 가 0 이하여도 단지 목록을 받을 수 없어 모두 `INVALID_ARGUMENT` 로 막는다 (판정은 `school_has_assigned_complexes`. 아파트 지역 매물이 학교 배정단지를 권할지도 이 함수로 가른다) (코드를 None 으로 넘기면 `ValidationError` 가 덤 조회에서 삼켜져 '받지 못해' 로 잘못 알려진다). 학교 ID 가 없는 응답은 응답 모델(`ZigbangSearchItemModel.id` 필수)이 먼저 막아 `PARSE_ERROR` 이니 `INVALID_ARGUMENT` 갈래에 닿지 않는다. 같은 이름 학교가 하나뿐인지는 다른 지역 해석처럼 좌표 없는 후보까지 세어 가른다 (위 '같은 이름 후보는 좌표 없는 결과까지 센다').
- 동·구 해석(`_region_place`)은 아파트 지역 해석(`region` 의 `resolve_apt_region`)과 같다: 같은 이름 동·구, `○가` 동, 구가 있는 시는 묻고, 리는 읍·면 코드로 찾는다. 행정동 이름의 `REGION_NOT_FOUND` 힌트(`legal_dong_hint`)도 `resolve_apt_region` 이 내서 `search listings apt` 와 같은 문구다. 단지 ID 목록에는 법정동 코드(동 8자리·구 5자리)를 정수로 넘긴다. `resolve_apt_region` 은 시·도와 '코드 있는 지역이 없음' 을 둘 다 `RegionNotFoundError` 로 던져, 지역 결과의 코드 단위(구·동·리가 모두 아님)로 시·도를 가려 `INVALID_ARGUMENT` 로 낸다. 리는 읍·면 목록으로 찾아 웹 목록 이름이 그 읍·면이라(`_ComplexPlace.list_name`, 결과의 `place` 는 찾은 이름 그대로) 순서 안내는 읍·면 이름을 쓰고, 단지 `address` 가 읍·면까지라 리 안의 단지를 가를 수 없다고 `[범위]` 로 알린다 (`resolve_apt_region` 의 `ri_check`).
- 단지 이름·지번 주소·세대수('1,161세대' 문구)·거리는 웹이 역·학교를 고를 때 함께 부르는 주변 단지 정보에서 붙인다: 역은 `GET /apt/subways/{id}` 의 `aptList`(거리 `distanceNum`, m), 학교는 `GET /apt/schools/{학교코드}` 의 `aptList`(이름·세대수·거리 문구). 강남역 `aptList` 112곳과 ID 112곳은 같은 집합이었다. 학교 응답에는 숫자 거리가 없고 '462m'·'1.1km' 문구만 있어 m 정수로 바꾼다 (`distance_m_of`), 주소도 없어 단지 카드 첫째 줄에서 받는다. 단지 카드는 `GET /apt/danjis/details`(`apts[0]=…` 15개까지, 웹과 같은 `type`·`id`·`order`)로 15곳씩 받아 첫째 줄(구·동·세대수)과 둘째 줄(`highlight`, 탭마다 뜻이 다르다)을 붙인다. 동·구는 주변 단지 정보가 없어 이름·주소·세대수도 카드 첫째 줄에서 받고(`_card_summary`, 주소는 구·동까지) 거리 키는 지운다. 주변 단지 정보·카드에 없는 ID 는 빼지 않고 그 값을 null 로 두고 `[참고]` 로 알린다 (역 `aptList` 에는 없는 ID 가 없었다). 이 요청은 덤이라 순서·수를 주는 `danjis/ids` 뒤에 부르고, 실패(요청 제한 포함, `SCHOOL_LOOKUP_ERRORS`)하면 ID 목록만 `[실패]` 로 낸다. `count` 가 null 이면 `limit` 만큼 꽉 찼을 때 `has_more` 를 true 로 본다 (`catalog` 과 같다). 분양 단지(`offer`·`preOffer`)도 `/apt/danjis/{id}` 가 200 이라 `apt-` 꼴로 낸다.
- 결과 순서가 웹 어느 목록인지 `notes` 로 알리고(역·학교는 가까운 순이 아니라는 말을 더한다) 학교에는 웹 학교 화면 하단 안내('학군배정 정보는 지역에 따라 실제 배정과 다소 차이가 있을 수 있습니다')를 `[참고]` 로 붙인다.

### 오피스텔 건물·주거 상세

### 실거래 (`real-price`)

- 실거래 API 는 없는 단지에도 빈 성공을 줘서, 첫 쪽의 단지 평형 정보(`areaInfos`)가 비면 단지 정보(`danjis/{id}`)로 있는지 한 번 더 확인해 없으면 `NOT_FOUND` 로 낸다 (거래 없는 단지도 평형 정보는 와서 평소에는 요청이 늘지 않고, 평형이 아직 없는 새 단지는 정상 0건이 된다). 지정한 평형이 평형 정보에 없으면 `INVALID_ARGUMENT`.
- 실거래 신고에는 전용면적만 있어 같은 전용면적의 평형이 여럿이면 직방이 거래마다 평형 후보를 모두 준다 (`areaInfos`). 웹은 첫 후보와 나머지 수('107A㎡외4')로 보여 주고, jibsa 는 같은 꼴로 `pyeong_name`('32A 외 4')을 내고 후보 전부를 `pyeong_names` 에 담는다 (`rt_price_to_real_price`). 웹(`getTypeOrPrice` 는 `areaInfos` 길이 - 1, `getType` 은 `e[0]`, 2026-11-15 번들)처럼 `areaInfos` 를 거르지 않고 전부 후보로 세고, 평 이름(`p`)이 빈 후보는 자리를 null 로 남겨 후보 수와 첫 후보가 웹과 같다 (첫 후보가 비면 `pyeong_name` 은 null). 후보가 하나면 `pyeong_names` 는 해당 없음이라 키를 지우고, `areaInfos` 가 빈 목록이면 후보를 모르는 것이라 null 이다 (`drop_not_applicable`).
- 거래마다 웹 실거래 탭이 그리는 값을 응답에서 옮긴다 (`rt_price_to_real_price`, 2026-11-17 웹 화면·응답 대조). 금액은 모두 만원 정수로 와서(원 단위 원본이 없다) 다시 계산하지 않고 `_manwon` 으로 낸다. `dongName` → `dong`: 값은 매매에만 오고 전월세는 null 이다. 웹 실거래 줄(`getSubTitle`)은 전월세에도 이 값을 그리므로 모든 거래에 `dong` 을 내고 직방이 주지 않으면 null 이다 ('동' 글자는 웹이 붙인다). `isRegistration` → `registered`: 직방은 참일 때만 키를 주고 매매에만 쓴다. 키가 없는 이유가 '2023년 1월 전 계약이라 표시 대상 아님' 일 수도 '아직 등기 전' 일 수도 있어 false 로 단정하지 않고 null 로 둔다. `isNewHighest`·`isNewLowest` → `new_high`·`new_low`: 참일 때만 키가 오고 매매·전세에만 나온다 (월세 표본 약 170건에는 없었다). 키가 없으면 그 배지가 없는 거래라 false 로 내고 월세는 키를 지운다. 웹 설명은 '최근 3년 이내 가장 높은(낮은) 거래가격을 경신한 거래' 라 단지 전체 최고가와 견준 값이 아니다. `pynPrice` → `price_per_pyeong_manwon`: 매매에만 오고(해제 거래 포함) 직방이 공급면적 기준 3.3㎡당 가격을 만원으로 반올림한 값이다. `charterRate` → `jeonse_ratio`: 0~1 실수(0.30523255813953487)를 자르지 않고 낸다. 전세이고 평형을 지정한 API(`/apt/danjis/{danjiId}/room-types/{id}/rt-prices`)에서만 오고 단지 전체 API 는 같은 거래에도 키가 없어 (2026-11-17 실측: apt-38487 전세) 그때는 키를 지운다. 분모는 그 달의 직방 시세이지 실거래 평균이 아니다. `offerPriceDiff` → `offer_price_diff_manwon`: 층별 분양가(없으면 청약홈 분양가)와의 차액이고 분양권 매매에서만 봤다 (표본 1건: 거래가 110000, 차액 37690). 분양권(`presale`)인데 값이 없으면 모름이라 null 이고, 분양권이 아닌 거래(입주권 포함)는 값이 없으면 해당 없어 키를 지운다. 새 필드는 기존 필드 뒤에 붙고 거래 유형별 키 정리는 `drop_not_applicable` 이 한다. 계약일 옆 'N' 표시(`isNew`)는 뜻을 알 수 없고 `roomTypeId` 는 화면에 안 보이고 평형 후보가 여럿이면 첫 후보라, 둘 다 내지 않는다.
- `--trade 전체` 는 `dealType=all` 로 받아 유형으로 거르지 않고 직방이 합친 순서 그대로 낸다 (웹 실거래 탭의 기본 탭. 매매와 전월세를 계약일 최신 순으로 섞고 같은 날짜면 전월세가 매매 앞이다). `rtDealType`(`sales`·`charter`·`rent`)이 거래마다 있어 필드 구성은 따로 부를 때와 같고, 한 유형만 부르면 거래 유형이 결과 맨 위에 있어 내지 않던 `trade_type` 을 전체에서만 거래마다 맨 앞에 낸다 (`show_trade_type`). `offset` 은 쪽 번호이고 `hasNext` 만 오며 총수는 없다. 전월세가 많은 단지(헬리오시티)는 앞 50건이 모두 전월세일 수 있다. 웹 전체 탭 첫 5줄이 같은 때 받은 API 응답 순서와 같았다 (2026-11-17). 평형 API(`/apt/danjis/{danjiId}/room-types/{id}/rt-prices`)도 `dealType=all` 을 받아 `--pyeong` 과 함께 쓸 수 있고 전세 거래에는 `jeonse_ratio` 도 온다 (2026-11-17 실측: apt-38487 `--pyeong 161652` 100건이 월세·전세·매매로 섞임). 전세·월세를 `rent` 에서 골라 쪽 수 안내를 붙이는 경로는 전체에 쓰지 않는다. 직방 거래 유형(`rtDealType`)을 읽지 못한 거래(모르는 값·null·키 없음)는 전체를 포함한 모든 `--trade` 에서 변환이 None 을 돌려줘 빼고, 센 수를 notes 끝에 `[제외] 거래 유형을 읽지 못한 실거래 N건을 뺐습니다` 로 알린다 (`get_real_prices` 의 `unknown`, 다방 실거래와 같은 꼴이다). `--limit` 으로 잘릴 자리의 거래는 세지 않는다.

### 단기임대 (`stay`)

- 단기임대(`stay-apis.zigbang.com`)는 두 경로다. 이름(역·학교·대학, 동·구)으로 찾고 `--radius` 가 없으면 웹 검색 결과 목록처럼 검색 API(`guest/items/search`)에 정렬을 보내 응답 ID 순서 그대로 앞 `limit` 개를 받는다 (`_search_stay_by_search_api`, `total` 은 검색 ID 수). 좌표·`--radius`·동 경계(대체 경로)는 지도(`guest/items/markers`) 핀 중 범위 안(반올림 없는 거리 또는 경계 안)만 남겨 웹 지도 목록과 같은 규칙으로 세운 뒤 앞 `limit` 개를 받는다 (`_search_stay_by_markers`·`stay_marker_order`, `total` 은 범위 안 핀 수). 두 경로 모두 받은 매물을 다시 거르거나 세우지 않고 `guest/items/by-ids` 로 50건씩 요약을 받아 고른 순서대로 낸다 (`_stay_summaries`). `by-ids` 는 노출 중·검수 완료 매물만 돌려줘서(실측) 목록에서는 상태를 다시 보지 않는다. 예약 달력(`guest/items/{id}/calendar`)은 손님 토큰을 붙여도 403 이었다 (로그인이 필요해 쓰지 않는다).
- 검색 API 정렬(2026-11-15 실측): `RECOMMENDED` 는 안 보내도 같은 순서(강남역 71건·역삼동 64건), `PRICE_ASC`·`STATION_DISTANCE_ASC` 는 같은 값이면 ID 큰 순이고 같은 요청은 늘 같은 순서다. `STATION_DISTANCE_ASC` 를 역이 아닌 검색에 보내면 400 `STATION_SORT_REQUIRES_SUBWAY` 라 요청 모델과 서비스가 먼저 막는다 (웹도 역 검색에서만 고를 수 있다). 역 검색은 서버가 역에서 약 1km 안만 주어(강남역 71건, 가장 먼 것 0.979km) `radius_km` 를 1 로 내고(`STAY_SUBWAY_RADIUS_KM`), 동·구 검색은 동 경계가 아니라 이웃 동 매물도 섞여 와(성수동2가 34건 중 성수동2가 17건, 화양동 9·자양동 5·성수동1가 3건) `[범위]` 로 알린다. 학교·대학 검색은 서버가 정하는 범위를 실측하지 못해 `radius_km` 를 내지 않고 `[범위]` 로만 알린다.
- 지도 핀 정렬은 웹 `sortStayMarkers` 그대로다: 추천순은 `totalScore` 높은 순, 같으면 ID 큰 순(`compareRecommended`), 가격순은 핀의 주당 합계 `weeklyTotalPrice`(주당 임대료+관리비, 원)가 숫자이면 그 값(정수가 아니어도 웹은 유한한 숫자면 쓰고, 모델도 `int | float` 로 받는다), 아니면 `weeklyPrice`(만원 미만 버림) × 10000 의 낮은 순(`getWeeklyTotalPrice`, 2026-11-19 번들. 같은 날 실측: 핀 1,608개 모두 `weeklyTotalPrice` 가 있었고 `weeklyPrice` 는 그 값을 만원 미만 버린 것이다. `weeklyPrice` 로 세운 옛 순서는 1,140자리가 달랐다), 최신순은 `reviewedAt` 늦은 순이고, 같은 값이면 추천순 규칙이다. 역 가까운 순은 지도 경로에서 막는다. 핀 좌표는 요약 좌표와 같다 (2026-11-15 실측 71건). 실측: 강남역 좌표 검색 추천순 앞 6건이 역 검색의 서버 추천순과 같고, 역 `--sort distance` 는 서버 `STATION_DISTANCE_ASC` 순서와 같다.
- 매물 `url` 은 웹 단기임대 매물 페이지(`https://www.zigbang.com/stay/item/<번호>`, `stay_item_url`)로 로그인 없이 열린다. 즉시입주 할인(`INSTANT`)은 웹 상세처럼 입주 시점 조건(`conditionDays`)을 붙인다: 0일이면 '오늘 입주 시', 1일 이상이면 '오늘부터 N일 이내 입주 시' 이고, null 이면 웹처럼 0일로 본다. 웹은 즉시입주 할인을 금액(`discountAmount`)으로만 보여 주고 0 이하면 줄을 숨겨, 금액이 없는 즉시입주 할인은 내지 않는다. 장기계약 할인(`LONG_TERM`)은 주 수(`conditionWeeks`)·할인율(`discountRate`)·주당 임대료(`weeklyRent`)가 모두 0보다 클 때만 '{주}주 이상 {율}% 할인' 으로 보여 주고 금액은 쓰지 않으며, 두 종류 밖의 할인은 그리지 않아 jibsa 도 같다. 웹은 할인의 `isActive` 를 보지 않아 jibsa 도 꺼진 할인을 거르지 않는다 (`stay_discount_label`, 2026-11-15 번들 `DiscountDetailList`·`pickDiscountTextsForCard`). 할인 문구의 금액은 반올림 없이 만원으로 쓴다 (2,500원 → '0.25만원', `format_manwon(won_to_manwon(…))`). 주당 임대료·관리비, 보증금, 청소비 등 단기임대의 다른 금액도 `won_to_manwon` 로 원 단위까지 낸다.
- 단기임대 날짜는 `checkOutDate` 까지 이용일로 센다 (11-02~11-08 = 7일). 검색(`guest/items/search`·`markers`)은 7~84일만 받아 `STAY_SEARCH_MIN_DAYS`·`STAY_SEARCH_MAX_DAYS` 로 요청 전에 막고, 서버의 `MIN/MAX_DURATION_VIOLATION` 도 입력 오류로 바꾼다(`_stay_search_call`).
- 상세(`listing stay-…`)에 날짜를 주면 상세 응답의 일정(`schedules`, 로그인 없이 온다)으로 웹 날짜 고르기 창 규칙을 그대로 따져 `available` 을 붙인다 (`stay_range_available`, 2026-11-15 번들 `resolveScheduleAutofill` 의 `isRangeAvailable`·`isStayRangeFreeOfOccupancy`, 요청이 늘지 않는다). 입주일이 오늘보다 앞이거나, 두 날짜 사이 일수가 최소 계약 주 × 7 − 1 보다 적거나(최소 계약 주가 null 이면 1주), 마지막 날이 입주일 + 83일(`getMaxCheckOut`)보다 뒤면 불가이고, `RESERVED`·`BLOCKED` 일정이 입주일~마지막 날 전날에 걸리거나 마지막 날이 `BLOCKED` 면 불가다. `schedules` 가 없으면 null 이다. 없는 날짜·지난 입주일·순서 오류만 요청 전에 막고(`ZigbangStayPeriod`·`validate_stay_dates`), 계약 주 밖은 웹처럼 `available: false` 다. 실측: stay-4114 의 막힌 기간(11-23~12-06)에 걸치면 false, 12-07~12-27 은 true (2026-11-15~16).
- 기간 총비용(청소비·직방 이용료·할인)은 웹이 로그인했을 때만 요금 계산(`price-calculation`)을 불러 보여 주어 (2026-11-15 웹: 로그인하지 않으면 날짜를 골라도 주당 금액만) 부르지 않는다. 날짜를 준 검색에는 목록 금액·가격순이 기간 비용이 아니라는 `STAY_WEEKLY_PRICE_NOTE` 를 늘 붙인다.
- 단기임대 지역 검색은 2026-10 에 세종의 동을 local1·local2 를 어떻게 줘도 400 `REGION_NOT_FOUND` 로 거절했다 (2026-10-11 실측: 반곡동을 세종특별자치시·세종시 × 세종·없음 조합 모두 400, 세종특별자치시 전체·양평읍·역삼동은 200). `_stay_region_search` 가 이를 `RegionNotFoundError` 로 바꾸고, CLI 가 room 과 같은 `_scope`(동 경계, 넓으면 반경)로 지도 칸을 다시 찾는다. 2026-11-10 에는 반곡동·어진동·나성동 모두 local1=세종특별자치시·local2=세종 으로 200 이고, 매물이 없는 읍·면(인제군 서화면·울릉군 울릉읍)도 200·0건이라 대체 경로를 타지 않는다. 다시 막힐 수 있어 대체 경로는 남겨 둔다. 이 경로를 타면 직방이 바뀐 것이라 `[실패]` 안내에 `UPDATE_MAYBE_NEEDED` 를 붙인다. 매일 API 감시는 업데이트 문구 없는 `[실패]` 를 잠깐 실패한 덤 조회로 보아, 붙이지 않으면 대체 경로도 0건일 때 고장 대신 확인 못 함으로 넘긴다.
- 단기임대 검색창은 `○가` 동(성수동1가·2가)과 구가 있는 시의 구를 따로 준다. 지역 검색 여럿을 합친 순서·수는 웹에 없어 합치지 않고 `divided_region_error` 로 묻는다 (2026-11-15 실측: 성수동2가 검색에 성수동1가 매물도 온다). 리는 지역 결과의 local3 이 그 위 읍·면이라 읍·면 기준으로 찾으므로(양근리 → 양평읍 창대리 매물) `boundary` 를 읍·면 이름으로 내고 `notes` 로 알린다 (`is_ri_code`).
- 단기임대 출력의 표기는 웹 이름을 따른다 (2026-11-17, `stay_parking`·`STAY_REFUND_POLICY_LABELS`). 주차 `LIMITED` 는 '제한적 가능' 으로 내고(가능·제한적 가능이면 웹처럼 유료·무료를 붙이고(번들 `AdditionalInfoSection` 은 `AVAILABLE`·`LIMITED` 둘 다 주차 요금을 보여 준다) 모르는 코드는 그대로 낸다) 위약금(`refund_policy`) `STANDARD` 는 웹 위약금 정보의 이름 '표준' 으로 낸다 (값은 유연·표준·엄격). 방 종류·옵션·할인 이름은 명령에 넣는 값이기도 해 웹 이름과 다르게 두었다 ([웹과 다른 점](#웹과-다른-점)).
- 단기임대 상세의 새 값은 상세 응답(`GET /guest/items/{id}`)에서 옮긴다 (2026-11-17 웹 상세 화면 대조, 실측 10건). 주방·거실 수(`kitchenCount`·`livingRoomCount`)는 0 도 오고 웹은 0 이면 그 줄을 숨기지만 jibsa 는 0 으로 낸다 ([웹과 다른 점](#웹과-다른-점)). 주차 대수·방식(`parkingCount`·`parkingMethod`, `SELF` 자주식·`MECHANICAL` 기계식, 실측은 `SELF` 와 null)은 `parking` 이 불가면 해당 없어 키를 지우고(`not_applicable_fields`), 가능·제한적 가능인데 직방이 주지 않으면 null 이다. 값을 넣지 않은 것(해당 없음)과 None 을 넣은 것(모름)을 `model_fields_set` 으로 가른다. 값만으로는 대수의 모름(null)과 해당 없음을 구분할 수 없어서다. 입·퇴실 시각(`checkinTime`·`checkoutTime`, 'HH:MM')과 방식(`checkinMethod`·`checkoutMethod`, `SELF` 비대면·`MEET` 임대인 대면·`KEYBOX` 키박스, 실측은 모두 `SELF`, 모르는 코드는 웹처럼 그대로)도 같은 응답 값이다 (`STAY_PARKING_METHOD_LABELS`·`STAY_CHECK_METHOD_LABELS`).
- 반려동물은 `itemOptions[]` 에서 `category == 'PET_FRIENDLY'` 인 원소가 있는지로 `pet_allowed` 를 정한다 (실측 `optionName` 은 `PET_ALLOWED` 하나지만 보지 않는다. 직방 웹 번들 `AdditionalInfoSection`·`OptionSection` 도 `category` 만 본다, 2026-11-17). 직방이 `itemOptions` 를 주지 않으면(`model_fields_set` 에 없음) 빈 목록으로 채워진 값에서 `any` 로 계산하지 않고 모름이라 null 이다. 웹 옵션 목록은 이 분류를 빼고 세고 (4230: 응답 옵션 22개, 화면 '21개 모두 보기') '반려동물 동반 가능/불가' 줄을 따로 그려, `options` 에서 이 분류를 빼 웹과 맞춘다 (`stay_detail_to_listing`). 추가 청소비(`petCleaningFee`, 원)는 웹이 동반 가능 여부와 상관없이 0 보다 크면 보여 주므로 `pet_cleaning_fee_manwon` 도 그렇게 낸다. 동반 가능이면 직방 값(0 이면 0, 주지 않으면 null), 동반 불가면 0 보다 클 때만 그 값을 내고 아니면 해당 없어 키를 지우며, 동반 가능 여부를 모르면(`pet_allowed` null) 0 보다 크면 그 값이고 아니면 null 이다. 웹은 0 이면 줄을 숨기지만 jibsa 는 가능인데 0 인 매물의 0 을 그대로 낸다 ([웹과 다른 점](#웹과-다른-점)).
- 예약 불가 기간(`unavailable_periods`)은 같은 응답의 `schedules[]` 에서 웹 달력이 막는 종류(`RESERVED` 예약·`BLOCKED` 막힘)이고 날짜가 온전한 일정만 낸다 (`stay_unavailable_periods`, 끝 날짜 포함, 직방이 1년 뒤까지 준다. `start`·`end` 는 직방 원문 글자가 아니라 날짜로 읽은 값의 `YYYY-MM-DD` 다). 막는 종류·날짜를 읽는 규칙이 `available` 을 정하는 `stay_range_available` 과 같아 두 값이 어긋나지 않는다. 웹 달력이 막지 않는 일정은 '예약 불가' 라고 내지 않는다. `schedules` 가 빈 목록이면 `[]`, 키가 없으면 null 이다 ([웹과 다른 점](#웹과-다른-점)).
- 위약금 표(`refund_rules`)는 응답 값이 아니다. 응답은 정책 이름(`refundPolicy`)만 주고 '입주 14일전·7일전·3일전·1일전·당일 이후' 다섯 행의 표는 웹 번들(`RefundPolicySection`)에 고정돼 있어, `STAY_REFUND_RULES` 에 옮겨 적고 `stay_refund_rules` 가 정책에 맞는 표를 낸다 (2026-11-17 번들. 표준 표는 stay-4114·4230·6448 화면에서도 확인했다). 웹은 `refundPolicy` 가 null 이거나 모르는 코드면 표준 표를 보여 주지만 jibsa 는 null 이다 ([웹과 다른 점](#웹과-다른-점)). 표가 바뀌면 매주 월요일 API 감시가 번들의 표 전체를 jibsa 표와 견주어 알린다 (`check_zigbang_stay_refund_rules`, [매일 API 감시](../README.md#매일-api-감시)). 웹 표의 시점 이름 수와 정책 행 수가 어긋나면(번들 구조 변경) 잘라 견주지 않고 이 검사가 '검사 코드 오류' 고장으로 보고된다. webpack 런타임의 `{번호:"해시"}` 표는 JS·CSS 둘인데 JS 표가 앞이고 CSS 번호는 단기임대 화면 조각 번호와 겹치지 않아 CSS 표를 잡지 않는다 (2026-11-17 리뷰 오탐). 표 아래의 고정 문구('위약금 규정은 임대인 설정에 따라 달라질 수 있습니다' 등)는 출력에 넣지 않고 사용자 문서가 알린다.
- 검색(`guest/items/search`)·지도 핀(`/guest/items/markers`)의 층 조건은 `floorTypes` 이고 웹 선택지는 다섯이다: `BASEMENT` '지하/반지하'·`FIRST` '1층'·`FLOOR_2_10` '2-10층'·`FLOOR_10_PLUS` '11층 이상'·`ROOFTOP` '옥탑' (`STAY_FLOOR_TYPE_BY_LABEL`). '11층 이상' 의 코드는 `FLOOR_10_PLUS` 고 `FLOOR_11_OVER` 는 400 `VALIDATION_ERROR` 다. 서버가 실제로 거른다 (2026-11-17 실측: 강남역 검색 72건 → `FLOOR_2_10` 46건은 모두 2~10층, `FLOOR_10_PLUS` 19건은 모두 11층 이상. 지도 핀 wydm6 176건 → 120건·30건). 10층 매물은 2-10층에 든다.

### 상가 (`store`)

- 웹 상가 검색처럼 범위 안 위치 목록(`POST /v2/store/article/stores`)을 한 번에 받고 그 순서대로 앞에서부터 요약(`stores/list`, 50건씩)을 받는다 (2026-11-15 번들 `HomeStoreListScreenModel.loadItems`: 응답 순서대로 15건씩, 정렬 없음). 요약 응답 순서에 기대지 않고 보낸 순서로 놓는다. 거리로 다시 세우지 않고 `distance_km` 는 검색 중심에서 잰 덧붙임이다.
- 범위는 `상권`(원: 중심·반경 m, `round(radius_km * 1000)`) 또는 `지역`(법정동 코드 10자리) 중 정확히 하나다 (`ZigbangStoreCircleModel`·`one_scope`). 서버가 범위 안 매물만 준다 (2026-11-15 실측: 역삼역 100m 2건~5000m 12,385건, 가장 먼 매물이 반경 안). 동(읍·면·동) 이름에 `--radius` 가 없으면 `지역` 으로 그 동 코드를 보내고, `○가` 로만 나뉜 동은 코드 여럿을 한 번에 보낸다 (`_store_scope`). 리·구·시·역·학교·좌표는 `상권` 원이다. 웹도 '업종으로 찾기' 화면에서 주소 검색 결과의 법정동 코드를 `지역` 에 문자열 목록으로 보낸다 (2026-11-17 번들 `makeRequestParams` 의 `지역: n.map(e => e.bjdCode)`·`StoreSearchFacilityItemRepository.getParams` 로 확인했고 화면 캡처로는 보지 않았다).
- `지역` 에 모르는 코드(리 코드, 5자리 시·군·구 코드)를 주면 에러 없이 전국 매물을 준다 (2026-11-15 실측: 57,782건). 그래서 10자리 코드만 받고, 리 코드는 그 위 읍·면 코드로 바꾸며, 코드가 없는 동은 `REGION_NOT_SUPPORTED` 로 막는다 (`store_region_codes`). CLI 는 리를 반경으로 찾아 지금은 읍·면 코드로 바꾸는 경로를 타지 않는다.
- 업종 조건을 걸면 응답에 공실 묶음('이 지역 비어있는 상가')이 따로 오고, 웹 지도 목록처럼 업종 묶음의 ID 뒤에 이어 한 위치 목록으로 만든다 (`search_store_listings`: 칸마다 일반 ID 를 앞에, 공실 ID 를 뒤에 이어 요약을 받는 번들 `HomeStoreListScreenModel` 의 `n.concat(r)` 와 같다). 공실 묶음도 범위 안 매물만 오고(2026-11-15 실측: 역삼역 1000m 카페/커피 공실 970건), 업종 묶음과 겹치지 않는다 (2026-11-19 실측: 역삼역 500m 카페/커피 겹침 0. 겹치면 앞 것만 둔다). 공실 묶음에서 온 줄은 `vacant_section` 이 true 이고 `total` 에도 센다. `total` 은 업종(또는 일반) 매물 수 + 공실 묶음 수이고, 공실 묶음이 있으면 `[참고]` 가 그 둘을 나눠 알린다. 공실 줄은 업종과 상관없어 업종 조건으로 줄지 않으므로, 공실 묶음이 있으면 `[일부]` 가 좁히라고 권하는 조건에서 업종을 뺀다 (`STORE_VACANT_NARROW`·`STORE_VACANT_SERVER_NARROW`). `vacant_section` 은 공실 묶음이 있거나 업종 조건이 있을 때 붙고(업종 조건 없이도 공실 묶음이 오면 표시한다), 둘 다 아니면 어느 묶음인지 가릴 일이 없어 키를 지운다 (`not_applicable_fields`). `--fields` 로 골라도 늘 남는다 (`cli/output.py` 의 `ALWAYS_FIELD_GROUPS`).
- 서버 순서는 시간이 지나면 바뀐다 (2026-11-15~16 실측: 연달아 4번은 같았고 20분쯤 사이에 맨 앞 매물들이 달라졌다). jibsa 는 부른 순간의 순서 그대로다 (역삼역 8건이 같은 때 받은 서버 순서와 같음). 상가는 `--next` 가 없다.
- 실측 (2026-11-15~16): 역삼역 1km `total` 2615 → 2578 (반올림 경계가 사라짐), `--business 카페/커피 --limit 60` 은 60건 → 53건 (반경 밖으로 채우지 않음).
- 거래가 끝난 상가(`status: 'close'`)는 위치 목록(`POST /v2/store/article/stores`)에서 빠진다 (2026-11-17 실측: 같은 원(역삼역 1000m)의 11-14 목록 2,579건에서 그 사이 빠진 8건의 요약이 모두 `close` 였고, 오늘 목록의 200m 임대 108건은 모두 `open`). 그래서 `total`(위치 목록 수)과 웹 목록의 'N개'(위치 목록 ID 수)가 같다. 거래가 끝난 매물의 상세는 웹이 '이 매물은 거래가 완료되었거나, 정보를 업데이트 중입니다' 창을 띄우고 jibsa 는 `LISTING_UNAVAILABLE` 을 낸다.
- 서버는 가격 조건을 받지 않는다. 웹 요청이 만드는 필드는 `sales_type`·`면적_gteq`·`면적_lt`·`first_floor`·`업종` 과 `domain`·`shuffle`·`상권`·`지역` 뿐이고 가격·보증금·월세·권리금·관리비 필드는 번들 어디에도 없다 (2026-11-17 번들 `StoreFilterUtils.makeQuery`·`makeRequestParams`). `월세금액_lteq`·`보증금액_lteq`·`권리금액_eq`·`관리금액_lteq`·`매매금액_lteq` 와 다른 이름 10여 개를 넣어 불러도 서버가 조용히 무시해 조건 없는 응답과 ID·순서가 같았고(역삼역 200m 임대 108건), 같은 본문에 아는 필드 `면적_lt: 30` 을 넣으면 0건이 와서 서버가 아는 조건은 건다. 그래서 가격 조건은 요약을 받은 뒤 거르고 가격 필드를 서버에 보내지 않는다 (서버가 무시해 조용히 틀린 결과가 된다. jibsa 가 거른 월세 300 이하 22건은 요약 금액으로 직접 센 수와 같았다).
- 거래 유형(`trade_type`)은 응답의 `sales_title`(매매·전세·월세)로 정한다. 웹 카드·상세가 그렇게 정하기 때문이다 (2026-11-17 번들 `StoreItemCard`·`createMetaData`: 매매면 매매금액, 전세·월세면 보증금액을 쓴다). 요약·상세 응답 모두 이 필드가 있고, 비거나 모르는 값이면 매매가 아닌 것을 임대로 보고 월세금액이 있으면 월세, 없으면 전세로 정한다 (`store_trade`). 지금까지 본 약 2,000건에서는 두 규칙의 답이 같아 출력은 그대로다 (`sales_title` 은 월세·매매뿐이고 전세 상가는 한 건도 없었다). 전세 상가는 표본이 없어 웹 화면 표기를 견주지 못했다.
- 업종이 '사무실' 이고 직방이 권리금을 주지 않으면 `key_money_manwon` 키를 내지 않는다 (해당 없음). 웹 상세는 사무실이면 권리금 줄을 숨기고 (2026-11-17 번들 `renderItemInfoData`), 캡처한 상가 340건에서 권리금이 `null` 인 199건이 모두 사무실이었다 (2026-11-15). 사무실이 아닌 매물의 값 없음은 `null`(모름)이고 값을 줬으면 0 도 그대로 낸다 (`STORE_OFFICE_BUSINESS`). 권리금 조건(`--key-money-*`)을 걸면 이런 사무실은 빼고, 확인한 후보 중 권리금만 빼면 다른 가격 조건에 맞았던 건수를 `[제외]` 로 알린다. 해당 없음을 0 으로 쳐 넣으면 직방이 주지 않은 값을 jibsa 가 만드는 것이라 그렇게 하지 않는다.

### 지역 후보·주소

- `search locations` 는 `/v2/search` 를 오피스텔·아파트로 두 번 부른다 (지역·오피스텔 건물과 아파트 단지가 따로 나온다).
- 세종 주소는 소스마다 시를 한 번 더 넣는다 ('세종 반곡동'·'세종시 반곡동', 상가는 local1·local2 가 둘 다 '세종특별자치시'). `normalize_address` 가 세 경우 모두 뺀다.

## 원본 금액 단위

최종 출력 금액은 모두 만원이고 [금액 규칙](../output-contract.md#금액단위)대로 원 단위까지 낸다. 직방 원본 응답의 단위는 action별로 다르다.

| 원본 응답 | 단위·처리 |
| --- | --- |
| 일반 주거 가격·상가 가격 | 대부분 만원. 해당 response 필드 설명을 확인한다 |
| 원룸·빌라 요약의 `manage_cost`, 웹 목록 요약의 `itemSummaries[].fee` | 원. `won_to_manwon`로 환산한다 |
| 주거 상세 `manageCost` | `amount` 는 만원, `fee` 와 `detail` 의 금액(`totalAmount`·`usageFee`·`normalManageCost`·`etcManageCost`·`avgManageCost`)은 원 |
| 아파트 상세 관리비 | 원. `won_to_manwon`로 환산한다 |
| 실거래 `rtPrice`·`rtPriceRent`·`pynPrice`·`offerPriceDiff` | 만원 정수 (원 단위 원본이 없다). 다시 계산하지 않고 `_manwon` 으로 그대로 낸다 |
| 건물 실거래 `rts` | 만원 |
| 단기임대 응답 금액 | 원. 주당 임대료·관리비·보증금·청소비·반려동물 추가 청소비(`petCleaningFee`) 모두 해당 정규화 경로를 확인한다. 지도 핀의 `weeklyTotalPrice` 는 주당 임대료+관리비(원)이고 `weeklyPrice` 는 그 값을 만원 미만 버린 값이라, 둘 다 정렬에만 쓴다 |

새 필드를 추가할 때 소스 이름만으로 단위를 결정하지 않고 action의 client docstring·response 모델을 확인한다.

단기임대 서비스(`search listings stay`)는 요금이 주 단위라 출력에서도 `rent_manwon`·`manage_cost_manwon` 키를 빼고 `weekly_rent_manwon`·`weekly_manage_cost_manwon` 으로 준다 (공통 출력 계약의 예외).

## 페이지네이션과 조건 처리

유형마다 요청 경로와 필터 적용 위치가 다르다. 원룸·오피스텔의 서버 필터, 아파트 전용면적의 후처리, 상가 가격의 로컬 필터, 단기임대의 주 단위 요금을 하나의 흐름으로 합치지 않는다. 단지 ID의 `apt-`·`officetel-`, 상세 ID의 `store-`·`stay-`·`coalition-` 접두사를 보존한다.

`--limit` 예산은 확인한 원본 수로 세고, 받은 뒤 뺀 매물은 다시 채우지 않는다. 직방에서는 조회 방식마다 이렇게 적용한다.

| 조회 | 예산 | 이유 |
| --- | --- | --- |
| 아파트 (동·구·단지) | 받은 원본 수. 제외한 만큼 채우지 않음 | 조건을 서버가 건다 |
| 원룸·오피스텔·빌라 | 종류별 직방 목록 앞 자리(종류 수로 나눈 `limit`)의 요약만 받음. 채우지 않음. 오피스텔 없이 원룸을 찾았는데 결과에 건물 ID 없는 오피스텔이 있으면 빠진 매물이 있던 지도 칸만(역 검색은 1회) 오피스텔 목록을 더 부른다 (2026-10-11 실측: 역삼동 원룸 1·3·5km 모두 1칸, 전에는 2·4·11칸) | 조건을 서버가 걸고, 원룸은 원룸형 `roomType` 만 요청해 섞여 오는 투룸 오피스텔을 막는다. 원룸 핀에는 건물 ID 가 없어 `complex_id` 를 오피스텔 핀에서 채운다 |
| 오피스텔 건물 | 섹션 순서로 이은 건물 매물 앞 `limit` 개의 요약만 받음. 채우지 않음 | 서버가 거래 유형·가격을 건다 |
| **상가 (예외)** | 직방 목록 앞의 후보를 `max(limit × 5, 60)` 개까지 확인하며 결과를 채움 | 가격 조건을 서버가 받지 않아(2026-11-17 실측: 가격 필드를 보내도 무시한다) 요약을 받은 뒤 거른다. 채우지 않으면 가격 조건을 건 검색이 거의 비어 온다 (2026-10-10 역삼역 1km 임대 월세 300 이하: 75건 중 8건, 보증금 3천·월세 200 이하: 75건 중 4건). 요약은 50건씩이라 요청은 많아야 후보 수 ÷ 50 회다 (`--limit` 20 까지 2회, 60 이면 6회, 120 이면 12회. 2026-10-10 역삼역 실측과 같음) |
| 단기임대 | 고른 순서(검색 API 의 서버 순서 또는 지도 핀을 웹 규칙으로 세운 순서)의 앞 `limit` 개의 요약만 받음. 채우지 않음 | 정렬에 쓰는 값(추천 점수·주당 금액·등록 시각)이 지도 핀에 있고, 이름 검색은 서버가 정렬해 준다. 범위 밖 핀은 요약을 받지 않는다 |

원룸·오피스텔·빌라 검색과 오피스텔 건물 매물, 상가 거래 유형(임대·매매)은 [공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)대로 서버가 건 유형·거래 유형·방 구조를 요약을 받은 뒤 다시 거르지 않는다 (2026-10-10 실측: 원룸·빌라·오피스텔 월세·전세·단기임대와 방 구조 조건 200건, 오피스텔 건물 3곳 34건, 상가 역삼역·성수동 임대·매매 662건 모두 조건 안). 원룸 목록에 섞여 오는 원룸형 오피스텔도 그대로 둔다. 받은 뒤 빼는 것은 거래 불가(`status`), 지원하지 않는 거래 종류, 지도 칸에서 받은 핀 중 반경·동 경계 밖, 원룸 목록과 오피스텔 목록에 함께 있는 매물의 두 번째뿐이다. 직방 매물은 거래 조건이 하나라 거래 조건 선택이 없다. 서버가 받지 않는 조건(아파트 전용면적, 상가 가격)만 받은 뒤 거르고, 값이 없으면 통과시키지 않는다.

검색 조건 묶음([공통 규칙](../provider-conventions.md#검색-조건-묶음))은 유형마다 따로 있다: `ZigbangRoomConditions`
(원룸·빌라·오피스텔 검색과 오피스텔 건물 매물, `common.room`), `ZigbangAptConditions`(`apt`), `ZigbangStoreConditions`(`store`),
`ZigbangStayConditions`(`stay.search`). `--condition`(기타 조건)은 모델에서 `extra_conditions` 다 (`conditions` 는 묶음 이름이라).
매물 유형(`property_types`)은 단지 매물 목록에 없어 `search_listings` 인자로 따로 받고, 단기임대 정렬은 `StaySort` 로 받는다.

핀 집계·조회한 원본 수·가격 확인 후보 수·최종 반환 수를 구분한다. 가격·관리비 없음 옵션의 충돌은 CLI에서 거절한다. 라벨 옵션(업종·방 구조·단기임대 방 종류·옵션·할인·층)은 CLI 의 `split_csv` 가 허용값으로 검증하고, service 는 검증된 라벨만 받는다. 라벨 → 서버 코드 사전(`*_BY_LABEL`) 조회의 KeyError 는 입력 오류가 아니라 내부 오류라 따로 잡지 않는다 (2026-10-10 실측: 잘못된 라벨 7종 모두 요청 전에 `INVALID_ARGUMENT`). 실거래 전세·월세는 혼합 응답에서 필터하며, 쪽 수 상한 없이 넘기면 `--limit 1000` 에 요청이 62회까지 나가(2026-10-10 실측: 헬리오시티 전세) 당근처럼 24쪽(최근 1200건)에서 멈추고 `notes` 로 본 범위를 알린다. 매매는 받은 거래를 모두 써서 `--limit` 최대 1200 도 24쪽이면 된다. 갱신 여부는 알려지지 않았으면 `null`이다.

## API 변경 시 점검

호스트·API 묶음별 헤더(`PLATFORM_HEADERS`·`APT_HEADERS`·`STAY_HEADERS`)·재시도는 client, 유형별 필터 직렬화는 request, catalog·핀·요약·상세는 response를 확인한다. service의 상세 보완 호출과 만료 판정, 아파트 상세로 넘기는 404 `code`(`APT_DETAIL_NOT_SUPPORTED_CODE`), 아파트·제휴 매물의 누락값을 함께 확인한다. 웹을 다시 배포하면 `sdk-version` 값이 바뀌어 매주 월요일 API 감시가 고장으로 알리니, 감시 내용의 웹 값으로 맞춘다. 단기임대 위약금 표(`STAY_REFUND_RULES`)가 웹 번들과 달라져도 같은 감시가 알리니, 알림이 보여 주는 웹 표로 맞춘다.

## 웹과 다른 점

[웹 화면과의 대응](../provider-conventions.md#웹-화면과의-대응) 원칙 안에서 직방 웹과 다르게 한 곳을 모은다. 2026-11-15 에 아파트 매물 상세, 원룸·빌라·오피스텔 목록 관리비와 상세 관리비 포함 항목, 아파트 목록의 묶음 줄, 실거래 평형 이름, 단기임대 매물 주소·할인 문구를 웹 화면과 맞췄고, 2026-11-15~16 에 원룸·빌라·오피스텔·상가·단기임대·아파트 매물 검색, 오피스텔 건물 매물, 같은 이름 지역·역 처리, 역 주변 단지(`search complexes`)를 웹 화면과 맞췄다. 2026-11-17 에는 2026-11-14~15 대조에서 웹과 다르지만 사실은 어긋나지 않는다고 본 나머지 차이(`real-price` 의 쪽 크기·기본 거래 유형·전세와 월세 나누기, `complex` 의 학군 수, `search locations` 의 단지 후보, 조건 값을 웹 눈금 밖으로 주기 등)를 아래에 옮겨 적었고, 확인하지 못해 남겨 둔 네 곳(아파트 신규분양 카드, 제휴 매물 상세, 상가 거래 종료, 상가 가격 조건)을 웹 화면·요청·번들로 확인했다. 그 네 곳에서 사실이 어긋난 곳은 없었다. 같은 날 단기임대 주차·위약금 표기, 상가 거래 유형(`sales_title`), 사무실 권리금 키, 아파트 묶음 줄의 `id` 순서(직방 응답 순서)와 매물 종류(`listing_kind`)를 웹에 맞췄다. 전세 상가는 표본이 없어 웹 화면 표기를 견주지 못했다. 또 같은 날 웹 화면에만 있던 값(아파트 실거래의 동·등기·신고가·신저가·평당가·전세가율·분양가 대비 차액, 아파트 매물의 평형·확인일·실매물 확인·위반 건축물·중개대상물 종류, 단기임대 상세의 주방·거실·주차·반려동물·입퇴실·예약 불가 기간·위약금 표)과 실거래 `--trade 전체`·아파트 `--no-new-sale`·단기임대 층 조건을 더했고, 웹과 다른 곳은 아래 항목('실거래 평당가' 부터)에 적었다. 2026-11-19 에는 또 웹 화면에만 있던 값(원룸·빌라·오피스텔 상세의 확인일·실매물 확인·HUG 안심임대인·위반 건축물·주변 생활 시설·배송 업체·건물 실거래·관리비 미포함 항목·부과 기준·방식, 아파트 상세의 HUG 안심임대인·찜 수·관리비 기준, `search complexes` 의 학교·동·구·`--order`·`highlight`, 상가 업종 검색의 공실 묶음, 실거래 전월세의 동)을 더했고, 웹과 다른 곳은 아래 항목('건물 실거래를 모두' 부터)에 적었다.

- **아파트 묶음 줄에 `listing_ids`.** 웹 카드는 묶인 매물 ID 를 보여 주지 않고, 누르면 그 호의 묶음 화면에서 중개사별 매물을 보여 준다. jibsa 는 같은 카탈로그 응답의 `itemIdList` 중 상세를 볼 수 있는 ID 를 `listing_ids` 로 덧붙이고 `id` 를 그 맨 앞으로 둔다. 묶음 화면이 보여 주는 매물을 ID 로 옮긴 것이고 줄의 가격·`url` 은 웹 카드와 같아, 매물·가격·순서는 바뀌지 않는다 (2026-11-15, `isPriceRange`·`itemIdList`).
- **아파트 목록 모든 줄에 `catalog_id`.** 웹 카드는 묶음 ID 를 보여 주지 않고 누르면 그 호의 묶음 화면으로 간다. jibsa 는 그 화면이 받는 호 ID·거래 유형을 모든 줄에 `catalog_id` 로 덧붙인다. 같은 카탈로그 응답의 `areaHoId`·`tranType` 을 옮긴 것이라 줄의 매물·가격·순서는 바뀌지 않는다 (2026-11-15, 번들 `ItemCard_AptItemCatalogCard` 의 `onPress`).
- **`catalog` 는 묶음 매물을 한 번에 끝까지.** 웹 묶음 화면은 20건을 보여 주고 스크롤하면 다음 20건을 받는다. jibsa 는 같은 API·같은 쪽 크기로 `itemCount` 까지(앞 120건까지) 이어 받아 한 번에 낸다. 매물과 순서는 웹이 스크롤로 보여 주는 것과 같다. 상세를 볼 수 없는 출처(직방·제휴 밖)는 `listing_ids` 처럼 빼고 `[제외]` 로 알린다 (2026-11-15 실측: 헬리오시티·은마 묶음 270건은 모두 직방·제휴라 빠진 매물이 없었다). 그 밖에는 빼지 않는다 (매물의 `tranType` 이 비어도 묶음의 거래 유형으로 낸다). 웹 묶음 카드는 매물별 관리비를 그리지 않는다 (화면의 '평균 22만원' 은 평형 평균, `/apt/danjis/{id}/room_types`). jibsa 의 매물별 `manage_cost_manwon` 은 같은 응답의 `monthlyCost` 로, 그 매물 상세 화면(`url`)이 보여 주는 금액과 같다 (2026-11-15 실측 51092076: 묶음·상세 모두 220000).
- **목록 관리비가 `itemSummaries` 에 없는 매물.** 웹 카드는 `itemSummaries[].fee` 만 보여 준다. jibsa 는 그 매물이 `itemSummaries` 에 없으면 같은 응답 `items[].manage_cost` 로 대신한다. 같은 응답이 같은 매물에 주는 원 단위 관리비라 웹과 다른 금액을 만들지 않고, 0원 매물은 이 값이 null 이라 0 대신 모름으로 나올 뿐이다 (2026-11-15, `itemSummaries`).
- **목록 관리비를 원 단위까지.** 웹 카드는 관리비를 0.1만원 아래를 버려 보여 준다 (375,700원 → '37.5만원'). jibsa 는 같은 `fee` 를 반올림·버림 없이 원 단위까지 낸다 (`37.57`). 같은 금액을 웹이 줄여 보여 줄 뿐이라 사실이 어긋나지 않고, 줄인 값을 내면 실제와 다른 금액을 사실처럼 보여 주게 되어 [금액 규칙](../output-contract.md#금액단위)대로 실제 금액을 낸다 (2026-11-15, `_app` 번들 `toManWonText`·`resolveManageCostText`). 원룸·빌라·오피스텔 상세도 같다: 웹 상세 맨 위 요약줄은 `amount`(0.1만원 아래를 버린 값)를 '37.5만원' 으로 쓰고, 관리비 내역(`detail`)이 없는 매물은 관리비 절에도 `amount` × 10000 원('375,000원')을 그린다. jibsa 는 이때 같은 응답의 원 단위 `fee` 를 낸다. 내역이 있으면 관리비 절이 원 단위 금액(정액 `totalAmount`·실비 `avgManageCost`)을 그려 jibsa 도 그 값이라 같다 (`_manage_cost_manwon`, 2026-11-15 번들 `renderOverviewData`·`renderManageCostData`).
- **단기임대 할인 금액을 만원으로.** 웹 상세는 즉시입주 할인을 '2,500원 할인' 처럼 원으로 쓴다. jibsa 는 금액 필드처럼 만원으로 써 '0.25만원 할인' 이다. 반올림 없이 단위만 바꾼 같은 금액이라 사실이 어긋나지 않는다 (2026-11-15, 번들 `DiscountDetailList`).
- **관리비 포함 항목을 이름 목록으로.** 웹은 정액 관리비를 '일반(공용) 관리비 220,000원', '전기 실비' 처럼 항목별 금액·부과 방식으로 보여 준다. jibsa 는 그 매물에서 관리비 금액에 든 항목의 이름만 `manage_cost_includes` 로 내고 금액은 `manage_cost_manwon` 합계 하나다 (그 밖의 매물은 웹이 그리는 `include` 이름 그대로다). 웹이 금액을 적어 보여 주는 항목만 고른 것이라 포함 여부가 웹 화면과 어긋나지 않는다 (2026-11-15, `renderManageCostData`).
- **실거래 평형 후보 전부를 `pyeong_names` 로.** 웹은 첫 후보와 나머지 수('107A㎡외4', ㎡ 이름)만 보여 준다. jibsa 는 `pyeong_name` 을 평 이름으로 같은 꼴('32A 외 4')로 내고 후보 전부를 `pyeong_names` 로 덧붙인다. 같은 거래의 `areaInfos` 를 그대로 옮긴 것이라 거래·순서는 바뀌지 않는다 (2026-11-15, `areaInfos`).
- **원룸·빌라·오피스텔 섹션 안을 섞지 않음.** 웹은 VIP 밖 섹션 안을 화면에서 무작위로 섞는데 jibsa 는 섞기 전 서버 순서 그대로 낸다. 매물 집합과 섹션 순서는 웹과 같고, 서버 순서는 같은 요청에 늘 같아 이어 받기 자리가 흔들리지 않는다 (2026-11-15, 번들 `_app` 의 `loadSectionsWithItemIdsByGeoHash`·`createSectionsToUpdate`). 오피스텔만은 서버가 섹션 안을 무작위로 섞어 주고 시간이 지나면 다시 섞어, jibsa 는 웹 www 가 보내지 않는 `withoutRandom` 을 늘 보내 섞지 않은 순서(매물 ID 오름차순)를 받는다. 웹이 어차피 화면에서 다시 섞어 섹션 안 순서는 웹에 정해진 것이 없고, 안심추천·안심일반 섹션의 매물은 섞는 요청과 같다 (2026-11-15~16 실측). VIP 섹션의 매물은 요청마다·시간마다 달라진다 (번들 `getOfficetelInquiryBoostingParams`: 웹은 앱 실험군에서만 이 값을 보낸다).
- **원룸·빌라·오피스텔 종류를 한 번에.** 웹은 종류마다 목록이 따로인데 jibsa 는 `limit` 을 종류 수로 고르게 나눠 종류별 묶음을 요청 순서로 잇는다. 종류마다의 목록 앞자리를 그대로 옮긴 것이라 순서·매물이 웹 종류별 목록과 같고, 원룸 목록 '이 지역 오피스텔' 과 오피스텔 목록에 함께 있는 매물은 앞 종류 목록에서만 세고 내(`--next` 로 이어 받아도 한 번) `[참고]` 로 알려 없는 매물을 만들지 않는다. 뒤 종류 목록은 그 매물만 건너뛴 순서라 남은 매물의 순서는 웹 종류별 목록과 같다 (2026-11-15, `RECOMMEND` 섹션·`_split_limit`. 2026-11-16 리뷰로 쪽 사이 겹침도 뺐다).
- **원룸·빌라·오피스텔을 반경·동 경계로 좁히기.** 웹 지도 목록은 화면 사각형인데 jibsa 는 지도 칸 핀 중 반경(반올림 없는 거리)·동 경계 안만 남기고 밖으로 채우지 않는다. 웹이 보여 주는 목록의 부분집합이라 순서·매물이 어긋나지 않는다. 역은 웹 역 목록처럼 서버가 반경을 받아 다시 자르지 않는다 (2026-11-15, `items/subways/{id}`).
- **원룸·빌라·오피스텔 지도 칸 여럿 잇기.** 웹은 화면에 맞는 칸들의 응답을 섹션별로 합치는데, jibsa 는 반경·경계를 덮는 칸들을 섹션 종류마다 칸 순서(`scope_geohashes`)로 잇고 어느 섹션에도 없는 핀은 맨 뒤에 둔다. 섹션 순서는 웹과 같은 순서표(`SECTION_ORDER`)이고, 섹션 밖 핀은 웹에서도 지도에 보이는 매물이라 빼지 않을 뿐이다 (2026-11-15, `createSectionsToUpdate`).
- **원룸·빌라·오피스텔 `limit`·`--next`.** 웹은 15개씩 스크롤로 요약을 받는데 jibsa 는 `limit` 만큼 받고 `--next` 로 종류별 자리를 이어 받는다. 같은 목록을 스크롤로 내려 보는 것과 같은 매물·순서다 (2026-11-15, `items/list`).
- **상가 반경 값.** 웹 상가 검색창은 역·동을 고르면 반경 1000m 원을 보내는데 jibsa 는 `--radius` 값을 같은 `상권` 필드에 미터로 보낸다. 서버가 받는 조합이고 서버가 그 반경 안만 같은 순서로 준다 (2026-11-15 실측: 100m 2건~5000m 12,385건, `ZigbangStoreCircleModel`).
- **상가 동 이름은 법정동 코드로.** 웹 상가 검색창은 역·동을 고르면 `상권` 원을 보내는데, 동 이름에 `--radius` 가 없으면 jibsa 는 웹 '업종으로 찾기' 화면이 주소 검색 결과의 법정동 코드를 문자열 목록으로 보내는 `지역` 필드로 그 동 안을 찾는다 (2026-11-17 번들 `makeRequestParams` 의 `지역: n.map(e => e.bjdCode)`·`StoreSearchFacilityItemRepository.getParams` 로 확인, 화면 캡처로는 보지 않았다). 웹이 보내는 필드이고 서버가 그 동 안 매물만 준다 (2026-11-15 실측: 역삼동 2,568건, 성수동1가·2가 507건). 모르는 코드는 전국을 주므로 10자리 코드만 보내고 없으면 막는다 (`store_region_codes`).
- **상가 가격 조건.** 웹 상가 검색에는 가격 조건이 없어 jibsa 는 직방 목록 앞의 후보 `max(limit × 5, 60)` 건의 요약을 받은 뒤 거른다. 웹에 없는 조건으로 좁히기라 순서는 그대로이고, 다 보지 못했으면 `[일부]` 로 알린다. 서버에 보내지 않는 것은 서버가 가격 필드를 조용히 무시하기 때문이다: 웹 요청이 만드는 필드(`sales_type`·`면적_gteq`·`면적_lt`·`first_floor`·`업종`·`상권`·`지역` 등)에 가격·보증금·월세·권리금·관리비가 없고, `월세금액_lteq` 등 가격 필드 열 개 넘게 넣어도 조건 없는 응답과 ID·순서가 같았으며 아는 필드 `면적_lt` 는 걸렸다. 거른 결과(월세 300 이하 22건)는 요약 금액으로 센 수와 같았다 (2026-11-15 `SCAN_FACTOR`·`MIN_SCAN_PINS`, 2026-11-17 실측: 역삼역 200m 임대 108건, 번들 `StoreFilterUtils.makeQuery`).
- **상가 업종 조건의 공실 묶음.** 웹은 업종을 고르면 '이 지역 비어있는 상가' 묶음을 업종 매물 뒤에 이어 보여 주고(번들 `HomeStoreListScreenModel` 이 칸마다 일반 ID 뒤에 공실 ID 를 `n.concat(r)` 로 잇고 요약을 받는다), jibsa 도 같게 업종 묶음 뒤에 공실 묶음을 이어 `total` 에 센다. 웹에 없는 `vacant_section`(공실 묶음에서 온 줄이면 true)만 덧붙여 에이전트가 업종 매물과 공실을 가르게 하고, `--fields` 로 골라도 늘 낸다. 웹이 보여 주는 매물·순서 그대로라 사실이 어긋나지 않는다 (2026-11-19 번들·실측: 역삼역 500m 카페/커피 업종 묶음과 공실 묶음의 겹침 0).
- **상가 순서는 부른 순간의 서버 순서.** 직방 상가 서버 순서는 시간이 지나면 바뀌어 같은 검색도 웹과 몇 분 차이로 부르면 앞쪽 매물이 다를 수 있다. jibsa 는 다시 세우지 않고 받은 순서 그대로라 같은 때의 웹과 같다 (2026-11-15~16 실측, `HomeStoreListScreenModel.loadItems`). 고치지 않고 사용자 문서에 알린다.
- **단기임대 지도 경로의 범위.** 웹 지도 목록은 화면 사각형 안 핀인데 jibsa 의 좌표·`--radius` 검색은 반경 원(대체 경로는 동 경계) 안 핀을 웹과 같은 규칙으로 세운다. 범위만 좁힌 부분집합이고 그 안의 순서·매물은 웹 지도와 같다 (2026-11-15 실측: 강남역 좌표 추천순 앞 6건이 서버 추천순과 같음, 번들 `sortStayMarkers`·`compareRecommended`).
- **단기임대 검색 결과를 한 번에.** 웹 검색 목록은 스크롤로 요약을 받는데 jibsa 는 고른 순서의 앞 `limit` 건을 by-ids 50건씩 한 번에 받는다. 같은 순서를 앞에서 자른 것이다 (2026-11-15, `guest/items/by-ids`).
- **단기임대 지역 검색 범위.** 동·구 이름은 웹 검색창처럼 직방 검색 결과 그대로라 이웃 동 매물이 섞인다. 다시 거르지 않고 `[범위]` 로 알리며, 학교·대학은 서버가 정하는 범위를 실측하지 못해 `radius_km` 를 내지 않는다 (2026-11-15 실측: 성수동2가 34건 중 17건이 그 동, `guest/items/search`).
- **단기임대 `available`.** 웹은 날짜 고르기 창이 막는 날짜를 고를 수 없게 할 뿐인데 jibsa 는 같은 규칙의 결과를 `true`/`false` 로 알린다. 매물·가격을 바꾸지 않는 출력 보강이다 (2026-11-15, 번들 `resolveScheduleAutofill` 의 `isRangeAvailable`·`isStayRangeFreeOfOccupancy`·`getMaxCheckOut`). 옮기지 못한 조건은 둘이다: 일정 유연성으로 앞뒤 날짜를 자동으로 맞추는 것(`buildOffsets`)은 `listing` 에 `--flexibility` 가 없어 0일만 보고, 웹의 '오늘' 은 브라우저 날짜인데 jibsa 는 한국 날짜로 본다. 웹 달력이 보지 않는 `maxContractWeeks` 는 쓰지 않는다 (실측 최대는 늘 12주).
- **아파트 역·좌표는 그 위치의 동 목록.** 웹은 역을 고르면 주변 단지 목록과 지도 가운데 동의 '○○동 주변 매물보기' 를 보여 주는데, jibsa 는 역·학교 이름과 좌표를 그 위치가 속한 동(`/apt/locals/polygon`, 정밀도 10)의 지역 목록으로 준다. 웹 그 동 화면과 매물·순서·수가 같다 (2026-11-15 캡처·실측: 강남역은 정밀도 7·8 에 서초동, 9 이상에 역 주소와 같은 역삼동).

- **`distance_km`·오피스텔 `complex_id`·`--details` 는 출력 보강.** 원룸·빌라·오피스텔·상가·단기임대의 `distance_km` 는 검색 중심에서 잰 거리를 덧붙인 것이고 순서에 쓰지 않는다 (단기임대 역 이름 검색의 `--sort distance` 는 서버 `STATION_DISTANCE_ASC` 순서다). 웹 원룸 목록은 오피스텔 건물 ID 를 보여 주지 않는데, jibsa 는 건물 ID 없는 오피스텔이 결과에 있으면 그 칸의 오피스텔 핀을 한 번 더 받아 같은 매물에 `complex_id` 만 덧붙인다. `--details` 는 웹 목록 카드에 없고 상세(`/v3/items` 의 `residenceType`·`approveDate`)에만 있는 건물 종류·사용승인일을 앞 30건의 상세(`/house/property/v1/items/{id}/detail`)에서 모아 붙이고 거래가 끝난 매물만 뺀다. 모두 같은 매물에 값만 보태 웹 순서·매물을 바꾸지 않는다 (2026-11-15, `_fill_officetel_complex_ids`·`attach_building_use`).

- **단기임대 `unavailable_periods`.** 웹은 상세의 `schedules` 를 날짜 고르기 창에서 날짜를 막는 데만 쓰고(`isUnavailableSchedule`·`generateDateRange`, 조각 3589·8185) 목록으로 보여 주지 않는다. jibsa 는 같은 일정을 같은 규칙(예약·막힘 유형만, 날짜가 없거나 틀린 일정은 뺌)으로 목록으로 낸다. `available` 과 같은 출력 보강이라 매물·가격을 바꾸지 않는다 (2026-11-17, 조각 3589·8185).
- **단기임대 위약금 표는 웹 번들의 고정 표.** 직방 응답은 정책 이름만 주고 웹이 번들에 고정한 표(`RefundPolicySection`)를 보여 준다. jibsa 는 그 표를 `STAY_REFUND_RULES` 에 옮겨 `refund_rules` 로 낸다. 웹과 같은 표라 사실이 어긋나지 않고, 직방이 표를 바꾸면 주 1회 감시가 알린다. 다른 점은 둘이다: 웹은 `refundPolicy` 가 null 이거나 모르는 코드면 표준 표를 보여 주지만 jibsa 는 정책을 모르는 매물에 표준이라고 단정하지 않고 null 로 낸다. 표 아래 안내('위약금 규정은 임대인 설정에 따라 달라질 수 있습니다', '입주 당일 취소는 불가합니다', '위약금은 결제(예약) 시점의 임대료를 기준으로 합니다', '관리비 / 청소비 / 보증금은 전액 환불 됩니다')는 표에 넣지 않고 사용자 문서가 계약 전 확인을 안내한다 (2026-11-17, 번들 `RefundPolicySection`, 표준 표는 stay-4114·4230·6448 화면과 같았다).
- **단기임대 층 조건 다섯 가지.** 웹 층 필터는 지하/반지하·1층·2-10층·11층 이상·옥탑이고 jibsa 도 같은 다섯을 `--floor` 로 받는다 (`지하`·`1층`·`2-10층`·`11층이상`·`옥탑`). 서버 코드는 `FLOOR_10_PLUS`(`FLOOR_11_OVER` 는 400)이고 10층은 2-10층에 든다. 서버가 실제로 거른 결과라 웹 필터와 같다 (2026-11-17 실측: 강남역 검색 72건 → 2-10층 46건·11층 이상 19건).
- **건물 실거래를 모두·일 단위 날짜·면적 원값으로.** 웹 매물 화면은 건물 실거래를 3건만 보이고 더보기로 5건씩 열며, 날짜를 'YY. M' 로, 면적을 정수로 버려 그린다. jibsa 는 직방이 준 거래를 모두 계약일 최신순으로, 날짜를 `YYYY-MM-DD` 로, 면적을 원값(㎡)으로 낸다. 같은 응답의 같은 거래를 펼쳐 한 번에 내고 웹이 줄여 그리던 값을 줄이지 않은 것이라 거래·순서·금액이 어긋나지 않는다 (2026-11-19, 번들 `loadRestOfDetailData`).
- **주변 생활 시설에 `distance_m`.** 웹은 시설까지 걸리는 분만 그리고 거리는 그리지 않는다. jibsa 는 같은 시설에 직방이 준 거리(m)를 더한다. 분은 웹 `resolveMinute`(`Math.round`)와 같고 시설·순서도 웹 그림과 같다. 웹 필터의 기본(앞 7개)은 적용하지 않고 가까운 시설이 있는 것을 모두 낸다. 응답 값을 보태고 웹이 줄여 보이던 것을 줄이지 않았을 뿐이라 사실이 어긋나지 않는다 (2026-11-19, 번들 `useRequestFacilities`·`FacilitiesAroundWalkingArea`).
- **관리비 부과 기준·방식 코드표와 갈래.** 기준·방식 코드 → 문구 표는 `_app` 번들(2026-11-19)의 표를 그대로 옮겼다. 웹은 정액 관리비가 항목별 내역을 알리지 않았으면(`hasInformed` false, 키가 없으면 사용료 여섯 항목이 모두 미제공·해당 없음) 방식 자리에 방식 코드 `05` 의 문구('중개 의뢰인이 세부내역을 고지하지 않아 전세입자 등을 통해 추정된 관리비를 안내해요.')를 그리고, jibsa 도 같은 판정(`_fixed_cost_uninformed`)으로 같은 문구를 `manage_cost_method` 로 낸다. 다른 점은 하나다. 내역을 알린 정액은 웹이 방식 설명 대신 '정액관리비' 이름표를 그리지만 jibsa 는 `manage_cost_method` 를 null 로 둔다 (방식 문구가 아니라 웹이 정액이라는 갈래에 붙인 이름표라 부과 방식 값으로 옮기지 않으며, 직방이 준 값이 아닌 것을 만들지 않는다). 미포함 항목은 웹이 그리는 갈래(내역 없이 금액만, 내역을 알리지 않은 정액, 실비)에서만 직방이 준 목록을 내고 그리지 않는 갈래(관리비 없음, 내역을 알린 정액)는 `[]` 라 웹과 같다.
- **찜 수는 0 도 내고 원룸·빌라·오피스텔은 키를 지움.** 웹 아파트 매물 화면은 하트 옆 찜 수가 0 이면 숫자를 그리지 않는데 jibsa 는 `zzim_count` 의 0 을 그대로 낸다. 웹이 숨긴 값을 더 보여 줄 뿐이다. 원룸·빌라·오피스텔의 찜 수는 웹 www 에서 그리지 않아(앱에만 있다) 해당 없음이라 키를 지운다 (2026-11-19, `APT_ONLY_DETAIL_FIELDS`).
- **오피스텔 주차 대수.** 웹 오피스텔 매물 정보의 주차는 `/v3/items` 의 `parkingCountText` '세대당 주차 대수 1대' 를 그린다. jibsa 는 상세 `/house/property/v1/items/{id}/detail` 의 `totalParkingCnt` 를 `total_parking_count` 로, 세대수를 `household_count` 로 낸다 (51107063 은 둘 다 33). 33 ÷ 33 = 1 이라 웹이 그리는 세대당 1대와 같은 사실이고, jibsa 는 그 나눗셈의 두 값을 낸다 (2026-11-19, 51107063 응답·번들).
- **`search complexes` 의 동·구는 최근입주만.** 웹 지역 화면에는 최근입주 목록뿐이고 인기 같은 다른 순서로 가는 길이 없다. jibsa 는 웹에 없는 목록을 만들지 않으려고 동·구에 최근입주 말고는 요청 전에 `INVALID_ARGUMENT` 로 막는다. 웹에 있는 목록만 내니 사실이 어긋나지 않는다 (2026-11-19 웹 조사, `complex_order_of`).
- **`search complexes` highlight·주소의 출처.** `highlight` 는 웹 단지 카드 둘째 줄을 글자 그대로 낸다 (탭마다 뜻이 다르다: 인기는 지역 순위, 최근입주는 입주 시기, 시세급변동은 1주 변동률, 평당가는 평당가). 학교·동·구의 `address` 는 카드 첫째 줄('송파구 가락동 · 179세대')의 구·동까지다. 웹 카드가 그리는 글자를 나눠 옮긴 것이라 사실이 어긋나지 않는다 (2026-11-19 캡처, `/apt/danjis/details`).
- **웹에 있지만 내지 않는 값.** 단기임대 1일당 요금·장기계약 할인을 적용한 임대료는 웹이 직접 계산해 버림한 값이라 jibsa 가 같은 값을 만들어 내지 않는다. 아파트 목록 줄의 '실매물 확인' 은 묶음 단위 값이고 분양 줄은 상세와 값이 달라 상세·`catalog` 매물에만 낸다. 실거래 계약일 옆 'N' 표시는 직방이 뜻을 설명하지 않아 내지 않고, 매물 화면의 등록 번호는 `id` 와 같은 값이다. 웹에 있는데 jibsa 에 없을 뿐이라 사실이 어긋나지 않는다 (2026-11-17). 2026-11-19 에 확인하고 내지 않기로 한 값도 같다: 상가 창업비용(웹이 보증금과 권리금을 더해 한 줄로 그리는 값이라 두 값을 이미 낸다), 원룸·빌라·오피스텔 찜 수(웹 www 에서 그리지 않는다), 실거래 한 건의 이력(`/apt/rt-prices/{rtId}/history`, 서버에는 있지만 웹이 부르지 않는다), 건물 층별 호실 그림(`/v2/bls/{pnu}`), 관리비 '확인 불가' 사유 글다. 모두 직방이 준 값을 jibsa 가 만들어 내지 않아 사실이 어긋나지 않는다.
