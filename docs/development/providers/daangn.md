## 소스 고유 구현

### 응답 형식과 요청 규칙

- 매물 상세·단지 정보·구 후기 페이지는 SSR HTML 에 seroval JS 식으로 심긴 라우터 상태(`$_TSR.router=($R=>$R[0]={...})`)의 `dehydratedData.relayRecords`(Relay 정규화 스토어)를 `relay.py` 가 꺼내 `__ref`/`__refs` 를 펼치고, `parser.py` 가 응답 모델로 만든다. 상세의 일부 값은 JSON-LD 에서 읽는다. 스토어가 없으면 `RelayStoreNotFoundError` (CLI 에서 `PARSE_ERROR`).
- 매물 목록은 웹이 쓰는 GraphQL(persisted query 만 받음)로 받는다. 실패도 HTTP 200 의 `errors` 로 와서 service 의 `unwrap_graphql()` 이 판정한다. 해시가 거절되면 대신 찾는 경로 없이 `UPSTREAM_ERROR` 다 (예전에는 동 지도 페이지 SSR 20건에 조건을 직접 걸었다. 웹에 없는 동작이라 #215 에서 뺐다).
- 지역·역·대학 이름은 웹 지도 검색창과 같은 GraphQL(`searchRegion`·`searchSubwayStationPois`·`searchSchoolPois`)로 찾는다. 예전에 쓰던 `www.daangn.com/kr/api/v1/regions/keyword` 는 당근마켓(중고거래)의 지역 API 라 부동산 웹 번들에 없고 좌표·행정동 구분이 없어 뺐다 (#215).
- 입력 타입이 틀리면 "알 수 없는 오류" 가 와서 preschoolByNo·getViewRankingArticles 는 숫자, trendingComplexes 의 regionId 는 문자열로 보낸다 (2026-10-10 실측).

### 브라우저 요청 (2026-11-09 실측)

공통 동작은 [브라우저 요청](../architecture.md#브라우저-요청). 당근만의 값:

- 첫 화면은 역삼동 지도 페이지(`/map/서울특별시/강남구/역삼동`). 당근 웹 지도 화면이라 Referer 가 자연스럽다. 쿠키는
  분석용(`_ga`·`_clck`)뿐이고 API 는 쿠키 없이 응답해 기다릴 쿠키가 없어, load 직후 빈 페이지로 떠난다. 그래서 첫 화면이 실제로
  부르는 사이트 API 는 load 까지의 2건(GraphQL)뿐이다 (2026-11-10 실측: 홈도 load 까지 1건. 지도 페이지를 그대로 두면 2초에
  37건, 10초에 94건으로 늘어, 예전에 적었던 '홈 55번·지도 22번'은 머문 시간에 따른 수였다).
  한 동의 경로라 당근이 지도 주소 꼴을 바꾸면 첫 화면이 4xx 가 되어 모든 당근 명령이 `UPSTREAM_ERROR` 다. API 경로가 바뀔 때와
  같아 매일 API 감시가 잡으면 `browser_entry_url` 을 고친다. 홈으로 다시 여는 경로는 두지 않는다 (평소에 타지 않는 경로라 깨져도
  알 수 없다).
- GraphQL(`realty.kr.karrotmarket.com`)은 `realty.daangn.com` 출처를 CORS 로 허용한다 (`content-type`·`x-realty-platform`,
  credentials 포함). Origin 은 브라우저가 붙인다.
- 헤더 (2026-11-12 실측·번들): 웹 API 클라이언트(ky)는 보내기 전 훅에서 모든 요청에 `x-realty-platform: realty-web` 을 붙인다
  (`graphql_header`. 없으면 GraphQL 이 403 Forbidden). Accept 는 넣지 않아 fetch 기본값 `*/*` 다. 로그인 토큰은 로그인했을 때만,
  `x-realty-ip`·`x-realty-ssr-user-agent` 는 서버 렌더링 때만 붙는다. 모든 요청에 붙일 헤더가 없어 `base_header` 를 두지 않는다.
  매물 상세·단지·구 후기 페이지 HTML 은 웹에서 페이지 열기라 `PAGE_REQUEST_EXTENSIONS` 를 달아 크롬이 페이지를 열 때 붙이는
  `accept`·`upgrade-insecure-requests` 를 붙인다 ([브라우저 요청](../architecture.md#브라우저-요청)의 헤더).

### 매물 목록 경로

- 동 이름의 `search listings`(`search_dong`)는 웹 지도에서 동 거품을 누르면 열리는 목록(`articleByClusterId`, `clusterId: 'REGION:<동 ID>'`, 페이지 넘김 쿼리)이다. 조건이 있든 없든 이 목록을 써서 그 동 매물만 준다 (2026-11-11 실측: 역삼동 100건 모두 역삼동, 쪽 사이 겹침 없음). 웹의 동 페이지(검색 엔진용 첫 화면)는 조건 없이 `articleFeed(originalRegionId)` 를 보여 주는데 주변 동 매물이 섞인다 (역삼동 20건 중 12건이 논현·삼성동). 예전에는 그 피드를 받아 주변 동 매물을 `in_regions: false` 로 표시하고 `○가` 여러 동을 커서 시각으로 합쳤다. 같은 동 이름이 조건 유무로 범위가 달라지지 않게 클러스터 목록 하나로 바꿨다 (#215, 2026-11-11 사용자 결정). `total` 은 웹 지도의 동 거품 수다 (`count_dong_listings`: `articleClusters`, `clusterType: REGION`, 동 단위 `zoomLevel: 8`, 웹이 동 거품을 그리는 줌 12(`REGION_CLUSTER_ZOOM`, mapDev `regionDongMinZoom`. 지역 거품은 줌 8 이상 13 미만에서만 요청하고 12 미만은 구 거품 7, 13 이상은 H3 거품) 의 동 중심 화면 범위, 경계 없이 `includeBoundaries: false`. 웹은 데스크톱에서만 true 이고, 받으면 화면 안 동 140여 곳의 경계로 응답이 1.4MB 였다: 2026-11-12 실측 역삼동 1,380,628 → 18,173바이트, 거품 수는 같다). 조건이 하나도 없으면 동 클러스터 목록·거품 모두 웹처럼 `propertyFilter: null` 을 명시해 보낸다 (`with_null_property_filter`. 매물 수·범위 목록·역 패널은 웹도 빈 필터 `{salesTypes: []}` 다, 2026-11-12 번들 대조). 참고로 웹 검색창에서 동을 고르면 줌 14 로 날아가 H3 거품과 범위 목록을 보여 주고, 이 클러스터 목록은 줌 12~13 에서 동 거품을 눌렀을 때 열린다. 동 피드의 `articlesCount` 는 주변 동까지 세고 1000 에서 잘려 쓰지 않는다 (같은 날 실측: 역삼동 월세 100 이하 거품 726, articlesCount 1000). 카드에 시·도(`name1`)가 빠지면 지역 검색으로 채운다 (`with_sido`, [출력 보강](#웹과-다른-점)). 이 목록은 그 동 매물만이라 동의 시·도로 미리 채운다. 동·지도 범위·역·대학 목록은 받은 매물을 `[:limit]` 로 자르지 않는다 (`_to_listings`). 서버가 `first` 만큼만 주고 요청 크기도 limit 을 넘지 않으며 (2026-11-12 실측: 동 목록 first 2·7 → 2·7건, 지도 범위 목록 3 → 3건, 역 주변 목록 3·7 → 3·7건), 자르면 이어 받기 커서가 잘린 매물 뒤를 가리켜 그 매물이 빠진다. 동 목록은 매물이 남았는데도 `hasNextPage: false` 를 주어 믿지 않고, 쪽이 요청한 수만큼 찼으면 다음 쪽도 받는다 (`connection_edges` 의 `full_page_more`). 2026-11-12 실측: 홍천군 내면은 거품 26건인데 20건 쪽이 false 였고 커서로 이어 받으면 나머지가 왔다. 당근 웹도 이 값을 믿어 목록이 20건에서 멈추는데(같은 날 브라우저 확인: 탭은 '매물 26', 목록은 20건에서 끝나고 다음 쪽을 요청하지 않음) 당근 버그라 따르지 않는다 (사용자 결정). 그렇게 짐작한 '더 있음' 만 받은 원본 수가 거품 수(`total`)에 닿으면 끈다. 거품 수는 첫 쪽을 받은 뒤 다음 쪽을 받기 전에 세어, 매물이 딱 20건인 동의 `--limit 40` 도 빈 쪽을 받지 않는다 (2026-11-12 리뷰). 서버가 `hasNextPage: true` 라고 한 것은 웹도 다음 쪽을 부르므로 끄지 않는다 (거품 수와 목록이 어긋나면 남은 매물을 놓친다, 2026-11-12 리뷰). 이어 받기 표에 받은 수(`received`)를 넣어 `--next` 에서도 센다. 첫 쪽에서 거품 수를 못 받았으면 `--next` 에서 다시 센다 (수가 없으면 짐작한 '더 있음' 을 끄지 못해 빈 쪽을 한 번 더 받는다, 2026-11-12 리뷰). 지도 범위 목록(`articleFeed`)은 `hasNextPage` 가 맞아 그대로 쓴다.
- 좌표의 `search complexes`(`list_bounds_complexes`)는 웹 지도 단지 탭의 '이 영역 단지' 목록(`ComplexListPanelViewportQuery`, `searchComplexes` 에 `input.locationFilter`)이다. 범위 계산·줌 기본(15)은 지도 범위 매물 검색과 같고(`map_view_bounds`, `common`), 조건·정렬·`tradeType`·`exclusiveUseArea` 는 동·구 클러스터 목록과 같다 (ComplexListPanel `X`·`Z` 가 같은 필터 atom 을 쓴다). 페이지 넘김은 `_collect_complexes` 가 둘을 함께 맡는다 (2026-11-12 실측: 역삼동 중심 줌 15 → 736세대 오피스텔부터 세대수 순).
- 구 이름과 좌표의 `search listings` 는 웹 지도 화면의 매물 목록(`search_map_area`)이다. 웹은 지도 화면의 북동·남서 꼭짓점을 `articleFeed`·`articlesCount` 의 `input.locationFilter` 에, 줌의 H3 해상도를 그 밖의 `input.resolution` 에 넣어 최근 순 목록과 '매물 N개' 를 받는다 (MapView `Jt`·`Wi`, MapShell `sf`). 웹 지도는 maplibre(512px 타일)이고, 검색창에서 고른 지역은 `19 − mapViewDefaultZoomLevel`(동 14·구 12·시·도 10), 역·대학은 15 로 연다. 데스크톱(960px 이상)은 지도 왼쪽 메뉴 180px 와 목록 패널 416px(400 + 여백 16, mapPanelOffset)를 뺀 영역을 범위로 보내고 고른 곳을 그 영역 가운데에 둔다. jibsa 는 화면이 없어 1440×900 창 기준(844×900px)으로 같은 식을 계산한다 (`map_view_bounds`. 위도 37.5° 줌 15 는 약 1.6×1.7km). `resolution` 은 웹 데스크톱 표(mapDev `T`)를 따른다 (`map_resolution`). 목록은 서버 순서(최근 순) 그대로 쓰고, `distance_km` 는 화면 가운데까지의 참고값이다. 예전의 반경 검색(`articleMapPoints` 핀 → 가까운 순 → `articlesByOriginalArticleIds` 카드, 반경 밖 이어 붙이기)은 웹 목록과 순서·범위가 달라 뺐다 (#215). 좌표 → 동은 `getRegionByCoordinate`. GraphQL 좌표는 문자열로 보내야 한다. 카드에는 시·도가 없어 지역 검색으로 채운다 (`with_center_sido`·`with_sido`). 구 이름이 중심과 같아도 넓은 화면에는 다른 시·도의 같은 이름 구가 들어와 중심의 시·도는 세종 매물에만 바로 쓴다 (2026-11-12 검증: 울산 남구 삼산동 가운데 줌 9 의 부산 남구 대연동). `articlesCount` 는 1000 에서 잘린다 (웹은 '999+').
- 작성자가 주소를 숨긴 매물(`isHideAddress`)은 `publicCoordinate` 가 실제 위치에서 옮긴 좌표이고 지도 핀(`articleMapPoints`)에 없으며 상세 주소도 동까지만 온다. 그래서 거리를 재지 않고 `distance_km` 를 `null` 로 두며 `hidden_location_notes` 로 알린다. 중심이 있는 검색의 매물은 `DaangnNearbyListing` 이라 거리를 모르면 키를 빼지 않고 `null` 이다 (중심 없는 단지 매물만 키를 뺀다). 2026-10-28 실측: 강남역 역 주변 100건 중 숨긴 18건은 역까지 도보 1~6분인데 공개 좌표가 역에서 0.35~1.78km, 숨기지 않은 82건은 모두 0.21km 안.
- `search listings --station` 은 역 주변 목록(`subwayStationArticleConnection`, 페이지 넘김 쿼리)을 쓰며 카드에 상태·거래 조건·역별 도보 시간이 다 있어 카드를 다시 받지 않는다. `--university` 는 웹 대학 페이지 목록(`universityArticleConnection`, `UniversityArticleListPanelPaginationQuery`)이고 연결 타입이 같아(CommuteArticleConnection) 같은 방식으로 받는다. 대학 둘레 범위는 서버가 정한다 (웹의 `landingRadiusMeter`). 웹 대학 페이지는 지도 필터가 하나도 없을 때만 원룸·투룸·오피스텔(`UNIVERSITY_DEFAULT_SALES_TYPES`, MapShell `Ff` 의 `??ke`)을 기본으로 보내고 역 패널은 빈 필터라, jibsa 도 대학 주변만 조건이 없으면 그 기본을 보내고 `notes` 로 알린다 (2026-11-12 번들 대조). 단지 매물(`list_complex_listings`)은 웹 단지 매물 패널(`ComplexArticleListPanel` 의 `F`)처럼 종류를 안 고르면 주거 5종(`COMPLEX_LISTING_DEFAULT_SALES_TYPES`)이다. 웹은 빈 목록(전체)으로 단지 매물을 부르지 않아 상가는 `-t` 로만 온다. 웹 검색창에서 대학을 고르면 지도 범위 목록이 열리지만, 대학 전용 목록이 있는 대학 페이지를 따른다.
- 역 주변 목록과 출퇴근 역별 매물(`commuteStationArticleConnection`)은 같은 `propertyFilter` 를 받지만 단지 세대수·주차대수(`minHouseholdCount`·`maxHouseholdCount`·`minParkingPerHousehold`)는 무시한다. 2026-10-31 실측: 강남역 아파트 전세 5억 이하가 `--household-min 500`·`--parking-min 1.5` 를 줘도 안 줘도 같은 4건(도시형·17세대 단지 포함), 통근 강남역 5분 안 역들의 아파트 전세 19건도 같았다. 같은 조건의 동 피드는 113건 → 9건이다. 카드에 세대수가 없어 받은 뒤 거를 수 없다. 웹은 이 조건을 그대로 보내 결과가 조용히 틀리므로 jibsa 는 역·대학 주변 목록에 이 조건을 주면 `INVALID_ARGUMENT` 로 막고, 출퇴근 검색은 이 옵션을 두지 않는다 (예전에는 역 좌표의 반경 검색으로 넘겼다, #215 에서 뺌).
- 출퇴근 검색(`search_commute`)은 `nearestCommuteStation` → `commuteStations`(갈 수 있고 조건에 맞는 매물이 있는 역 전부, 요청 1회·페이지 없음. 서버가 매물 조건으로 역을 거른다: 2026-11-13 실측 강남역 조건 없음 411곳·아파트 전세 285곳·연세 0곳. 그래서 0곳이면 역이 아니라 조건에 맞는 매물이 없다고 알린다. 웹 출퇴근 지도의 역 핀·'보고 있는 지역' 탭·역 상세 시간이 쓰는 `CommuteMapViewPinsQuery`) → 역마다 `commuteStationArticleConnection` 으로 매물을 모은다. 역별 매물은 `articlesByOriginalArticleIds` 카드와 필드·값이 같아 (2026-10-11 실측: 역삼역·합정역 20건씩 모양·값 모두 같음) 역 주변 목록처럼 카드를 다시 받지 않는다. 역별 매물은 페이지 넘김 쿼리(`CommuteStationDetailPaginationQuery`)라 `after` 로 100건씩 이어 받는다 (첫 페이지는 기존 `CommuteStationDetailQuery` 와 결과가 같다, 2026-10-10 실측). 웹처럼 회사에서 가장 가까운 역까지 도보 60분이 넘으면 역이 없다고 보고 `NOT_FOUND` 이고(`COMMUTE_MAX_WALK_TO_STATION`, 웹 `useNearestStation`), 회사 역 자체는 찾지 않는다 (예전에는 0분 역으로 넣었다). 역은 웹 '보고 있는 지역' 탭(CommuteFeed `k` 의 `toSorted` durationMinutes)처럼 지하철 시간 순(같으면 서버 순서)으로 세우고 `--max-minutes` 로 거른다. 예전에는 `commuteFeed` 를 50곳씩 4쪽까지 넘기며 '시간 순' 이라는 실측 전제로 앞부분을 끊었는데 번들에 그 보장이 없고 200곳 상한에 걸려 `reachable_stations` 를 덜 셌다 (#215, 2026-11-12 번들 대조). 역 안 매물 순서는 서버 순서 그대로다 (예전에는 통근 시간 순으로 다시 세웠다, #215). 웹이 역 묶음에 보여 주는 '편도 N분'(회사 도보 + 지하철, CommuteFeed `M` 의 `t+e.durationMinutes`)을 `one_way_minutes` 로 주고, 예전의 매물별 합산 통근 시간(매물 도보 + 지하철 + 회사 도보)은 웹에 없는 계산이라 뺐다. 역 묶음의 `route` 는 같은 응답의 `routeWaypoints`(웹 역 상세의 경로)를 출근 방향 구간으로 바꾼 것이다 (`_route`). 서버 경로는 회사 역에서 시작해 타는 역에서 끝나고 역마다의 `lineName` 은 그 역에서 다음 역까지 구간의 노선이라(마지막 역은 앞 노선을 되풀이), 뒤에서부터 (다음 역 → 이 역, 이 역의 노선) 구간을 만든다. 웹 역 상세(CommuteStationDetailView)는 이 순서를 뒤집지 않고 그린다 (2026-11-13 번들 2026-11-v73 대조, 강남역·여의도역 회사 828경로 실측: 모두 역 수 = 환승 + 2, 처음 = 회사 역, 끝 = 타는 역). 서버 경로를 그대로 역·노선 목록으로 주면 출근 방향과 거꾸로이고 노선이 '그 역에서 타는 노선' 으로 읽혀 틀리기 쉽다. 역이 둘보다 적거나 역·노선 이름이 빠졌거나 처음·끝이 회사 역·타는 역이 아니면 짐작하지 않고 `null`(모름)이고, 경로가 없거나 빈 목록이어도 `null` 이다. 역 이름은 `station_name` 으로 맞춘다.

### 위치 찾기 (웹 지도 검색창)

웹 지도 검색창(`MapShell` 의 `$o`)은 이름을 받으면 지역(`searchRegion`)·지하철(`searchSubwayStationPois`)·대학(`searchSchoolPois`)·초중고(`searchSchools`)·단지(`searchComplexes`)를 동시에 찾아 칸별로 보여 주고, 사용자가 하나를 고르면 그 화면으로 간다. 이름의 종류를 짐작하지 않는다. jibsa 도 종류별 입력(지역 이름·`--station`·`--university`)을 따로 받고, 모두 이름이 정확히 같은 곳만 쓴다 (#215). `search locations` 는 다섯 칸을 그대로 준다. 회사 위치(`search commute`)를 웹은 카카오 장소 검색으로 찾는데, 당근 API 가 아니라 쓰지 않고 이 검색들의 좌표를 쓴다. 도로명 주소는 검색창의 주소 모드(`preset: 'address'`, `searchAddress` → 고른 후보를 `unitByAddress` 로 좌표. MapShell `Mo`·`_s`)로 받는다 (`--address`, `find_address`). 이 모드는 웹에서 후기 지도(`xs`, 줌 17)만 켜고 매물 지도 검색창은 켜지 않아, jibsa 는 받은 좌표를 좌표 검색과 같은 줌 15 의 지도 범위 목록·회사 위치로 쓴다 (같은 API 로 더 편하게, #215). 후보가 하나(또는 도로명·지번 주소가 입력과 정확히 같은 하나)일 때만 고르고 여럿이면 `REGION_AMBIGUOUS` 다. 건물 이름은 주소 검색이 찾지 않아 받지 않는다. 다른 소스로 대신 찾지 않는다 ([계층](../architecture.md#계층)).

- 지역(`resolve_area`): `searchRegion` 은 법정동·구·시·도를 중심 좌표·지도 레벨과 함께 시·도 → 구 → 동 순으로 준다 (2026-11-11 실측: '서울' 은 서울특별시·25개 구·동 순으로 100곳이 넘는다). 한 번에 100곳씩 받는다. 동 이름은 비슷한 이름까지 합쳐도 100곳에 못 미치고 (2026-11-12 실측: 중앙동 35곳), 시·도·구 이름은 그 아래 동까지 와서 넘지만 (중구 222곳, 서울 493곳) 시·도·구가 동보다 앞에 와 첫 쪽에 다 있다. 그래서 첫 쪽만 받고, 동만 받는 명령(`popular-listings`)에 구를 주어 그 구의 동을 후보로 셀 때만 나머지 쪽을 받는다 (`_remaining_areas`. 첫 쪽만 보면 '서울 중구' 의 동 74곳 중 23곳만 셌다). 비슷한 지역 후보의 수는 첫 쪽에서 센다. 행정동(역삼1동)·리(양근리)는 주지 않는다. 이름이 비슷한 곳도 섞여 와서(이도이동 → 외도이동·이호이동) 마지막 낱말이 `name3` 과 같은 동, 없으면 `name2` 가 같은 구만 쓴다. 앞 낱말은 시·도·구로 좁히는 데 쓴다 (`place_in`. '강남' 은 강남구에 맞고 '남구' 는 강남구, '동구' 는 성동구에 맞지 않는다). 검색은 마지막 낱말로만 한다. `search locations` 는 웹 검색창처럼 검색어를 통째로 보낸다. 지역 검색은 띄어 쓴 이름도 받아 같은 곳을 준다 (2026-11-12 실측: '강남구 신사동' → 강남구 신사동 1곳).
- 같은 이름이 여러 곳이면 `REGION_AMBIGUOUS`. 동의 예시는 구 이름이 모두 다르면 '강남구 신사동', 구 이름까지 같은 동이 있으면 시·도까지 붙인 후보 이름이다 (`_same_dong_hint`. 2026-11-13 실측: 태평로2가는 서울·대구 중구라 '중구 태평로2가' 를 다시 넣어도 모호했다). 동을 받지 않는 명령(`trending-complexes`)은 같은 이름 동이 여러 곳이면 동을 고르게 하지 않고 `INVALID_ARGUMENT` 로 그 동들의 구(시·도까지 붙인 이름)를 준다 (`_dong_not_accepted`. 한 곳이면 `trending_region_of` 가 그 구를 권한다). 시·도는 그 아래 구를, 구가 있는 시('수원시')는 시 노드가 오지 않고 '수원시 권선구' 처럼 시 이름이 붙은 구가 와서 그 구를, 세종은 동을 후보로 준다. 이름이 같은 곳이 없고 비슷한 지역만 있으면 그 지역을 후보로 `REGION_AMBIGUOUS` 다 (`성수동` → 성수동1가·2가). 역 이름('강남역')은 지역 검색이 역 둘레 동(역삼동)을 비슷한 지역으로 줘서 후보를 권하지 않고 `REGION_NOT_FOUND` 로 끝내 CLI 가 `--station` 을 알린다.
- 역(`find_station`): 역 검색은 앞부분이 같은 역을 모두 주고 주소가 없어, '역' 을 뗀 이름이 같은 역만 고른다. 같은 이름 역(양평: 경의중앙선·서울5호선)은 웹 역 화면처럼 첫 역을 쓰고 다른 역을 노선 붙인 이름으로 `notes` 에 알린다 (`same_station_notes`). 그 이름('서울5호선 양평역')을 주면 그 노선이 다 있는 역만 본다.
- 대학(`find_university`): 캠퍼스마다 따로 오고 `name` 은 대학 이름, `fullName` 은 캠퍼스까지 붙인 이름이다 (2026-11-11 실측: 연세대학교 → 국제·미래·신촌캠퍼스). 본교는 `fullName` 이 null 이기도 하다 (2026-11-13 실측: 고려대학교 본교 null, 세종캠퍼스 '고려대학교 세종캠퍼스'). 대학원은 `name` 이 따로라('경영대학원') 대학 이름에 섞이지 않는다. 먼저 웹 검색창이 보여 주는 이름(`fullName ?? name`, MapShell `uu`, `university_label`)이 입력과 같은 곳이 하나면 그곳을 쓰고, 아니면 `name`·`fullName` 이 같은 곳을 보아 여럿이면 `REGION_AMBIGUOUS` 다 (예전에는 `name`·`fullName` 만 봐서 '고려대학교' 가 본교·세종캠퍼스로 늘 모호했고 후보 '고려대학교' 를 다시 넣어도 같았다). 캠퍼스 이름은 대학 이름(첫 낱말)으로 검색해 맞춘다. 웹 대학 검색 쿼리(`fetchUniversitySearchResultQuery`)는 변수가 `input`·`first` 뿐이고 `pageInfo` 가 없어 다음 쪽을 받을 수 없다 (2026-11-13 번들 대조, 웹은 4곳). 그래서 요청 모델의 상한 50곳(`UNIVERSITY_CANDIDATES`)을 받고, 50곳이 다 오면 잘렸을 수 있다고 본다: `search locations` 는 `[일부]` `notes`, `find_university` 는 첫 낱말 검색에서 못 찾으면 이름 전체로 한 번 더 찾고 그래도 없으면 `REGION_NOT_FOUND` 힌트에 알린다 (예전에는 20곳이라 고려대학교 23곳 중 치의학대학원 안암캠퍼스 등 3곳이 알림 없이 빠졌다).

### 세종·리 주소

- 세종은 시·군·구가 없어 매물·지역 검색 모두 `name2` 가 `''` 로 오므로 빈 구 이름도 채우는 대상이다 (2026-10-11 실측: 빼면 주소가 '반곡동' 만 나갔다).
- 인기 매물 순위는 동이 속한 구 단위인데, 세종은 그 동 안에서만 매긴다 (새롬동 7건·반곡동 1건이 모두 그 동, 자곡동은 강남구 다른 동 28건). 웹 순위 화면(`PopularArticleRankingPanel`)은 탭 없이 URL(`popular_articles=<지역 ID>:<종류>`)로 종류 하나를 받아 `salesTypes:[종류]`·`limit:30` 으로 부르고, 종류는 원룸·투룸·아파트·오피스텔만 받는다 (mapSearchSchema `Qe`). jibsa 도 그 네 종류 중 하나·30위까지만 받는다 (`POPULAR_PROPERTY_TYPES`·`POPULAR_MAX_LIMIT`, #215. 예전에는 11종·여러 종류·최대 100·기본 20). 종류 없는 전체 순위는 웹에 화면이 없지만(홈 CEO 그리드만 구 ID·전체·12건) 서버가 구 전체 순위를 주어 남겼다. `tradeTypes: []` 는 Relay `Literal` 인자라 변수로 보내지 않는다 (2026-11-12 번들 대조).
- 세종(`세종`)은 지역 검색에서 시·도(`세종특별자치시`, ID 1241)로 온다. 그 ID 로 부르면 실거래 피드는 세종 전체를 주지만 단지 목록(`searchComplexes`)은 0건이고 구 후기 페이지도 없어 (2026-10-11 실측) 지역 실거래만 세종 전체로 찾고(`resolve_realsale_region(sejong_whole=True)`) 그 밖은 세종의 동을 고르게 한다.
- 동·구를 받는 지역 실거래·단지 목록·후기와 `search listings` 에 단지 이름을 주면 지역 검색에 없어 `REGION_NOT_FOUND` 다. 이때만 CLI(`_complex_name_hint`)가 단지 후보를 3곳 물어 이름이 든 단지의 ID·주소를 힌트에 싣는다. 지역 검색이 단지 이름에 비슷한 지역을 주면(`은마` → 은하면) `SimilarAreasError`(`REGION_AMBIGUOUS`)라 그때도 묻고, `역삼` → 역삼동 처럼 지역을 찾던 이름일 수도 있어 지역 후보는 두고 단지를 힌트 끝에 덧붙인다. `complex.py` 가 `region.py` 를 가져와 서비스에서 단지 검색을 부르면 순환 import 라 CLI 에 둔다.

받기와 거래 유형 고르기만 바꿔 끼운다), 전월세의 계약 종류는 웹 배지(ComplexTopicPanel `pd`: `useRenewalOfContractRight` → '갱신', `contractType === 'RENEWAL'` → '재계약')와 1:1 로 `contract_type`(`contract_type_of`)·`renewal_right` 둘로 않는다. 지역 실거래는 계약 종류 없이 오기도 해서 그때는 `null` 이다. 지역 실거래 카드의 신고가 배지와 '직전 최고가 대비' 는 웹 카드(MapShell `yc`: `isNewHigh===true && !cancel`, SALE 이고 해제가 아닐 때 `Un(tradePrice, previousMaxPrice)`)와 같이 일반 피드에도 `realsale_summary`)은 덤 조회라 본 조회 뒤에 묻고 실패하면 `summary: null` 과 `partial_failure_note` 다. 시세 그래프 응답의 `latestKbSale`(원)은 `kb_sale_of` 가 만원으로 바꿔 `price-trend` 에 붙인다.
- 학교 카드(`_web_school_card`)는 ComplexSchoolSection `Ve`·`He`·`Ue`·`G`·`Re`·`L` 을 따른다: 분은 `Math.round` 로 견주고 표기는 최소 1분(`_web_minutes`), 20분 안 학교가 없으면 시간·거리 순 첫 학교, 배정 학교의 시간·거리는 `workingTime`·`distance` 대체값을 쓴다 (2026-11-12 번들 대조).
- 평형: 당근 웹은 아파트형 단지(`APARTMENT`·`MIXED_USE`·`REDEVELOPMENT`, services2 `Os`)에 공급 평 묶음(`supplyPyeongAreaGroups`)이 있으면 평형을 그것으로, 아니면 전용면적 묶음(`exclusiveAreaGroups`)으로 고른다 (utils `n()`). 실거래(`useTransactionComplexPagination_Query`)·시세 그래프(`useTransactionComplexRefetchQuery`)는 공급 평형이면 그 묶음 평형들의 타입 코드(`ptpCds`)를, 아니면 `exclusiveUseAreaGroup`(그래프는 `exclusiveUseArea: {g, g+1}` 도)을 보내고 한 단지에서 두 방식을 섞지 않는다 (ComplexTopicPanel `jd` 의 `s`). 그래서 `choose_pyeong` 은 공급 평 묶음이 있는 단지에 `--area` 를 주면 `INVALID_ARGUMENT` 로 막고, 전용 묶음 단지는 없는 묶음도 막는다 (2026-11-12 번들 대조). 타입 코드와 대표 묶음·평형별 세대수(`ptpTotHsehCnt`)·노드 ID 는 단지 비교 칸(`complex_compare`, 약 78KB)에서 받는다 (`compare_column`·`pyeong_groups`·`choose_pyeong`). 단지 페이지 SSR 에도 공급 평 묶음은 있지만 평형별 세대수가 없다. 전용 84㎡ 묶음은 32평·33평 타입을 함께 가져 웹의 32평 목록과 달랐다 (2026-11-12 실측: 헬리오시티 매매 50건 중 28건이 33평. 32평 ∪ 33평의 ptpCds 는 84 묶음과 같은 50건). `real-price` 는 평형을 주지 않으면 모든 평형이고(거래마다 면적이 있다), `price-trend` 는 웹처럼 대표 평형이다 (2026-11-12 사용자 결정). 평형 묶음이 없는 단지는 웹이 고를 평형이 없어(`ai([])` 가 null) 시세 그래프 대신 '아직 등록된 실거래가가 없어요' 만 보여 주므로, `price-trend` 도 그래프를 받지 않고 빈 결과와 안내를 준다 (예전에는 모든 평형을 섞은 평균을 냈다).
- 시세 추이 계산은 웹 그래프(usePriceChartFragment `b`·`m`, PriceChart `X`·`Z`)를 따른다: 기간 탭 1년·3년·전체 = 12·36·180개월, `new Date(올해, 이번 달 - N, 1)` 부터라 이번 달까지 N+1 개 달, 변화율은 기간 안 첫 거래 달과 마지막 거래 달 평균 비교, 거래 달이 둘이 안 되면 탭을 막는다. 그래프 머리의 '최근 3개월 평균'은 이번 달 - 3 부터의 거래 수 가중 평균이고 없으면 12개월 안 마지막 달이다. 예전 비교 그래프 쿼리(`ComplexComparePriceChartQuery`)의 `excludeMonthlyRent` 는 결과를 바꾸지 않았다 (2026-11-12 실측: 84㎡ 전세 106개 달이 같음. 지금 쓰는 `useTransactionComplexRefetchQuery` 에는 이 변수가 없다).
- 단지 비교(`compare_complexes`)는 웹 비교 화면(compare chunk `$`·`he`·`ve`·`_e`·`ut`·`je`·`Ue`·`ge`, managementCost `g`·`v`)을 따른다 (`$` 가 세대수 최다 평형, `he` 는 묶음 목록 고르기): 첫 단지는 대표 묶음에서 세대수가 가장 많은 평형, 나머지 단지는 첫 단지 평형 전용면적의 정수와 묶음별 세대수 최다 평형 전용면적의 정수가 가장 가까운 묶음(같으면 대표 묶음, 그다음 세대수 많은 묶음)이다. 평형 자료(KB·실거래)는 전용면적 묶음 쪽에 있어 타입 코드로 찾는다. 평균 호가는 거래 종류(`__typename`)별로 0원을 뺀 평균(월세는 보증금, JS `Math.round`), 최근 실거래는 그 평형의 매매 첫 건·전월세 5건 중 전세·월세 첫 건(월세는 보증금도 있어야 보여 준다, `Ue`), KB 월세는 보증금과 월세 상한이 모두 있을 때만, 목표 면적 비교에서 전용면적을 모르는 묶음은 건너뛰고(`_e`), 평형 타입 코드를 전용 묶음에서 못 찾으면 평형 칸을 비운다(`ge`). 관리비는 달이 1~12 인 달의 ㎡당 관리비 평균(반올림) × 전용면적이다. 웹은 매매·전세·월세 탭을 하나씩 보여 주지만 jibsa 는 한 번에 주고, `--area` 로 모든 단지의 목표 면적을 정할 수 있다 (jibsa 개선). 목표 면적은 첫 단지 평형에서만 정해, 첫 단지에 평형이 없으면 나머지도 대표 평형이다 (예전에는 평형이 있는 다음 단지의 면적을 이어 써 안내의 '대표 평형' 과 달랐다, 2026-11-12 리뷰). 관리비 연월이 숫자가 아니면 웹(NaN)처럼 그 달을 건너뛴다. 웹과 맞추는 반올림(JS `Math.round`, .5 를 늘 올림)은 `js_round` 하나로 쓴다.
- `trendingComplexes` 는 웹의 인기 급상승 단지(어제 대비 오늘 조회 급상승)다. 웹은 전국(`ALL`)·시·도 탭(`trendingRegionTabsQuery` 의 depth 1)과 시·군·구 페이지(`TrendingRegionSeoQuery`)로만 부르고 동으로는 부르지 않아, jibsa 도 지역 검색의 시·도·구 ID 만 보낸다 (`trending_region_of`, #215. 시·도 ID 는 탭과 지역 검색이 같다: 서울 1·세종 1241). 더 보기 패널(`TrendingComplexListPanelListQuery`)처럼 50곳을 받고, 대표 평형은 대표 묶음에서 세대수(`ptpTotHsehCnt`)가 가장 많은 평형이다 (MapShell `zu`). 예전에 동으로 부를 때는 같은 동도 때에 따라 개수가 다르고 이른 아침마다 비었다 (2026-10-27 실측: 역삼동이 아침 6~8시 감시 7번 중 5번 0곳). 빈 결과는 `notes` 로 알리고, 매일 감시는 빈 목록도 정상으로 본다 (`Step.empty_ok`).
- `nearby-complexes` 는 웹 단지 화면에서 '같은 동 단지' 칸이 추천 '○○와 함께 본 단지'(`ComplexNearbySectionRecQuery`, `complexDetailRecommendation`)로 바뀐 뒤에도 같은 동 단지 목록을 준다. 웹에 남은 호출은 단지 페이지 SEO 로더(`first: 300`)뿐이고 그 본문(ComplexTopicPanel `to`)은 기타 유형(ETC)·기준 단지를 빼고 단지 ID 순으로 세운 뒤 기준 단지 ID 앞뒤에서 번갈아 10곳만 링크로 쓴다. 사용자가 보는 화면이 없는 자료라 jibsa 는 1200곳까지 모두 받아 세대수 순으로 주고(웹과 다른 범위·정렬, 2026-11-12 사용자 결정) 기타 유형 제외만 웹과 같다. 추천은 요청에 실험 그룹(`arm: 'D1'`)·정책 버전·볼 때마다 새 `opportunityId` 가 붙고 `status` 가 `shown` 이 아니면 웹이 칸을 숨기는 실험 기능이라 따라가지 않았다. 같은 동 목록(`ComplexNearbySectionQuery`)은 단지 페이지의 검색 엔진용 본문(숨긴 '○○동 근처 단지')이 아직 부른다. 동 ID 는 단지 페이지 쿼리(`ComplexIdSeoQuery`, `complex_region`)의 `region.originalId` 에서 받고(단지 비교 칸의 `region.id` 는 Relay id 라 동 ID 가 아니다), 카드는 11월 번들에서 사라진 `ComplexNearbySectionCardsQuery`(ba9845…) 대신 지도 단지 목록 카드 `ComplexListPanelMapPinsQuery`(`originalIds`, `tradeType: 'BUY'`)다. 이 카드의 `liveArticleCount` 에는 `total` 이 없어 매매·전세·월세 수를 따로 준다 (#215, 2026-11-12 번들 대조·실측: 역삼동 258곳·화곡동 705곳 카드를 한 번에 받음).

- 단지 근처 어린이집·유치원(`list_preschools`)은 웹 단지 화면 학군의 '더 보기'(`ComplexSchoolListPanelQuery`, `complex_schools`)로 받는다. 당근은 단지에서 1km 안을 가까운 순으로 20곳까지 줘(`PRESCHOOL_SERVER_MAX`), 20곳이면 `[일부]` 로 알린다 (2026-11-11 실측: 예전 반경 쿼리 `educationMapPoints` 와 대조해 역삼래미안은 1km 안 31곳 중 20곳, 양평역한라비발디2단지는 1km 안 11곳 모두). 순서·거리는 웹(`ComplexSchoolSection`)을 따른다: 이 단지 주민 이용 수(`complexResidentCount`) 많은 순, 같으면 학군 정보 좌표(`proptierDanji.coordinate`, 없으면 단지 좌표)에서 시설까지 직선거리 가까운 순이다. 거리는 웹처럼 반지름 6371km 하버사인을 미터로 반올림한 정수(JS `Math.round`)로 견주고 같으면 서버 순서를 지킨다 (`_web_distance_m`. 서버도 거리 순으로 주지만 기대지 않는다. 2026-11-12 번들 대조: 예전에 적었던 '반올림 전 값' 은 틀렸다). 출력의 `distance_km` 는 그 미터 거리를 km 소수 둘째 자리로 반올림한 값이라 순서와 어긋나지 않는다 (계산은 공통 `haversine_km` 에 웹 반지름을 준다). 후기 수는 웹(`surveyResult?.reviewCount ?? 0`)처럼 설문이 없거나 수를 몰라도 0개다 (2026-11-11 번들 대조). 목록에 어린이집·유치원 구분이 없어 `preschool`(`preschoolByNo`)로 본다. 상세의 설문 응답 수(`survey_responses`)도 웹 상세(`Mu` 의 `surveyResult?.responseCount ?? 0`)처럼 없으면 0 이다.
- 개발 호재(`developments`·`development`)와 위치·반경으로 찾던 `preschools` 는 당근 웹이 지도의 개발 구역·교육 시설 레이어 쿼리(`DevelopmentDistrictOverlayQuery`·`EducationPoiLayerQuery`)를 없애 뺐다 (2026-11-10 번들 대조: 지도 쿼리 14개에 없고, 같은 데이터를 주는 다른 쿼리도 없다). 개발 사업 상세(`DevelopmentDetailQuery`)는 웹에 남았지만 주소의 `dev_busi_no` 로만 열리고 사업 번호를 얻을 목록이 없어 함께 뺐다. 레이어 토글 로그 이름(`click_map_development_layer_toggle`·`click_map_education_layer_toggle`)만 남은 것은 기능이 남은 흔적이 아니다. 예전 문서대로 부른 `preschools` 의 뺀 옵션과 없앤 두 명령은 CLI 의 `CHANGED_USAGE` 가 사용법 오류 `hint` 로 새 사용법을 알린다. `preschools` 의 다른 사용법 오류(옵션 오타·인자 누락)에는 붙이지 않고, 지역·역 이름(띄어 써도)은 단지 ID 검사(`complex_id_value`)가 알린다. 옛 절 이름으로 부른 `jibsa guide daangn developments` 는 따로 알리지 않는다. `NOT_FOUND` 의 `hint` 에 절 목록이 나오고, 재개발·재건축은 `docs/llm.md` 의 `재개발` 행이 네이버 명령으로 보낸다.
- 어린이집 전화번호·홈페이지·좌표(거리 계산에만 쓴다), 인기 단지 사진, 단지 비교·좋은 동네의 후기 요약 글은 읽거나 내보내지 않는다.
- 좋은 동네 추천의 라이프스타일 지표(`LIFESTYLE_INDICATORS`)와 기준 연도는 웹 번들에서 옮겼다. 추천 지역(`livableRegionScopes`)은 통계 기준 연도의 시·도 이름이라 광주광역시(24)·전라남도(36)가 아직 따로다 (2026-10-10 실측). `--region` 의 시·도 줄임말·옛 이름·통합 이름은 시·도 앞부분과 시·군·구 이름('광주시' 는 경기도 광주시)을 먼저 본 뒤 정식 명칭으로 맞추고, 전남광주통합특별시('전남')는 두 곳을 모두 넣는다 (`_scope_sidos`). 구가 있는 시의 구는 추천 지역에 '수원시 장안구' 처럼 두 단어로 와서(2026-10-11 실측: 경기 20곳 등 37곳) 전체 이름·구 이름·시 이름(그 시의 구 모두)으로 맞춘다 (`_region_codes`). 옛 이름('광주'·'전라남도')이 한 곳만 찾는 건 추천 데이터가 둘을 나눠 주기 때문이고 지역 이름 해석(`place_in`)과 다른 건 의도다.

## 페이지네이션과 조건 처리

동·지도 범위 목록은 20건씩 최대 6페이지, 역·대학 주변 매물과 출퇴근 역별 매물은 100건씩(역당 CLI 최대 120)이다. 받은 원본 수로 예산을 세고 제외된 결과를 채우지 않는다. 단지 후보·지역 단지는 50개씩 커서로 받고 최대 1200을 적용한다. 기본은 지역 단지 120, 단지 후보 20이다 (`COMPLEX_CANDIDATE_LIMIT`, 비슷한 이름까지 주는 검색이라 앞쪽만 관련 있다). 실거래는 50건씩 최대 24페이지이며 전세·월세는 섞인 전월세에서 골라낸다. 학교는 API에 limit을 보내지 않고 받은 배정 단지를 서버 순서 그대로 거른 뒤 자른다. 이 숫자는 CLI 조회 예산이며 서버의 보편적인 한도로 간주하지 않는다.

실거래의 다음 페이지 커서가 없거나 같은 커서가 반복되면 안내하고 중단한다. 반복된 페이지를 거래 수에 다시 더하지 않는다. 단지 후보·지역 단지·단지 매물·실거래는 모두 다음이 있다던 쪽 뒤에 페이지 정보가 없는(null) 쪽·같은 커서를 돌려준 쪽이면 세기 전에(`stalled_page`), 다음이 있다면서 쓸 항목(null 이 아닌 node)이 없는 쪽·커서 없음이면 센 뒤에(`next_cursor`) 멈춘다. 목록 끝은 늘 항목과 함께 hasNextPage=false 로 와서 이것은 응답이 바뀐 것일 수 있으므로, 멈춤 안내(`cursor_stopped_note`)에 `UPDATE_MAYBE_NEEDED` 를 넣어 매일 API 감시가 결과가 비지 않은 날에도 고장으로 센다. 통근 역 목록(`commuteStations`)은 페이지 없이 한 번에 온다 (2026-11-12 실측: 서울역 60분 495곳). 매물은 가까운 10곳(`COMMUTE_MAX_STATIONS`)만 찾는다. 서버는 지하철 60분 안 역까지만 주어(`COMMUTE_SERVER_MAX_MINUTES`) `--max-minutes`가 60을 넘으면 안내한다 (2026-10-11 실측: 강남역 9쪽 411곳·양평역 42곳 모두 60분에서 목록이 끝났다). 매물 목록(동·지도 범위·역·대학 주변 매물, 출퇴근 역별 매물)은 `connection_edges` 하나가 이어 받고, 다음이 있다면서 쓸 edge 가 없는 쪽·커서 없음·같은 커서 되풀이를 주면 그 쪽을 센 뒤 `next_cursor` 로 멈춰 `cursor_stopped_note` 를 `[일부]` 로 붙인다 (`stalled_page` 는 쓰지 않는다. --limit 을 늘려도 같은 자리에서 멈추므로 --limit 안내 대신 이 안내다). 예전에는 역 주변·출퇴근 매물은 요청 2번 안에 끝난다고 보고 커서 반복 검사를 두지 않았고, 빈 쪽 뒤에도 그 커서를 그대로 `next` 로 돌려줘 `--next` 가 같은 빈 쪽을 되풀이했다 (2026-11-12 리뷰). 지하철 시간이 없는 역은 시간 상한을 확인할 수 없어 제외하며 환승 횟수와 회사까지 도보 시간이 없으면 0으로 만들지 않는다.

CLI는 위치 조회 전에 검색 조건을 검증해 잘못된 조합이 위치 API 요청 제한에 가려지지 않게 한다. 요청 모델도 역전된 금액·면적·세대수 범위와 유한하지 않은 면적·주차 수를 거절한다. 매물 검색 조건 묶음 `DaangnListingConditions`(`common`, 동·지도 범위·역·대학·출퇴근·단지 매물 공통)는 [공통 규칙](../provider-conventions.md#검색-조건-묶음)과 달리 조건 조합(원룸이 아닌데 방 구조, 유형을 골랐는데 아파트·오피스텔이 없는 세대수·주차대수)도 모델에서 검사한다. 세대수·주차대수는 웹 필터(`Gc`)가 유형이 비었거나 아파트·오피스텔이 있을 때만 보내는 것을 따른다 (예전에는 `-t 아파트` 하나일 때만 받았다, #215. 2026-11-11 실측: 역삼동 유형 없이 `--household-min 300` 이 6370건 → 298건). 지역 단지 목록은 `DaangnComplexConditions`(`complex`)다.

매물 유형은 건축물 용도와 방 구조가 섞인 당근 카테고리다. `ONE_ROOM`은 `OPEN_ONE_ROOM`·`SPLIT_ONE_ROOM`을 찾으며 아파트·오피스텔의 방 1개를 포함하는 보편적인 방 수 조건이 아니다. 웹의 방 수 조건도 `TWO`·`THREE`·`FOUR_OR_MORE`뿐이다. 이를 CLI의 원룸 검색 안내와 사용자 문서에 명시한다. 매물 종류는 작성자가 고른 하나라 같은 건물도 갈린다 (2026-10-10 실측: 오피스텔 단지 '엘리젠트' 매물 3건 중 방 1개 1건은 원룸, 2건은 오피스텔로 올라 `-t 원룸`에 1건만 나왔다). 목록 카드에는 방 수(`roomCnt`)가 없고 상세 SSR에만 있으며(목록 5경로·`articleByOriginalArticleId` 원본 확인), 단지 종류(`complex.type`)는 모든 목록 카드에 온다. 그래서 종류를 다시 거르지 않고 안내만 한다. 원룸·오피스텔·투룸 검색의 한계와 `-t 원룸,오피스텔` 은 찾을 때마다 같은 안내라 `notes` 대신 `docs/llm.md` 에 두고, `property_type_notes`는 원룸 외 유형과 `--structure`를 함께 주면 거의 원룸만 오는 점(같은 날 실측: 동 20건 모두 원룸, 역 20건·통근 50건 중 단지 없는 오피스텔 1건씩만 섞임)을 알리고, `complex_building_notes`는 원룸·투룸으로 올렸지만 오피스텔·아파트 단지에 있는 매물을 ID·단지 이름으로 알린다 (추가 요청 없음). `-t 투룸`(TWO_ROOM 카테고리)은 **투룸 이상**(쓰리룸·포룸이상 포함)이고 목록에 방 수가 없어 좁힐 수 없다. 이 점도 `docs/llm.md` 에 있고, 목록의 `room_type` 은 `null`(모름)이다. 상세의 `room_type` 은 유형과 상관없이 방 수를 먼저 보고(2개 이상이면 투룸·쓰리룸·포룸이상), 방 1개거나 방 수를 모르면 원룸 구조만 쓴다 (`room_type_of`, 2026-10-10 실측: 분리형원룸으로 올린 방 2개 매물). 네이버 `_room_type` 과 같은 기준이다. 상세의 `complex_type` 은 SSR 단지(`PropComplex.type`)를 `COMPLEX_TYPE_LABELS` 로 바꾼 것이다. 당근은 도시형생활주택 단지를 `APARTMENT`·`MIXED_USE` 로 준다 (2026-10-10 실측: 블루밍하우스(도시형)·경원하이츠텔(도시형) 등). 이름의 "(도시형)"으로 종류를 바꾸지 않는다. 카테고리·이름으로 추측하지 않는다는 [공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)을 따른다. ㎡ 면적은 일반 매물 전용, 주택·건물·공장 연면적, 토지 대지면적이므로 모든 유형을 전용면적이라고 설명하지 않는다.

### 서버 필터와 직접 거르는 조건

[공통 기준](../provider-conventions.md#서버-필터와-클라이언트-후처리)을 따른다. 동 목록(`articleByClusterId`)·지도 범위 목록(`articleFeed`)·역·대학 주변 매물·출퇴근·단지 매물은 서버가 조건을 건 응답이라 유형·면적을 다시 거르지 않는다. `-t 원룸`에 다른 카테고리가 섞여 와도 그대로 둔다 (2026-10-10 실측: 역삼동·신림동 원룸·오피스텔·투룸·아파트 피드 433건 모두 요청 카테고리 안이었다). 받은 뒤에는 중복·거래 불가를 빼고, 거래 조건이 여럿인 매물은 당근 웹 목록(`services2` 의 `Fo`)처럼 검색한 거래 유형으로만 보여 줄 거래를 고른다 (`trade_of`): 거래가 하나면 그것, 거래 유형이 겹치는 거래가 하나면 그것, 없으면 대표 거래, 여럿이면 그중 대표(없으면 첫) 거래다. 금액은 보지 않고 매물을 빼지도 않는다. 예전에는 금액까지 다시 맞춰 보고 맞는 거래가 없으면 빼서 서버가 준 매물보다 적게 보여 줬다 (#215). 후보는 웹 `Fo` 와 같은 다섯 거래(매매·전세·월세·단기임대·연세, `TRADE_TYPE_BY_TRADE`)이고, 아는 거래가 하나도 없는 매물(거래 조건이 비었거나 당근이 새 거래 유형만 올림)은 고를 거래가 없어 빼고 사유와 수를 `no_trade_notes` 의 `[제외]` 안내로 알린다. 예전에는 연세(YEAR)를 후보에서 빼 제주 연세만 올린 매물이 여기로 빠지고(2026-11-12 실측: 제주시 연동 50건 중 15건, 노형동 50건 중 13건) `listing` 도 `NO_TRADE_INFO` 로 막혔다. `--trade` 없이 금액 조건만 주면 웹처럼 거래 유형을 짐작하지 않고 `notes` 로 알린다. 공통 `infer_trade_types` 는 다른 소스가 짐작에 쓰고, 당근은 `--trade` 를 줬을 때 금액 조건이 걸릴 유형이 있는지만 그 함수로 검사한다. 상세(`listing --trade`)도 웹 상세가 목록 필터의 거래 유형(`filteredTradeTypes`)으로 가격을 보여 주는 것처럼 고르고, 그 거래가 없으면 대표 거래와 `notes` 를 준다 (예전에는 `TRADE_NOT_OFFERED` 에러). `--details`(`attach_details`)도 목록을 받은 뒤 목록의 거래가 내려간 매물을 대표 거래의 유형·가격으로 바꾸고 `notes` 로 알린다 (예전에는 같은 에러로 뺐다).

연세(YEAR, `YearTrade`)는 1년치 월세를 한 번에 내는 제주 거래다 (2026-11-13 실측·번들 2026-11-v73 대조). 목록 카드와 상세 SSR 모두 `{type: YEAR, deposit, yearlyPay}`(둘 다 만원, 보증금 0 도 있다: 4723433 0/500)를 주고 상세에는 `brokerCommissions` 의 `tradeType: YEAR` 중개보수가 있다. 웹 카드는 `연세 {보증금} / {연세}만원`(5014421 '연세 1,000 / 1,400만원')이고 월로 나눈 값은 없어, jibsa 도 `trade_type: 연세`·`deposit_manwon`·`yearly_rent_manwon`(1년치 그대로)으로 내고 `rent_manwon` 은 해당 없음으로 뺀다 (`article_to_listing`). 만원 숫자만 보면 월세로 읽기 쉬워 결과에 연세가 있으면 `emit` 이 그 값으로 읽는 법(`yearly_rent_note`)을 `[참고]` 로 붙인다. 웹 필터는 제주(`isJeju`: 주소에 '제주' 또는 위도 34 미만)에서만 '연세' 칩과 연세 범위(`yearlyPay`, 만원)를 보여 주고, 보증금 범위(`depositPay`)는 MONTH·SHORT·YEAR·BORROW 에, 월세 범위(`monthlyPay`)는 MONTH·SHORT 에만 보여 준다 (services2 `$c`). jibsa 는 `--trade 연세`(`tradeTypes: ['YEAR']`)·`--yearly-rent-min/--yearly-rent-max`(`propertyFilter.yearlyPay`)를 지역과 상관없이 받는다 (2026-11-13 실측: 노형동 `tradeTypes ['YEAR']`·`yearlyPay {maxAmount: 500}` 은 연세 500 이하 매물만). `--trade` 가 연세뿐인데 `--rent-*` 를 주면 연세 범위 옵션을 알리는 `INVALID_ARGUMENT`, 연세 없는 `--trade` 에 `--yearly-rent-*` 는 공통 `infer_trade_types`(`yearly`)가 `INVALID_ARGUMENT` 로 막는다. 연세가 없는 다른 소스의 안내에는 연세를 넣지 않는다 (`SHARED_TRADE_TYPES`).

매물 검색에서 직접 거르는 조건은 없다 (학교 배정 단지의 `-t`·`--household-min` 은 [웹과 다른 점](#웹과-다른-점)). 예전에 필터 API 가 거절되면 조건 없는 지도 페이지 20건에 유형·거래·금액을 직접 걸던 비상 경로는 웹에 없는 동작이라 뺐다 (#215).

GraphQL의 HTTP 200도 `errors`를 검사한다. persisted-query 거절과 그 밖의 upstream 실패를 구분한다. 거절은 `FeedQueryRejectedError`(`JibsaError`, `UPSTREAM_ERROR`)라 따로 안내할 곳(지도 범위·출퇴근 검색, 단지 후보 등)만 먼저 잡고, 나머지 명령은 그대로 `UPSTREAM_ERROR`와 업데이트 안내로 끝난다. 좌표 → 동(`region_or_none`)은 결과 표시와 시·도 채우기에만 쓰여 실패해도(요청 제한 포함) 받아 둔 매물을 돌려준다. 역·대학 주변 목록이 실패하면 다른 목록으로 바꿔 찾지 않고 그대로 에러로 끝난다. 덤으로 받는 조회(`search locations` 의 역·대학·학교·단지 후보, 동 후기 수, 조건에 맞는 매물 수, 지도 범위 검색의 중심 동)가 실패하면 받은 결과는 그대로 돌려주고 `partial_failure_note` 로 이유(API 변경·요청 제한·서버 오류·응답 형식 변경)를 `notes` 에 붙인다. `search locations` 의 실패한 역·대학·학교 칸과 하나도 받지 못한 단지 칸은 `[]` 가 아니라 `null`(모름)이다. 이유마다 다음 행동(업데이트·기다리기·다시 시도)이 달라서다. 업데이트가 필요하다는 끝말은 `UPDATE_NEEDED`·`UPDATE_MAYBE_NEEDED` 상수로만 쓴다. 매일 API 감시가 이 상수를 가져와 `notes` 에서 고장을 찾기 때문이다. 덤 조회(시·도 채우기 `sido_of` 포함)가 잡는 실패는 `JibsaError`·`HTTPError`(요청 제한 포함)와, JSON 이 아닌 응답·응답 모델 검증 실패(`ValueError`)다 (`OPTIONAL_LOOKUP_ERRORS` = 세 소스 공통 `OPTIONAL_LOOKUP_BASE_ERRORS` 에 `JibsaError` 를 더한 것). 덤 조회 하나가 차단 페이지를 받았다고 모아 둔 매물을 버리지 않고, `partial_failure_note` 가 '응답 형식이 달라 업데이트가 필요할 수 있다' 고 알린다. 주된 결과를 받는 조회는 에러(형식 오류는 `PARSE_ERROR`)로 끝내고, 요청 제한은 다음 요청도 같은 제한에 걸릴 때 바로 올린다. 좌표 검색의 실패를 동 검색 성공처럼 출력하지 않는다. 거래 조건이 여럿이면 선택한 거래의 가격·중개보수를 같이 정규화한다. 상태뿐 아니라 숨김·노출 제한·거래 조건 존재도 검사한다. 예약중(`RESERVED`)은 계약이 깨질 수 있어 웹처럼 내보내고 `status` 로 알린다 (2026-11-11 사용자 결정). 비활성 중개소(`bizProfile.status` 가 `ACTIVE` 아님)는 웹 상세(`ArticleDetail`, "비활성화된 중개소의 매물이에요")처럼 상세(`listing`·`--details`)에서만 막는다 (`_inactive_broker`). 목록 카드의 `bizProfile` 에는 상태가 없어(id·badges 만, 상세 SSR 에만 `status`) 웹도 목록에는 보여 주고, 목록에서 막으려면 매물마다 상세를 받아야 한다 (2026-11-11 실측·사용자 결정). 상태 키가 없으면 막지 않는다. 목록·SSR 상세가 같은 노출 상태를 주지는 않는다 (2026-10-10 실측: 목록은 통과했지만 상세에 `ArticleInvisibleInfo_NotVerified` 가 있어 상세가 거절된 매물). 목록에서 매물마다 상세를 다시 부르지 않으므로 상세 수준의 거래 가능 여부를 목록 전체에 보장하지 못한다.

## 웹과 다른 점

[웹 화면과의 대응](../provider-conventions.md#웹-화면과의-대응) 원칙 안에서 당근 웹과 다르게 한 곳을 모은다. 자세한 근거는 각 절에 있고 여기서는 무엇이 다르고 왜 사실이 어긋나지 않는지만 적는다.

- **`nearby-complexes` 의 범위·정렬.** 웹에 남은 것은 단지 페이지 SEO 본문(`first: 300` 중 단지 ID 순 10곳 링크)뿐인데 jibsa 는 같은 쿼리(`complexes(region3Id)`)로 같은 동 단지를 1200곳까지 모두 받아 세대수 순으로 준다. 기타 유형(ETC) 제외는 웹과 같다. 같은 쿼리가 주는 단지를 범위·정렬만 달리한 것이라 단지·수치는 웹 자료 그대로다 ([단지·실거래](#단지실거래), 2026-11-12 사용자 결정).
- **실거래 전세·월세 가르기와 지역 전월세.** 웹은 매매·전/월세 두 탭이고 jibsa 는 웹 카드가 표시에 쓰는 `monthRentFee` 로 전세·월세를 나눈다. 지역 실거래(`region-real-price`)의 전월세(`BORROW`, 서버가 가격 순을 거절해 `LATEST`)는 웹 실거래 화면이 보내지 않는 조회다. 같은 API 가 받는 변수로 받은 거래 한 건 한 건은 웹 카드와 같다 ([단지·실거래](#단지실거래)).
- **지역 단지 목록의 최근 실거래 3건.** 웹 단지 카드(ComplexListItem)는 해제되지 않은 첫 1건만 보여 주는데, `search complexes` 의 `recent_trades` 는 같은 카드 응답에 온 거래를 앞에서부터 3건(`COMPLEX_RECENT_TRADES`)까지 준다. 학교 배정 단지는 웹처럼 1건이다. 같은 응답의 거래를 순서대로 더 보여 준 것이라 거래 한 건 한 건은 웹 자료 그대로다 ([단지·실거래](#단지실거래), 2026-11-12 사용자 결정).
- **학교 이름 줄임으로 한 번 더 찾기.** `school` 에 '○○초등학교' 처럼 종류까지 주면 웹 검색창처럼 그 이름으로 찾고, 이름이 그대로 같은 학교가 하나뿐이 아니면(없거나 여럿) '○○초' 로도 찾아 합친다 (`resolve_school`, `SCHOOL_KIND_SHORT_NAMES`. 같은 학교가 하나면 그 학교라 더 찾지 않는다. 여럿이면 후보 목록에 줄인 이름으로만 나오는 학교까지 넣는다: '도곡초등학교' 는 경기 광주·화순 두 곳뿐이고 '도곡초' 에는 서울도곡초등학교도 나온다, 2026-11-13 리뷰·실측). 당근 검색은 '대치초등학교' 로 서울대치초등학교를 못 찾는데(웹도 0건) '대치초' 로는 찾는다. 같은 검색 API 에 웹 검색창에 넣을 수 있는 다른 이름을 보낸 것이라 찾은 학교는 웹에서 '대치초' 로 찾아도 나오는 학교이고, 여럿이면 고르지 않고 후보를 알린다 (2026-11-12 실측, 사용자 결정).
- **페이지 크기.** 서버가 받는 만큼 한 번에 더 받는다. 단지 목록 50(웹 20), 단지 매물 20(10), 역·대학 주변 100(10), 출퇴근 역별 100(10), 실거래 50(4~20), 지역 검색 100(4), 대학 검색 50(4. 이 쿼리는 다음 쪽이 없어 50곳이 다 오면 `[일부]` 로 알린다), 후기 1(20, 후기 수만 쓴다). 동·지도 범위 목록은 웹처럼 20 이다. 같은 목록을 더 긴 쪽으로 받은 것이라 매물·순서는 같다 ([페이지네이션과 조건 처리](#페이지네이션과-조건-처리)).
- **동 목록의 `hasNextPage: false` 를 믿지 않는다.** 웹은 이 값을 믿어 거품 수가 더 많은데도 20건에서 멈추는 당근 버그다. jibsa 는 쪽이 찼으면 커서로 이어 받고, 그렇게 짐작한 '더 있음' 은 거품 수(`total`)에 닿으면 끈다 (서버가 true 라고 한 것은 웹처럼 따른다). 같은 목록을 커서로 이어 받은 것이고 `total` 은 웹 지도에 보이는 거품 수다 ([매물 목록 경로](#매물-목록-경로), 사용자 결정).
- **웹에 없는 조건으로 좁히기.** `--max-minutes`(웹은 갈 수 있는 역 전부를 시간 순으로 보여 준다), `--years`(실거래 연결에 기간 인자가 없어 받은 뒤 계약일로 거르고 기간 앞 거래가 나온 쪽에서 멈춘다), 신고가 `--previous-days`(웹은 최근 공개일만 보여 주지만 같은 변수 `includePreviousDays` 를 서버가 받는다), `school` 의 `-t`·`--household-min`(`schoolByCode` 가 받지 않는 조건이라 받은 배정 단지를 서버 순서 그대로 둔 채 단지 유형(`아파트` 는 주상복합 포함)·세대수로 거르고 `--limit` 으로 자른다). 모두 웹 결과의 부분집합이거나 서버가 받는 변수다 ([출퇴근](#매물-목록-경로)·[단지·실거래](#단지실거래)).
- **탭을 한 번에, 평형을 한 번에.** `compare` 는 웹의 매매·전세·월세 탭을 한 번에 주고 `--area` 로 모든 단지의 목표 면적을 정할 수 있다 (웹은 첫 단지 평형으로만 정한다). `real-price` 는 평형을 안 주면 웹 평형 탭을 모두 합친 모든 평형이다 (거래마다 면적이 있어 어느 탭의 거래인지 안다. `price-trend` 는 웹처럼 대표 평형). 칸 하나하나의 값·계산식은 웹과 같다 ([단지·실거래](#단지실거래)).
- **종류 없는 `popular-listings`.** 웹 순위 화면은 종류 하나를 꼭 받지만(홈 그리드만 전체·12건) 서버는 구 전체 순위를 주어 남겼다. 서버가 그대로 주는 순위라 다시 세우지 않는다 ([세종·리 주소](#세종리-주소)).
- **대학 주변은 대학 페이지 목록.** 웹 검색창에서 대학을 고르면 지도 범위 목록이 열리지만, 대학 전용 목록(`universityArticleConnection`)이 있는 웹 대학 페이지를 따른다. 그 페이지의 기본 종류(원룸·투룸·오피스텔)도 그대로 보내고 `notes` 로 알린다 ([매물 목록 경로](#매물-목록-경로)).
- **대학 후보가 잘렸을 때 이름 전체로 한 번 더 찾기.** `--university` 는 대학 이름(첫 낱말)으로 찾고, 50곳이 다 왔는데 이름이 같은 곳이 없으면 이름 전체로 한 번 더 찾는다. 웹 검색창에 그 이름을 넣은 것과 같은 검색이라 찾은 캠퍼스는 웹에서도 그 이름으로 나오고, 여럿이면 고르지 않고 후보를 알린다 (2026-11-13).
- **`--address` 를 매물 지도와 회사 위치에.** 웹 검색창의 주소 모드(`searchAddress` → `unitByAddress`)는 후기 지도에서만 켜지고 매물 지도 검색창에는 없다. jibsa 는 같은 API 로 받은 주소 좌표를 `search listings` 에서는 좌표 검색과 같은 줌 15 의 지도 화면 범위로, `search commute` 에서는 회사 위치로 쓴다. 주소는 좌표를 얻는 데만 쓰고 그 뒤 목록은 웹 지도를 그 좌표로 옮긴 화면·그 좌표를 회사로 둔 출퇴근 지도와 같은 API·변수라, 매물·순서는 웹에서 그 자리를 보면 나오는 것이다. 찾은 주소는 `search listings` 는 결과의 `address`, `search commute` 는 `[범위]` `notes` 로 알린다 ([위치 찾기](#위치-찾기-웹-지도-검색창), #215).
- **출퇴근 회사 위치를 당근 검색으로.** 웹 출퇴근 지도는 회사 위치를 카카오 장소 검색으로 찾는데, 당근 API 가 아니라 jibsa 는 쓰지 않고 동·구 중심(`searchRegion`), 역·대학·도로명 주소 좌표(웹 검색창과 같은 당근 검색)나 `--lat/--lng` 를 회사 위치로 쓴다. 좌표가 정해진 뒤의 가까운 역·갈 수 있는 역·역별 매물은 웹과 같은 API(`nearestCommuteStation` → `commuteStations` → `commuteStationArticleConnection`)라, 웹에서 같은 자리를 회사로 고르면 같은 결과다. 고른 회사 역은 결과의 `workplace_station` 으로 알린다 ([위치 찾기](#위치-찾기-웹-지도-검색창)·[매물 목록 경로](#매물-목록-경로), #215).
- **출퇴근 매물은 가까운 10곳 역만.** 역 목록(`reachable_stations`)은 웹 탭처럼 전부 세고 매물은 지하철 시간 순 앞 10곳(`COMMUTE_MAX_STATIONS`)만 받는다. 역 순서가 웹 '보고 있는 지역' 탭과 같아 앞부분을 끊은 것이다 ([페이지네이션과 조건 처리](#페이지네이션과-조건-처리)).
- **출퇴근 경로는 출근 방향 구간으로.** 웹 역 상세(CommuteStationDetailView)는 서버 `routeWaypoints` 를 회사 역부터 타는 역까지 그대로 그리고, 역마다 붙은 노선은 그 역에서 다음 역까지 구간의 노선이다. jibsa 의 `route` 는 같은 경로를 뒤에서부터 읽어 타는 역 → 회사 역 방향의 구간(`from_station`·`to_station`·`line`)으로 준다. 역·노선은 서버 경로 그대로이고 방향만 바꾼 것이라 웹 역 상세와 사실이 같다. 처음이 회사 역·끝이 타는 역이 아니거나 역·노선 이름이 빠지는 등 모양이 다르면 짐작하지 않고 `null` 이다 ([매물 목록 경로](#매물-목록-경로), 2026-11-13 번들 2026-11-v73 대조·강남역·여의도역 회사 828경로 실측).
- **역·대학 주변의 세대수·주차 조건을 `INVALID_ARGUMENT` 로 막는다.** 웹은 이 조건을 그대로 보내고 서버가 무시해 조용히 틀린 결과를 보여 준다. 틀린 결과를 웹처럼 내지 않고 막는 쪽을 골랐다 ([매물 목록 경로](#매물-목록-경로), 2026-10-31 실측).
- **연세를 제주 밖에서도 받는다.** 당근 웹은 제주(`isJeju`)에서만 '연세' 칩과 연세 범위(`yearlyPay`)를 보여 주지만 jibsa 는 `--trade 연세`·`--yearly-rent-*` 를 지역과 상관없이 같은 서버 변수(`tradeTypes: ['YEAR']`·`propertyFilter.yearlyPay`)로 보낸다. 웹 UI 에 없지만 서버가 받는 조합이라 나온 매물은 웹 목록에도 연세 카드로 나오는 매물이고, 금액도 웹 카드('연세 1,000 / 1,400만원')처럼 1년치 그대로다 (월로 나누지 않는다). 거래 고르기는 웹 `Fo` 와 같다 ([서버 필터와 직접 거르는 조건](#서버-필터와-직접-거르는-조건), 2026-11-13).
- **직전 최고가 대비 비율을 소수 둘째 자리로.** 웹 실거래 카드(RealsaleFeedListQuery `g`)는 '직전 최고가 대비 ±N%' 를 정수로 반올림하고 0 이 되면 소수 첫째 자리(최소 0.1)로 보여 준다. jibsa 의 `previous_high_change_percent` 는 같은 값(거래가와 `previousMaxPrice`)으로 같은 비율을 셈하고 자릿수만 늘려 소수 셋째 자리에서 .5 를 올린다 (값이 바뀌었는데 0.00 이면 ±0.01). 비율 자체는 웹과 같고 웹은 이것을 더 거칠게 보여 줄 뿐이다 (2026-11-13 사용자 결정. 0.25% 를 웹은 0.3, 예전 jibsa 는 Python `round` 로 0.2 를 주었다).
- **출력 보강.** `distance_km`(검색 중심·화면 가운데까지의 참고값, 주소 숨긴 매물은 `null`), 카드에 없는 시·도 채우기(`with_sido`·`sido_of`. 구 이름이 전국에 하나면 구마다 한 번, 여러 시·도에 있으면(중구·남구) 그 구 이름 검색을 끝까지 받아 그 구들의 동을 한꺼번에 채우고, 구·동 이름까지 같은 동(서울·대구 중구 태평로1가, 대구·울산 중구 교동)은 카드의 지역 ID 가 지역 검색 결과의 ID 와 같아 그 ID 로 가른다(`relay_id`, 2026-11-12 실측). 끝까지 받지 못하면 동 이름으로 찾는다. 찾은 시·도는 이어 받기 표에 담는다), 같은 이름 역 `notes`, 매일 감시용 `UPDATE_*` 끝말. 매물·가격·순서·수를 바꾸지 않는 덧붙임이다 ([매물 목록 경로](#매물-목록-경로)).

## API 변경 시 점검

해시와 GraphQL 헤더는 client, 변수·필터 코드와 좌표 문자열 직렬화는 request, 연결·커서·거래 필드는 response에서 확인한다. 웹이 쿼리를 바꿔도 서버가 옛 해시를 한동안 받아 명령은 정상으로 돈다 (2026-11-11 손 대조: 해시가 바뀐 쿼리 3개와 번들에서 사라진 쿼리 3개 모두 서버가 옛 해시를 받았다). 그래서 매주 월요일 API 감시가 jibsa 해시를 웹 번들의 같은 이름 쿼리와 견준다 (`check_daangn_queries`, [매일 API 감시](../README.md#매일-api-감시)). 해시마다 웹 쿼리 이름은 client 의 `web_query_names` 이고, 해시를 더하면 짝도 더한다 (`test_every_query_hash_has_web_query_name`). 알림대로 고친다: 해시가 바뀐 쿼리는 알려 준 새 해시로 바꾸고 응답 필드가 바뀌었는지 본다. 웹에서 사라진 쿼리는 그 명령의 대안을 정한다 (개발 호재처럼 기능이 없어졌으면 명령을 뺀다). 이름만 바뀐 쿼리는 `web_query_names` 를 고친다. 웹에 새로 생긴 쿼리(기준 목록 `scripts/monitor/daangn_web_queries.txt` 에 없음)는 jibsa 가 쓰는 기능이 옮겨 갔는지 본 뒤 `api_check.py daangn-queries` 로 기준 목록을 다시 쓴다. 웹에만 있는 기능은 넣지 않아도 된다. SSR 변경은 relay → parser → 응답 모델 순으로 추적한다. 라우터 상태의 seroval 문법(`$R[n]=` 등록·`$R[n]` 참조, `!0`·`!1`, 문자열 이스케이프)과 `__ref`/`__refs`를 별도로 확인한다 (2026-10-17 웹 배포 전에는 `window.RELAY_STORE = "..."` 였다). 원본 본문·사진·연락처가 출력 모델로 새지 않도록 최종 service 모델도 검토한다.
