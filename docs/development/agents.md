# 에이전트 작업 나누기

[개발 규약](../../AGENTS.md) · [이슈·PR 절차](workflow.md) · [검증과 테스트](README.md#검증과-테스트) · [웹 화면과의 대응](provider-conventions.md#웹-화면과의-대응)

코딩 에이전트가 이 저장소에서 일을 서브에이전트에 나눌지 정하고 나눠 맡길 때의 규칙이다. 도구에 따라 다른 것(모델 이름,
정의 파일 위치)은 `CLAUDE.md` 에 있다. 이 문서는 사용자와 함께 정한 운용 방식이라, 바꿀 때는 사용자와 먼저 맞춘다.

## 나눌지 정하기

일을 받으면 먼저 서브에이전트에 맡길지부터 정하고, 고치기 전에 설명하는 계획([AGENTS.md 작업 절차](../../AGENTS.md#작업-절차))에
한 줄로 적는다.

- **직접 한다:** 간단한 일, 또는 에이전트 하나가 순서대로 하면 끝날 일. 넘기면 지시서와 보고를 거치며 맥락이 빠지고 비용만
  는다.
- **맡긴다:** 아래 경우다. 동시에 돌릴 일이 아니면 하나만 띄운다.
  - 서로 겹치지 않는 일을 동시에 돌릴 때 (소스별 조사, 파일이 겹치지 않는 구현 묶음). 이때만 여럿을 띄운다.
  - 넓게 읽고 결론만 필요할 때
  - 주 에이전트의 판단에 끌려가지 않는 독립 리뷰가 필요할 때
  - 브라우저 캡처처럼 출력이 커서 주 에이전트의 맥락을 덮을 조사일 때

## 역할

- **주 에이전트**는 범위를 정하고 계획을 세우고, 서브에이전트의 결과를 받아 최종 검증을 한다. 사용자와 결정을 주고받는
  것도 주 에이전트만 한다.
- **서브에이전트**는 코드 수정·문서 작성·조사 같은 실제 작업을 한다. 이슈·브랜치·커밋·PR 같은 git 쓰기는 맡기지 않는다
  ([작업 절차](../../AGENTS.md#작업-절차): 그것은 사용자가 시킬 때 주 에이전트가 한다).
- 조사 서브에이전트는 Edit·Write 도구 없이 띄운다. Bash 로는 여전히 파일을 고칠 수 있으니 지시서에 '저장소 파일은 고치지
  않는다' 를 적는다.

## 맡길 때 지시서에 넣는 것

목표, 건드릴 파일과 건드리지 않을 파일(동시에 도는 다른 에이전트와 겹치지 않게), 이미 배제한 것, 따를 문서 링크
(`AGENTS.md` "꼭 지킬 것" 을 먼저 읽으라는 줄 포함), 판정 기준, 검증 범위, 보고 형식. 가설을 주면 "확인했다" 로 돌아오기
쉬우니 확인할 것은 질문으로 준다. 지시서를 또렷하게 쓸 수 없으면 아직 맡길 만큼 이해하지 못한 것이다.

## 검증 분담

- **서브에이전트는 자기 변경의 기본 검증만 한다.** `ruff check`·`mypy` 0건, 바꾼 부분 테스트만 이름으로, 바꾼 동작마다 실제
  조회 1회. 전체 `pytest`·웹 대조·넓은 실제 조회는 하지 않는다 (요청 예산과 비용).
- **주 에이전트가 나머지를 본다.** 웹 캡처와의 대조, 여러 서브에이전트의 변경이 서로 맞물리는지, 문서가 코드와 일치하는지,
  `--next`·매일 API 감시 목록처럼 변경이 번지는 곳, 미리 정한 소수의 실제 조회. 서브에이전트가 "확인했다" 고 해도 그대로 믿지
  않고 다시 본다.
- 서브에이전트의 **보고는 압축해서** 받는다: 바꾼 파일·함수, 실행한 검증과 결과, 바꾼 동작마다 실제 조회 1건의 핵심 필드,
  고치지 않은 것과 이유, 손댈 문서 목록. 전체 diff 나 긴 JSON 은 넘기지 않는다.

## 동시에 띄울 때

- 실제 API 를 부르는 서브에이전트는 **소스당 하나**만 띄운다. 요청 제한 상태는 모든 프로세스가 공유해 병렬로 불러도 빨라지지
  않고, 네이버는 차단 위험이 크다.
- 파일을 고치는 서브에이전트는 파일이 겹치지 않게 나눈다. 겹치면 차례로 띄운다. `CHANGELOG.md`·`docs/llm.md`·매일 API 감시
  목록처럼 여러 묶음이 함께 고칠 파일은 묶음이 직접 고치지 않고 고칠 내용만 보고하게 해, 문서 단계나 주 에이전트가 한 번에 고친다.
- 큰 변경은 **조사 → 결정 목록 → 겹치지 않는 묶음 동시 구현 → 문서 → 주 에이전트 검증** 순서로 나눈다. 결정 목록은
  [AGENTS.md 작업 절차](../../AGENTS.md#작업-절차)대로 사용자에게 설명하고 허락받은 뒤 구현한다. 결정과 그 이유는 PR 본문에 남기고,
  웹과 다르게 한 것은 그 소스 가이드의 "웹과 다른 점" 에 적는다.

## 코드 리뷰

리뷰는 지적을 모으는 단계와 지적을 가려내는 단계로 나눈다. 리뷰어의 지적을 그대로 믿지 않는다.

1. **관점별로 나눠 리뷰한다.** 관점은 다섯 가지로 정해져 있다: 규약 위반(`AGENTS.md` 꼭 지킬 것), 정확성·버그, 출력 계약([output-contract.md](output-contract.md)),
   웹 대응([웹 화면과의 대응](provider-conventions.md#웹-화면과의-대응)), 요청 수·차단 위험. 리뷰어 수는 변경 크기로 정한다.
   변경이 작아도 리뷰어는 하나 띄운다. 대개 주 에이전트가 짰거나 지켜본 코드라, 주 에이전트가 리뷰하면 제 판단을 따라가기 쉽다.

   크기는 바뀐 코드 파일(`src/` 아래. 문서·테스트·픽스처는 세지 않는다)·소스·명령으로 정하고, 애매하면 큰 쪽으로 한다.

   | 변경 크기 | 지적 모으기 | 재검증 |
   | --- | --- | --- |
   | 작음 (한 소스, 명령 하나, 코드 파일 다섯 개 안쪽) | 리뷰어 하나가 다섯 관점을 다 본다 | 지적이 다섯 건 안쪽이면 주 에이전트가 직접 재현한다 |
   | 중간 (한 소스 안에서 명령 둘 이상, 또는 코드 파일 다섯 개 넘음) | 리뷰어 둘·셋에 관점을 묶어 나눈다 (예: 규약·웹 대응 / 정확성·출력 계약 / 요청 수) | 검증 에이전트를 소스당 한 번에 하나 (대개 하나) |
   | 큼 (소스 둘 이상, 또는 `core/`·소스에 매이지 않은 `cli/` 코드) | 관점마다 리뷰어 하나 | 검증 에이전트를 소스당 한 번에 하나 |
   | 코드 아님 (문서·에이전트 정의·명령·워크플로만 바뀜) | 파일 다섯 개 안쪽이면 리뷰어 하나, 넘으면 둘·셋 | 재현할 jibsa 동작이 없어 검증 에이전트 없이 주 에이전트가 원문 대조로 확인한다 |

   검증 에이전트는 한 번에 지적 열 건쯤 받는다. 한 소스의 지적이 그보다 많으면 같은 소스 안에서 차례로 더 띄운다 (동시에는 하나).

2. **지적마다 재검증한다.** 검증 에이전트(작은 변경에서 지적이 몇 개뿐이면 주 에이전트)가 그 상황을 실제 CLI 조회나 원본 API
   응답으로 재현해 본다 (요청은 최소로). 코드만 읽고 판정하지 않는다. jibsa 동작과 상관없는 문서·설정 지적은 원문을 대조해 판정한다.
   대상이 PR·다른 브랜치면 작업 트리의 코드가 그 변경이 아니라 재현할 수 없다. 이때는 재검증을 하지 않고 보고 첫 줄에 "재현하지
   않은 리뷰" 라고 적는다 (작업 트리를 바꾸거나 브랜치를 받아 오지 않는다).
3. **넷으로 가른다.** 같은 문제를 가리키는 지적이 여럿이면 하나만 가르고, 나머지는 어느 지적과 같은지 적어 중복으로 묶는다
   (판정 종류가 아니라 묶는 규칙이다). 같은 줄이라도 문제가 다르면 따로 가른다.
   - **진짜 문제**: 고친다.
   - **오탐**(코드는 맞는데 그렇게 보일 수 있는 것): 고치지 않되, 다음 리뷰가 또 걸지 않게 이유를 남긴다. 웹과의 차이에 관한
     것이면 그 소스 가이드의 "웹과 다른 점" 절에, 그 밖은 그 코드 자리에 `# 리뷰 오탐 (YYYY-MM-DD): 이유` 주석으로.
   - **미확인**(재현도 반박도 못 한 것): 무엇을 더 보면 가릴 수 있는지 적는다.
   - **일어날 수 없는 상황**(응답에 없는 값, 모델이 막는 입력 등): 사용자에게 보여 주지 않는다. 주 에이전트는 근거를 훑어
     잘못 갈린 것이 없는지 본다.
4. **사용자에게는 진짜 문제와 오탐을** 근거(재현한 명령·응답)와 함께, **미확인은 따로** 보고한다. 리뷰어가 실패해 리뷰되지 않은
   관점이 있으면 그것도 알린다. 고치는 것은 사용자가 정한 뒤다.

## 보조 장치

반복되는 절차는 도구의 슬래시 명령·에이전트 정의·워크플로로 만들어 두면 덜 틀린다. 코드 리뷰, 웹 대조 조사, 허락받은 계획의
묶음 구현, 새 엔드포인트 추가([provider-conventions.md](provider-conventions.md#새-엔드포인트-추가-순서)), 매일 API 감시의
`api-broken` 이슈 대응([매일 API 감시](README.md#매일-api-감시) → 소스별 "API 변경 시 점검" → 패치 릴리스), PR 열기 전 점검,
릴리스([release.md](release.md))를 만들어 두었고, 목록은 `CLAUDE.md` 에 있다. 새로 만들 때도 이 문서의 규칙(나눌지 정하기, 소스당
하나, 공용 파일은 한 곳에서, 허락받은 뒤 고치기)을 그대로 따르게 한다.
