# 에이전트 작업 나누기

[개발 규약](../../AGENTS.md) · [이슈·PR 절차](workflow.md) · [검증과 테스트](README.md#검증과-테스트) · [웹 화면과의 대응](provider-conventions.md#웹-화면과의-대응)

코딩 에이전트가 이 저장소에서 일을 서브에이전트에 나눌지 정하고 나눠 맡길 때의 규칙이다. 도구에 따라 다른 것(모델 이름,
정의 파일 위치)은 `CLAUDE.md` 에 있다. 이 문서는 사용자와 함께 정한 운용 방식이라, 바꿀 때는 사용자와 먼저 맞춘다.

## 나눌지 정하기

일을 받으면 먼저 서브에이전트에 맡길지부터 정하고, 고치기 전에 설명하는 계획([AGENTS.md 작업 절차](../../AGENTS.md#작업-절차))에
한 줄로 적는다.

- **직접 한다:** 도구를 열 번 안쪽으로 불러 끝나는 가벼운 일 (일 자체에 드는 읽기·수정·조회를 센다. 고친 뒤의 `ruff`·`mypy`·
  테스트·실제 조회 확인은 맡겨도 주 에이전트가 하므로 세지 않는다). 코드 몇 줄 수정(파일이 둘셋이어도 합쳐 열 줄 안쪽), 문서 몇 줄
  고치기(옵션 하나를 바꾸고 `docs/<source>.md`·`docs/llm.md`·`CHANGELOG.md` 에 몇 줄씩처럼 파일이 여럿이어도), 파일 몇 개만 열어 보면 되는 확인, 사용자와 주고받으며 정해야 하는 일 (서브에이전트는 대화를 모른다). 주 에이전트는
  호출마다 큰 맥락을 다시 읽으므로, 이보다 길어질 일은 아래처럼 맡긴다 (2026-11-17 사용자 결정: 지난 한 달 주 세션이 토큰의
  56% 였고 호출마다 평균 27만 토큰을 읽었다. 서브에이전트는 2만 토큰 안팎에서 시작한다).
- **커밋 준비는 길어도 직접 한다** (사용자가 이슈·커밋을 시켰을 때). 커밋 전 변경을 이슈별 커밋으로 나누는 계획(어느 줄을 어느
  커밋에 넣을지)과 커밋별 파일 상태(scratchpad 에만 만들고, 상태가 앞 커밋 위에 쌓인다), 이슈 본문·커밋 메시지를 주 에이전트가
  쓴다. 변경을 만들고 검증한 주 에이전트는 무엇이 어느 관심사인지 이미 알지만, 서브에이전트는 diff 를 처음부터 다시 읽어야 해
  오래 걸린다 (2026-11-22 사용자 결정: 9,500줄 변경을 나누는 계획을 서브에이전트에 맡겼더니 12분이 넘도록 나오지 않았다.
  이슈 본문·커밋 메시지도 같은 이유로 2026-11-23 에 정했다). 상태의 모든 줄이 HEAD 나 작업 트리에 있는지와 상태마다의 검사를
  확인한 뒤 이슈 열기·커밋·push 를 한다. 다 만든 커밋을 새 브랜치로 바로 올리면 이슈에 커밋이 보이지 않으므로, 커밋을 올릴
  브랜치는 빈 채로 먼저 원격에 만들고 그 뒤에 커밋을 push 한다 ([workflow.md](workflow.md#모든-커밋은-이슈에서-시작한다) 2단계).
- **맡긴다:** 아래 경우다. 동시에 돌릴 일이 아니면 하나만 띄운다.
  - **코드 수정은 위의 작은 수정 말고는 모두 맡긴다.** 주 에이전트는 지시서를 쓰고 마지막 확인([검증 분담](#검증-분담)의
    주 에이전트 검증)만 한다. 주 에이전트는 맥락이 커서 도구를 부를 때마다 그 맥락을 다시 읽어, 직접 고치면 느리고
    토큰이 많이 든다 (2026-11-17 사용자 결정: 리뷰 지적 15건을 코드 파일 7개에 걸쳐 주 에이전트가 직접 고쳐 느렸다).
    파일이 겹치지 않는 묶음이 둘 이상이면 `implement-bundles` 로 동시에 돌리고(계획에 "implement-bundles 로 구현한다" 와 묶음마다
    고칠 파일을 적어 허락받는다), 하나면 `coder` 하나를 띄운다 (작업자 모델은 `CLAUDE.md`). 같은 소스여도 나누고, 같은
    파일을 고치는 일은 한 묶음에 넣는다. 다른 묶음이 기대는 공통 모듈(예: 그 소스의 `service/common/` 에 새로 두는 함수)은
    먼저 도는 묶음(`first`)으로 빼고, 그 함수·상수의 이름·인자·뜻은 계획에서 정해 둔다. 작은 고침(옵션 하나 정리 등)은 따로
    띄우지 않고 가까운 묶음에 붙인다.
  - **문서 일이 위 "직접 한다" 를 넘을 때** (도구를 열 번 넘게 부를 일: 여러 절을 새로 쓰기, "웹과 다른 점" 처럼 여러 사실을
    옮겨 적기) `doc-writer` 하나를 띄운다.
  - 서로 겹치지 않는 일을 동시에 돌릴 때 (소스별 조사, 파일이 겹치지 않는 구현 묶음, 명령 묶음별 소스 리뷰). 이때만 여럿을 띄운다.
  - 파일을 여럿 읽거나 도구를 열 번 넘게 불러야 하는 조사로, 결론만 필요할 때
  - 주 에이전트의 판단에 끌려가지 않는 독립 리뷰가 필요할 때
  - 브라우저 캡처처럼 출력이 커서 주 에이전트의 맥락을 덮을 조사일 때

## 역할

- **주 에이전트**는 범위를 정하고 계획을 세우고, 서브에이전트의 결과를 받아 최종 검증을 한다. 사용자와 결정을 주고받는
  것도 주 에이전트만 한다.
- **지시서 검사자**(`brief-checker`)는 작업자를 띄우기 전에 지시서만 읽고 빈틈을 찾는다 ([띄우기 전 지시서 검사](#띄우기-전-지시서-검사)).
- **서브에이전트**는 코드 수정·문서 작성·조사 같은 실제 작업을 한다. 이슈·브랜치·커밋·PR 같은 git 쓰기는 맡기지 않는다
  ([작업 절차](../../AGENTS.md#작업-절차): 그것은 사용자가 시킬 때 주 에이전트가 한다).
- 조사 서브에이전트는 Edit·Write 도구 없이 띄운다. Bash 로는 여전히 파일을 고칠 수 있으니 지시서에 '저장소 파일은 고치지
  않는다' 를 적는다.

## 맡길 때 지시서에 넣는 것

목표와 왜 하는지(배경·사용자 결정 한두 줄. 지시서가 실제 코드와 맞지 않을 때 작업자가 엉뚱하게 메우지 않고 알아채게 한다),
건드릴 파일과 건드리지 않을 파일(동시에 도는 다른 에이전트와 겹치지 않게), 이미 배제한 것, 따를 문서 링크
(`AGENTS.md` "꼭 지킬 것" 을 먼저 읽으라는 줄 포함), 판정 기준, 검증 범위, 보고 형식. 가설을 주면 "확인했다" 로 돌아오기
쉬우니 확인할 것은 질문으로 준다. 지시서를 또렷하게 쓸 수 없으면 아직 맡길 만큼 이해하지 못한 것이다.

구현 묶음(`implement-bundles`)의 작업자에게는 판단할 거리를 남기지 않는다 (지시서가 실제 코드와 맞지 않을 때는 아래 문단대로
하고 보고한다). 작업자 모델은 얽힌 일에도 올리지 않고(`CLAUDE.md`)
얽힘은 계획을 세운 주 에이전트가 지시서에서 푼다. 코드 작업자에게는 고칠 함수와 바꿀 내용, 지우는 코드면 그것을 부르는 곳
전부(주 에이전트가 찾아 적는다), 바뀌면 안 되는 동작을 준다. 기본 동작이나 전제를 바꾸면 옛 동작을 전제로 한 곳(다른 파일이
붙이는 안내·도움말·판정, 거르는 규칙을 바꾸면 바뀐 후보로 예시·hint 를 만드는 곳, 같은 뜻을 말하는 짝 안내와 그 태그)도 주 에이전트가 찾아 그 파일까지 맡긴다. 응답으로 무언가를 판정하게 하면 빈 응답·조회 실패를 어떻게
볼지와 판정의 근거가 되는 실측을, 새 값 필드면 0·없음을 어떻게 낼지를 기존 관례(`won_to_manwon_range` 는 0 을 값 없음으로
본다)와 함께 적는다. 한 필드에 값이 나오는 곳을 더하면(배지 = 확인 방식 + HUG) 조합마다 나오는 값과 그 뜻을 코드·문서 작업자
지시서에 함께 적는다 (2026-11-18 네이버 기능 추가 리뷰의 버그 세 건이 모두 지시서에 없던 파급이었다: 구 이름의 기본 동작을
경계 전체로 바꾸며 `region.py` 가 붙이는 '반경으로 찾았다' 안내를 놓침, 빈 하위 지역 목록을 '구 없는 시' 로 읽음, 월세 호가
짝의 0 처리를 월세에만 함). 값이 비는 경우는 **모름**(`null`)·**해당 없음**(키 삭제)·**없음**(`[]`) 중 무엇인지 경우마다 따로
적고(유형을 모를 때를 '그 유형이 아닐 때' 와 묶지 않는다), 새 칸·새 판정마다 값이 비는 모양을 모두 정한다 (`null`, 빈 글자, `'-'`,
키 없음, 바깥 연결이 `null` 인 경우와 안쪽 목록만 `null` 인 경우). 새 응답 모델은 목록·총수·다음 쪽처럼 서버가 비워 줄 수 있는 칸을
`| None` 으로 받아 한 칸 때문에 명령 전체가 `PARSE_ERROR` 로 깨지지 않게 하라고 적는다. 도움말·문서의 사용 예는 주 에이전트가
실제로 불러 성공한 값만 지시서에 준다. 두 묶음 이상이 같은 변환을 쓰게 되면 그 공용 함수(`service/common/` 등)를 먼저 도는
묶음에 맡겨 묶음마다 복사하지 않게 한다. 여러 소스가 같은 일을 하게 되면 문구·판정을 `core/` 공용 함수 하나로 두고 소스마다 따로 쓰게
하지 않으며, 공통 층을 새로 만들면 그것이 대신하는 옛 개별 처리를 같은 계획에서 지운다 (2026-11-18 네이버 2단계 리뷰: 모호한 이름 `한남3구역` 을 예시로 주거나 유형 모름을
해당 없음으로 묶은 지시서, 공용 파일을 아무 묶음에도 맡기지 않아 단지 행 변환이 세 곳에 복사된 것이 지적의 절반이었다).
리뷰 지적을 고치는 지시서에는 지적된 자리와 함께 **같은 모양(같은 판정, 같은 응답 모양, 같은 문장)을 이번 diff 전체에서 찾아
함께 고치고 찾은 자리를 보고하라**고 적는다 (2026-11-18 네이버 2단계 3차 리뷰: 지적된 학교 응답 모델만 `| None` 으로 고치고
같은 모양의 평형 묶음·평당가·재개발 자동완성 모델을 남겨 다시 지적됐다).
**지시서도 띄우기 전에 셀프 체크한다.** 작업자는 지시서의 문장과 값을 그대로 옮기고, 셀프 체크도 "지시서대로" 로 통과시킨다.
그래서 지시서에 적은 안내 태그(`[일부]`·`[참고]` 등, `docs/common.md`)·조사·에러 code·message·hint·값의 모양(정수인지 소수가
올 수 있는지, 모름·해당 없음·없음)을 규칙 문서와 [리뷰 체크리스트](review-checklist.md)에 대 보고 띄운다. 웹에서 가져온 값 중
화면 크기·확대 단계처럼 계산으로 나오는 값은 한 곳에서 잰 결과 숫자가 아니라 그 계산을 준다 (계산을 모르면 조건이 다른 두 곳
이상에서 잰다, 체크리스트 `web-9`). (2026-11-19 네이버 빌라 `real-price` 리뷰 지적 다섯 건 중 넷이 지시서에서 나왔다: `[일부]`
대신 `[참고]` 를 적어 줌, 572549 한 곳에서 잰 위도 폭을 상수로 줌, 평당가를 정수인 것처럼 적음, 옵션 이름 뒤 조사.)
문서 작업자에게는 문서에 들어갈 사실을 항목으로 준다 ("웹과 다른
점" 이면 항목마다 무엇이 다르고 왜 사실이 어긋나지 않는지, 확인한 날짜·번들 심볼). 이것을 적지 못하면 계획이 덜 된 것이라 묶음을
띄우지 않는다.

**지시서에 적는 동작 사실은 입구부터 따라가 확인한 것만 적는다.** 무엇을 보내고 막는지, 기본값이 무엇인지는 그 명령의 입구(CLI 옵션
검사)부터 서비스·요청까지 따라가 확인한 것만 적고, 한 함수만 보고 적지 않는다. 상한·"더 있음" 판정은 무슨 수로 하는지(받은 수인지
걸러 남은 수인지, 서버가 그 값으로 정렬해 주는지)를 적는다. 실패를 여럿 모으는 반복이면 멈춤·안내가 첫 실패가 아니라 실패마다
정해지는지 적는다. 그리고 지시서 항목마다 **확인할 갈래**(새 상한, 새 안내, 새 옵션 검사, 실패 순서, 값이 비는 모양)를 적는다.
주 에이전트가 고친 뒤 이 목록을 하나씩 태운다 ([검증 분담](#검증-분담)).

**지시서와 다르게 할 때.** 이 문단이 원문이다. 에이전트 정의·워크플로는 옮겨 적지 않고 이 문단을 가리킨다.
작업자(구현 묶음, 혼자 띄우는 `coder`·`doc-writer`)가 지시서대로 할 수 없거나 다르게 하는 편이 맞아 보이면, 작은 차이는 하고
보고의 "지시서와 다르게 한 것" 에 이유와 함께 적는다. 작은 차이는 고칠 파일 안에서만 쓰이는 이름이나 고칠 파일 안에서의 위치
차이다. 고칠 파일 밖(다른 파일·다른 묶음·테스트)에서 부르는 함수·상수의 이름·인자를 바꾸는 것, 고칠 파일 밖으로 옮기는 것,
동작(출력·에러·요청)이 달라지는 것은 하지 않고 고치지 않은 것으로 이유와 함께 보고한다 (부르는 쪽이 깨지거나 동시에 도는
묶음의 파일을 덮어쓴다). 문서 작업자는 지시서의 사실·이름·위치가 지금 코드와 다르면 코드를 따르고 그렇게 쓴 곳을 보고하며, 지시서의 고칠 문서 밖이나
코드(`src/`·`scripts/`·`tests/`)는 고치지 않고 보고한다. 받아들일지는
주 에이전트가 정한다 ([검증 분담](#검증-분담)).

## 띄우기 전 지시서 검사

`implement-bundles` 를 부르기 전에 `brief-checker` 하나(모델은 `CLAUDE.md`)가 모든 묶음 지시서와 문서 지시서를 읽고 빈틈을 찾는다.
지시서를 쓴 주 에이전트의 셀프 체크(위)는 제 판단에 끌려가 빈틈을 놓치기 쉬워, 계획을 모르는 눈으로 한 번 더 본다. 검사자는 지시서
파일과 묶음별 고칠 파일만 받고 지시서 밖의 대화 맥락은 받지 않는다. 질문은 `brief-checker` 정의에 있다.

- 주 에이전트는 지적마다 지시서를 고치거나, 그대로 두는 이유를 적은 기록 파일(scratchpad)을 만들고 그 경로를 워크플로의 `briefCheck`
  로 넘긴다. 없으면 워크플로가 시작하지 않는다. 그대로 두는 지적은 사용자에게 알린다.
- 혼자 띄우는 `coder`·`doc-writer` 도 지시서 항목이 다섯 개를 넘으면 같은 검사를 한다.

(2026-11-20: 당근 코드 전체 리뷰 지적을 `implement-bundles` 로 고친 뒤 `/review-diff` 가 17건을 더 냈다. 원인은 규칙이 없어서가 아니라
있는 규칙을 건너뛴 것이었다: 동작 사실을 한 함수만 보고 적은 지시서, 값이 비는 모양을 `null` 만 정한 지시서, 작업자가 "이게 더
맞다" 고 적은 경고를 흘려들음, 새로 만든 갈래를 태우지 않은 주 에이전트 확인, 코드와 대조하지 않은 문서.)

## 검증 분담

- **서브에이전트는 자기 변경의 기본 검증만 한다.** `ruff check`·`mypy` 0건, 바꾼 부분 테스트만 이름으로, 바꾼 동작마다 실제
  조회 1회. 전체 `pytest`·웹 대조·넓은 실제 조회는 하지 않는다 (요청 예산과 비용). 구현 묶음(`implement-bundles`)은 주 에이전트가
  고치기 전·후 출력을 비교하므로 작업자가 실제 조회를 하지 않고 `ruff`·`mypy`·바꾼 테스트만 한다 (같은 확인을 두 번 하지 않게).
  작업자도 실제 조회를 해야 하는 일이면 계획에 그 이유를 적고 `workerLiveChecks` 를 켠다.
- **구현 묶음을 띄우기 전에 주 에이전트가 고치기 전 출력을 남긴다.** 바뀔 명령과 바뀌면 안 되는 명령을 정해 한 번에 돌려 두고,
  묶음이 모두 끝나면 같은 명령으로 비교한다. 저장한 경로는 `implement-bundles` 의 `baseline` 으로 넘기고, 없으면 워크플로가
  시작하지 않는다. 지금은 일어나지 않는 분기(값이 없을 때, 상한 도달)는 실제 응답의 값만 바꾸거나
  상한을 낮춰 태운다 ([코드 리뷰](#코드-리뷰) 2단계). 기본 동작을 바꿨으면 그 동작을 끄는 옵션과 함께 준 명령(구 이름에
  `--radius` 등)도 고치기 전·후 비교에 넣는다. 새로 만든 에러·안내(`notes`·`hint`)는 그 경우를 실제로 일으키고(틀린 번호, 없는
  평형, 모호한 이름 등) **안내대로 다시 불러 성공하는지**까지 본다. 도움말·문서에 새로 넣은 사용 예도 그대로 불러 본다. 원래 지적 재현과 평소 출력 비교만으로는
  새로 만든 갈래(새 상한·붙여 쓴 옵션·실패 순서)가 태워지지 않으므로, 고친 뒤에는 지시서의 "확인할 갈래" 를 하나씩 태운다 (값 바꿔
  넣기·상한 낮추기·순서 바꾸기).
- **주 에이전트는 서브에이전트가 고친 일을 늘 직접 검증한다.** 범위는 지시서 항목마다 실제 변경(`git diff --stat` 과 그 자리)에서
  됐는지 대조, 고치기 전·후 결과 비교와 미리 정한 소수의 실제 조회, 여러 서브에이전트의 변경이 서로 맞물리는지, 문서가 바뀐
  코드와 맞는지(바뀐 이름·필드·옵션을 `grep`. 안내가 **언제** 나오는지 적은 문장은 그 갈래의 코드와 대고, `CHANGELOG.md` 는 같은 종류의
  변경(에러 코드 변경, 라이브러리 예외·반환 모양 변경)이 같은 절에 있는지 본다), `--next`·매일 API 감시 목록처럼 변경이 번지는 곳, 조사원이 가져온 웹 캡처 결과와의 대조까지다.
  서브에이전트가 "확인했다" 고 해도 그대로 믿지 않고 다시 본다. 작업자 보고의 `concerns`(지시대로 했지만 걸리는 점)는 지시서가 틀렸다는
  신호로 본다. 주 에이전트는 하나씩 답하고(고칠지, 그대로 둘지) 그대로 두려면 그 경우를 실제로 돌려 본 근거를 대며, 답한 결과를 사용자
  보고에 적는다. 작업자의 사실 주장("모두 X 라 영향 없다")도 받아들이기 전에 확인한다. 바뀐 코드를 처음부터 다시 읽으며 버그를 찾는 검토는 하지 않고
  리뷰어에게 맡긴다 (주 에이전트는 호출마다 큰 맥락을 다시 읽는다). 주 에이전트가 직접 고친 곳은 작업자와 같은 기준으로
  끝낸다: 바뀐 동작의 흔적(닿지 않게 된 갈래·낡은 주석)을 지우고, [리뷰 체크리스트](review-checklist.md)에서 **언제** 신호가
  있는 항목에 대 본다 (`coder`·`doc-writer` 도 끝내기 전에 한다). 셀프 체크는 "훑었다" 로 끝내지 않고 걸린 항목마다 그 경우를
  어떻게 확인했는지(코드로 따라감·가짜 응답으로 돌림·실제 조회) 한 줄을 보고에 남긴다 (2026-11-18: "훑었다" 고 보고한 작업에서
  체크리스트에 이미 있는 종류가 리뷰에서 열 건 나왔다). 작업자가 "고칠 파일 밖이라 고치지 않았다" 고 남긴 항목은
  사용자에게 끝났다고 보고하기 전에 모두 처리하거나 사용자에게 묻는다.
- **지시서와 다르게 한 것은 주 에이전트가 정한다.** 받아들일지 판단해 사용자에게 알리고, 받아들이지 않으면 다시 맡기거나 직접
  고친다. 구현 묶음의 문서 단계는 주 에이전트가 정하기 전에 돌아 그 차이대로 문서를 썼을 수 있으니, 그 문서도 함께 되돌린다.
- **큰 변경은 독립 리뷰를 할지 묻는다.** `/review-diff` 명령의 복잡도 표에서 간단을 넘는 변경(중간·복잡), 또는 운용 규칙
  파일(`AGENTS.md`·`CLAUDE.md`·`docs/development/agents.md`·`.claude/`)을 여러 곳 고친 변경(규칙 문장끼리 어긋나기 쉽다)을 마치면, 사용자에게
  보고할 때 `/review-diff` 로 독립 리뷰를 할지 묻는다. 리뷰어는 계획을 모르고 코드만 봐 주 에이전트가 놓친 문제를 잡지만, 한 번에
  코드 작업자 한 번의 약 두 배를 써 묻지 않고 띄우지 않는다 (2026-11-17 사용자 결정: 검증은 주 에이전트가 늘 하고, 따로
  띄우는 검증은 큰 변경에만 더한다. 지난 한 달 리뷰어 한 번이 평균 약 560만, 코드 작업자 한 번이 약 310만 토큰이었다).
- 서브에이전트의 **보고는 압축해서** 받는다: 바꾼 파일·함수, 실행한 검증과 결과, 바꾼 동작마다 실제 조회 1건의 핵심 필드,
  지시서와 다르게 한 것과 이유, 지시대로 했지만 걸리는 점(`concerns`, 다르게 한 것·고치지 않은 것과 섞지 않고 "영향 없다" 같은
  판단에는 근거로 돌린 명령·`grep` 결과를 함께), 고치지 않은 것과 이유, 손댈 문서 목록. 전체 diff 나 긴 JSON 은 넘기지 않는다.

## 동시에 띄울 때

- 실제 API 를 부르는 서브에이전트는 같은 소스라도 동시에 띄워도 된다. 요청 제한 상태를 모든 프로세스가 공유해, 여럿이 불러도
  합친 요청 수가 소스별 상한(`jibsa limits`)을 넘지 않는다. 다만 **같은 소스는 동시에 셋까지**로 하고, 더 필요하면 앞의 것이
  끝난 뒤 띄운다 (분당 상한을 나눠 쓰고, 조사원이 직접 여는 브라우저는 요청 제한에 잡히지 않는다). 범위는 서로 겹치지 않게 나눈다.
  네이버도 같은 상한이다. 예전에는 한 번에 하나만 띄웠다 (첫 화면 한 번이 부르는 요청이 많은데([네이버 가이드](providers/naver.md))
  에이전트끼리는 여는 때를 서로 맞출 수 없고, jibsa 도 첫 화면이 스스로 부르는 요청을 연 뒤에 세어 미리 막지 못해서다,
  [브라우저 요청](architecture.md#브라우저-요청)). 그런데 첫 화면 요청은 사람이 페이지를 열 때 나가는 묶음과 같고, 조심할 것은
  우리가 직접 보내는 요청의 속도다. 2026-11-16 실측: 네이버 웹 대조 조사원 셋을 동시에 돌려(저마다 브라우저를 직접 열고 jibsa
  명령 8개 안팎, 한 조사원은 14분에 front-api 120건·1분 최대 25건) 429 가 한 번도 없었다. 이때 첫 화면 열기는 2~3분씩 떨어져
  있었고, 셋이 같은 순간에 여는 경우는 재지 못했다. 429 가 나오면 이 문단과 두 워크플로(`web-parity-panel`·`implement-bundles`)의 상한을 함께 되돌린다.
- 파일을 고치는 서브에이전트는 파일이 겹치지 않게 나눈다. 겹치면 차례로 띄운다. 파일이 겹치지 않으면 같은 소스의 구현 묶음도
  동시에 띄운다 (같은 소스는 셋까지. 다른 묶음이 기대는 묶음은 먼저). `CHANGELOG.md`·`docs/llm.md`·매일 API 감시
  목록처럼 여러 묶음이 함께 고칠 파일은 묶음이 직접 고치지 않고 고칠 내용만 보고하게 해, 문서 단계나 주 에이전트가 한 번에 고친다.
- 큰 변경은 **조사 → 결정 목록 → 겹치지 않는 묶음 동시 구현 → 문서 → 주 에이전트 검증** 순서로 나눈다. 결정 목록은
  [AGENTS.md 작업 절차](../../AGENTS.md#작업-절차)대로 사용자에게 설명하고 허락받은 뒤 구현한다. 결정과 그 이유는 PR 본문에 남기고,
  웹과 다르게 한 것은 그 소스 가이드의 "웹과 다른 점" 에 적는다.

## 코드 리뷰

리뷰는 지적을 모으는 단계와 지적을 가려내는 단계로 나눈다. 리뷰어의 지적을 그대로 믿지 않는다.

1. **리뷰어 하나가 한 맥락에서 리뷰한다.** 관점은 여섯 가지로 정해져 있다: 규약 위반(`AGENTS.md` 꼭 지킬 것), 정확성·버그, 출력 계약([output-contract.md](output-contract.md)),
   웹 대응([웹 화면과의 대응](provider-conventions.md#웹-화면과의-대응)), 요청 수·차단 위험, 구조·중복·단순화(이미 있는 함수를 다시
   만들기, 같은 규칙을 여러 곳에 따로 두기, 닿지 않는 겹친 검사). 관점마다 지난 리뷰에서 나온 패턴은
   [리뷰 체크리스트](review-checklist.md)에 있다. 리뷰어는 리뷰 묶음(diff·감싼 함수·부르는 곳 위치를 미리 모은 파일, `/review-diff` 3단계. PR 리뷰는 diff 파일만, `/review` 는 묶음 없이 맡은 파일)을 한 번 읽고 일반 관점(줄 단위, 지운 동작, 호출부 추적, 언어
   함정)과 체크리스트 여섯 절을 차례로 대 본 뒤, 중복만 지우고, 같은 맥락에서 빈 곳을 한 번 더 찾는다 (단계는 `reviewer`
   정의). 리뷰를 하기로 했으면 변경이 작아도 리뷰어를 띄운다. 대개 주 에이전트가 짰거나 지켜본 코드라, 주 에이전트가 리뷰하면 제 판단을 따라가기 쉽다.

   **리뷰어를 여럿 띄우지 않는다.** 2026-11-16 에 관점별·파일 묶음별로 리뷰어를 여럿 띄워 봤는데, 리뷰어마다 diff·주변
   코드·grep 결과를 따로 읽고, 에이전트는 호출마다 그때까지 쌓인 맥락을 다시 읽어 비용이 리뷰어 수 × 호출 수 × 맥락으로 커졌다.
   실측: 36개 파일(바뀐 줄 약 2,100) diff 에 관점별 Sonnet 리뷰어 6명이 9.8M 토큰 환산(호출 31~82회, 끝날 때 맥락 18만~38만),
   파일 묶음별 5명도 끝나기 전에 5.2M 이었다. 한 맥락이면 diff 와 주변 코드를 한 번만 읽고 모든 관점이 같이 쓴다.

   **예외: 변경분이 아니라 한 소스의 코드 전체를 리뷰할 때는 명령 묶음마다 리뷰어 하나를 둔다** (`/review`). 이때는 리뷰어마다
   읽는 파일이 달라 diff 처럼 같은 것을 거듭 읽지 않는다. 오히려 한 맥락에 소스 전체(수만 줄)를 담으면 읽은 파일이 호출마다
   다시 읽혀 뒤로 갈수록 비싸지고 덜 본다 (2026-11-19 사용자 결정: 당근 코드 전체 약 18,000줄을 리뷰어 하나에 맡기다 멈췄다).
   파일별이 아니라 명령의 흐름(`cli` 명령 → `service` → `request`·`response` → `client` 의 그 메서드)으로 묶어야 층 사이
   버그(서버가 거른 것을 다시 거르기, 도움말과 동작이 어긋남)를 본다. 여러 명령이 같이 쓰는 파일은 공용 묶음 리뷰어 하나만
   통째로 보고, 다른 리뷰어는 부르는 함수만 연다. 묶는 법은 `/review` 명령, 모델 기준은 `CLAUDE.md`, 지적은 모두 모아 중복을 지운 뒤 2단계로 넘긴다.

   변경분 리뷰(`/review-diff`)의 리뷰어 모델은 변경의 복잡도로 정한다 (최소 Sonnet medium, 최대 Opus high. 표는 `/review-diff` 명령). 복잡도는 바뀐 코드 파일
   (`src/` 아래. 문서·테스트·픽스처는 세지 않는다)·소스·명령으로 정하고, 애매하면 위 칸으로 한다.

2. **지적마다 재검증한다.** 그 상황을 실제 CLI 조회나 원본 API 응답으로 재현해 본다 (요청은 지적당 1~2회). 지적이 다섯 건
   안쪽이면 주 에이전트가 직접 하고, 넘으면 검증자 하나(모델은 `CLAUDE.md`)에 목록을 통째로 넘긴다. 주 세션은 맥락이 커서
   지적마다 재현하면 호출마다 그 맥락을 다시 읽고, 검증자는 지적 목록과 그 자리 코드만 읽어 작게 끝난다. 주 에이전트는 검증자의
   판정을 다시 재현하지 않고 근거만 훑는다 (5단계). 코드만 읽고 판정하지 않는다. jibsa 동작과 상관없는 문서·설정 지적은 원문을 대조해 판정한다.
   구조·중복·단순화 지적은 겹쳤다는 자리들을 나란히 대조해 판정하고, "닿지 않는 코드" 라는 주장만 그 경로를 CLI 로 불러 확인한다.
   이 관점에서는 "한쪽만 고치면 어긋난다" 가 가정이 아니라 지적의 요지라, 겹침·비슷한 경로 중 일부에만 붙은 처리·닿지 않는
   코드가 지금 코드에 실제로 있으면 지금 출력이 맞아도 진짜 문제다. 두 곳의 규칙이 다르면 그 차이가 일부러인지(응답 형식이 달라
   읽는 법이 다르다 등) 보고, 일부러면 오탐이고 아니면 진짜 문제다 (합치면 바뀌는 출력을 근거에 적는다).
   다만 지금 데이터로는 그 상황을 만들 수 없어 재현하지 못해도, 서버가 보낼 수 있는 값이나 닿을 수 있는 상태에서 코드가 틀린
   출력·에러에 이르면 진짜 문제로 가른다. 서버가 보낼 수 있는 값은 값이 없을 때의 모양(`null`·빈 글자·빈 목록·`'-'` 같은 표시
   글자)과 지금 값의 연장(소수, 더 큰 수, 더 짧은 쪽, 이름이 같은 후보, 상한 도달)이다. "실측에 아직 없다"·"본 적 없다"·"아직
   상한에 안 닿는다" 는 진짜 문제가 아닐 이유가 아니다. 재현은 실제 응답의 값만 바꿔 넣거나 상한 상수를 낮춰 그 분기를 태워
   보고, 근거에 "재현 못 함, 코드로 확인" 과 재현하지 못한 이유, 실측에서 본 값(예: 단지 38곳 모두 목록)을 적는다.
   진짜 문제가 아닌 것: 코드를 잘못 읽은 지적, 코드가 나중에 바뀌어야만 문제가 되는 지적("나중에 누가 이 함수를 검사 없이
   부르면"), 응답 형식 자체가 바뀌는 것(필드 이름·자료형이 바뀌거나 엔드포인트가 사라짐. [매일 API 감시](README.md#매일-api-감시)가 잡는다).
   대상이 PR·다른 브랜치면 작업 트리의 코드가 그 변경이 아니라 재현할 수 없다. 이때는 재검증을 하지 않고 보고 첫 줄에 "재현하지
   않은 리뷰" 라고 적는다 (작업 트리를 바꾸거나 브랜치를 받아 오지 않는다).
3. **넷으로 가른다.** 같은 문제를 가리키는 지적이 여럿이면 하나만 가르고, 나머지는 어느 지적과 같은지 적어 중복으로 묶는다
   (판정 종류가 아니라 묶는 규칙이다). 같은 줄이라도 문제가 다르면 따로 가른다.
   - **진짜 문제**(재현됐거나, 재현할 조건이 없어도 위 기준으로 코드가 틀린 출력·에러에 이르는 것): 고친다. 고칠 방향은
     덜 바뀌는 쪽이 아니라 결과가 더 좋은 쪽으로 정한다.
   - **오탐**(지금 어떤 입력을 줘도 코드가 맞는데 틀려 보이는 것. 코드를 잘못 읽은 지적, 코드가 나중에 바뀌어야만 문제가
     되는 지적도 여기다. 구조·중복·단순화 지적은 출력이 맞는지가 아니라 2단계의 그 관점 기준으로 가른다): 고치지 않되, 다음 리뷰가 또 걸지 않게 이유를 남긴다. 웹과의 차이에 관한
     것이면 그 소스 가이드의 "웹과 다른 점" 절에, 그 밖은 그 코드 자리에 `# 리뷰 오탐 (YYYY-MM-DD): 이유` 주석으로.
     이유는 '지금 어떤 입력에도 코드가 맞는 이유'(막는 코드 위치, 실제 응답의 자료형, 웹 동작이면 그 웹 코드 위치인 번들 청크·함수)여야
     하고 "실측에서 못 봤다"·"문서에 그렇게 적었다" 는 이유가 아니다 (문서는 코드를 보고 쓴 것이라 제자리를 돈다). 오탐으로 가르기 전에
     그 자리 주석이 설명하는 동작이 실제 코드 동작과 같은지 본다 (당근 주차 주석이 코드와 반대였다). '-' 같은 글자가 와서
     깨진다는 걱정은 그 칸이 실제 응답에서 글자로 오는지 먼저 본다 (JSON 숫자로 오는 칸은 글자가 올 수 없고, 자료형이 바뀌면 매일 API
     감시 몫이다). 2026-11-20 오탐 주석 60개를 이 기준으로 다시 따졌더니 진짜 문제 8건과 근거가 약한 주석 17건이 나왔다.
   - **미확인**(재현도 반박도 못 했고 코드로도 틀렸다고 단정할 수 없는 것. 그 입력이 오면 코드가 맞는지조차 모를 때만이다.
     서버가 보낼 수 있는 입력이 오면 틀리는 것은 분명한데 그 입력의 실례만 못 찾았으면 미확인이 아니라 진짜 문제다): 무엇을 더 보면 가릴 수 있는지 적는다.
   - **일어날 수 없는 상황**(jibsa 코드가 그 입력을 스스로 막는 것: 옵션 검사, 요청 모델, 앞 단계에서 이미 거름. 막는 자리
     `파일:줄` 을 근거로 댄다. 응답에 아직 안 온 값은 여기 들지 않는다): 사용자에게 보여 주지 않는다. 주 에이전트는 근거를 훑어
     잘못 갈린 것이 없는지 본다.
4. **사용자에게는 진짜 문제와 오탐을** 근거(재현한 명령·응답. 코드로 확인한 것은 그 흐름과 재현하지 못한 이유)와 함께, **미확인은 따로** 보고한다. 구조·중복·단순화의 진짜 문제는
   버그와 나눠 "정리할 것" 으로 적는다. 리뷰어가 실패해 리뷰가 덜 됐으면 그것도 알린다. 고치는 것은 사용자가 정한 뒤다.
5. **고칠 계획에서 빼는 이유는 셋뿐이다.** 진짜 문제가 아닌 지적을 계획에서 뺄 때마다 이유를 하나 댄다: 오탐(지금 어떤
   입력에도 코드가 맞다), 일어날 수 없음(jibsa 코드가 그 입력을 막는다), 사용자가 정할 일(호환 깨짐 등). 2·3단계의 판정도 이
   기준으로 다시 훑어, 근거가 "응답에 안 왔다"·"실측에 없다"·"문서에 그렇게 적었다" 뿐인 일어날 수 없음·오탐과 근거가 "재현할 입력을 못 찾았다"
   뿐인 미확인은 진짜 문제로 옮긴다 (2026-11-16: 주소 검색 1건이 고른 동과 같은 곳인지 대조하지 않은 지적이 미확인으로 남아
   계획에서 빠졌다. 두 자료가 어긋나는 실례만 못 찾았을 뿐 그 응답이 오면 코드가 틀렸다). 주 에이전트가
   계획을 세우며 스스로 빼는 것(예: 상한에 닿았을 때의 안내)도 같다.
6. **체크리스트를 키운다.** 진짜 문제가 체크리스트에 없던 종류면 그 관점 절에, 오탐이 되풀이될 만한 종류면 "지적하지 말 것" 에
   한 줄 더한다 (관점 절 항목은 규칙·확인법·사례 `파일:줄` 하나·언제). 이미 있는 항목이면 더하지 않는다. 있던 항목인데
   리뷰어가 놓쳤으면 그 "언제" 를 그 diff 의 모양까지 넓힌다. 고칠 계획에 함께 넣어 허락받는다.

## 보조 장치

반복되는 절차는 도구의 슬래시 명령·에이전트 정의·워크플로로 만들어 두면 덜 틀린다. 코드 리뷰, 웹 대조 조사, 허락받은 계획의
묶음 구현과 그 전의 지시서 검사, 새 엔드포인트 추가([provider-conventions.md](provider-conventions.md#새-엔드포인트-추가-순서)), 매일 API 감시의
`api-broken`·`api-warning` 이슈 대응([매일 API 감시](README.md#매일-api-감시) → 소스별 "API 변경 시 점검" → 고장이면 패치 릴리스), PR 열기 전 점검,
릴리스([release.md](release.md))를 만들어 두었고, 목록은 `CLAUDE.md` 에 있다. 새로 만들 때도 이 문서의 규칙(나눌지 정하기, 같은
소스는 동시에 셋까지, 공용 파일은 한 곳에서, 허락받은 뒤 고치기)을 그대로 따르게 한다.
