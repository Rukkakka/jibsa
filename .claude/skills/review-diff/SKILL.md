`docs/development/agents.md` 의 "코드 리뷰" 절을 실행한다. 대상: `$ARGUMENTS` (비어 있으면 커밋 전 변경과 이 브랜치의 커밋 전부: `git diff HEAD`, `git status --short` 의 추적 안 된 파일, `git diff main...HEAD`. 에이전트는 시키지 않으면 커밋하지 않아 리뷰할 변경이 대개 커밋 전에 있다).

**리뷰어는 하나다.** 관점·파일로 나눠 리뷰어를 여럿 띄우지 않는다 (같은 diff 와 주변 코드를 저마다 읽어 토큰이 곱으로 는다, 같은 절 1단계). 변경분이 아니라 한 소스의 코드 전체(또는 그 명령 몇 개의 코드 전체)가 대상이면 이 명령이 아니라 `/review` 다.

**PR 번호나 다른 브랜치가 대상이면** 재현은 지금 작업 트리의 코드로 돌아가 그 변경을 재현하지 못한다. 작업 트리를 바꾸지 않고(사용자의 커밋 전 변경이 있을 수 있다) 브랜치를 새로 받아 오지도 않는다. 재현 없이 코드 리뷰만 하고, 보고 첫 줄에 "재현하지 않은 리뷰" 라고 적는다. 리뷰어는 파일을 작업 트리에서 열면 다른 코드를 읽게 되므로, 지시서에 그 코드를 읽는 법을 적고 "작업 트리 파일은 열지 않는다. 규칙 문서·소스 가이드도 그 리비전에서 읽는다" 를 넣는다.
- **로컬에 있는 브랜치:** 변경은 `git diff main...<브랜치>`, 파일 내용은 `git show <브랜치>:<경로>`.
- **PR:** 주 에이전트가 `gh pr diff <번호>` 를 scratchpad 에 저장해 그 경로를 지시서에 준다. 파일 전체가 필요하면 `gh pr view <번호> --json headRefOid` 의 커밋으로 `gh api 'repos/{owner}/{repo}/contents/<경로>?ref=<커밋>' --jq .content | base64 -d`.

1. **기계 검사.** 대상이 작업 트리면 `.venv/bin/ruff check && .venv/bin/mypy` 와 바뀐 부분 테스트(이름으로)를 먼저 돌린다. 실패는 리뷰 보고에 함께 적는다.

2. **리뷰어 모델 정하기.** 바뀐 코드 파일(`src/` 아래. 문서·테스트·픽스처는 세지 않는다)·소스·명령으로 정한다. 애매하면 위 칸으로 한다.

   | 복잡도 | 기준 | 리뷰어 모델 |
   | --- | --- | --- |
   | 간단 | 한 소스, 명령 하나, 코드 파일 다섯 개 안쪽, 또는 코드 아님 (문서·에이전트 정의·명령·워크플로만) | Sonnet medium |
   | 중간 | 한 소스 안에서 명령 둘 이상, 또는 코드 파일 다섯 개 넘음 | Opus medium |
   | 복잡 | 소스 둘 이상, `core/`·소스에 매이지 않은 `cli/` 코드, 또는 지우는 코드가 여러 명령에 걸림 | Opus high |

   사용자가 `/review-diff` 를 직접 쳤으면 복잡도와 모델을 한 줄로 알리고 바로 돌린다. 치지 않았는데 요청을 보고 이 명령을 골랐으면 같은 내용을 알리고 허락받은 뒤 돌린다.

3. **리뷰어 띄우기.** `reviewer` 하나를 Agent 로 띄운다 (`model`·`effort` 는 위 표). 리뷰 단계(관점 A~D 와 체크리스트 여섯 절 → 중복 지우기 → 빈 곳 찾기)는 그 정의에 있다. 띄우기 전에 리뷰 묶음을 만든다: `.venv/bin/python scripts/review/review_packet.py --out <scratchpad>/review_packet.txt` (로컬 브랜치가 대상이면 `--head <브랜치>`). 묶음의 구성(① diff ② 추적 안 된 파일 ③ 부르는 곳)과 크기 한도는 `scripts/review/review_packet.py` 의 docstring 에 있다. 리뷰어가 감싼 함수를 열고 부르는 곳을 grep 하느라 도구를 하나씩 수십 번 부르던 것을 미리 모은다 (2026-11-26 사용자 결정. 리뷰어 한 번 평균 43번 호출·858만 토큰, 토큰의 97~99% 가 캐시 읽기라 호출 수가 곧 비용이다). PR 이 대상이면 묶음 없이 위 "PR" 대로 diff 파일을 준다. 지시서에는 리뷰 대상 한 줄과 묶음 경로(PR 이면 diff 파일 경로. 리뷰어는 그 파일을 한 번 읽고 다시 볼 때는 그 파일에서 연다), 그리고 무엇을 바꾸려던 변경인지 한두 줄을 준다 (배경일 뿐 범위를 좁히지 않는다. `CHANGELOG.md` 에서 뽑았으면 그렇다고 밝힌다. 리뷰어는 diff 전체를 본다, `reviewer` 정의 1단계). 주 에이전트의 판단(어디가 맞다고 봤는지)은 주지 않는다 (리뷰어가 그 판단을 따라가지 않게).

4. **재현·보고·고칠 계획은 `/review` 의 5~7단계를 따른다** (`.claude/skills/review/SKILL.md`. 묶음표·덜 본 곳·범위 밖은 그 명령에만 있다). 이 명령에서만 다른 것:
   - 대상이 PR·다른 브랜치면 재현하지 않고 같은 문제끼리만 묶으며, 보고 첫 줄에 "재현하지 않은 리뷰" 라고 적는다 (위 "PR 번호나 다른 브랜치가 대상이면").
   - 보고 첫머리에 2단계에서 정한 복잡도도 적는다.
