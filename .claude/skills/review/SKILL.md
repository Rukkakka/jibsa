`docs/development/agents.md` 의 "코드 리뷰" 절을 실행한다. 대상: `$ARGUMENTS` (비어 있으면 커밋 전 변경과 이 브랜치의 커밋 전부: `git diff HEAD`, `git status --short` 의 추적 안 된 파일, `git diff main...HEAD`. 에이전트는 시키지 않으면 커밋하지 않아 리뷰할 변경이 대개 커밋 전에 있다).

**리뷰어는 하나다.** 관점·파일로 나눠 리뷰어를 여럿 띄우지 않는다 (같은 diff 와 주변 코드를 저마다 읽어 토큰이 곱으로 는다, 같은 절 1단계).

**PR 번호나 다른 브랜치가 대상이면** 재현은 지금 작업 트리의 코드로 돌아가 그 변경을 재현하지 못한다. 작업 트리를 바꾸지 않고(사용자의 커밋 전 변경이 있을 수 있다) 브랜치를 새로 받아 오지도 않는다. 재현 없이 코드 리뷰만 하고, 보고 첫 줄에 "재현하지 않은 리뷰" 라고 적는다. 리뷰어는 파일을 작업 트리에서 열면 다른 코드를 읽게 되므로, 지시서에 그 코드를 읽는 법을 적고 "작업 트리 파일은 열지 않는다. 규칙 문서·소스 가이드도 그 리비전에서 읽는다" 를 넣는다.
- **로컬에 있는 브랜치:** 변경은 `git diff main...<브랜치>`, 파일 내용은 `git show <브랜치>:<경로>`.
- **PR:** 주 에이전트가 `gh pr diff <번호>` 를 scratchpad 에 저장해 그 경로를 지시서에 준다. 파일 전체가 필요하면 `gh pr view <번호> --json headRefOid` 의 커밋으로 `gh api 'repos/{owner}/{repo}/contents/<경로>?ref=<커밋>' --jq .content | base64 -d`.

1. **기계 검사.** 대상이 작업 트리면 `.venv/bin/ruff check && .venv/bin/mypy` 와 바뀐 부분 테스트(이름으로)를 먼저 돌린다. 실패는 리뷰 보고에 함께 적는다.

2. **리뷰어 모델 정하기.** 바뀐 코드 파일(`src/` 아래. 문서·테스트·픽스처는 세지 않는다)·소스·명령으로 정한다. 애매하면 위 칸으로 한다.

   | 복잡도 | 기준 | 리뷰어 모델 |
   | --- | --- | --- |
   | 간단 | 한 소스, 명령 하나, 코드 파일 다섯 개 안쪽, 또는 코드 아님 (문서·에이전트 정의·명령·워크플로만) | Sonnet high |
   | 중간 | 한 소스 안에서 명령 둘 이상, 또는 코드 파일 다섯 개 넘음 | Opus high |
   | 복잡 | 소스 둘 이상, `core/`·소스에 매이지 않은 `cli/` 코드, 또는 지우는 코드가 여러 명령에 걸림 | Opus xhigh |

   사용자가 `/review` 를 직접 쳤으면 복잡도와 모델을 한 줄로 알리고 바로 돌린다. 치지 않았는데 요청을 보고 이 명령을 골랐으면 같은 내용을 알리고 허락받은 뒤 돌린다.

3. **리뷰어 띄우기.** `reviewer` 하나를 Agent 로 띄운다 (`model`·`effort` 는 위 표). 리뷰 단계(관점 A~D 와 체크리스트 여섯 절 → 중복 지우기 → 빈 곳 찾기)는 그 정의에 있다. 지시서에는 리뷰 대상 한 줄과 diff 를 볼 명령(예: `git diff HEAD`, 추적 안 된 파일 경로), 그리고 무엇을 바꾸려던 변경인지 한두 줄을 준다. 주 에이전트의 판단(어디가 맞다고 봤는지)은 주지 않는다 (리뷰어가 그 판단을 따라가지 않게).

4. **지적마다 재현하기.** 대상이 PR·다른 브랜치면 하지 않고 같은 문제끼리만 묶는다. 판정 기준은 `docs/development/agents.md` "코드 리뷰" 2·3단계 원문 하나다.
   - **지적이 다섯 건 안쪽이면 주 에이전트가 직접** 재현한다 (검증자를 띄우는 고정 비용이 더 든다). 방법은 `review-verifier` 정의의 "검증자로서 따로 지킬 것" 과 같다.
   - **다섯 건을 넘으면 `review-verifier` 하나(Sonnet high)에 목록을 통째로** 넘긴다 (소스마다 나누지 않는다). 주 세션은 맥락이 커서 지적마다 재현하면 호출마다 그 맥락을 다시 읽는다. 지시서에는 지적마다 `파일:줄`, 관점, 무엇이 틀리는지, 재현할 명령을 리뷰어가 쓴 그대로 넘기고, 주 에이전트의 판단(어느 것이 맞아 보이는지)은 넣지 않는다.
   - **검증자의 판정은 근거만 훑는다** (다시 재현하지 않는다). 근거가 "응답에 안 왔다"·"실측에 없다" 뿐인 오탐·일어날 수 없음과 근거가 "재현할 입력을 못 찾았다" 뿐인 미확인은 진짜 문제로 옮기고 (같은 절 5단계), 근거가 빈약하거나 서로 어긋나는 판정만 그 한 건을 직접 확인한다.
   - 같은 문제를 가리키는 지적은 하나로 묶는다. 일어날 수 없음은 사용자에게 건수만 알린다.

5. **보고.** 리뷰어 모델, 검증자를 띄웠는지, 기계 검사 결과를 첫머리에 적는다. 진짜 문제와 오탐을 근거(재현 명령·응답 핵심 필드·`파일:줄`)와 함께 보고한다. 근거가 "재현 못 함, 코드로 확인" 인 진짜 문제는 그렇게 밝히고 재현하지 못한 이유를 함께 적는다. 구조·중복·단순화(`design`) 관점의 진짜 문제는 버그와 나눠 "정리할 것" 으로 따로 적는다 (겹친 자리 `파일:줄` 들과 합칠 모양). 미확인은 무엇을 더 보면 가릴 수 있는지와 함께 따로 적는다. 오탐은 어디에 어떤 문장으로 남길지(코드 주석 `# 리뷰 오탐 (YYYY-MM-DD): 이유` 또는 소스 가이드 "웹과 다른 점")를 함께 제안한다.

6. 고치는 것과 오탐 기록 남기기는 **사용자가 정한 뒤** 한다 (AGENTS.md 작업 절차: 계획을 설명하고 허락받기). 계획에서 빼는 지적마다 `docs/development/agents.md` "코드 리뷰" 5단계의 세 이유 중 하나를 댄다. 체크리스트에 없던 종류의 진짜 문제·오탐이면 체크리스트에 더할 줄도 계획에 넣는다 (같은 절 6단계). 커밋·PR 코멘트는 시킬 때만.
